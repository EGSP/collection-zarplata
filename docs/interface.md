# Интерфейс (SDUI)

- Сервер отдаёт JSON-описания форм и списков: поля, типы, ссылки на справочники, табличные части, группы, порядок обхода, доступные действия с учётом прав.
- Вместе с ними сервер отдаёт схему оболочки: подсистемы, их группы, объекты и страницы в группах. Состав меню задаёт конфигурация, а не клиент.
- Экран, который не сводится к списку или форме, конфигурация объявляет страницей: её компонент входит в сборку клиента, а сервер отдаёт только её имя и заголовок. См. «Страницы конфигурации».
- Описание по умолчанию строится из метаданных. В метаданных его можно переопределить: сгруппировать поля, скрыть поле, изменить подпись.
- Клиент рендерит описание через реестр виджетов: каждому виду поля соответствуют поле ввода и компонент отображения на Ant Design.
- Правила проверки (обязательность, границы, длина) входят в описание формы, и клиент проверяет по ним ввод до отправки. Окончательную проверку выполняет сервер.
- Из Refine используется ядро `@refinedev/core`: ресурсы, маршрутизация, хуки данных. Компоненты форм и списков — собственные, на Ant Design.
- Экраны собираются из web SDK (`src/web/sdk`): стандартные форма записи и список объекта и собственные экраны конфигурации используют одни и те же компоненты и хуки. См. «Web SDK».
- Refine подключается через собственный data provider, который переводит свои методы в вызовы `/api/perform`.
- Лёгкие вычисления клиент выполняет сам. Сложные оформляются собственным действием на сервере.

## Формат описаний

`GET /api/metadata` требует входа и возвращает `{ "objects": [...], "pages": [...], "shell": {...} }`: объекты конфигурации, которые пользователь вправе читать, и страницы, которые он вправе открывать, в порядке файлов реестра, а также схему оболочки (подраздел [«Схема оболочки»](#схема-оболочки)). Страница описана именем и заголовком: `{ "name", "title" }`. Типы формата лежат в `src/server/ui/descriptions.ts`. В этом файле нет импортов Nest и Effect, поэтому клиент импортирует его напрямую. Описания строятся в `src/server/ui/views.ts` из тех же метаданных, что таблицы базы и схемы проверки входных данных, поэтому набор полей и правила проверки на форме совпадают с тем, что примет сервер. Полные описания строятся один раз при первом запросе, отбор по правам выполняется при каждом запросе.

Описание объекта (`ObjectView`): `kind`, `name`, `title`, `form`, `list` и `tableParts`. Последнее содержит описания всех частей для просмотра, независимо от раскладки формы. У регистров `form` равен `null`: их строки записывают только документы.

Описание формы (`FormView`):

| Свойство | Содержимое |
|---|---|
| `fields` | Поля на форме в порядке объявления: `name`, `title`, `kind`, `target`, `readOnly`, `rules`, `inputElement`, а также `choices` (перечень значений строки), `initial` (начальное значение строки), `computed` (формула), `suggestions` (источник числовых подсказок), `expandedTablePart` (часть объекта ссылки для просмотра) |
| `tableParts` | Табличные части: `name`, `title`, `columns` — поля строки в том же формате |
| `groups` | Раскладка: `{ title, elements }`. Строка в `elements` — имя поля или табличной части, объект `{ element }` — собственный элемент конфигурации. Каждое поле и каждая табличная часть входят ровно в одну группу |
| `traversal` | Порядок обхода с клавиатуры: имена редактируемых полей и табличных частей. Собственных элементов групп в нём нет |
| `actions` | Действия формы: `name`, `title`, `standard`, `input` и `tableParts` входных данных собственного действия |
| `calculations` | Полный набор полей и частей для расчётов, включая скрытые раскладкой формы |
| `creationMode` | Режим, в котором форма новой записи открывается по умолчанию: `tab` — во вкладке, `dialog` — в модальном окне |

- `rules` содержит правила проверки: `required`, `minimumLength`, `maximumLength`, `minimum`, `maximum`, `integer`. Обязательная строка не может быть пустой. Значение денег и их границы указаны в копейках.
- `readOnly` получают поля, которые заполняет платформа: `number` и `posted` документа, а также вычисляемые числовые поля. Они показываются на форме, но не входят в порядок обхода. `guid` и `deletedAt` на форму не выводятся.
- Стандартные действия справочника — `save`, `markDeleted`, `unmarkDeleted`; у документа к ним добавляются `post` и `unpost`. За ними идут собственные действия объекта. В описание попадают только действия, на которые у пользователя есть право; форму без `save` клиент показывает только для просмотра.

Описание списка (`ListView`):

Над списком есть поле «Поиск» с очисткой, отдельно от условий отбора. Введённый текст применяется через 300 мс после последнего изменения, а очистка без задержки убирает только поиск. Применение поиска возвращает список на первую страницу, сохраняя отборы и сортировку. Клиент передаёт текст в `search` действия `list`.

| Свойство | Содержимое |
|---|---|
| `columns` | Поля записи, кроме стандартных `guid` и `deletedAt`; `role` различает измерения (`dimension`) и ресурсы (`resource`) |
| `filters` | Отборы: поле и допустимые способы сравнения `operators` |
| `sortable` | Поля, по которым можно сортировать; регистратор не сортируется |
| `defaultSort` | Сортировка при открытии: справочник по наименованию, документ по дате и номеру от новых к старым, движения по периоду от новых к старым, сведения по измерениям в порядке объявления |
| `deletionMark` | У записей есть пометка удаления; клиент показывает её признаком строки, а не колонкой |
| `tableParts` | Имена частей для раскрытия строки списка только для чтения |

Способы сравнения зависят от вида поля: у строк — `contains`, `equals` и `notEquals`; у чисел, денег, дат и дат со временем — `equals`, `notEquals`, `greater`, `greaterOrEqual`, `less`, `lessOrEqual` и `contains`; у логических значений, ссылок и регистратора — `equals` и `notEquals`. `contains` ищет подстроку без учёта регистра, а `%` и `_` в ней — обычные символы. Общий модуль формата значений рядом с форматом описаний используется клиентом для отображения и сервером для поиска: правило перевода копеек в рубли, десятичная запятая и вид даты задаются один раз. Для `contains` интерфейс предлагает свободный текстовый ввод, в том числе части даты или суммы; при переходе к точному сравнению или обратно прежнее значение очищается. Соответствие видов полей и способов сравнения задано в формате описаний (`filterOperators`), и действие `list` принимает те же способы, поэтому отбор из описания всегда можно передать в `list` без перевода.

## Переопределение формы

По умолчанию форма состоит из одной группы без заголовка: поля в порядке объявления, затем табличные части. `.form(...)` в описании объекта меняет раскладку:

```ts
.form((form) => form
    .group('Основное', ['item', 'date', 'number'])
    .group('Строки документа', ['lines', SampleTotal])
    .hide('posted')
    .title('comment', 'Примечание')
    .input('comment', SampleComment)
    .creation('dialog'))
```

- `group(title, elements)` выводит поля и табличные части группой с заголовком. Группы идут в порядке объявления, элементы внутри группы — в указанном порядке. Элементы, не попавшие ни в одну группу, собираются после групп в группу без заголовка.
- `hide(name)` убирает поле или табличную часть с формы и из порядка обхода.
- `title(name, title)` меняет подпись на форме; в списке остаётся подпись из описания поля.
- Порядок обхода следует за раскладкой групп, поэтому перестановка групп и элементов меняет и его.
- Собственный элемент формы (подраздел [«Элементы формы»](metadata.md#элементы-формы)) указывается билдером из файла объявления. В группе он стоит наравне с полями и табличными частями, занимает всю ширину группы и в порядок обхода не входит. Вне группы элемент поставить нельзя.
- `input(field, element)` назначает элемент полем ввода для поля. На форме он заменяет виджет вида поля, а поле остаётся на своём месте в раскладке и в порядке обхода, с той же подписью и проверкой. Реестр виджетов при этом не меняется: в списке и в отборе поле выводится стандартным виджетом.
- Элемент назначается полю в метаданных, а не выбирается клиентом по имени поля: раскладка и порядок обхода строятся на сервере, и `commit()` проверяет их целиком.
- `creation(mode)` задаёт режим создания записи: `tab` открывает форму новой записи во вкладке, `dialog` — в модальном окне поверх списка. Без вызова запись создаётся во вкладке. Это умолчание, а не запрет: место вызова может указать режим само (команда открытия записи в разделе [«Web SDK»](#web-sdk)), а адрес `/<вид>/<имя>/new` всегда открывает вкладку. На существующие записи режим не действует. Режим задаётся один раз. В окне создаются записи справочников «Номенклатура» и «Физические лица»: полей на их формах немного.

Переопределение действует только на форму. Ошибки переопределения обнаруживает `commit()` при запуске (раздел [«Проверки при сборке»](metadata.md#проверки-при-сборке)).

## Схема оболочки

Оболочка состоит из подсистем, подсистема из групп, группа из ссылок на объекты и страницы конфигурации. Схема описывается билдером в `src/configuration/shell.ts`:

```ts
import { shell } from '../server/ui/shell.js';
import { Employees } from './catalogs/employees.catalog.js';
import { Shift } from './documents/shift.document.js';
import { ShiftWorkplace } from './pages/shift-workplace.page.js';

export const applicationShell = shell()
    .subsystem('masterData', (subsystem) => subsystem
        .title('НСИ')
        .group('Справочники', [Employees])
        .group('Документы', [Shift])
        .group('Рабочие места', [ShiftWorkplace]));
```

- Подсистемы, группы и пункты группы показываются в порядке описания. Объекты и страницы стоят в группе в общем порядке. Имя подсистемы отличает её от остальных, пользователь видит заголовок.
- Объект и страница указываются импортированными билдерами, а не строками. Один объект или страницу можно указать в нескольких группах и подсистемах: содержимое подсистемы — список ссылок.
- Вся проверка выполняется типами при `npm run typecheck`: значение, которое не является билдером объекта или страницы, и повтор имени подсистемы не компилируются. Имена подсистем накапливаются в параметре типа билдера оболочки. При запуске сервера схема не проверяется.
- Объект, не указанный в схеме, в окнах подсистем не показывается, но его список открывается по адресу, а форма записи — по ссылке из другой записи. Страница, не указанная в схеме, открывается по адресу. Предупреждений об этом нет: объект или страница могли быть скрыты намеренно.
- Файл схемы один, путь к нему постоянный, поэтому генератор реестра его не ищет: сервер импортирует его напрямую, как файл ролей.

В ответе `GET /api/metadata` схема лежит в свойстве `shell`: `{ "subsystems": [{ "name", "title", "groups": [{ "title", "items": [{ "kind", "name" }] }] }] }`. У пункта-страницы `kind` равен `page`, у объекта это его вид. Сервер оставляет в схеме только объекты, которые пользователь вправе читать, и страницы, которые он вправе открывать. Группа без таких пунктов, в том числе пустая в конфигурации, и подсистема без групп в ответ не попадают. Заголовок объекта клиент берёт из его описания в `objects`, заголовок страницы — из `pages`.

## Каркас клиента

Клиент предоставляет именованные группы для компонентов конфигурации: `ShellGroups.home` на главном экране и `ShellGroups.list(Objects.<вид>.<имя>)` над поиском и отбором стандартного списка. Группы существуют только в клиенте и не входят в `GET /api/metadata`. У каждого списка своя группа, а пустая группа не занимает места. Главный экран показывает «Нет доступных объектов», только если нет ни подсистем, ни фактически выведенных компонентов, в том числе когда компоненты возвращают `null`.

Состав групп описывается в `src/configuration/shell-groups.tsx` вызовом `defineShellGroups`. Каждая запись массива добавляет `content` в `parent`: компонент с `component` и необязательным перечнем `requiredObjects` либо вложенную группу. `shellGroup(name, orientation)` объявляет собственную группу с уникальным именем и ориентацией `vertical` (по умолчанию) или `horizontal`. Вложенная группа стоит наравне с компонентами; порядок массива задаёт порядок показа. Объявления известны до отрисовки всех вкладок, поэтому порядок монтирования на состав не влияет. Циклы вложенности, повторное назначение родителя и разные ориентации одного имени завершаются ошибкой при загрузке конфигурации.

Один компонент можно добавить в несколько групп. У компонента нет отдельного права: доступ определяется правами объектов. Если хотя бы одного объекта из `requiredObjects` нет среди доступных описаний, компонент не монтируется и не отправляет запросов. При самостоятельной проверке компонент сначала получает описание через `useObjectView` и только после этого монтирует часть, которая читает данные. Он импортирует из платформы только web SDK, а из серверных модулей только типы, как компонент страницы; границу всех файлов `.tsx` конфигурации проверяет `npm run typecheck`.

Пробные компоненты читают регистр пробных сведений и стоят в собственных горизонтальных группах на главном экране и над списком пробного документа. Роль `reader` не читает пробные сведения: это позволяет проверить отсутствие блоков и запрещённых запросов, сохранив доступ к списку документа. Для проверки вертикальной раскладки достаточно сменить ориентацию двух пробных групп в клиентской конфигурации.

Все модальные окна сохраняют открытое состояние и введённые значения при нажатии на затемнённую область вокруг окна. Это правило задано один раз в общем провайдере Ant Design и действует также на новые окна. Окно закрывается крестиком, клавишей Esc или переходом из самого окна; кнопки «Отмена» и «Выполнить» сохраняют своё назначение. Пока собственное действие выполняется, окно его входных данных не закрывается: Esc отключён, крестик и «Отмена» недоступны. После отказа сервера окно остаётся открытым с ошибками полей и снова допускает закрытие.

Каркас — это сессия, data provider, приложение Refine, ресурсы которого строятся из описаний объектов, список подсистем из схемы оболочки и вкладки открытых окон. Формы и списки объектов работают поверх него и описаны в подразделах [«Web SDK»](#web-sdk), [«Реестр виджетов»](#реестр-виджетов), [«Ссылки»](#ссылки), [«Списки»](#списки) и [«Формы»](#формы).

### Сессия и запросы к API

- Все запросы приложения идут через один экземпляр axios (`src/web/common/api.ts`). Ошибка запроса приводится к `ApiError`: статус HTTP, текст сервера, а для единого эндпоинта ещё пути полей с ошибками проверки (`fields`) и ключ недостающего права (`right`). Если ответ не получен, статус равен 0.
- Токены лежат в `HttpOnly`-cookie, поэтому клиент не видит ни их, ни срок их действия и судит о сессии по ответам сервера. Ответ 401 принимает перехватчик axios (`src/web/authentication/session.ts`): он обновляет токены запросом `POST /api/authentication/refresh` и повторяет исходный запрос. Вызывающий код получает ответ повтора, поэтому истёкший access-токен не виден ни TanStack Query, ни интерфейсу.
- Обновление токенов одно на всю страницу. Refresh-токен одноразовый: если бы каждый запрос, получивший 401, обновлял токены сам, сервер принял бы только первое обновление. Одновременные запросы ждут общего обновления. Запрос запоминает номер пары токенов, с которой отправлен; если к приходу ответа 401 пара уже заменена, запрос только повторяется.
- Сессия считается завершённой, когда 401 вернул и повтор запроса. Отказ в самом обновлении её ещё не завершает: токены могла заменить соседняя вкладка, у которой общие cookie.
- Состояние сессии хранится в TanStack Store: `unknown` — приложение только открыто, `active` — сервер принял запрос пользователя, `ended` — сервер отказал после обновления токенов либо пользователь вышел. По состоянию auth provider Refine отвечает на проверку входа. Отдельного запроса «кто я» у сервера нет, поэтому при открытии приложения состояние выясняет загрузка описаний объектов.
- При завершении сессии данные и описания объектов удаляются из кеша TanStack Query: следующий вошедший пользователь не увидит данных предыдущего.

### Data provider

Refine называет ресурс одной строкой, а сервер различает объекты по виду и имени. Имя ресурса состоит из вида и имени объекта через точку: `catalog.sample`. Методы data provider (`src/web/data-provider/data-provider.ts`) переводятся в действия единого эндпоинта:

| Метод Refine | Действие | Входные данные |
|---|---|---|
| `getList` | `list` | Отбор, сортировка и страница; условие отбора с текстом поиска передаётся параметром `search`, условие поиска по представлению записи параметром `presentation` |
| `getOne` | `get` | `id` — `guid` записи |
| `getMany` | пакет действий `get` | `ids`: перечень `guid`; одновременные вызовы уходят одним запросом |
| `create` | `save` без `guid` | `variables` — значения полей и табличные части, как в `payload.fields` |
| `update` | `save` с `guid` | `id` и `variables`; запись заменяется целиком |
| `deleteOne` | `markDeleted` | `id` — `guid` записи |
| `custom` | любое, в том числе собственное | `url` — ресурс и действие через косую черту: `document.sample/post`, `platform.journal/history`; `payload` — входные данные действия |

- Запись возвращается в том виде, в каком её отдал сервер. Её идентификатор — `guid`; поля `id`, принятого в Refine, у записей нет.
- Операторы отбора Refine переводятся в способы сравнения сервера: `eq` — `equals`, `ne` — `notEquals`, `gt` — `greater`, `gte` — `greaterOrEqual`, `lt` — `less`, `lte` — `lessOrEqual`, `contains` — `contains`. Операторы `null` и `nnull` становятся сравнением с `null`. Группа `and` раскрывается в общий список условий. Группа `or` и остальные операторы завершаются ошибкой: молча пропущенное условие показало бы лишние записи.
- В режиме страниц `server` запрашивается одна страница. В режимах `client` и `off` Refine ждёт все записи сразу, и data provider читает их страницами по 500 записей, пока не получит все.
- Метод HTTP в `custom` значения не имеет: единый эндпоинт принимает только `POST`.

### Ресурсы, подсистемы и адреса

- Ресурсы Refine строятся из ответа `GET /api/metadata`: один ресурс на объект конфигурации. Ресурсы плоские, без ресурсов-групп: один объект может стоять в нескольких группах схемы оболочки, поэтому меню строится из схемы, а не из ресурсов.
- Слева показан список подсистем из схемы оболочки. Нажатие на подсистему открывает модальное окно с её группами. Пункт группы — ссылка на список объекта или на страницу конфигурации; переход по ней закрывает окно. Слева от названия пункта стоит иконка: у объекта по его виду (справочник, документ, регистр оборотов, регистр сведений), у страницы собственная. Иконку выбирает клиент по виду пункта.
- Под списком подсистем стоят кнопки «Документация» и «Выйти». Первая открывает сайт документации в новой вкладке браузера (раздел [«Документация»](documentation.md)).
- Подсистема не подсвечивается по открытой странице: страница объекта не принадлежит одной подсистеме.
- Адреса: `/<вид>/<имя>` открывает список объекта, например `/catalog/sample`; `/<вид>/<имя>/new` и `/<вид>/<имя>/<guid>` открывают форму записи; `/page/<имя>` открывает страницу конфигурации; `/` открывает главный экран. Главный экран пуст: объекты пользователь открывает из окон подсистем. Список, форма и страница конфигурации открываются во вкладках, см. «Вкладки открытых окон».
- Страница конфигурации открывается, если её имя есть и в ответе сервера, и в реестре страниц клиента (`pages.generated.ts`). Неизвестное имя и страница без права показывают «не найдено»: для клиента они неразличимы. Пока страница не задала заголовок сама, вкладка показывает заголовок из объявления.
- Всё приложение закрыто проверкой входа. Без сессии на его месте показывается экран входа, а адрес не меняется: отдельного адреса у экрана входа нет. Поэтому после входа открывается та же страница, в том числе когда сессия истекла посреди работы. После явного выхода открывается главный экран: следующим может войти другой пользователь.
- Раскладка показывает страницы вкладок только после загрузки описаний объектов. Пока они загружаются, виден признак ожидания; при ошибке — сообщение с кнопкой повтора.
- Refine получает общий с приложением клиент TanStack Query. Запросы не повторяются сами ни при возврате в окно или восстановлении сети, ни после отказа сервера. Проверка входа Refine на время своего запроса убирает приложение с экрана, и её повтор закрыл бы все вкладки. Отказ в праве или в проверке данных от повтора не изменится.
- Уведомления Refine выводятся компонентом уведомлений Ant Design, их встроенные заголовки переведены на русский язык. Описанием ошибки служит текст сервера. Отправка сведений об использовании на сервер Refine отключена.

### Вкладки открытых окон

Открытые списки, формы и страницы конфигурации остаются вкладками, как окна в 1С (`src/web/tabs/`). Над страницей стоит полоса вкладок. Первая вкладка — главный экран: на ней иконка без заголовка, закрыть её нельзя.

- Вкладку определяет путь адреса. Поэтому отдельной команды «открыть вкладку» нет: ссылка из окна подсистемы, из списка или из другой записи, прямой адрес и кнопки браузера «Назад» и «Вперёд» меняют адрес, а набор вкладок выводится из него. Адрес с новым путём открывает вкладку, адрес с путём открытой вкладки делает её активной. Новая вкладка встаёт сразу за активной.
- Строка запроса принадлежит вкладке: в ней список хранит сортировку, отбор и страницу. Скрытая вкладка помнит свою строку запроса. При возврате на вкладку, в том числе по ссылке без строки запроса, адрес браузера приводится к запомненному.
- Страницы всех вкладок и главный экран остаются смонтированными, неактивные скрыты. Так вкладка сохраняет несохранённые значения формы, отбор, текст поиска и страницу списка. Если бы страница пересоздавалась при переключении, ввод терялся бы.
- Общих маршрутов у приложения нет: каждая вкладка раскладывает страницы по своему адресу, а не по адресу браузера. Поэтому скрытый список не реагирует на адрес активной вкладки и не меняет его.
- Всё, что действует на приложение в целом, страница включает только на активной вкладке. Так устроены сочетания клавиш формы: иначе Esc закрыл бы все открытые формы сразу.
- Страница обращается не к вкладке, а к ближайшей области окна (`src/web/window/`): области она сообщает заголовок, несохранённые изменения, изменённую и созданную запись, у неё узнаёт, видна ли пользователю, и её просит закрыться. Реализаций области три: вкладка, главный экран и модальное окно с формой записи. Каждая сама решает, что значит обращение. Область главного экрана нужна компонентам конфигурации на нём, чтобы открыть форму записи в окне; закрыть её нельзя, а заголовок и сообщение о созданной записи она не использует. Поэтому страница, в том числе форма записи, не зависит от того, в чём показана.
- У области может быть рамка: собственные места для заголовка и кнопок действий. У вкладки рамки нет, и каркас страницы выводит заголовок и кнопки над содержимым. У модального окна рамка есть: заголовок с отметками состояния стоит в шапке окна, кнопки в его нижней части.
- Модальное окно с формой записи (`src/web/forms/record-dialog.tsx`) открывает команда открытия записи SDK в режиме окна. Адреса у окна нет: вкладки выводятся из адреса, и адрес окна открыл бы вкладку. Поэтому окно после перезагрузки страницы не восстанавливается. После создания записи окно закрывается и отдаёт её `guid` коду, который его открыл.
- Окно принадлежит области, со страницы которой открыто, и регистрируется в ней вложенной областью: закрытие вкладки, выход и закрытие страницы браузера учитывают несохранённые изменения в окне. Окно выводится в слой страницы вкладки: затемнение закрывает только страницу, а полоса вкладок и список подсистем остаются доступны. Окно видно, только пока активна его вкладка; при возврате на вкладку оно показано снова с введёнными значениями. Форма в окне может открыть следующее окно, оно вкладывается в первое.
- Крестик окна, Esc и кнопка «Закрыть» спрашивают то же подтверждение, что и вкладка. Esc обрабатывает форма, а не окно Ant Design: она отличает закрытие списка выбора от закрытия окна.
- Несохранённые изменения область узнаёт через проверки: функции, которые читают признак в момент вызова. Форма сбрасывает признак сразу после записи и тут же закрывает область, а признак в состоянии React к этому моменту ещё не обновился бы. Проверок в области может быть несколько; область изменена, если изменён хотя бы один участник. Вложенная область регистрируется в родительской одной проверкой. Так же области вкладок регистрируются в общем наборе приложения, по которому спрашивается подтверждение перед выходом и перед закрытием вкладки браузера.
- Подтверждение перед закрытием спрашивает область. Крестик в полосе вкладок стоит вне области, поэтому вызывает команду закрытия, которую область вкладки передала набору вкладок.
- Страница сообщает области заголовок, и он становится заголовком вкладки. У списка это заголовок объекта. У формы это представление записи, у новой записи заголовок объекта с пометкой «(новый)»; после записи заголовок меняется на представление. Представление по ссылке форма читает по записанному состоянию: несохранённый выбор ссылки запись ещё не называет. У страницы конфигурации это заголовок из объявления, пока она не задала свой.
- Вкладка закрывается крестиком, форма также кнопкой «Закрыть» и клавишей Esc. Активной становится соседняя слева вкладка, а если её нет, главный экран. В истории браузера адрес закрытой вкладки заменяется адресом новой активной.
- Набор вкладок хранится в памяти страницы. После перезагрузки открыты главный экран и вкладка текущего адреса. Вкладки стоят под проверкой входа и при завершении сессии закрываются: следующий вошедший пользователь не увидит вкладок и данных предыдущего.

## Web SDK

Web SDK (`src/web/sdk`) — набор компонентов, хуков и типов платформы, из которого собираются экраны клиента. У него одна точка входа, `src/web/sdk/index.ts`. Всё, что из неё экспортировано, считается публичным контрактом клиента; остальные модули `src/web` остаются внутренними и могут меняться. Стандартные форма записи (`src/web/forms/`) и список объекта (`src/web/lists/`) собраны из SDK и служат образцами собственных экранов.

- SDK состоит из функциональных компонентов React и хуков, экран пишется обычным JSX. Базовых классов для наследования нет: клиент построен на хуках, а классовый компонент вызывать их не может. Описания интерфейса билдерами тоже нет.
- В SDK входит только то, что знает о платформе: данные, права, описания объектов, область окна, фокус. Раскладку, типографику и прочие элементы без такой связи экран берёт из Ant Design напрямую, обёртки для них не пишутся.
- Иконки экран берёт из реестра `Icons` (`src/web/sdk/icons.tsx`) по смыслу действия, а не по рисунку: `<Icons.open />`, `<Icons.add />`. Реестр сопоставляет смыслу значок Ant Design, поэтому одно действие выглядит одинаково на всех экранах, а рисунок меняется в одном месте. Пакет `@ant-design/icons` импортирует только реестр. Если нужного смысла в нём нет, в реестр добавляют запись. У иконки без подписи рядом есть название для чтения с экрана и подсказка: так оформлена кнопка перехода к записи у поля ссылки.
- Хуки данных SDK служат единственным путём к API для кода вне платформы: хуки Refine и `/api/perform` такой код напрямую не вызывает. Так сброс сохранённых ответов сервера и показ ошибок остаются в одном месте.
- Если экрану не хватает элемента или хука и он пригодится другим экранам, его добавляют в SDK, а не пишут на месте.

- Хуки списка и записи отдают условия отбора и сортировку в формате действия `list`, тех же типов, что в описании списка. Типы Refine в контракт SDK не входят.
- Объект хуки и компоненты принимают двумя способами. Описание с сервера (`ObjectView`) типов записи не несёт: записи имеют общий тип, имена полей и действий — строки. Так работают стандартные список и форма. Ссылка на объект `Objects.<вид>.<имя>` несёт тип строки списка, тип записи и имена стандартных и собственных действий, выведенные из билдера. По ней компилятор проверяет имена колонок `RecordTable`, поля сортировки и постоянного отбора `useRecordList` вместе с типом значения, имя действия у `ActionButton` и `useAction`, а `useRecord` и `useRecordList` возвращают записи точного типа. Опечатка в имени не собирается.
- Хуки области окна обращаются к ближайшей области и вне области завершаются ошибкой. Экран не знает, вкладка это или модальное окно: `useWindowScope` отдаёт признак активности, закрытие с подтверждением и сообщения об изменённой и о созданной записи, `useWindowTitle` задаёт заголовок. `useUnsavedChanges` можно вызвать на одном экране несколько раз, по разу на каждую часть со своим признаком изменений. Каркас `Page` сообщает области свой заголовок; свойство `windowTitle` задаёт другой заголовок области или отключает его. Заголовок, отметки и кнопки каркас выводит в рамку области, если она есть, иначе над содержимым.
- `useOpenRecord` отдаёт команду открытия формы записи. Команда принимает объект, `guid` записи либо `null` для новой записи и необязательный режим: `tab` или `dialog`. Без режима новая запись открывается в режиме создания из описания формы (`creationMode`), существующая во вкладке. В режиме вкладки команда переходит по адресу записи. В режиме окна она возвращает итог, когда окно закрыто: `guid` записи, которую в окне записали или над которой выполнили действие, либо `null`, если окно закрыто без записи. Режим указывает место вызова, а конфигурация задаёт только умолчание: общего состояния «как открывать записи объекта» нет, потому что страницы всех вкладок смонтированы одновременно, и результат зависел бы от порядка их монтирования.
- `hasOpenDialog` сообщает, открыто ли модальное окно поверх экрана. Экран передаёт свой корневой элемент: окно, в котором показан сам экран, поверх него не лежит и не учитывается. Иначе форма в модальном окне сочла бы себя закрытой собственным окном и отключила бы свои сочетания клавиш.
- `useRecordList` принимает постоянный отбор экрана, например «только непроведённые». Он действует вместе с отбором пользователя, в отбор пользователя не входит и им не снимается.
- `RecordTable` по настройке выводит только перечисленные колонки и показывает выбор строки. Выбор хранит экран: таблица сообщает о нём и показывает выбранной строку, которую получила.
- `useRecordList` по настройке хранит состояние списка в адресе вкладки. Адрес у вкладки один, поэтому так может работать только один список на экране; остальные хранят состояние в памяти.
- `useAction` показывает уведомление об успехе и об отказе сервера и после успеха помечает устаревшими сохранённые ответы сервера о данных. Отказ завершает вызов ошибкой `ApiError`, по которой экран отмечает поля из перечня `fields`.
- Кнопка действия получает объект, запись и имя действия. Она не выводится, если действия нет в описании формы объекта: сервер оставляет там только действия, на которые у пользователя есть право. Не выводится и действие, неприменимое к записи в её состоянии: из пары «Пометить на удаление» и «Снять пометку удаления» применимо одно, отмена проведения применима только к проведённому документу. Во время запроса кнопка недоступна. Если у собственного действия есть входные данные, кнопка сначала открывает окно с их полями; экран может передать входные данные сам, тогда окно не открывается.
- Стандартное действие кнопка выполняет над записью по её `guid`. Действие `save` кнопка сама не выполняет: значения полей знает только форма. Для таких случаев экран заменяет выполнение своим, а кнопка сохраняет проверку прав, окно входных данных и признак ожидания. Так устроена стандартная форма: перед действием она записывает несохранённые изменения.
- Контракт поля ввода SDK публикует из реестра виджетов без изменений: значение, обработчик изменения, недоступность, приём фокуса. На нём держатся обход с клавиатуры и проверка ввода. Собственный элемент на месте поля ввода соблюдает этот же контракт.
- Данные формы элемент получает хуками, а не свойствами. `useFormData` отдаёт описание объекта, описание формы, записанное состояние, признак «только просмотр» и функцию изменения значения; элемент перерисовывается, когда форма записана или перечитана либо изменились её ограничения. Описание формы (`view`) служит перечнем того, из чего она состоит: поля, табличные части и действия, стандартные и собственные. `useFormValue` отдаёт текущее значение одного поля или строки табличной части вместе с несохранённым вводом и перерисовывает элемент только при изменении этого значения. У поля, которого на форме нет или которое заполняет платформа, возвращается значение из записанного состояния.
- Оба хука принимают ссылку на объект `Objects.<вид>.<имя>`: по ней запись и имена полей получают точные типы. Элемент со ссылкой, поставленный на форму другого объекта, завершается ошибкой: типы записи были бы неверны. Без ссылки элемент подходит форме любого объекта, а запись имеет общий тип.
- Изменение значения через `useFormData` форма учитывает как ввод пользователя: оно считается несохранённым, сразу проверяется по правилам поля с показом ошибки под ним и уходит в `save` вместе с остальными значениями. Вместо значения можно передать функцию от текущего значения формы: так меняют значение, которое зависит от прежнего, например добавляют строку табличной части. Значение из `useFormValue` элемент получает с отрисовкой, и второе из двух изменений подряд, вычисленное по нему, отменило бы первое. Изменить можно редактируемое поле формы или строки табличной части; имя другого поля завершает вызов ошибкой. На форме только для просмотра и у поля, которое элемент сделал недоступным, значение не меняется.
- `runAction` из `useFormData` выполняет действие формы по имени так же, как его кнопка: форма записывает несохранённые изменения, выполняет действие и показывает запись в новом состоянии. Вызов возвращает результат действия; отказ сервера завершает его ошибкой, уведомление о нём уже показано. Собственное действие получает переданные входные данные без изменений: `guid` записи форма к ним не добавляет, его передаёт элемент. Так элемент выводит собственную кнопку действия, которому нужны `guid` открытой записи или данные с формы, а стандартную кнопку скрывает через `useFormRestrictions`; скрытие на вызов не влияет. Окно входных данных элемент при необходимости показывает сам компонентом `ActionDialog`, убрав из описания действия поля, которые заполняет сам. Выполнить можно только действие из описания формы, то есть разрешённое пользователю. На экране, который действия по запросу элементов не выполняет, вызов завершается ошибкой.
- `useFormRestrictions` объявляет ограничения формы от имени элемента: признак `readOnly` делает недоступной для изменения всю форму, `readOnlyFields` перечисляет недоступные поля и табличные части, `hiddenActions` — скрытые действия. По ссылке на объект имена полей и действий проверяет компилятор. Ограничения действуют, пока элемент стоит на форме. Требования нескольких элементов объединяются: поле недоступно и действие скрыто, если этого требует хотя бы один.
- Условие элемент вычисляет при каждой отрисовке и передаёт хуку готовые ограничения, поэтому форма меняет состояние вслед за условием без повторного открытия: после записи, после действия над записью, после ответа на чтение других данных. Пока условие не известно, элемент передаёт `null`.
- Ограничения собирает учёт `useFormRestrictionRegistry`, который ведёт экран формы и передаёт поставщику данных. Элемент узнаёт условие только после того, как форма с записью появилась на экране. Поэтому, пока требования не собраны, учёт считает форму недоступной целиком, а все действия скрытыми: так запись, которую менять нельзя, не выглядит изменяемой даже на время загрузки. Требования не собраны до первого сбора и пока хотя бы один элемент передал `null`. Элементы объявляют требования в эффекте раскладки, и форма применяет их до того, как браузер её покажет.
- `FormDataProvider` стоит внутри формы Ant Design и снаружи групп полей. Стандартная форма передаёт ему реестр компонентов элементов конфигурации и учёт ограничений; без поставщика `FieldGroup` выводит поле виджетом его вида, а элемент группы пропускает. На экране, который учёт ограничений поставщику не передал, элемент с ограничениями завершается ошибкой: молча не применённое ограничение выглядело бы как работающее.

## Реестр виджетов

Числовое поле с `suggestions` использует ввод с подсказками вместо обычного числового виджета. При открытом выборе читаются первые 50 подходящих записей справочника; поиск учитывает представление и числовые значения. Подсказка показывает название и число. Выбор сохраняет только число, которое остаётся редактируемым. Помеченные записи и пустые значения источника исключаются.

Вычисляемые поля показывают текущий результат только для чтения. Поставщик данных формы пересчитывает строки, затем шапку по общим с сервером формулам. Поэтому изменение ячейки, добавление строки через элемент конфигурации и удаление строки сразу меняют итог. Сервер повторяет расчёт перед проверкой и сохранением.

Формы и списки о видах полей сами ничего не знают: компонент для поля они берут из реестра виджетов (`src/web/widgets/registry.tsx`). Реестр сопоставляет каждому виду поля (`FieldKind`) два компонента. Поле ввода служит для ввода или выбора значения. Компонент отображения выводит значение текстом там, где его нельзя изменить: в ячейке списка и на форме у полей только для чтения.

| Вид поля | Поле ввода | Отображение |
|---|---|---|
| `string` | Текстовое поле; пустое поле отдаёт `null`, а не пустую строку | Текст |
| `number` | Поле для числа; при правиле `integer` дробную часть ввести нельзя | Число с разделителями разрядов |
| `money` | Поле для суммы в рублях с двумя знаками после запятой | Рубли с двумя знаками после запятой |
| `date` | Выбор даты в календаре | `ДД.ММ.ГГГГ` |
| `dateTime` | Выбор даты и времени | `ДД.ММ.ГГГГ ЧЧ:ММ` по часовому поясу браузера |
| `boolean` | Флажок | «Да» или «Нет» |
| `reference` | Выбор записи другого объекта с поиском и кнопка перехода к выбранной записи | Представление записи со ссылкой на её форму |
| `guid` | Нет: значение заполняет платформа | Текст |
| `recorder` | Нет: значение заполняет платформа | Представление документа со ссылкой на его форму |

- Реестр обязан перечислить все виды полей, и это проверяется типами. Если на сервере появится новый вид поля, клиент не соберётся, пока для него не добавлена пара компонентов.
- Значение остаётся в формате сервера на всём пути: деньги в копейках, даты строками ISO, ссылка в виде `guid`, отсутствие значения в виде `null`. В привычный человеку вид значение переводит само поле ввода, и оно же переводит введённое обратно. Поэтому значения формы уходят в `save`, а значение отбора в `list` без преобразования, и общего слоя преобразования нет.
- Все поля ввода принимают один набор свойств, принятый для элементов формы Ant Design: значение, обработчик изменения, признак недоступности, а также описание поля. Поэтому одно и то же поле ввода стоит в шапке формы, в ячейке табличной части, в условии отбора списка и в окне входных данных собственного действия.
- Каждое поле ввода умеет принять фокус по команде извне. Этим пользуется форма, когда ставит фокус в первое поле новой записи; на этом же будет построен обход с клавиатуры.
- Правила проверки Ant Design строятся из `rules` описания поля в одном месте (`src/web/widgets/validation.ts`): обязательность, длина строки, границы числа, целочисленность. Значение проверяется в формате сервера, поэтому граница суммы сравнивается в копейках, а в сообщении называется в рублях.

## Ссылки

Поле вида `reference` хранит `guid` записи другого объекта. Пользователю `guid` ничего не говорит, поэтому вместо него всегда выводится представление записи: текст, по которому человек её узнаёт. У записи справочника это наименование, у документа: «<заголовок объекта> № <номер> от <дата>». Общий модуль представлений (`src/server/ui/reference-presentation.ts`) используется сервером и клиентом, поэтому в поле ссылки, в ячейке списка, в колонке регистратора и в заголовке формы запись называется одинаково. Список получает готовые представления со своей страницей, а вне списка клиент читает записи по ссылкам.

Справочник может объявить представление по ссылке: `.presentation('<поле>')`. Тогда его запись везде показывается представлением записи, на которую ссылается это поле: в ячейке списка, в поле выбора, в ссылке на форму, в колонке табличной части, в заголовке формы и вкладки. Наименование у такого справочника остаётся обычным обязательным полем.

- Представление берётся по ссылке при каждом показе и в наименование не копируется. Копия устаревала бы при изменении целевой записи, в том числе импортом из 1С.
- Поле представления по ссылке должно быть обязательной ссылкой с заданной целью. Представление также может состоять из текста, полей шапки и значений колонок частей (раздел [«Представление из частей»](metadata.md#представление-из-частей)). Циклы ссылок с заданными целями отклоняет сборка метаданных.
- Сервер читает целевые записи пакетом вместе со страницей списка: сначала записи, на которые ссылаются колонки, затем одним запросом на целевой объект записи, по которым они называются. Число запросов зависит от числа объектов, а не строк.
- Вне списка клиент читает запись по ссылке и использует готовое служебное поле `$presentation` ответа `get`. Целевые записи и используемые колонки частей читает сервер пакетами. Заголовок формы и вкладки, ссылки и поля выбора используют этот же текст; представление не хранится в отдельной колонке.
- Если целевого объекта нет в описаниях, пользователь не вправе его читать: вместо представления написано «Нет доступа», как у ссылки на недоступный объект. Сервер таким записям текста не даёт, и поиск их не находит.

- Вне списка клиенту нужны записи по списку `guid`. Чтения, начатые за один проход отрисовки, уходят на сервер одним пакетом действий `get`, общим для всех объектов страницы. Это делает метод `getMany` data provider. В ячейках списка отдельное чтение не выполняется: представления страницы имеют приоритет перед кешем записей.
- Прочитанная запись хранится в общем кеше запросов и в течение минуты повторно не запрашивается. Изменение записи самим пользователем сбрасывает сохранённые ответы раньше.
- Пакет выполняется целиком или не выполняется вовсе. Для ссылок это допустимо: записи физически не удаляются, поэтому чтение по сохранённой ссылке всегда находит запись, а объекты без права чтения клиент не запрашивает.
- Поле ввода ссылки представляет собой выпадающий список с поиском по представлению записи (параметр `presentation` действия `list`), включая части составного представления. Предлагаются первые 20 записей в порядке сортировки объекта по умолчанию; помеченные на удаление не предлагаются. Запрос уходит, только когда список открыт.
- Уже сделанная ссылка на помеченную запись остаётся в силе: поле показывает её представление, хотя выбрать её заново нельзя.
- Если целевого объекта нет в описаниях, у пользователя нет права его читать. Тогда записи не запрашиваются, вместо представления написано «Нет доступа», а выбрать другую запись в поле нельзя.

## Списки

Если объект объявил части для списка, строка получает раскрытие с таблицами только для чтения. Компоненты просмотра монтируются при раскрытии и запрашивают запись через обычный `get`; закрытый список дополнительных `get` для строк не отправляет, а `list` не возвращает массивы частей. Используемые для составного представления колонки сервер читает отдельно, не включая их в ответ. Переключатель «Раскрыть строки страницы» раскрывает все записи текущей страницы. Его состояние хранится параметром `expandTableParts=true` вместе с состоянием списка и восстанавливается после перезагрузки.

Над поиском и отбором стандартного списка выводится его клиентская группа. Компонент в ней вызывает `useListControls({ hideCreate: true, hiddenRowActions: ['markDeleted', 'unmarkDeleted'] })`, чтобы скрыть кнопку «Создать» и действия пометки удаления. Настройки принадлежат экземпляру списка: соседние смонтированные вкладки на них не влияют. Ограничения нескольких компонентов объединяются; при изменении настроек или удалении компонента снимаются только его ограничения. Вне стандартного списка хук ничего не меняет, поэтому тот же компонент можно поставить на главный экран.

Ограничения касаются только показа кнопок. Права сервера, `useOpenRecord` и адрес `/<вид>/<имя>/new` продолжают работать. Собственная таблица может передать `hiddenRowActions` непосредственно в `RecordTable`; таблицы внутри пробного блока не получают ограничений стандартного списка автоматически.

Страница `/<вид>/<имя>` показывает список объекта (`src/web/lists/`). Он собран из SDK: хук списка читает страницу, а поиск, отбор и таблица записей показывают и меняют её состояние. Список строится только по описанию списка, поэтому новый объект конфигурации получает его без изменений клиента.

- Колонки берутся из `columns`, при открытии действует сортировка `defaultSort`. Щелчок по заголовку колонки из `sortable` сортирует список по ней и заменяет прежнюю сортировку, повторный щелчок меняет направление.
- Над таблицей пользователь составляет отбор из условий: поле из `filters`, способ сравнения из `operators` этого поля и значение. Значение вводится в поле ввода из реестра виджетов. Условия соединяются через «и», условие без значения не применяется.
- Отдельное поле «Поиск» ищет фрагмент в любой видимой колонке вместе с условиями отбора. Ввод применяется с задержкой и возвращает первую страницу; очистка сохраняет отборы. Общее число строк, страницы и сортировка относятся к найденному набору.
- Под таблицей переключаются страницы и размер страницы: 20, 50 или 100 записей, по умолчанию 50.
- Сортировку, отбор, текст поиска и номер страницы Refine хранит в адресе страницы (`syncWithLocation`). Поэтому адрес с отбором можно сохранить в закладки, а после перезагрузки страницы список открывается в прежнем состоянии. Текст поиска Refine хранить не умеет, поэтому он записывается в отбор отдельным условием с именем поля `$search`; data provider передаёт его серверу параметром `search`, а не условием. Пока вкладка списка открыта, список своё состояние не теряет. Строка запроса не различает типы, и число после разбора адреса возвращается строкой. Поэтому router provider приложения (`src/web/application/router-provider.ts`) приводит значения отбора к виду поля по описанию списка.
- Запись, помеченная на удаление, остаётся в списке: в первой колонке стоит значок пометки, текст строки бледнее обычного. У проведённого документа в первой колонке стоит значок проведения.
- Двойной щелчок по строке или щелчок по ссылке в первой колонке открывает форму записи. Если первая колонка сама содержит ссылку, она открывает целевую запись; двойной щелчок по строке открывает её владельца. Кнопка «Создать» есть, если в описании формы есть действие `save` и компонент клиентской группы не скрыл её через SDK. Она открывает запись командой SDK без указания режима: форма открывается во вкладке или в окне поверх списка, как задано в конфигурации объекта. Запись, созданная в окне, появляется в списке сама, адрес и набор вкладок при этом не меняются. Меню в конце строки ставит или снимает пометку удаления, если это действие есть среди действий формы.
- Списки обоих видов регистров доступны только для просмотра: в них нет кнопки «Создать», меню в строках и перехода к форме. У движений в колонке регистратора стоит представление документа, которое открывает его форму; у сведений отображаются измерения и ресурсы.

## Формы

У записи есть собственный адрес: `/<вид>/<имя>/new` открывает форму новой записи, `/<вид>/<имя>/<guid>` открывает форму существующей (`src/web/forms/`). По адресу форма открывается в отдельной вкладке: на запись ведут ссылки из списков, из строк регистров и из других форм. Ту же форму команда открытия записи SDK показывает в модальном окне поверх страницы; так создаётся запись объекта, у которого в конфигурации задан режим создания в окне (подразделы [«Переопределение формы»](#переопределение-формы) и [«Вкладки открытых окон»](#вкладки-открытых-окон)). У обоих видов регистров формы нет, и их адреса форм показывают страницу «не найдено». Если сервер запись не отдал, на месте формы показывается его сообщение и кнопка возврата в список.

Страница вкладки только разбирает адрес. Чтение существующей записи с признаком ожидания и сообщением об отказе сервера вынесено в отдельный компонент, который от адреса не зависит: что предложить пользователю при отказе, ему передаёт вызывающий код. Поэтому форму существующей записи показывает и модальное окно: при отказе оно предлагает закрыться.

- Форма собрана из SDK. Значения и ошибки полей хранит форма Ant Design, а загрузку, запись и действия выполняют хуки данных SDK. Отдельно форма помнит записанное состояние: запись в том виде, в каком её последним вернул сервер. По нему выводятся заголовок, отметки «Помечен на удаление» и «Проведён» и поля только для чтения, к нему применяются действия.
- Группы выводятся в порядке описания: группа с заголовком блоком с заголовком, группа без заголовка без рамки. Табличная часть занимает всю ширину формы.
- Собственный элемент конфигурации в группе занимает всю её ширину и свойств не получает. Элемент, назначенный полю, стоит на месте поля ввода: значение и обработчик изменения ему передаёт элемент формы Ant Design, как и виджету, поэтому подпись, ошибку проверки и отметку «Сервер отклонил значение» показывает форма. Значения и записанное состояние элементы читают из данных формы SDK, а изменение значения элементом форма считает несохранённым так же, как ввод пользователя. На форме только для просмотра поля ввода и кнопки Ant Design внутри элемента недоступны: недоступность им передаёт форма.
- В форме новой записи обязательный флажок снят, а обязательные дата и время равны текущему моменту: так заполняется дата нового документа. Строка с начальным значением из описания получает его; так же заполняется новая строка табличной части. Остальные поля пусты, в том числе поля только для чтения: номер документа сервер назначает при записи.
- Форма без действия `save` в описании открывается только для просмотра.
- Состоянием формы может управлять собственный элемент конфигурации (подраздел [«Элементы формы»](metadata.md#элементы-формы)): он объявляет ограничения, а форма применяет их объединение. Форма, недоступная целиком, выглядит как форма только для просмотра: поля и табличные части не редактируются, действие «Записать» скрыто само, обход с клавиатуры отключён, а остальные элементы узнают о недоступности по признаку «только просмотр» данных формы. Отдельное недоступное поле или табличная часть не редактируется и не входит в обход, остальные части формы работают как обычно. Значение недоступного поля остаётся в значениях формы и уходит в `save`, поэтому запись его не обнуляет.
- Скрытое действие не выводится кнопкой, а его сочетание клавиш запрос не отправляет: кнопки и сочетания проверяют видимость действия одной функцией.
- Пока элементы не сообщили ограничения, форма недоступна целиком и показывает только кнопку «Закрыть». Фокус в первое поле новой записи ставится после того, как ограничения собраны.
- До отправки форма проверяет значения по правилам из описания. Сообщение показывается под полем, а в табличной части у ячейки; пока есть ошибки, запрос не отправляется. Если сервер ответил 400, поля из его перечня `fields` отмечаются ошибкой «Сервер отклонил значение», а текст сервера показывается уведомлением: отдельного текста на каждое поле сервер не присылает. Ответы 403 и 409 показываются уведомлением с текстом сервера. При любой ошибке введённые значения остаются на форме.
- Значение ячейки табличной части лежит в форме по пути «табличная часть, номер строки, поле». Сервер называет поле с ошибкой таким же путём (`payload.fields.lines.0.text`), поэтому его ошибки сопоставляются с полями напрямую.
- Действие `save` заменяет запись целиком, а на форме есть не все её поля: переопределение `.hide(...)` убирает поле из описания формы. Поэтому в `save` отправляется загруженная запись, в которой значения полей формы заменены введёнными. Иначе запись обнулила бы скрытые поля. Поля, которые заполняет платформа, сервер во входных данных пропускает.
- Кнопки действий строятся из `actions` описания, поэтому действие без права на форме не появляется. Из пары «Пометить на удаление» и «Снять пометку удаления» показывается применимое, «Отменить проведение» показывается только у проведённого документа. В форме новой записи доступны только «Записать» и «Провести».
- Все действия, кроме «Записать», применяются к записанному состоянию. При несохранённых изменениях форма сначала записывает их и только затем выполняет действие, двумя последовательными запросами: у новой записи до ответа на запись нет `guid`, который нужен действию. Если действие после успешной записи отклонено, запись остаётся сохранённой.
- После каждого изменения записи на сервере форма сообщает области окна её `guid`, а после создания записи сообщает об этом отдельно. Что делать дальше, решает область. Вкладка формы новой записи получает адрес существующей записи, форма остаётся открытой, и повторное открытие этой записи находит ту же вкладку. Модальное окно после создания записи закрывается. В истории браузера адрес новой записи заменяется, поэтому кнопка «Назад» к пустой форме не возвращает. Форма новой записи у объекта одна: кнопка «Создать» при уже открытой новой форме возвращает к ней.
- Собственное действие доступно для записанной записи. Если у него есть входные данные, кнопка действия открывает окно с полями из того же реестра виджетов. Поля окна заполняются так же, как поля новой записи: обязательные дата и время равны текущему моменту. После выполнения запись читается с сервера заново: действие могло её изменить.
- После любого изменяющего действия сохранённые ответы сервера о данных помечаются устаревшими: открытые списки и ссылки перечитываются сразу, остальные при следующем открытии. Сбрасываются ответы обо всех объектах, потому что проведение меняет строки регистров, а собственное действие может изменить любые записи.
- Переключение вкладок данные формы не теряет, поэтому подтверждение спрашивается только при закрытии вкладки формы с несохранёнными изменениями: крестиком, кнопкой «Закрыть» или клавишей Esc. Отказ оставляет вкладку открытой. Выход из приложения закрывает все вкладки и спрашивает подтверждение, если несохранённые изменения есть хотя бы на одной. При закрытии вкладки или окна браузера подтверждение показывает сам браузер; оно тоже учитывает все вкладки приложения, потому что изменения могут быть на скрытой форме.
- Табличная часть сделана отдельным компонентом, который получает только её описание и не зависит от остальной формы. Форма знает свои поля ввода и табличные части по именам и может перевести фокус на любое имя из порядка обхода `traversal`.

## Работа с клавиатуры

В колонке-ссылке с `expandedTablePart` строка раскрывает часть целевой записи компонентом SDK `RecordTablePart`. Этот же компонент работает в списке и в элементе конфигурации; `onRowClick` передаёт прочитанную строку вызывающему экрану. Сам просмотр запись не меняет. Например, элемент формы может добавить выбранную строку в текущую часть через `useFormData`.

Входные табличные части собственного действия выводятся в его окне тем же компонентом `TablePart`, с теми же проверками ячеек, вычислениями и обходом Enter. Серверный путь ошибки начинается с `payload.lines.0.field`, без промежуточного `fields`. Экран может передать входные строки через `ActionButton.input` или `useAction`, тогда окно не открывается.

Форма обходит редактируемые поля по порядку `traversal` из описания: Enter переводит фокус вперёд, Shift+Enter назад. Поля только для чтения и поля, которые элемент формы сделал недоступными для изменения, в обход не входят. На границе шапки обратный обход останавливается в первом поле.

Собственный элемент, назначенный полю, участвует в обходе на месте этого поля и получает фокус в новой записи, если поле первое в порядке: для этого он принимает фокус по контракту поля ввода. Кнопка внутри элемента по Enter срабатывает сама, как и остальные кнопки формы. Собственный элемент в группе без назначенного поля в порядок обхода не входит: контракта поля ввода он соблюдать не обязан.

При переходе в пустую табличную часть форма добавляет первую строку и ставит фокус в её первую ячейку. Внутри строки обход идёт по колонкам описания. После последней ячейки Enter переходит в первую ячейку следующей строки, а если её ещё нет, добавляет строку. Shift+Enter из первой ячейки возвращает в последнюю ячейку предыдущей строки, а из первой строки в предыдущее поле формы. Ссылки на поля ячеек учитываются по устойчивым ключам строк, поэтому удаление строки не меняет адреса полей остальных строк.

Открытый список выбора или календарь обрабатывает Enter и Esc сам: Enter выбирает значение, Esc закрывает выбор. Следующее нажатие работает с формой. Во время составного ввода текста переходы не выполняются.

Сочетания TanStack Hotkeys действуют на форме активной вкладки: Ctrl+S записывает её, Ctrl+Enter проводит документ и закрывает вкладку только после успеха, Esc закрывает вкладку с обычным подтверждением при несохранённых изменениях. В форме, показанной в модальном окне, сочетания действуют так же и закрывают окно, а в формах под окном не действуют. Esc, которую обработала форма, до обработчика Ant Design не доходит: иначе то же нажатие закрыло бы только что открытое окно подтверждения. Сочетания вызывают те же действия, что кнопки, и доступны только при наличии действия в описании формы. Поэтому пользователь без права записи не может записать форму сочетанием клавиш. Окна подтверждения и входных данных собственных действий получают клавиши сами; действия записи за ними не запускаются. Повторное нажатие во время запроса не запускает второе действие.

Обход полей и учёт фокуса входят в SDK (`useFieldTraversal`), поэтому собственный экран с формой получает тот же обход; значения хранятся в форме Ant Design, серверные данные в TanStack Query. Табличная часть использует таблицу Ant Design с собственным обходом ячеек, без замены остальных частей формы.
