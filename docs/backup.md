# Резервное копирование

Приложение копирует файл базы во время работы: по расписанию и по кнопке. Копии лежат в каталоге `backups`, проверяются перед сохранением и хранятся в заданном числе. Страница для администратора, который настраивает копирование и восстанавливает базу, и для разработчика серверной части.

## Как устроено копирование

Копию пишет команда `VACUUM INTO`: драйвер Turso (`0.8.0`) не реализует метод `backup()`, а простое копирование файла работающей базы может захватить частично записанные страницы. `VACUUM INTO` читает базу в одной транзакции чтения, поэтому копия содержит состояние на начало команды: все подтверждённые до этого момента записи и ни одной незавершённой. Запись основного соединения при этом не блокируется.

Драйвер выполняет `VACUUM INTO` одним синхронным шагом. В основном потоке такой шаг остановил бы обработку всех запросов: на базе 43 МБ простой составил около 10 секунд. Поэтому команду выполняет рабочий поток (`worker_threads`) с отдельным соединением только для чтения. Пока он работает, приложение отвечает на запросы и принимает изменения. База размером 200 МБ копируется примерно за минуту. Копия занимает на диске не больше места, чем сама база, поэтому перед запуском проверьте свободное место на странице копий.

Порядок одной копии:

1. Рабочий поток пишет снимок в файл `<имя>.db.partial`.
2. Тот же поток открывает снимок и выполняет `PRAGMA integrity_check`. Любой результат, кроме `ok`, считается ошибкой.
3. Сервер переименовывает `.partial` в `<имя>.db`. До переименования файл не считается копией и в списке не показывается.
4. Сервер удаляет копии сверх `keep`, начиная с самых старых.

Старые копии удаляются только после успешной новой: при ошибке записи, проверки или отмене они остаются все. Файлы `.partial`, оставшиеся после аварийной остановки процесса, сервер удаляет при запуске. Файлы в каталоге, чьё имя не совпадает с именем копии, не показываются и не удаляются.

Имя копии: `backup-2026-10-18_08-00-12-345-schedule.db`. Время местное, с миллисекундами; последняя часть указывает источник: `schedule` или `manual`. Время и источник восстанавливаются из имени, поэтому копии нельзя переименовывать: переименованный файл перестанет быть копией для приложения.

Рабочий поток запускает сценарий [`snapshot.worker.ts`](https://github.com/EGSP/collection-zarplata/blob/main/src/server/database/snapshot.worker.ts), логику снимка содержит [`database.snapshot.ts`](https://github.com/EGSP/collection-zarplata/blob/main/src/server/database/database.snapshot.ts). В [исполняемом файле](delivery.md#как-собрать-исполняемый-файл) отдельных файлов нет: сценарий потока встроен ресурсом SEA `snapshot-worker.cjs`, а путь к нативному модулю Turso поток берёт из общего `process.env`.

## Где лежат копии

Каталог не настраивается. Он называется `backups` и лежит:

| Запуск | Расположение |
|---|---|
| Исполняемый файл | Рядом с исполняемым файлом |
| Из исходников (`npm start`, `npm run dev`) | Рядом с файлом настроек, то есть в рабочем каталоге |
| `--test-database=<файл>` | Рядом с файлом тестовой базы |
| `--database=memory` | Копирование недоступно: база существует только в памяти. Страница это сообщает, создание копии отклоняется |

Недоступный каталог (отключённый диск, нет прав) не останавливает запуск. Сервер пишет предупреждение в лог, а страница копий показывает текст ошибки вместо списка.

## Настройки

Блок `backup` в `collection-zarplata.settings.json` необязателен:

```json
{
  "backup": {
    "schedule": ["0 8 * * *", "0 13 * * *", "0 20 * * *"],
    "keep": 30
  }
}
```

| Поле | Формат и назначение |
|---|---|
| `schedule` | Список строк cron в местном времени сервера. Без поля или с пустым списком делаются только ручные копии. Строки разбирает `Cron` из Effect; ошибка в любой строке останавливает запуск и называет эту строку |
| `keep` | Целое число не меньше `1`: сколько последних копий хранить. По умолчанию `30` |

Общий формат файла настроек описан в разделе [«Сборка и запуск»](build-and-launch.md#файл-настроек). Чтобы проверить расписание на тестовой базе, добавьте повторяемый параметр `--test-backup-schedule=<cron>`. Он допустим только вместе с `--test-database`:

```bash
npm run start:check -- --test-database=C:/Temp/collection-zarplata-test/test.db --test-pin=482915 --port=3101 --test-backup-schedule="*/2 * * * *"
```

## Расписание

Плановый цикл запускается после синхронизации структуры базы и раз в 30 секунд сверяется с часами. Он находит последний наступивший срок по всем строкам и запускает копию, если этот срок позже последнего обработанного. Срок опаздывает не больше чем на интервал проверки.

Пропущенный срок догоняется. При запуске сервера последним обработанным считается время новейшей копии в каталоге. Если сервер был выключен или компьютер спал и срок прошёл, после включения делается одна копия. Несколько пропущенных сроков тоже дают одну копию: берётся только последний.

Срок отмечается обработанным до запуска копии. Поэтому отказ (уже идут две копии) или ошибка копии не повторяются каждые 30 секунд, а ждут следующего срока. Плановая копия, которую не удалось начать из-за предела, пишет предупреждение в лог сервера.

## Предел и отмена

Одновременно идут не больше двух копий, плановых и ручных вместе: каждая читает всю базу, и большее число только замедлило бы диск. Третья отклоняется, API отвечает `409`.

Отмена прерывает копию и завершает рабочий поток; недописанный файл удаляется, прежние копии остаются. У отмены есть ограничение: драйвер не прерывает начатый нативный шаг `VACUUM INTO`, а `interrupt()` соединения доступен только из занятого потока. Поэтому отмена большой копии вступает в силу после окончания команды: на базе 200 МБ это до 40 секунд. Пока поток не остановился, копия показана со статусом «Прерывается». Остановка сервера прерывает идущие копии так же.

## Ошибки

| Ситуация | Поведение |
|---|---|
| Каталог недоступен при запуске | Предупреждение в логе и на странице; запуск продолжается |
| Не хватило места, ошибка записи, проверка `integrity_check` не пройдена | Файл `.partial` удаляется, старые копии остаются; ошибка идёт в лог и в итог последней копии на странице |
| Копия отменена | Файл `.partial` удаляется, итог «отменена» |
| Процесс остановлен аварийно | Файл `.partial` остаётся до следующего запуска и тогда удаляется |
| Начата третья копия | Отказ: `409` для ручной, предупреждение в логе для плановой |

Итог последней копии хранится в памяти процесса: после перезапуска он пуст. Список готовых копий читается из каталога.

## Страница «Резервные копии»

Страница находится в подсистеме «Администрирование», группа «Обслуживание». Видимость задаёт право страницы `Rights.page.backups.open`; данные требуют отдельных прав на копии ([ниже](#api-и-права)).

Страница показывает:

- диск каталога: всего, занято, свободно;
- путь каталога, расписание, ближайшую плановую копию и число хранимых копий;
- идущие копии с кнопкой «Прервать» (с подтверждением);
- итог последней копии;
- таблицу готовых копий: имя, время, источник, размер.

Кнопка «Создать копию» доступна при праве записи. Пока идут копии, страница перечитывает состояние раз в 2 секунды через параметр `refreshInterval` хука [`useActionResult`](web-sdk/hooks.md#чтение-данных).

## API и права

Действия идут через [единый эндпоинт](single-endpoint.md) с целью `{ "kind": "platform", "name": "backups" }`.

| Действие | Право | Результат |
|---|---|---|
| `list` | `platform.backups.read` | Состояние для страницы: `available`, `directory`, `disk` (`total`, `used`, `free` в байтах), `directoryError`, `files`, `running`, `limit`, `schedule`, `nextRun`, `keep`, `lastOutcome`, `canWrite` |
| `create` | `platform.backups.write` | Описание начатой копии (`id`, `source`, `startedAt`, `cancelling`). Запрос не ждёт окончания копирования |
| `cancel` | `platform.backups.write` | Пустой объект. В `payload` передаётся `{ "id": "<guid копии>" }`; неизвестный или уже завершённый `id` даёт `404` |

Без права ответ `403`, без входа `401`. Копия содержит всю базу, включая хеши PIN и данные магазина, поэтому права на просмотр и создание отдельные и не следуют из прав объектов. Администратор получает их вместе с остальными ([«Права (RBAC)»](authorization.md#права-страниц-и-платформы)).

Создание и отмена записываются в [журнал](journal.md) с целью `platform.backups` и guid копии до запуска. Если копию начать нельзя, транзакция запроса откатывает и запись журнала. Итоги копий в журнал не попадают: у них нет пользователя. Они видны в логе сервера и в `lastOutcome`.

## Как восстановить базу из копии

1. Остановите приложение и убедитесь, что процесс завершён.
2. Сохраните текущий файл базы, если он нужен для разбора причин. Затем удалите рядом с ним файлы `<база>-wal` и `<база>-shm`: служебные данные прежней базы испортят открытую копию.
3. Скопируйте нужный файл из `backups` на место файла по `databasePath` под его прежним именем. Саму копию в `backups` оставьте на месте.
4. Оставьте в настройках прежний `pinHmacSecret`. Пользователи и токены в копии подписаны им; с другим секретом PIN перестанут подходить.
5. Запустите приложение, войдите и проверьте данные. Изменения, сделанные после момента копии, в базе отсутствуют.

## Как проверить копию отдельно от рабочей базы

Проверка не затрагивает рабочую базу и её порт.

1. Создайте пустой каталог и положите в него исполняемый файл той же версии.
2. Скопируйте в каталог нужную копию. Относительный `databasePath` отсчитывается от каталога настроек.
3. Создайте рядом `collection-zarplata.settings.json`: `databasePath` указывает на скопированный файл, `pinHmacSecret` равен рабочему, `port` свободный и отличается от рабочего, `host` оставьте `127.0.0.1`.
4. Запустите файл из этого каталога, войдите своим PIN и сравните списки с рабочими данными.
5. Остановите процесс и убедитесь, что порт свободен.

Запуск может применить к копии миграции и создаст рядом служебные файлы, поэтому проверяйте скопированный файл, а не оригинал из `backups`.
