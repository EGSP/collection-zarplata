# Инструменты разработки

Страница предназначена разработчику: здесь описаны проверка типов и правил Effect, граф модулей сервера и работа с исходниками внешних библиотек. Установка зависимостей, сборка и ручная проверка приложения описаны в разделе [«Сборка и запуск»](build-and-launch.md).

## Как проверить код

Выполняйте команды из корня рабочей копии проекта с установленными зависимостями.

После каждого изменения кода запустите:

```bash
npm run typecheck
```

Команда обновляет реестр объектов конфигурации, проверяет границы импортов и связь документации с кодом, затем проверяет типы без сборки файлов. Проверка охватывает сервер и конфигурацию, служебные скрипты, настройку сайта документации и клиент. Исправьте найденные ошибки и предупреждения Effect, затем повторите проверку; подавлять их вместо исправления не следует.

Для подробного отчёта Effect по серверному проекту запустите:

```bash
npm run diagnostics
```

Этот отчёт относится к корневому `tsconfig.json` и не заменяет проверку остальных проектов командой `typecheck`. После успешной проверки типов проверьте изменённое поведение приложения [вручную](build-and-launch.md). В проекте не создаются автотесты и не подключаются тестовые фреймворки.

## Как подключена проверка Effect

Проект использует TypeScript 7 и пакет `@effect/tsgo`. При установке зависимостей скрипт `prepare` выполняет `effect-tsgo patch --typescript --no-oxlint`: он подключает Effect Language Service к установленному TypeScript. Поэтому команды проекта вызывают `tsc`, а проверка выдаёт и диагностики TypeScript, и диагностики Effect. Состав команд определён в [`package.json`](https://github.com/EGSP/collection-zarplata/blob/main/package.json).

Запись плагина `@effect/language-service` находится в [`tsconfig.base.json`](https://github.com/EGSP/collection-zarplata/blob/main/tsconfig.base.json). Её наследуют сервер, служебные скрипты и клиент. [Настройка сайта документации](https://github.com/EGSP/collection-zarplata/blob/main/docs/tsconfig.json) проверяется отдельно и не наследует базовую настройку.

## Граф модулей сервера

Страница `/modules-graph` показывает модули NestJS запущенного сервера и связи между ними. По ней видно, откуда модуль получает зависимости, от каких модулей зависит больше всего других и какие импорты не используются напрямую. Страницу открывает кнопка «Граф модулей» в левой панели приложения; она открывается в новой вкладке браузера, как документация.

Граф строится по контейнеру Nest работающего приложения, поэтому совпадает с фактическим составом модулей. Данные отдаёт `GET /api/modules-graph`. Запрос требует входа: без сессии страница предлагает войти в приложение. Сама страница собирается вместе с клиентом отдельной точкой входа Vite и использует его тему и Ant Design.

### Что показывает граф

Узел обозначает модуль, стрелка ведёт от зависимого модуля к его зависимости. Зависимым считается модуль, который импортирует данный или внедряет его провайдеры.

Каждый признак показан своим способом, чтобы признаки не смешивались:

| Признак | Как показан |
|---|---|
| Число зависимых модулей | Насыщенность синей заливки и размер узла: чем больше зависимых, тем темнее и крупнее узел |
| Вид модуля | Форма, рамка и значок узла |
| Категория связи | Цвет и штрих линии |
| Число внедрений через связь | Толщина линии |

| Вид модуля | Узел |
|---|---|
| Обычный | Прямоугольник со сплошной рамкой |
| Глобальный (`@Global()`) | Капсула с диагональной штриховкой и значком глобуса |
| Динамический (`forRoot()`, `register()` и подобные методы) | Двойная рамка и значок молнии |
| Ядро Nest | Пунктирная рамка и значок шестерёнки |

| Категория связи | Линия | Значение |
|---|---|---|
| Импорт | Тёмная сплошная | Модуль указан в `imports` декоратора `@Module()` или динамического модуля, и его провайдеры внедряются |
| Неиспользуемый импорт | Красно-оранжевые точки | Модуль указан в `imports`, но ни один класс не получает его провайдеры |
| Подключение в корне | Светло-серая тонкая | Корневой модуль импортирует модуль, чтобы подключить его к приложению |
| Через `@Global()` | Жёлто-оранжевый пунктир | Модуль внедряет провайдер глобального модуля без импорта |
| Через реэкспорт | Зелёный штрихпунктир | Провайдер доступен, потому что импортированный модуль экспортирует его модуль дальше |
| Через `forwardRef()` | Розовая сплошная | Импорт записан через `forwardRef()`, то есть модули зависят друг от друга по кругу |

Цвета связей взяты из палитры Окабэ и Ито, которую различают и люди с нарушениями цветового зрения. Штрих дублирует различие цветом.

Неиспользуемый импорт может оказаться лишним, но не обязательно: модуль иногда импортируют ради реэкспорта или порядка инициализации. Импорты корневого модуля выделены отдельно: корневой модуль собирает приложение, и внедрения через его импорты не нужны. Без этого все они выглядели бы неиспользуемыми и заслоняли бы действительно лишние.

Модуль ядра Nest содержит `HttpAdapterHost`, `ModulesContainer` и другие средства фреймворка. По умолчанию он скрыт, чтобы не загромождать граф.

Nest делает глобальный модуль доступным каждому модулю. Если показывать эту доступность целиком, каждый модуль оказался бы связан с каждым глобальным. Поэтому связь через `@Global()` появляется только там, где модуль действительно внедряет провайдер глобального модуля. Явный импорт показывается всегда: модуль мог импортировать другой ради реэкспорта или порядка инициализации.

Внедрения учитывают параметры конструктора и свойства с `@Inject()` у провайдеров, контроллеров, классов модулей и улучшителей. Улучшитель (guard, interceptor, pipe или filter), подключённый декоратором вроде `@UseGuards()`, Nest создаёт в модуле контроллера. Поэтому зависимости `AuthenticationGuard` у контроллера данных относятся к модулю данных.

### Как пользоваться страницей

- Холст перемещается перетаскиванием, масштаб меняется колесом мыши. Кнопки в левом нижнем углу вписывают граф в окно, мини-карта в правом нижнем углу показывает видимую часть.
- Курсор над модулем подсвечивает его соседей и связи с ними, курсор над связью подсвечивает её и оба модуля. Остальные элементы приглушаются.
- Пункты легенды справа подсвечивают на графе свою категорию связей или свой вид модуля. Щелчок по пункту закрепляет подсветку и раскрывает список связей или модулей: например, так находятся все неиспользуемые импорты. Наведение на строку списка подсвечивает её элемент, щелчок открывает подробности.
- Щелчок по модулю показывает справа его классы, зависимости, зависимых и внедрения внутри модуля. Наведение на строку зависимости или зависимого подсвечивает связь на графе. Щелчок по связи показывает её категорию и таблицу внедрений: какой класс получает какой провайдер, через параметр конструктора или свойство.
- Узлы можно перетаскивать. Кнопка «Разложить заново» возвращает рассчитанное размещение.
- Флажки над холстом скрывают связи через `@Global()` и показывают модуль ядра Nest.
- Кнопка «В приложение» открывает главный экран приложения в той же вкладке.

### Как размещаются узлы

Начальное размещение рассчитывает [dagre](https://github.com/dagrejs/dagre) послойной раскладкой. Модули распределяются по слоям так, чтобы каждая связь шла сверху вниз: корневой модуль приложения оказывается наверху, общие модули вроде настроек и базы данных внизу. Внутри слоя порядок подбирается так, чтобы связи соседних слоёв пересекались как можно реже. Расчёт учитывает размеры узлов, поэтому крупные узлы не перекрывают соседей. Цикл через `forwardRef()` dagre разрывает, временно разворачивая одну из связей.

Холст построен на React Flow (`@xyflow/react`). Раскладка пересчитывается при смене набора модулей и связей, например при показе модуля ядра. Подсветка и выбор элемента положение узлов не меняют.

### Ограничения

Граф читает внутренние классы Nest `Module` и `InstanceWrapper`: публичного API для разрешённых зависимостей у фреймворка нет. После обновления NestJS проверьте, что страница по-прежнему показывает связи и внедрения. Сервер строит граф один раз, при первом запросе: состав модулей после запуска не меняется. Сбор данных реализован в [сервисе графа](https://github.com/EGSP/collection-zarplata/blob/main/src/server/modules-graph/modules-graph.service.ts).

## Как читать исходники внешних библиотек

Репозиторий Effect подключён через `git subtree` в `repos/effect` и служит справочником по API и примерам. Перед использованием API Effect сверяйтесь с [`packages/effect/src`](https://github.com/EGSP/collection-zarplata/tree/main/repos/effect/packages/effect/src), [`LLMS.md`](https://github.com/EGSP/collection-zarplata/blob/main/repos/effect/LLMS.md) и [`ai-docs`](https://github.com/EGSP/collection-zarplata/tree/main/repos/effect/ai-docs).

При разработке приложения исходники в `repos/` используются только для чтения. Приложение импортирует библиотеки из установленных пакетов, а не из этого каталога; локальные правки внешних исходников требуют отдельного поручения.

## Как обновить исходники Effect

Обновление справочной копии Effect выполняется отдельной задачей в рабочей ветке. Команда создаёт коммиты, поэтому её запуск требует явного одобрения пользователя согласно [правилам работы агентов](https://github.com/EGSP/collection-zarplata/blob/main/AGENTS.md):

```bash
git subtree pull --prefix=repos/effect https://github.com/Effect-TS/effect.git main --squash
```

Команда получает изменения из внешнего репозитория и включает их в текущую ветку. Обновление `repos/effect` не меняет версию установленного пакета `effect`: зависимости приложения задаются отдельно в `package.json`.
