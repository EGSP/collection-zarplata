# Инструменты разработки

Страница для разработчика: проверка типов и правил Effect, отчёт об inline-стилях, граф модулей сервера и исходники внешних библиотек. Установка зависимостей, сборка и ручная проверка приложения описаны в разделе [«Сборка и запуск»](build-and-launch.md).

## Как проверить код

Выполняйте команды из корня рабочей копии с установленными зависимостями. После каждого изменения кода запускайте:

```bash
npm run typecheck
```

Команда обновляет реестр объектов конфигурации, проверяет границы импортов и связь документации с кодом, затем проверяет типы без сборки файлов. Типы проверяются у сервера с конфигурацией, служебных скриптов, настройки сайта документации и клиента. Ошибки и предупреждения Effect исправляйте, а не подавляйте.

Подробный отчёт Effect по серверному проекту даёт команда:

```bash
npm run diagnostics
```

Отчёт относится только к корневому `tsconfig.json`, поэтому `typecheck` она не заменяет. После успешной проверки типов проверьте изменённое поведение [вручную](build-and-launch.md): автотесты и тестовые фреймворки в проект не добавляются.

## Как найти inline-стили

Правила [раскладки](components.md#компонент-заполняет-контейнер) запрещают в конфигурации inline-стили ширины, отступов и размера шрифта. Найти оставшиеся помогает отчёт:

```bash
npm run styles:report
```

Скрипт [`inline-styles-report.ts`](https://github.com/EGSP/collection-zarplata/blob/main/scripts/inline-styles-report.ts) выводит каждое свойство `style={…}` в файлах `.tsx`: файл, строку и выражение одной строкой. В конце стоят число стилей и число файлов. По умолчанию просматривается `src/configuration`; другие каталоги передаются аргументами:

```bash
npm run styles:report -- src/web/sdk src/web/widgets
```

Отчёт только сообщает и всегда завершается успешно, поэтому это не проверка и не запрет. Часть стилей допустима, например `minWidth: 0` для многоточия во flex-строке, и решение о каждом месте принимает разработчик. По этой же причине команда не входит в проверки перед отчётом и в `npm run typecheck`. Скрипт разбирает текст, а не синтаксическое дерево, и ищет выражение до парной закрывающей скобки.

## Как подключена проверка Effect

Проект использует TypeScript 7 и пакет `@effect/tsgo`. При установке зависимостей скрипт `prepare` выполняет `effect-tsgo patch --typescript --no-oxlint` и подключает Effect Language Service к установленному TypeScript. Поэтому команды проекта вызывают обычный `tsc`, а он выдаёт и диагностики TypeScript, и диагностики Effect. Состав команд задан в [`package.json`](https://github.com/EGSP/collection-zarplata/blob/main/package.json).

Плагин `@effect/language-service` записан в [`tsconfig.base.json`](https://github.com/EGSP/collection-zarplata/blob/main/tsconfig.base.json), его наследуют сервер, служебные скрипты и клиент. [Настройка сайта документации](https://github.com/EGSP/collection-zarplata/blob/main/docs/tsconfig.json) базовую не наследует и проверяется отдельно.

## Граф модулей сервера

Страница `/modules-graph` показывает модули NestJS запущенного сервера и связи между ними. По ней видно, откуда модуль получает зависимости, какие модули нужны большинству остальных и какие импорты не используются. Открывает её кнопка «Граф модулей» в левой панели приложения, в новой вкладке, как и документацию.

Граф строится по контейнеру Nest работающего приложения, поэтому совпадает с фактическим составом модулей. Данные отдаёт `GET /api/modules-graph`, запрос требует входа: без сессии страница предлагает войти в приложение. Страница собирается вместе с клиентом отдельной точкой входа Vite и использует его тему и Ant Design.

### Что показывает граф

Узел обозначает модуль, стрелка ведёт от зависимого модуля к его зависимости. Зависимым считается модуль, который импортирует данный или внедряет его провайдеры. Каждый признак показан своим способом, чтобы признаки не смешивались:

| Признак | Как показан |
|---|---|
| Число зависимых модулей | Насыщенность синей заливки и размер узла: чем больше зависимых, тем темнее и крупнее узел |
| Вид модуля | Форма, рамка и значок узла |
| Категория связи | Цвет и штрих линии |
| Число внедрений через связь | Толщина линии |

| Вид модуля | Узел |
|---|---|
| Обычный | Прямоугольник со сплошной рамкой |
| Глобальный (`@Global()`) | Капсула с диагональной штриховкой и значком глобуса |
| Динамический (`forRoot()`, `register()` и подобные методы) | Двойная рамка и значок молнии |
| Ядро Nest | Пунктирная рамка и значок шестерёнки |

| Категория связи | Линия | Значение |
|---|---|---|
| Импорт | Тёмная сплошная | Модуль указан в `imports` декоратора `@Module()` или динамического модуля, и его провайдеры внедряются |
| Неиспользуемый импорт | Красно-оранжевые точки | Модуль указан в `imports`, но ни один класс не получает его провайдеры |
| Подключение в корне | Светло-серая тонкая | Корневой модуль импортирует модуль, чтобы подключить его к приложению |
| Через `@Global()` | Жёлто-оранжевый пунктир | Модуль внедряет провайдер глобального модуля без импорта |
| Через реэкспорт | Зелёный штрихпунктир | Провайдер доступен, потому что импортированный модуль экспортирует его модуль дальше |
| Через `forwardRef()` | Розовая сплошная | Импорт записан через `forwardRef()`: модули зависят друг от друга по кругу |

Цвета связей взяты из палитры Окабэ и Ито, которую различают и люди с нарушениями цветового зрения; штрих дублирует цвет.

Неиспользуемый импорт не всегда лишний: модуль иногда импортируют ради реэкспорта или порядка инициализации. Импорты корневого модуля вынесены в отдельную категорию, потому что корневой модуль собирает приложение и внедрения через них не нужны. Иначе все они выглядели бы неиспользуемыми и заслоняли бы действительно лишние.

Nest делает глобальный модуль доступным каждому модулю. Если показывать эту доступность целиком, каждый модуль был бы связан с каждым глобальным. Поэтому связь через `@Global()` появляется, только когда модуль действительно внедряет провайдер глобального модуля. Явный импорт показывается всегда.

Модуль ядра Nest содержит `HttpAdapterHost`, `ModulesContainer` и другие средства фреймворка. По умолчанию он скрыт.

Внедрения учитывают параметры конструктора и свойства с `@Inject()` у провайдеров, контроллеров, классов модулей и улучшителей. Улучшитель (guard, interceptor, pipe или filter), подключённый декоратором вроде `@UseGuards()`, Nest создаёт в модуле контроллера. Поэтому зависимости `AuthenticationGuard` у контроллера данных относятся к модулю данных.

### Как пользоваться страницей

- Холст перемещается перетаскиванием, масштаб меняется колесом мыши. Кнопки в левом нижнем углу вписывают граф в окно, мини-карта в правом нижнем углу показывает видимую часть.
- Курсор над модулем подсвечивает его соседей и связи с ними, курсор над связью подсвечивает её и оба модуля. Остальное приглушается.
- Пункты легенды справа подсвечивают категорию связей или вид модулей. Щелчок закрепляет подсветку и раскрывает список связей или модулей: так находятся, например, все неиспользуемые импорты. Наведение на строку списка подсвечивает её элемент, щелчок открывает подробности.
- Щелчок по модулю показывает справа его классы, зависимости, зависимых и внедрения внутри модуля. Щелчок по связи показывает её категорию и таблицу внедрений: какой класс получает какой провайдер, через параметр конструктора или свойство.
- Узлы можно перетаскивать, кнопка «Разложить заново» возвращает рассчитанное размещение.
- Флажки над холстом скрывают связи через `@Global()` и показывают модуль ядра Nest.
- Кнопка «В приложение» открывает главный экран в той же вкладке.

### Как размещаются узлы

Начальное размещение рассчитывает [dagre](https://github.com/dagrejs/dagre) послойной раскладкой. Каждая связь идёт сверху вниз: корневой модуль оказывается наверху, общие модули вроде настроек и базы данных внизу. Внутри слоя порядок подбирается так, чтобы связи соседних слоёв пересекались реже, а размеры узлов учитываются, чтобы крупные узлы не перекрывали соседей. Цикл через `forwardRef()` dagre разрывает, временно разворачивая одну из связей.

Холст построен на React Flow (`@xyflow/react`). Раскладка пересчитывается при смене набора модулей и связей, например при показе ядра. Подсветка и выбор положение узлов не меняют.

### Ограничения

Граф читает внутренние классы Nest `Module` и `InstanceWrapper`, потому что публичного API для разрешённых зависимостей у фреймворка нет. После обновления NestJS проверьте, что страница по-прежнему показывает связи и внедрения. Сервер строит граф один раз, при первом запросе, поэтому состав модулей после запуска не меняется. Сбор данных реализован в [сервисе графа](https://github.com/EGSP/collection-zarplata/blob/main/src/server/modules-graph/modules-graph.service.ts).

## Как читать исходники внешних библиотек

Репозиторий Effect подключён через `git subtree` в `repos/effect` и служит справочником по API и примерам. Перед использованием API Effect сверяйтесь с [`packages/effect/src`](https://github.com/EGSP/collection-zarplata/tree/main/repos/effect/packages/effect/src), [`LLMS.md`](https://github.com/EGSP/collection-zarplata/blob/main/repos/effect/LLMS.md) и [`ai-docs`](https://github.com/EGSP/collection-zarplata/tree/main/repos/effect/ai-docs).

Каталог `repos/` только для чтения: приложение импортирует библиотеки из установленных пакетов, а локальные правки внешних исходников требуют отдельного поручения.

## Как обновить исходники Effect

Обновление выполняется отдельной задачей в рабочей ветке. Команда создаёт коммиты, поэтому её запуск требует явного одобрения пользователя согласно [правилам работы агентов](https://github.com/EGSP/collection-zarplata/blob/main/AGENTS.md):

```bash
git subtree pull --prefix=repos/effect https://github.com/Effect-TS/effect.git main --squash
```

Версия установленного пакета `effect` при этом не меняется: зависимости приложения задаются отдельно в `package.json`.
