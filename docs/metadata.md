# Метаданные

Раздел предназначен разработчику конфигурации: здесь описаны виды объектов, правила объявления полей и поведения, подключение собственных экранов и проверка описаний. Метаданные задают общий контракт для хранения, проверки данных и стандартного интерфейса. Бизнес-правила магазина описаны в [правилах учёта](accounting-rules.md), работа с записями через API в [разделе данных](single-endpoint.md).

## Виды объектов

| Вид | Назначение | Функция описания |
|---|---|---|
| Справочник | Условно-постоянные данные: сотрудники, номенклатура, точки | `catalog(name)` |
| Документ | Событие с датой, номером и статусом «проведён / не проведён» | `document(name)` |
| Регистр | Строки, которые документ записывает при проведении; по ним считаются обороты | `register(name)` |
| Регистр сведений | Текущие независимые значения по уникальному набору измерений | `informationRegister(name)` |

Конфигурация определяет, какие регистры нужны для учёта. Строка регистра (движение) всегда ссылается на документ-регистратор. Один документ может записать несколько строк, например по одной на каждого сотрудника смены. При повторном проведении старые строки документа удаляются и записываются заново, поэтому проведение идемпотентно.

Поддерживаются только регистры оборотов: ресурсы строк суммируются. Регистров остатков с видом движения «приход / расход» нет. Остаток получается суммой движений со знаком: один документ записывает положительное количество, другой отрицательное, а [итог регистра](#итоги-и-ограничения-регистра) по измерениям даёт текущее значение.

Регистр сведений имеет отдельный вид `informationRegister`. У него нет документа-регистратора, периода, номера строки, `guid` и пометки удаления. Все измерения обязательны и вместе определяют запись; ресурсы содержат её значения и допускают все прикладные виды полей, включая строки и ссылки. Периодичность и история значений не поддерживаются. История действий доступна в общем журнале.

## Стандартные поля

Стандартные поля добавляет платформа; конфигурация не объявляет их повторно. Состав задан в `src/server/metadata/standard-fields.ts`.

| Вид | Стандартные поля | Идентификатор записи |
|---|---|---|
| Справочник | `guid`, `deletedAt`, `name` | `guid` |
| Документ | `guid`, `deletedAt`, `number`, `date`, `posted` | `guid` |
| Регистр | `recorder`, `period`, `lineNumber` | Регистратор и номер строки |
| Регистр сведений | Нет | Набор измерений |

`recorder` содержит документ-регистратор (`{ document, guid }`), `period` содержит дату и время движения, `lineNumber` нумерует строки одного регистратора. Дата документа хранится с временем. `guid` генерируется как UUIDv7: идентификаторы упорядочены по времени.

Стандартного поля `code` у справочников нет: запись определяется GUID, пользователю показывается наименование. Конфигурация может объявить собственное поле `code`. Миграция `20261007_remove_catalog_code` удаляет прежнюю стандартную колонку и её индексы, сохраняя GUID, остальные поля, внешние связи и самостоятельно объявленный `code`.

## Пометка удаления

Справочники и документы физически не удаляются. Пометкой служит поле `deletedAt`: если дата заполнена, объект помечен на удаление. Кто поставил пометку, фиксирует журнал. Сведения удаляются физически по измерениям, а движения удаляются при отмене проведения.

## Описание объекта

### Как добавить объект

1. Создайте файл внутри `src/configuration` с суффиксом вида объекта: `*.catalog.ts`, `*.document.ts`, `*.register.ts` или `*.information-register.ts`.
2. Экспортируйте ровно один билдер соответствующего вида. Другие значения экспортировать можно; `commit()` в файле конфигурации не вызывается.
3. Задайте заголовок, прикладные поля и поведение цепочкой вызовов. Каждый вызов возвращает новый неизменяемый билдер.
4. Запустите `npm run typecheck`, затем приложение в режиме проверки по [инструкции сборки и запуска](build-and-launch.md). Генерация подключит файл автоматически; сервер при запуске проверит описание. Ошибка останавливает запуск с `MetadataError` и указывает объект и место проблемы.

Ниже показано сочетание возможностей билдера на условной конфигурации сотрудников и смен. Это иллюстрация API, а не готовый файл: цели ссылок и политики должны быть объявлены в конфигурации.

```ts
import { Effect } from 'effect';
import { catalog, document, movements, register } from '../../server/metadata/index.js';
import { Positions } from './positions.catalog.js';
import { closedPeriodByDocumentDate } from '../policies/closed-period.js';
import { preventPostedDocumentDeletion } from '../policies/posted-document-deletion.js';

export const Employees = catalog('employees')
    .title('Сотрудники')
    .field('position', (field) => field.reference(Positions).title('Должность'))
    .field('hiredAt', (field) => field.date().title('Дата приёма').required())
    .field('rate', (field) => field.money().title('Ставка').minimum(0))
    .tablePart('contacts', (part) => part
        .title('Контакты')
        .field('kind', (field) => field.string().title('Вид').required().maximumLength(20))
        .field('value', (field) => field.string().title('Значение')))
    .action('dismiss', (action) => action
        .title('Уволить')
        .input((input) => input.field('dismissedAt', (field) => field.date().required()))
        .handle((input) => Effect.log(input.dismissedAt)))
    .form((form) => form
        .group('Основное', ['name', 'position'])
        .hide('rate'));

export const Accruals = register('accruals')
    .title('Начисления')
    .dimension('employee', (field) => field.reference(Employees))
    .resource('amount', (field) => field.money().required());

export const Shift = document('shift')
    .title('Смена')
    .tablePart('staff', (part) => part
        .field('employee', (field) => field.reference(Employees).required())
        .field('amount', (field) => field.money().required()))
    .policy(closedPeriodByDocumentDate())
    .policy(preventPostedDocumentDeletion())
    .posting((record) => Effect.succeed([
        movements(Accruals, record.staff.map((line) => ({ employee: line.employee, amount: line.amount }))),
    ]));
```

### Контракт объявления

- Ссылки на другие объекты передаются самими билдерами (`field.reference(Positions)`), а не строками. Если файлы импортируют друг друга по кругу, цель передаётся функцией: `field.reference(() => Employees)`. Ссылаться можно на справочники и документы.
- Каждый вызов `.field(...)`, `.tablePart(...)`, `.dimension(...)` и `.resource(...)` расширяет тип билдера, поэтому TypeScript выводит тип записи из цепочки без отдельной генерации типов: `RecordOf<typeof Employees>`. Стандартные поля известны заранее по виду объекта и тоже входят в тип. Обязательное поле имеет тип значения, необязательное допускает значение или `null`, табличная часть содержит массив строк.
- Обработчик проведения `.posting(...)` есть только у документа. Он получает сохранённую запись документа с табличными частями и возвращает Effect со строками регистров. Строки одного регистра собирает `movements(Регистр, строки)`: тип строки выводится из билдера регистра, поэтому TypeScript отклоняет неизвестные измерения и ресурсы. `period` строки можно не указывать: платформа подставит дату документа; регистратор и номер строки платформа заполняет сама. Обработчику, как и собственному действию, доступны из окружения Effect `ActionContext`, `ActionDispatcher`, `Database` для чтения, `Metadata` с описаниями объектов конфигурации и [проверка прав пользователя](authorization.md#как-проверить-право-в-коде-конфигурации). Изменения через прямой вызов `Database.run` запрещены; для вложенной записи используется `ActionDispatcher`.
- Ограничение итога `.constraint(...)` есть только у регистра оборотов. Оно объявляется после измерений и ресурсов, которые называет; правила приведены в разделе [«Итоги и ограничения регистра»](#итоги-и-ограничения-регистра).
- Собственные действия выполняет диспетчер после проверки прав и входных данных. Имя действия попадает в тип билдера, поэтому право на него доступно переменной `Rights.catalog.employees.actions.dismiss`. Переопределение формы применяется при построении описаний форм (раздел [«Интерфейс (SDUI)»](interface.md)). `.policy(...)` привязывает к объекту именованную проверку, которая выполняется до изменения данных. Аргументы зависят от действия; контракт описан в [политиках записи](write-policies.md).

## Поля

### Ссылочные значения

Полная ссылка на запись содержит `kind` (`catalog` или `document`), `name` объекта конфигурации и `guid` записи. Функция `objectReference` собирает её из известной цели и GUID. Поле `field.reference()` принимает такую ссылку; поле с заданной целью `field.reference(Объект)` сохраняет прежний формат GUID, поскольку цель уже есть в метаданных. Оба вида полей показывают представление записи и открывают её карточку по общему правилу формирования адресов. В таблицах это наименование справочника или представление документа, поле ввода позволяет выбрать запись и открыть её кнопкой. Без права чтения целевого объекта представление не запрашивается: показывается «Нет доступа».

### Виды и свойства полей

| Поле | Значение в записи | Свойства |
|---|---|---|
| `field.string()` | строка | `minimumLength`, `maximumLength` |
| `field.number()` | число | `minimum`, `maximum`, `integer` |
| `field.money()` | целое число копеек | `minimum`, `maximum` в копейках |
| `field.date()` | строка `YYYY-MM-DD` | |
| `field.dateTime()` | строка ISO 8601 с часовым поясом | |
| `field.boolean()` | логическое значение | |
| `field.reference(Объект)` | `guid` объекта; цель задана в метаданных | |
| `field.reference()` | `{ kind, name, guid }`, ссылка на любой справочник или документ | |
| `field.composite([...])` | значение одного из вариантов вместе с его типом | задаются вариантам; см. [«Составное поле»](#составное-поле) |

У всех полей есть `title` и `required`. Строка может ограничить ввод перечнем значений (`choices`) и задать начальное значение (`initial`): им форма заполняет поле в новой записи и в новой строке табличной части. Начальное значение действует только на форму; запись через единый эндпоинт без значения поле не заполняет. Табличные части и входные данные действий состоят из тех же полей.

У регистра движений измерения (`.dimension`) задают разрезы отбора и группировки, ресурсы (`.resource`) содержат числа или деньги для суммирования. Требуется хотя бы один ресурс. У регистра сведений измерения задают ключ, а ресурсы допускают любые прикладные виды полей; его правила приведены в [разделе независимых сведений](#независимые-сведения).

### Составное поле

Составное поле принимает значение одного из нескольких объявленных вариантов. Оно нужно там, где пользователь либо выбирает запись, либо вписывает значение вручную: например, «Куда оплачено» хранит ссылку на приёмника оплаты или произвольный текст.

```ts
.field('receiver', (field) => field.composite([
    field.string().maximumLength(200),
    field.reference(PaymentReceivers),
]).title('Куда оплачено'))
```

Значение хранит тип варианта рядом с данными, поэтому строка «100» и число 100 остаются разными значениями. Незаполненное поле равно `null`.

| Вариант | Значение в записи и в API |
|---|---|
| `field.string()`, `field.date()`, `field.dateTime()` | `{ type: 'string', value: 'Сейф' }`; `type` равен виду варианта |
| `field.number()`, `field.money()` | `{ type: 'number', value: 100 }`; деньги в копейках |
| `field.boolean()` | `{ type: 'boolean', value: true }` |
| `field.reference(Объект)` | `{ type: 'reference', kind: 'catalog', name: 'paymentReceivers', guid }` |

Правила объявления:

- Вариантов не меньше двух. Вариантом служит простой вид поля или ссылка с заданной целью; полная ссылка `field.reference()` и другое составное поле вариантом быть не могут.
- Простой вид и цель ссылки не повторяются: значение называет вариант только типом и целью. Несколько ссылок на разные объекты допустимы.
- Ограничения задаются варианту: длина и перечень значений строки, границы и целочисленность числа. Подпись и обязательность задаются самому полю. Формула, числовые подсказки, начальное значение и раскрытие табличной части у варианта не поддерживаются.
- `RecordOf` выводит тип поля объединением значений объявленных вариантов; код конфигурации различает их по свойству `type`.

#### Способ ввода

Платформа делит виды полей по способу ввода. Значение способа `fluent` можно написать текстом: строка, число, сумма, ссылка с заданной целью, которую пользователь находит по представлению записи. Значению способа `solid` нужен собственный элемент ввода: дата, дата со временем, логическое значение. Соответствие задано один раз реестром `fieldInputModes` в `src/server/metadata/composite.ts` и в конфигурации не настраивается.

Способ составного поля сборка описаний выводит из вариантов. Если каждый вариант вводится текстом, поле получает `fluent`: в интерфейсе это одно текстовое поле с подсказками по всем вариантам. Хотя бы один вариант способа `solid` делает `solid` всё поле: пользователь сначала выбирает тип значения. Результат записан в описании поля свойством `inputMode` и передаётся клиенту; клиент его не вычисляет.

| Варианты | Способ |
|---|---|
| Строка и ссылка | `fluent` |
| Строка, число и ссылки на два объекта | `fluent` |
| Строка с перечнем значений и ссылка | `fluent`: значения перечня предлагаются подсказками |
| Дата и строка | `solid` |
| Число и логическое значение | `solid` |

Конфигурация может отключить текстовый ввод: `field.composite([...]).inputMode('solid')`. Это нужно, когда значения вариантов легко спутать, например строку и сумму. Обратной настройки нет: поле с датой или флажком в одной строке ввода не набрать. Поведение обоих способов описано в разделе [«Реестр виджетов»](interface.md#составное-поле).

#### Где доступно и как сравнивается

Поле доступно в шапке, в табличной части, во входных данных действия, в измерениях регистров и в ресурсах регистра сведений. Ресурсы регистра движений суммируются, поэтому остаются числами или деньгами.

Равенство, ключ сведений и группировка итогов учитывают тип, значение и цель ссылки. Сравнения «больше» и «меньше» действуют внутри одного простого типа: условие с числом отбирает только числовые значения и не затрагивает строки и ссылки; для ссылки и логического значения такие сравнения недоступны. Сортировка сначала упорядочивает значения по имени типа (`boolean`, `date`, `dateTime`, `money`, `number`, `reference`, `string`), затем по значению внутри типа; незаполненные значения идут первыми при сортировке по возрастанию. Ссылки одного объекта упорядочены по GUID, а не по представлению.

Хранение описано в разделе [«База данных»](database.md#хранение-значений), ввод и показ в разделе [«Реестр виджетов»](interface.md#реестр-виджетов), формат отбора в разделе [«API данных»](single-endpoint.md#отбор-по-полю).

## Итоги и ограничения регистра

Итог регистра оборотов равен сумме ресурсов его движений по сочетанию значений измерений. Он не хранится: платформа считает его запросом по движениям при каждом чтении. Через API итог возвращает действие [`totals`](single-endpoint.md#итоги-регистра).

### Зачем нужны ограничения

Правило, которое связывает несколько документов, выражается движениями одного регистра и ограничением его итога. Например, продажа записывает положительное количество по товару, возврат записывает отрицательное, а регистр объявляет, что сумма по продаже и товару не бывает меньше нуля. Возврату не нужно читать таблицы продаж и других возвратов, а новый вид документа подчиняется правилу, как только начинает записывать движения в этот регистр.

Ограничение проверяет платформа, а не [политика записи](write-policies.md). Политика выполняется до изменения данных и новых движений не видит. Проверка после записи движений нужна ещё и потому, что нарушить правило может отмена проведения: без движений продажи итог по ней станет отрицательным, если по ней проведены возвраты.

### Объявление ограничения

```ts
export const SampleRegister = register('sample')
    .title('Пробный регистр')
    .dimension('item', (field) => field.reference(Sample).title('Элемент справочника').required())
    .resource('quantity', (field) => field.number().title('Количество').required())
    .resource('amount', (field) => field.money().title('Сумма').required())
    .constraint('stock', (constraint) => constraint
        .by(['item'])
        .minimum('quantity', 0)
        .message(({ totals }) => Effect.succeed(`Количество по элементу справочника уходит в минус на ${-totals.quantity}`)));
```

| Вызов | Контракт |
|---|---|
| `.constraint(name, define)` | Добавляет ограничение. У регистра их может быть несколько; имена не повторяются |
| `.by([...])` | Измерения, по сочетанию значений которых считается итог. Без вызова проверяется итог по всему регистру |
| `.minimum(resource, value)` | Ресурс и наименьшее допустимое значение его суммы; для денег в копейках. Обязателен |
| `.message(fn)` | Текст отказа. Функция получает `{ dimensions, totals }` и возвращает `Effect` со строкой |

`dimensions` содержит значения измерений из `.by(...)` для нарушенного сочетания, `totals` содержит суммы всех ресурсов регистра по нему после изменения движений. Функции текста доступны те же сервисы, что и политике: `Database` для чтения в текущей транзакции, `Metadata`, `ActionContext` и `ActionDispatcher`. Она может прочитать, например, представление документа из измерения. Без `.message(...)` платформа называет в отказе регистр, ресурс, итог и допустимое значение.

TypeScript принимает в `.by(...)` только измерения, а в `.minimum(...)` только ресурсы регистра; `.by(...)` вызывается раньше `.message(...)`, чтобы тип `dimensions` совпал с выбранными измерениями. Сборка описаний повторяет проверку имён и отклоняет ограничение без `.minimum(...)`.

### Когда ограничение проверяется

Платформа проверяет ограничения после каждого изменения движений документа: при проведении, при повторном проведении после записи проведённого документа, при отмене проведения, при пометке проведённого документа на удаление и при [перепроведении всех документов](single-endpoint.md#перепроведение-документов). Проверка не зависит от политик документа и прав на отдельные действия.

Итог пересчитывается только по сочетаниям значений измерений, которые встречаются в удалённых и в записанных движениях документа. Если сумма ресурса меньше наименьшего значения, действие завершается отказом с HTTP 409 и текстом ограничения, а транзакция запроса откатывается: движения, признак проведения и остальные изменения запроса остаются прежними.

Проверяется итог после изменения, а не его направление. Если ограничение добавлено к регистру, в котором итог уже нарушен, любое изменение движений по этому сочетанию измерений отклоняется, пока итог не станет допустимым.

Сумма дробного ресурса округляется до девяти знаков после запятой: иначе погрешность двоичного сложения давала бы итог чуть меньше нуля там, где движения в сумме дают ноль. Деньги и целые числа суммируются точно.

### Чтение итога из конфигурации

Политика, собственное действие и обработчик проведения читают итог функцией `totals` из `src/server/data/register-totals.ts`:

```ts
const rows = yield* totals(SampleRegister, { by: ['item'], where: { item: guid } });
// rows: ReadonlyArray<{ item: string; quantity: number; amount: number }>
```

| Настройка | Контракт |
|---|---|
| `by` | Измерения группировки. Пустой список даёт одну строку с итогом по всем отобранным движениям |
| `where` | Значения измерений, которым равны движения; `null` отбирает незаполненное измерение |
| `period` | `{ from, before }`: период движения не раньше `from` и раньше `before`; обе границы необязательны |

Строка результата содержит измерения из `by` и суммы всех ресурсов. Сочетание без движений в результат не попадает. Имена измерений проверяет компилятор по билдеру регистра. Чтение идёт в транзакции текущего действия и видит изменения, уже выполненные в этом запросе.

## Независимые сведения

Один файл `*.information-register.ts` экспортирует билдер регистра. Например, пробный регистр описан так:

```ts
import { informationRegister } from '../../server/metadata/index.js';
import { Sample } from '../catalogs/sample.catalog.js';

export const SampleInformation = informationRegister('sample')
    .title('Пробный регистр сведений')
    .dimension('source', (field) => field.string().title('Источник').maximumLength(100))
    .dimension('externalObject', (field) => field.string().title('Внешний объект').maximumLength(100))
    .resource('description', (field) => field.string().title('Описание').maximumLength(500))
    .resource('item', (field) => field.reference(() => Sample).title('Элемент справочника'));
```

### Ключ и значения

Обязательность измерений добавляет сам билдер, в том числе в выведенный тип записи. `commit()` требует хотя бы одно измерение и один ресурс. Порядок ключа совпадает с порядком объявления измерений.

### Хранение и изменение

При синхронизации создаётся таблица `informationRegister_<имя>` с составным первичным ключом по измерениям и ограничением `NOT NULL` для каждого измерения. База не допускает двух строк с одним ключом; запись при конфликте ключа заменяет только ресурсы. Индексы измерений позволяют искать сведения по части ключа. Политики `.policy(...)` проверяют сохранение и физическое удаление; форм, табличных частей и собственных действий у этого вида объекта нет.

## Общие табличные части и просмотр строк

`tablePart((part) => part.field(...))` создаёт общее объявление колонок. `.include(ОбщиеКолонки)` переносит их в часть объекта или входных данных действия; после него можно добавить свои колонки. Билдер остаётся неизменяемым, `RecordOf` сохраняет типы общих колонок, обязательность и дополнительные колонки конкретного объекта. Повтор имён отклоняется при сборке.

В конфигурации магазина `src/configuration/goods.ts` объявляет общие колонки товаров продажи, рассрочки, отвеса и возврата: название, код, комментарий, «Проведено в 1С», стоимость, скидку и итог. Код является необязательной строкой до 50 символов, комментарий до 500 символов, отметка логическим значением. Код и название не ссылаются на номенклатуру. Состав колонок общий, но копирование значений между документами задаётся явно по [правилам учёта](accounting-rules.md#общие-правила).

`.listTableParts(['lines'])` задаёт части для раскрытия строки стандартного списка. Они показываются только для чтения и загружаются обычным `get` при раскрытии, а не включаются в `list`. В колонке-ссылке части `.expandTablePart('lines')` разрешает просмотр указанной части целевой записи; сборка проверяет её существование.

Собственное действие объявляет строки через `.input((input) => input.tablePart('lines', ...))`. Обработчик получает типизированный массив, проверенный вместе с остальными входными данными. Окно действия использует ту же таблицу, правила ввода и обход Enter, что форма записи. Экран может передать массив сразу через SDK без открытия окна.

## Вычисляемые поля

Числовое поле шапки или строки справочника и документа объявляет `.computed(выражение)`. Фабрика `formula` задаёт константу (`value`), поле текущей строки или шапки (`field`), сумму колонки части (`sum`), арифметику (`add`, `subtract`, `multiply`, `divide`) и округление до целого (`round`). Деньги считаются в копейках: сумма после скидки округляется после умножения исходной суммы на долю после скидки.

Сумма принимает условие отбора строк: `formula.sum('goods', 'total', { field: 'state', equals: 'В отвесе' })` складывает только строки, у которых колонка `state` равна указанному значению. `formula.count('goods', условие)` возвращает число строк, с условием или без него. Колонка условия может быть любого вида, в том числе строкой: числом становится только результат. Так шапка хранит остаток и число строк в одном из состояний без служебных колонок в строке.

```ts
.field('netAmount', (field) => field.money().required().computed(
    formula.round(formula.multiply(formula.field('amount'),
        formula.subtract(formula.value(1), formula.divide(formula.field('discount'), formula.value(100)))))))
```

Сервер перед проверкой и записью вычисляет сначала поля строк, затем поля шапки. Переданное клиентом вычисляемое значение заменяется, даже если оно отсутствует или имеет неверный тип. Формулы исполняются в порядке зависимостей. Пустое числовое значение считается нулём; деление на ноль и бесконечный результат возвращают ошибку ввода. Ссылки на отсутствующие или нечисловые поля, на отсутствующую колонку условия и циклы формул останавливают сборку метаданных. Результат хранится обычной колонкой, участвует в поиске, сортировке и отборе. Изменение формулы не пересчитывает прежние записи: новый результат появляется при следующей записи.

В форме поле показывается только для чтения и пропускается при обходе Enter. Тот же язык выражений пересчитывает несохранённые значения, включая изменения строк через SDK; окончательный результат определяет сервер. Формулы доступны и во входных данных собственного действия.

## Числовые подсказки

`.suggestions(Справочник, 'поле')` у числа или денег задаёт источник подсказок. Источник должен быть справочником с числовым полем того же вида; вычисляемый получатель недопустим. Выбор показывает представление записи и число, а в поле подставляет только число без ссылки на источник. Его можно изменить или ввести напрямую. Правило работает в шапке и строке. Незаполненные значения и записи с пометкой удаления не предлагаются; чтение требует доступа к справочнику.

## Представление из частей

Представление задаёт текст записи в ссылках и списках. Справочник может делегировать его обязательному полю-ссылке с заданной целью: `.presentation('person')`. Тогда сотрудник показывается ФИО физического лица, хранящимся в одном месте. Правила отображения ссылки приведены в [разделе интерфейса](interface.md#ссылки).

Справочник и документ могут объявить `.presentation([...])`: `{ text }` добавляет текст, `{ field }` показывает поле, `{ field, format: 'date' }` показывает дату без времени, `dateTime` включает время. Формат `number` показывает число; у номера документа убирает ведущие нули, не меняя хранимый номер. `{ tablePart, field, separator }` перечисляет значения колонки в порядке строк, разделитель по умолчанию равен `, `. Например:

```ts
.presentation([{ text: '№ ' }, { field: 'number', format: 'number' }, { text: ' от ' },
    { field: 'date', format: 'date' }, { text: ', ' }, { tablePart: 'lines', field: 'item' }])
```

Ссылка в части заменяется представлением целевой записи. Сервер строит текст при чтении и передаёт служебным полем `$presentation`; отдельной колонки хранения нет. Переименование цели меняет текст при следующем чтении. Используемые части и ссылки читаются пакетами: число запросов зависит от состава описания и размера порции, а не от каждой строки списка. Циклы представлений с заданными целями отклоняются при сборке, повторные полные ссылки прерывает кеш запроса.

## Проверка повторов имён в типах

Методы билдера отклоняют повтор литерального имени при проверке типов. Для полей объекта проверяются также совпадения со стандартными полями его вида. Измерения и ресурсы регистра используют общий набор имён. Поля табличной части и входных данных действия проверяются внутри своей части или действия, поэтому одинаковое имя в разных частях допустимо. Отдельно проверяются повторы имён самих табличных частей и собственных действий.

Ограничение сохраняет тип имени и добавляет в ошибку текст причины, например `имя поля повторяется` или `имя поля совпадает со стандартным полем`, вместе с конфликтующим именем. Оно не меняет состояние билдера и поведение при выполнении.

Имя типа `string` не раскрывает конкретное значение, поэтому проходит проверку типов. После такого объявления накопленный набор ключей тоже может расшириться до `string`, и проверка повторов этого набора остаётся за `commit()`. Проверка стандартных полей выполняется отдельно и продолжает отклонять явно указанные стандартные имена. Все проверки сборки описания сохраняются, включая проверку имён, полученных во время выполнения.

## Проверки при сборке

`commit()` сообщает обо всех проблемах описания сразу:

- имена объектов, полей, табличных частей и действий записаны в lowerCamelCase латиницей без `_`, не длиннее 60 символов и не совпадают с ключевыми словами SQLite; эти имена используются для таблиц и колонок;
- имена полей не повторяются и не совпадают со стандартными полями; имя табличной части не совпадает с именем поля;
- ссылка указывает на справочник или документ, который есть в конфигурации;
- границы и длины согласованы: минимум не больше максимума, у денег границы целые;
- у составного поля не меньше двух вариантов; вариант является простым видом поля или ссылкой с заданной целью, простой вид и цель не повторяются, подпись и обязательность у варианта не заданы; способ ввода задан только составному полю и только как `solid`;
- ресурс регистра оборотов является числом или суммой;
- начальное значение задано строковому невычисляемому полю и входит в его перечень значений, если перечень есть;
- имя собственного действия не совпадает со стандартным, у действия задан обработчик;
- обработчик проведения задан только у документа;
- ограничение итога задано только у регистра оборотов, называет существующие измерения без повторов и существующий ресурс, имеет конечное наименьшее значение; имена ограничений не повторяются;
- представление по ссылке задано только у справочника и называет существующее обязательное поле-ссылку с заданной целью; части представления называют существующие поля и колонки, формат даты применяется только к дате или дате и времени;
- форма ссылается на существующие поля и табличные части; элемент входит не больше чем в одну группу, не бывает одновременно скрыт и выведен в группу; группа не пуста; `guid` и `deletedAt` не выводятся в группы; обязательное поле, которое заполняет пользователь, не скрыто; режим создания записи задан не больше одного раза;
- собственный элемент формы объявлен в файле `*.form-element.ts`; подключения объявлены через `defineFormComponent`: замена называет существующее нескрытое поле ввода или табличную часть, вставка называет существующую группу и место в ней; одному месту назначена одна замена;
- стандартные поля добавлены, то есть вызван `withStandardFields()`.

`commitConfiguration` дополнительно проверяет, что имена объектов одного вида не повторяются и в представлениях нет циклов ссылок с заданными целями.

## Проверка входных данных

По описанию строится Effect Schema (`src/server/metadata/schema.ts`):

- `inputSchema(description)` описывает входные данные записи объекта: поля, которые заполняет пользователь, и табличные части. Поля, которые заполняет платформа (`guid`, `deletedAt`, `number`, `posted`, `recorder`, `lineNumber`), в схему не входят;
- `actionInputSchema(description, action)`: входные данные собственного действия;
- `fieldsSchema(fields)` и `fieldSchema(field)`: схема набора полей и одного поля.

Обязательное поле должно быть передано, а обязательная строка не может быть пустой. Необязательное поле можно пропустить или передать `null`. Сообщения об ошибках пишутся на русском языке.

## Страницы конфигурации

Интерфейс объекта строится по его описанию: список и форма. Экран, который к ним не сводится, например рабочее место, конфигурация объявляет страницей. Сервер получает имя и заголовок для меню и прав, клиент получает компонент при сборке. Компонент не передаётся через `/api/metadata`.

### Как добавить страницу

1. Создайте объявление `*.page.ts` и компонент `*.page-component.tsx` с общим началом имени внутри `src/configuration`.
2. В объявлении экспортируйте один билдер `page(...)` с уникальным именем и заголовком, компонент экспортируйте по умолчанию.
3. Указывайте объекты через `Objects.<вид>.<имя>`, данные читайте и изменяйте хуками web SDK. Настройте право страницы по [правилам доступа](authorization.md).
4. Проверьте типы и импорты командой `npm run typecheck`, запустите приложение в режиме проверки и откройте `/page/<имя>` под пользователем с нужным правом.

Минимальная пара файлов показывает список непроведённых пробных документов:

```ts
// src/configuration/pages/sample-workplace.page.ts: объявление
import { page } from '../../server/ui/pages.js';

export const SampleWorkplace = page('sampleWorkplace').title('Пробное рабочее место');
```

```tsx
// src/configuration/pages/sample-workplace.page-component.tsx: компонент, экспорт по умолчанию
import { Page, RecordTable, useRecordList } from '../../web/sdk';
import { Objects } from '../objects.generated';

export default function SampleWorkplacePage() {
    const documents = Objects.document.sample;
    const list = useRecordList(documents, { permanentFilter: [{ field: 'posted', operator: 'equals', value: false }] });
    return (
        <Page title="Пробное рабочее место">
            <RecordTable object={documents} list={list} columns={['number', 'date', 'item']} />
        </Page>
    );
}
```

### Контракт и граница импортов

- Объявление отделено от компонента. Сервер собирает `src/configuration` без React и DOM, а имя и заголовок страницы нужны ему для меню и прав. Файлы `*.tsx` каталога конфигурации исключены из серверной сборки и проверяются настройками клиента.
- Имя страницы подчиняется правилам имён объектов и не повторяется. Оно входит в адрес `/page/<имя>` и в ключ права.
- Генератор находит страницы по именам файлов и сам проверяет парность: объявление без компонента и компонент без объявления останавливают генерацию с названием файла. В режиме слежения нарушение только выводится в журнал, а реестры остаются прежними: файлы страницы создаются по одному. Экспорт объявления (ровно один билдер страницы) и имя страницы сервер проверяет при запуске и останавливается с `MetadataError`.
- Страница не импортирует значения из файлов объектов. Файл объекта тянет за собой билдеры, Effect, обработчики действий и политики с чтением базы: такой импорт включил бы серверный код в сборку клиента. Объект страница указывает ссылкой `Objects.<вид>.<имя>` из `objects.generated.ts`. Тип ссылки выведен из билдера импортом только типа, а вид и имя во время работы берутся из пути обращения, который компилятор сверяет с билдерами. Поэтому генератору по-прежнему не нужно разбирать исходники, чтобы узнать имена объектов.
- Из клиента страница импортирует только web SDK. Границу проверяет скрипт `scripts/configuration-imports-check.ts`, который `npm run typecheck` запускает перед проверкой типов: импорт внутреннего модуля `src/web`, импорт значения из серверного кода или файла объекта останавливают проверку с названием файла и строки. Компилятор запрещать импорты по каталогам не умеет, поэтому проверка вынесена в скрипт.
- Сервер сообщает клиенту только имена и заголовки доступных страниц.

Полный образец в `src/configuration/pages/sample-workplace.page-component.tsx` показывает непроведённые пробные документы и кнопку «Провести» для выбранной строки.

## Элементы формы

Стандартная форма выводит поля и табличные части из описания объекта. Блок с собственной логикой, например итог по табличной части или поле ввода с кнопкой, конфигурация объявляет элементом формы. У элемента есть объявление для сервера и компонент для клиента, как у страницы.

### Как добавить элемент

1. Создайте пару `*.form-element.ts` и `*.form-element-component.tsx` с общим началом имени внутри `src/configuration`.
2. В объявлении экспортируйте один результат `defineFormComponent(...)` с уникальным именем и местом подключения. React-компонент экспортируйте по умолчанию из соседнего файла.
3. Для замены ввода укажите `override` со ссылкой на объект и именем `field` либо `tablePart`. Для дополнительного блока укажите `insert` со ссылкой на объект, заголовком группы `group` и необязательным `after`.
4. Получайте данные и общие механизмы формы через SDK. Проверьте типы и импорты командой `npm run typecheck`, затем работу компонента на форме.

Например, блок итога объявляет место рядом со своим компонентом:

```ts
import { defineFormComponent } from '../../server/metadata/form-elements.js';
import { Objects } from '../objects.generated.js';

export const SampleTotal = defineFormComponent({
    name: 'sampleTotal',
    insert: { object: Objects.document.sample, group: 'Строки и итог', after: 'lines' },
});
```

Замена таблицы объявляется таким же способом:

```ts
export const SamplePayments = defineFormComponent({
    name: 'samplePayments',
    override: { object: Objects.document.sample, tablePart: 'payments' },
});
```

### Контракт элемента

| Настройка | Назначение и ограничения |
|---|---|
| `name` | Уникальное имя по правилам имён объектов; по нему клиент находит компонент |
| `override.object` | Типизированная ссылка `Objects` на справочник или документ |
| `override.field` или `override.tablePart` | Ровно одно существующее место ввода; скрытое место и поле, заполняемое платформой, недопустимы |
| `insert.object`, `insert.group` | Объект и существующая группа с единственным объявлением этого заголовка |
| `insert.after` | Поле или часть в этой группе; без настройки блок вставляется в начало |
| `attachments` | Массив подключений вместо одиночного `override` или `insert`; типы каждого места проверяются отдельно |

Один компонент может объявить несколько мест подключения. Вставки в одно место идут в порядке файлов реестра. Блок занимает всю ширину группы и не входит в обход полей. Замена сохраняет место, подпись и остановку обхода исходного поля или части. Две замены одного места отклоняются при запуске. Настройки компонентов в `.form(...)` объекта больше не поддерживаются: там остаются поля, части, группы, подписи, скрытие и режим открытия.

Объявление и React-компонент разделены, потому что сервер проверяет подключения без загрузки React, DOM и web SDK. Объявление импортирует `defineFormComponent` и нейтральные ссылки `Objects`; файлы объектов доступны ему только как типы. Генератор перед сборкой находит пары, а в режиме разработки следит за добавлением и удалением файлов. При запуске сервер применяет подключения к копии раскладки, проверяет результат и отдаёт готовую форму клиенту.

Блок вставки получает данные хуками `useFormData` и `useFormValue`. Замена поля получает `InputProperties`, замена части получает `TablePartInputProperties`: описание, строки, обработчик изменения, недоступность, ссылку для фокуса и возврат обхода назад. Строки остаются в форме при переключении представления; полную таблицу компонент выводит через `TablePart`. Проверка колонок работает и без смонтированных ячеек. Хуки и компоненты перечислены в разделе [«Web SDK»](web-sdk.md#состав).

Права у компонента нет: он виден там, где видна форма, а чтение данных и выполнение действий проверяются по правам объектов. Компонент не обращается к форме Ant Design и API напрямую. Реестр компонентов подключает стандартная форма, а не SDK: импорт реестра из SDK создал бы цикл зависимостей.

### Ограничения интерфейса

Элемент может управлять состоянием формы: сделать недоступной для изменения всю форму, отдельное поле или табличную часть и скрыть действие. Для этого он объявляет ограничения хуком [`useFormRestrictions`](web-sdk/hooks.md#ограничения-формы) и может ничего не выводить. Условие вычисляет компонент, а не настройка в описании объекта: оно может зависеть от состояния записи, значений формы и данных других объектов, и описание объекта не разрастается настройками на каждый случай.

Ограничения управляют только интерфейсом. Права и единый эндпоинт они не меняют: действие, скрытое на форме, по-прежнему выполняется через `/api/perform`, а запрет изменения записи задаёт политика записи объекта (раздел [«Политики записи»](write-policies.md)).

Условие в следующем примере зависит от сохранённого комментария. Если взять вводимое значение, форма заблокируется после ввода первой буквы и не позволит сохранить комментарий. Это фрагмент компонента; импорты SDK и `Objects` опущены.

```tsx
// Элемент, который управляет состоянием формы и ничего не выводит
export default function SampleLock() {
    const form = useFormData(Objects.document.sample);
    const locked = (form.saved?.comment ?? null) !== null;
    useFormRestrictions(Objects.document.sample, locked ? { readOnly: true, hiddenActions: ['post'] } : {});
    return null;
}
```

Пробные элементы стоят на форме пробного документа: блок «Итого до скидки» под табличной частью «Строки» показывает сумму колонки «Сумма», а поле «Комментарий» заменено собственным полем ввода с кнопкой, которая подставляет текст «Проверено». Компонент оплаты переключает одно поле суммы и таблицу; итог оплаты пересчитывается из строк. Элемент блокировки управляет состоянием формы: документ с записанным комментарием нельзя изменить и провести с формы, о чём элемент сообщает строкой под полями.

## Обнаружение объектов конфигурации

Во время работы исполняемого файла исходники `.ts` недоступны, поэтому объекты, страницы и элементы формы обнаруживаются на этапе сборки. Скрипт `scripts/metadata-generate.ts` (`npm run metadata:generate`) находит файлы объектов `src/configuration/**/*.{catalog,document,register,information-register}.ts`, файлы страниц (подраздел [«Страницы конфигурации»](#страницы-конфигурации)) и файлы элементов формы (подраздел [«Элементы формы»](#элементы-формы)) и генерирует в `src/configuration` четыре файла:

| Файл | Кому нужен | Содержимое |
|---|---|---|
| `configuration.generated.ts` | серверу | Импорт каждого файла объекта и каждого объявления страницы и элемента формы целиком, списки `configurationModules`, `pageModules` и `formElementModules` с путём файла и его экспортом, объект прав `Rights`, построенный из модулей объектов и страниц (раздел [«Права (RBAC)»](authorization.md)) |
| `objects.generated.ts` | клиенту | Ссылки на объекты `Objects` для страниц и элементов формы; файлы объектов импортируются только как типы |
| `pages.generated.ts` | клиенту | Реестр страниц: объявление и компонент каждой страницы |
| `form-elements.generated.ts` | клиенту | Реестр элементов формы: объявление и компонент каждого элемента |

- Сгенерированные файлы исключены из git и помечены комментарием, что вручную их не редактируют. Команды `dev`, `build` и `typecheck` сначала запускают генерацию, поэтому в новом клоне или worktree файлы появляются сами.
- В `npm run dev` скрипт работает с флагом `--watch`: при появлении, удалении или переименовании файла объекта, страницы или элемента формы реестры обновляются, `tsc --watch` пересобирает сервер, `node --watch` перезапускает его, а Vite обновляет клиент. Файл перезаписывается, только если его текст изменился.
- Ссылки на объекты и реестры компонентов лежат в разных файлах. Реестр импортирует компоненты страниц или элементов, а компоненты импортируют ссылки на объекты: в одном файле получился бы циклический импорт, и при загрузке компонента ссылки могли бы быть ещё не определены.

### Сборка описаний при запуске

Платформа читает только сгенерированный реестр. Сервис метаданных извлекает билдер из каждого модуля объекта: экспорт должен содержать ровно один билдер, а его вид должен совпадать с суффиксом файла. Отдельно собираются объявления компонентов формы. Их подключения применяются перед проверкой описаний объектов; исходные билдеры не изменяются.

После проверки модулей сервис добавляет стандартные поля через `withStandardFields()` и вызывает `commitConfiguration`. Описания собираются один раз, до приёма запросов, и остаются неизменными до перезапуска. `commit(configuration)` собирает один объект в окружении билдеров конфигурации; `commitConfiguration(builders)` собирает и проверяет все объекты вместе. Обе операции возвращают Effect, готовый результат содержит неизменяемые `ObjectDescription`.

Нарушение соглашения о файлах или ошибка описания останавливает запуск с `MetadataError`: сообщение указывает файл или объект, место и суть проблемы. Проблемы файлов сообщаются до проверки описаний, поскольку без корректного экспорта проверка ссылок породила бы вторичные ошибки. Доступ к готовым описаниям даёт `MetadataService`: `objects` возвращает все объекты, `find(kind, name)` возвращает один объект либо `undefined`.

## Пробные объекты

Пробные объекты служат образцами объявления и ручной проверки возможностей платформы. Они находятся рядом с прикладными объектами конфигурации и не описывают бизнес-правила магазина.

| Образец | Что демонстрирует |
|---|---|
| `catalogs/sample.catalog.ts` | Числовое поле для подсказок, цель ссылки документа |
| `catalogs/sample-delegate.catalog.ts` | Представление справочника по ссылке |
| `documents/sample.document.ts` | Ссылки шапки и строк, вычисления, составное представление, раскрытие частей, собственное действие и проведение в регистр; строка с отрицательным количеством уменьшает итог регистра. Составные поля шапки: «Куда оплачено» (строка либо ссылка) и «Отметка» (строка, число либо ссылка) вводятся текстом, «Срок» (дата либо строка) требует выбора типа |
| `documents/sample-selection.document.ts` | Общие колонки с дополнительным примечанием, выбор строк документа-источника через SDK |
| `registers/sample.register.ts` | Движения, записанные пробным документом, ограничение «количество по элементу справочника не меньше нуля» и составные измерения, по которым итог группируется с учётом типа значения |
| `information-registers/sample.information-register.ts` | Ключ из двух измерений и ресурсы разных видов |
| `information-registers/sample-composite.information-register.ts` | Составное поле в ключе сведений и в ресурсе; у ресурса текстовый ввод отключён настройкой `inputMode('solid')` |
| `pages/sample-workplace.*` | Собственная страница со списком и действием проведения |
| `form-elements/sample-*` | Итог текущих строк, собственное поле ввода, ограничения формы и выбор строк |

Пути указаны относительно `src/configuration`. Общие колонки объявлены в `sample-lines.ts`: в строках вычисляется сумма после скидки, в шапке документа их итог. Выбор строк использует `RecordTablePart` и SDK формы; просмотр по ссылке раскрывает часть целевого документа. Код образцов можно читать вместе с разделом [«Web SDK»](web-sdk.md).
