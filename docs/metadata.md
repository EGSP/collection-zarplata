# Метаданные

Раздел для разработчика конфигурации: виды объектов, объявление полей и поведения, собственные экраны и проверка описаний. Метаданные задают единый контракт для хранения, проверки данных и стандартного интерфейса. Бизнес-правила магазина лежат в [правилах учёта](accounting-rules.md), работа с записями через API описана в [API данных](single-endpoint.md).

## Виды объектов

| Вид | Назначение | Функция описания |
|---|---|---|
| Справочник | Условно-постоянные данные: сотрудники, номенклатура, точки | `catalog(name)` |
| Документ | Событие с датой, номером и статусом «проведён / не проведён» | `document(name)` |
| Регистр | Строки, которые документ записывает при проведении; по ним считаются обороты | `register(name)` |
| Регистр сведений | Текущие независимые значения по уникальному набору измерений | `informationRegister(name)` |

Строка регистра (движение) всегда ссылается на документ-регистратор. Один документ может записать несколько строк, например по одной на каждого сотрудника смены. При повторном проведении старые строки документа удаляются и записываются заново, поэтому проведение идемпотентно.

Регистры только оборотов: ресурсы строк суммируются, регистров остатков с видом движения «приход / расход» нет. Остаток равен сумме движений со знаком: один документ записывает положительное количество, другой отрицательное, а [итог регистра](#итоги-и-ограничения-регистра) по измерениям даёт текущее значение.

У регистра сведений (`informationRegister`) нет документа-регистратора, периода, номера строки, `guid` и пометки удаления. Все измерения обязательны и вместе определяют запись; ресурсы допускают любые прикладные виды полей, включая строки и ссылки. Периодичности и истории значений нет: историю действий хранит общий журнал.

## Стандартные поля

Стандартные поля добавляет платформа, повторно их объявлять не нужно. Состав задан в `src/server/metadata/standard-fields.ts`.

| Вид | Стандартные поля | Идентификатор записи |
|---|---|---|
| Справочник | `guid`, `deletedAt`, `name` | `guid` |
| Документ | `guid`, `deletedAt`, `number`, `date`, `posted` | `guid` |
| Регистр | `recorder`, `period`, `lineNumber` | Регистратор и номер строки |
| Регистр сведений | Нет | Набор измерений |

`recorder` хранит документ-регистратор (`{ document, guid }`), `period` дату и время движения, `lineNumber` нумерует строки одного регистратора. Дата документа хранится с временем. `guid` генерируется как UUIDv7, поэтому идентификаторы упорядочены по времени.

Стандартного поля `code` у справочников нет: запись определяет GUID, пользователь видит наименование. Собственное поле `code` конфигурация объявить может. Миграция `20261007_remove_catalog_code` удалила прежнюю стандартную колонку и её индексы, сохранив GUID, остальные поля, внешние связи и самостоятельно объявленный `code`.

## Пометка удаления

Справочники и документы физически не удаляются: если `deletedAt` заполнено, объект помечен на удаление, а кто поставил пометку, фиксирует журнал. Сведения удаляются физически по измерениям, движения удаляются при отмене проведения.

## Описание объекта

### Как добавить объект

1. Создайте файл внутри `src/configuration` с суффиксом вида объекта: `*.catalog.ts`, `*.document.ts`, `*.register.ts` или `*.information-register.ts`.
2. Экспортируйте ровно один билдер этого вида. Другие значения экспортировать можно; `commit()` в файле конфигурации не вызывается.
3. Задайте заголовок, поля и поведение цепочкой вызовов. Каждый вызов возвращает новый неизменяемый билдер.
4. Запустите `npm run typecheck`, затем приложение в режиме проверки по [инструкции сборки и запуска](build-and-launch.md). Генерация подключит файл сама, а сервер при запуске проверит описание. Ошибка останавливает запуск с `MetadataError` и называет объект и место проблемы.

Условный пример сотрудников и смен показывает сочетание возможностей билдера. Это иллюстрация API, а не готовый файл: цели ссылок и политики в конфигурации должны существовать.

```ts
import { Effect } from 'effect';
import { catalog, document, movements, register } from '../../server/metadata/index.js';
import { Positions } from './positions.catalog.js';
import { closedPeriodByDocumentDate } from '../policies/closed-period.js';
import { preventPostedDocumentDeletion } from '../policies/posted-document-deletion.js';

export const Employees = catalog('employees')
    .title('Сотрудники')
    .field('position', (field) => field.reference(Positions).title('Должность'))
    .field('hiredAt', (field) => field.date().title('Дата приёма').required())
    .field('rate', (field) => field.money().title('Ставка').minimum(0))
    .tablePart('contacts', (part) => part
        .title('Контакты')
        .field('kind', (field) => field.string().title('Вид').required().maximumLength(20))
        .field('value', (field) => field.string().title('Значение')))
    .action('dismiss', (action) => action
        .title('Уволить')
        .input((input) => input.field('dismissedAt', (field) => field.date().required()))
        .handle((input) => Effect.log(input.dismissedAt)))
    .form((form) => form
        .group('Основное', ['name', 'position'])
        .hide('rate'));

export const Accruals = register('accruals')
    .title('Начисления')
    .dimension('employee', (field) => field.reference(Employees))
    .resource('amount', (field) => field.money().required());

export const Shift = document('shift')
    .title('Смена')
    .tablePart('staff', (part) => part
        .field('employee', (field) => field.reference(Employees).required())
        .field('amount', (field) => field.money().required()))
    .policy(closedPeriodByDocumentDate())
    .policy(preventPostedDocumentDeletion())
    .posting((record) => Effect.succeed([
        movements(Accruals, record.staff.map((line) => ({ employee: line.employee, amount: line.amount }))),
    ]));
```

### Контракт объявления

- Ссылки на другие объекты передаются самими билдерами (`field.reference(Positions)`), а не строками. Если файлы импортируют друг друга по кругу, цель передаётся функцией: `field.reference(() => Employees)`. Целью служит справочник или документ.
- Каждый вызов `.field(...)`, `.tablePart(...)`, `.dimension(...)` и `.resource(...)` расширяет тип билдера, поэтому TypeScript выводит тип записи из цепочки без генерации типов: `RecordOf<typeof Employees>`. Стандартные поля входят в тип по виду объекта. Обязательное поле имеет тип значения, необязательное допускает значение или `null`, табличная часть содержит массив строк.
- Обработчик проведения `.posting(...)` есть только у документа. Он получает сохранённую запись с табличными частями и возвращает Effect со строками регистров. Строки одного регистра собирает `movements(Регистр, строки)`: тип строки выводится из билдера регистра, поэтому TypeScript отклоняет неизвестные измерения и ресурсы. `period` можно не указывать, платформа подставит дату документа; регистратор и номер строки она заполняет сама. Обработчику и собственному действию доступны из окружения Effect `ActionContext`, `ActionDispatcher`, `Database` для чтения, `Metadata` с описаниями объектов и [проверка прав](authorization.md#как-проверить-право-в-коде-конфигурации). Прямой вызов `Database.run` для изменений запрещён: вложенную запись выполняет `ActionDispatcher`.
- Ограничение итога `.constraint(...)` есть только у регистра оборотов и объявляется после измерений и ресурсов, которые называет ([«Итоги и ограничения регистра»](#итоги-и-ограничения-регистра)).
- Собственное действие выполняет диспетчер после проверки прав и входных данных. Имя действия входит в тип билдера, поэтому право на него доступно как `Rights.catalog.employees.actions.dismiss`. Переопределение `.form(...)` применяется при построении описаний форм ([«Интерфейс (SDUI)»](interface.md)). `.policy(...)` привязывает к объекту именованную проверку, которая выполняется до изменения данных; контракт описан в [политиках записи](write-policies.md).

## Поля

### Ссылочные значения

Полная ссылка содержит `kind` (`catalog` или `document`), `name` объекта конфигурации и `guid` записи; `objectReference` собирает её из цели и GUID. Её принимает `field.reference()`. Поле с заданной целью `field.reference(Объект)` хранит один GUID, потому что цель уже есть в метаданных. Оба поля показывают представление записи и открывают карточку по общему правилу адресов; поле ввода позволяет выбрать запись и открыть её кнопкой. Без права чтения целевого объекта представление не запрашивается, вместо него показывается «Нет доступа».

### Виды и свойства полей

| Поле | Значение в записи | Свойства |
|---|---|---|
| `field.string()` | строка | `minimumLength`, `maximumLength` |
| `field.number()` | число | `minimum`, `maximum`, `integer` |
| `field.money()` | целое число копеек | `minimum`, `maximum` в копейках |
| `field.date()` | строка `YYYY-MM-DD` | |
| `field.dateTime()` | строка ISO 8601 с часовым поясом | |
| `field.boolean()` | логическое значение | |
| `field.reference(Объект)` | `guid` объекта; цель задана в метаданных | |
| `field.reference()` | `{ kind, name, guid }`, ссылка на любой справочник или документ | |
| `field.composite([...])` | значение одного из вариантов вместе с его типом | задаются вариантам, см. [«Составное поле»](#составное-поле) |

У всех полей есть `title` и `required`. Строка может ограничить ввод перечнем значений (`choices`) и задать начальное значение (`initial`): им форма заполняет поле в новой записи и в новой строке табличной части. Начальное значение действует только на форму, запись через единый эндпоинт без значения поле не заполняет. Табличные части и входные данные действий состоят из тех же полей.

У регистра движений измерения (`.dimension`) задают разрезы отбора и группировки, ресурсы (`.resource`) содержат числа или деньги для суммирования; нужен хотя бы один ресурс. У регистра сведений измерения образуют ключ, ресурсы допускают любые виды полей ([«Независимые сведения»](#независимые-сведения)).

### Составное поле

Составное поле хранит значение одного из объявленных вариантов. Оно нужно, когда пользователь либо выбирает запись, либо вписывает значение вручную: например, «Куда оплачено» хранит ссылку на приёмника оплаты или произвольный текст.

```ts
.field('receiver', (field) => field.composite([
    field.string().maximumLength(200),
    field.reference(PaymentReceivers),
]).title('Куда оплачено'))
```

Значение хранит тип варианта рядом с данными, поэтому строка «100» и число 100 различаются. Незаполненное поле равно `null`.

| Вариант | Значение в записи и в API |
|---|---|
| `field.string()`, `field.date()`, `field.dateTime()` | `{ type: 'string', value: 'Сейф' }`; `type` равен виду варианта |
| `field.number()`, `field.money()` | `{ type: 'number', value: 100 }`; деньги в копейках |
| `field.boolean()` | `{ type: 'boolean', value: true }` |
| `field.reference(Объект)` | `{ type: 'reference', kind: 'catalog', name: 'paymentReceivers', guid }` |

Правила объявления:

- Вариантов не меньше двух. Вариантом служит простой вид поля или ссылка с заданной целью; полная ссылка `field.reference()` и другое составное поле недопустимы.
- Простой вид и цель ссылки не повторяются, потому что значение называет вариант только типом и целью. Ссылки на разные объекты допустимы.
- Варианту задаются ограничения: длина и перечень значений строки, границы и целочисленность числа. Подпись и обязательность задаются самому полю. Формул, числовых подсказок, начального значения и раскрытия табличной части у варианта нет.
- `RecordOf` выводит тип поля объединением значений вариантов; код конфигурации различает их по свойству `type`.

#### Способ ввода

Платформа делит виды полей по способу ввода. Значение способа `fluent` пишется текстом: строка, число, сумма, ссылка с заданной целью, которую пользователь находит по представлению записи. Значению способа `solid` нужен собственный элемент ввода: дата, дата со временем, логическое значение. Соответствие задаёт реестр `fieldInputModes` в `src/server/metadata/composite.ts`, в конфигурации оно не настраивается.

Способ составного поля сборка описаний выводит из вариантов. Если каждый вариант `fluent`, поле тоже `fluent`: в интерфейсе одно текстовое поле с подсказками по всем вариантам. Один вариант `solid` делает `solid` всё поле: пользователь сначала выбирает тип значения. Результат лежит в описании поля свойством `inputMode`; клиент его не вычисляет.

| Варианты | Способ |
|---|---|
| Строка и ссылка | `fluent` |
| Строка, число и ссылки на два объекта | `fluent` |
| Строка с перечнем значений и ссылка | `fluent`: значения перечня предлагаются подсказками |
| Дата и строка | `solid` |
| Число и логическое значение | `solid` |

Текстовый ввод можно отключить: `field.composite([...]).inputMode('solid')`. Это нужно, когда значения вариантов легко спутать, например строку и сумму. Обратной настройки нет: дату или флажок в одной строке ввода не набрать. Поведение обоих способов описано в разделе [«Реестр виджетов»](interface.md#составное-поле).

#### Где доступно и как сравнивается

Поле доступно в шапке, табличной части, входных данных действия, измерениях регистров и ресурсах регистра сведений. Ресурсы регистра движений суммируются, поэтому остаются числами или деньгами.

Равенство, ключ сведений и группировка итогов учитывают тип, значение и цель ссылки. Сравнения «больше» и «меньше» действуют внутри одного простого типа: условие с числом отбирает только числа и не затрагивает строки и ссылки; для ссылки и логического значения они недоступны. Сортировка упорядочивает значения по имени типа (`boolean`, `date`, `dateTime`, `money`, `number`, `reference`, `string`), затем по значению внутри типа; при сортировке по возрастанию незаполненные идут первыми. Ссылки одного объекта сортируются по GUID, а не по представлению.

Хранение описано в [«Базе данных»](database.md#хранение-значений), ввод и показ в [«Реестре виджетов»](interface.md#реестр-виджетов), формат отбора в [«API данных»](single-endpoint.md#отбор-по-полю).

## Итоги и ограничения регистра

Итог регистра оборотов равен сумме ресурсов его движений по сочетанию значений измерений. Он не хранится, а считается запросом по движениям при каждом чтении. Через API его возвращает действие [`totals`](single-endpoint.md#итоги-регистра).

### Зачем нужны ограничения

Правило, которое связывает несколько документов, выражается движениями одного регистра и ограничением его итога. Продажа записывает положительное количество по товару, возврат отрицательное, а регистр требует, чтобы сумма по продаже и товару не была меньше нуля. Возврату не нужно читать таблицы продаж и других возвратов, а новый вид документа подчиняется правилу, как только пишет движения в этот регистр.

Ограничение проверяет платформа, а не [политика записи](write-policies.md): политика выполняется до изменения данных и новых движений не видит. Проверка после записи нужна и потому, что правило может нарушить отмена проведения: без движений продажи итог по ней станет отрицательным, если по ней проведены возвраты.

### Объявление ограничения

```ts
export const SampleRegister = register('sample')
    .title('Пробный регистр')
    .dimension('item', (field) => field.reference(Sample).title('Элемент справочника').required())
    .resource('quantity', (field) => field.number().title('Количество').required())
    .resource('amount', (field) => field.money().title('Сумма').required())
    .constraint('stock', (constraint) => constraint
        .by(['item'])
        .minimum('quantity', 0)
        .message(({ totals }) => Effect.succeed(`Количество по элементу справочника уходит в минус на ${-totals.quantity}`)));
```

| Вызов | Контракт |
|---|---|
| `.constraint(name, define)` | Добавляет ограничение. У регистра их может быть несколько; имена не повторяются |
| `.by([...])` | Измерения, по сочетанию значений которых считается итог. Без вызова проверяется итог по всему регистру |
| `.minimum(resource, value)` | Ресурс и наименьшее допустимое значение его суммы; для денег в копейках. Обязателен |
| `.message(fn)` | Текст отказа. Функция получает `{ dimensions, totals }` и возвращает `Effect` со строкой |

`dimensions` содержит значения измерений из `.by(...)` для нарушенного сочетания, `totals` суммы всех ресурсов регистра по нему после изменения движений. Функции текста доступны те же сервисы, что и политике: `Database` для чтения в текущей транзакции, `Metadata`, `ActionContext` и `ActionDispatcher`, например чтобы прочитать представление документа из измерения. Без `.message(...)` отказ называет регистр, ресурс, итог и допустимое значение.

TypeScript принимает в `.by(...)` только измерения, а в `.minimum(...)` только ресурсы регистра. `.by(...)` вызывается раньше `.message(...)`, чтобы тип `dimensions` совпал с выбранными измерениями. Сборка описаний повторяет проверку имён и отклоняет ограничение без `.minimum(...)`.

### Когда ограничение проверяется

Платформа проверяет ограничения после каждого изменения движений документа: при проведении, при повторном проведении после записи проведённого документа, при отмене проведения, при пометке проведённого документа на удаление и при [перепроведении всех документов](single-endpoint.md#перепроведение-документов). Политики документа и права на отдельные действия на проверку не влияют.

Итог пересчитывается только по сочетаниям измерений из удалённых и записанных движений документа. Если сумма ресурса меньше наименьшего значения, действие завершается отказом с HTTP 409 и текстом ограничения, а транзакция запроса откатывается: движения, признак проведения и остальные изменения остаются прежними.

Проверяется итог после изменения, а не его направление. Если ограничение добавлено к регистру с уже нарушенным итогом, любое изменение движений по этому сочетанию отклоняется, пока итог не станет допустимым.

Сумма дробного ресурса округляется до девяти знаков после запятой: иначе погрешность двоичного сложения давала бы итог чуть меньше нуля там, где движения в сумме дают ноль. Деньги и целые числа суммируются точно.

### Чтение итога из конфигурации

Политика, собственное действие и обработчик проведения читают итог функцией `totals` из `src/server/data/register-totals.ts`:

```ts
const rows = yield* totals(SampleRegister, { by: ['item'], where: { item: guid } });
// rows: ReadonlyArray<{ item: string; quantity: number; amount: number }>
```

| Настройка | Контракт |
|---|---|
| `by` | Измерения группировки. Пустой список даёт одну строку с итогом по всем отобранным движениям |
| `where` | Значения измерений, которым равны движения; `null` отбирает незаполненное измерение |
| `period` | `{ from, before }`: период движения не раньше `from` и раньше `before`; обе границы необязательны |

Строка результата содержит измерения из `by` и суммы всех ресурсов; сочетание без движений в результат не попадает. Имена измерений проверяет компилятор по билдеру регистра. Чтение идёт в транзакции текущего действия и видит изменения, уже сделанные в этом запросе.

## Независимые сведения

Файл `*.information-register.ts` экспортирует билдер регистра. Пробный регистр описан так:

```ts
import { informationRegister } from '../../server/metadata/index.js';
import { Sample } from '../catalogs/sample.catalog.js';

export const SampleInformation = informationRegister('sample')
    .title('Пробный регистр сведений')
    .dimension('source', (field) => field.string().title('Источник').maximumLength(100))
    .dimension('externalObject', (field) => field.string().title('Внешний объект').maximumLength(100))
    .resource('description', (field) => field.string().title('Описание').maximumLength(500))
    .resource('item', (field) => field.reference(() => Sample).title('Элемент справочника'));
```

### Ключ и значения

Билдер сам делает измерения обязательными, в том числе в выведенном типе записи. `commit()` требует хотя бы одно измерение и один ресурс. Порядок ключа совпадает с порядком объявления измерений.

### Хранение и изменение

При синхронизации создаётся таблица `informationRegister_<имя>` с составным первичным ключом по измерениям и `NOT NULL` у каждого измерения. Две строки с одним ключом база не допускает, а запись при конфликте ключа заменяет только ресурсы. Индексы измерений ускоряют поиск по части ключа. Политики `.policy(...)` проверяют сохранение и физическое удаление; форм, табличных частей и собственных действий у этого вида нет.

## Общие табличные части и просмотр строк

`tablePart((part) => part.field(...))` создаёт общее объявление колонок. `.include(ОбщиеКолонки)` переносит их в часть объекта или входных данных действия, после него можно добавить свои колонки. `RecordOf` сохраняет типы и обязательность общих и дополнительных колонок. Повтор имён отклоняется при сборке.

В конфигурации магазина `src/configuration/goods.ts` объявляет общие колонки товаров продажи, отвеса и возврата: название, код, комментарий, «Проведено в 1С», стоимость, скидку и итог. Код (необязательная строка до 50 символов) и название не ссылаются на номенклатуру. Состав колонок общий, а копирование значений между документами задают [правила учёта](accounting-rules.md#общие-правила).

`.listTableParts(['lines'])` задаёт части, которые раскрываются под строкой стандартного списка. Они показываются только для чтения и загружаются обычным `get` при раскрытии, а не входят в `list`. В колонке-ссылке части `.expandTablePart('lines')` разрешает просмотр указанной части целевой записи; сборка проверяет, что она существует.

Собственное действие объявляет строки так: `.input((input) => input.tablePart('lines', ...))`. Обработчик получает типизированный массив, проверенный вместе с остальными входными данными. Окно действия использует ту же таблицу, правила ввода и обход Enter, что форма записи; экран может передать массив через SDK, не открывая окна.

## Вычисляемые поля

Числовое поле шапки или строки справочника и документа объявляет `.computed(выражение)`. Фабрика `formula` задаёт константу (`value`), поле текущей строки или шапки (`field`), сумму колонки части (`sum`), число строк (`count`), арифметику (`add`, `subtract`, `multiply`, `divide`) и округление до целого (`round`). Деньги считаются в копейках: сумма после скидки округляется после умножения исходной суммы на долю после скидки.

`sum` и `count` принимают условие отбора строк: `formula.sum('goods', 'total', { field: 'state', equals: 'В отвесе' })` складывает только строки, у которых `state` равна указанному значению. Колонка условия может быть любого вида, в том числе строкой: числом становится только результат. Так шапка хранит остаток и число строк в одном состоянии без служебных колонок.

```ts
.field('netAmount', (field) => field.money().required().computed(
    formula.round(formula.multiply(formula.field('amount'),
        formula.subtract(formula.value(1), formula.divide(formula.field('discount'), formula.value(100)))))))
```

Перед проверкой и записью сервер вычисляет сначала поля строк, затем поля шапки, в порядке зависимостей. Переданное клиентом вычисляемое значение заменяется, даже если оно отсутствует или имеет неверный тип. Пустое число считается нулём; деление на ноль и бесконечный результат возвращают ошибку ввода. Ссылки на отсутствующие или нечисловые поля, на отсутствующую колонку условия и циклы формул останавливают сборку метаданных. Результат хранится обычной колонкой и участвует в поиске, сортировке и отборе. Изменение формулы не пересчитывает прежние записи: новый результат появится при следующей записи.

В форме поле только для чтения и пропускается при обходе Enter. Тот же язык выражений пересчитывает несохранённые значения, включая изменения строк через SDK, но окончательный результат определяет сервер. Формулы доступны и во входных данных собственного действия.

## Числовые подсказки

`.suggestions(Справочник, 'поле')` у числа или денег задаёт источник подсказок: справочник с числовым полем того же вида. Вычисляемое поле получателем быть не может. Подсказка показывает представление записи и число, а в поле подставляется только число без ссылки на источник; его можно изменить или ввести напрямую. Правило работает в шапке и строке. Незаполненные значения и помеченные на удаление записи не предлагаются; нужен доступ к справочнику на чтение.

## Представление из частей

Представление задаёт текст записи в ссылках и списках. Справочник может делегировать его обязательному полю-ссылке с заданной целью: `.presentation('person')`, тогда сотрудник показывается ФИО физического лица, хранящимся в одном месте. Отображение ссылки описано в [«Ссылках»](interface.md#ссылки).

Справочник и документ могут объявить `.presentation([...])` из частей: `{ text }` добавляет текст, `{ field }` показывает поле, `{ field, format: 'date' }` дату без времени, `dateTime` с временем. Формат `number` показывает число и убирает ведущие нули номера документа, не меняя хранимый номер. `{ tablePart, field, separator }` перечисляет значения колонки в порядке строк, разделитель по умолчанию `, `. Например:

```ts
.presentation([{ text: '№ ' }, { field: 'number', format: 'number' }, { text: ' от ' },
    { field: 'date', format: 'date' }, { text: ', ' }, { tablePart: 'lines', field: 'item' }])
```

Ссылка в части заменяется представлением целевой записи. Сервер строит текст при чтении и передаёт служебным полем `$presentation`; колонки хранения нет, поэтому переименование цели меняет текст при следующем чтении. Части и ссылки читаются пакетами: число запросов зависит от состава описания и размера порции, а не от числа строк списка. Циклы представлений с заданными целями отклоняются при сборке, повторные полные ссылки прерывает кеш запроса.

## Проверка повторов имён в типах

Методы билдера отклоняют повтор литерального имени уже при проверке типов: у полей объекта также совпадение со стандартным полем его вида, у измерений и ресурсов регистра общий набор имён. Поля табличной части и входных данных действия проверяются внутри своей части или действия, поэтому одинаковое имя в разных частях допустимо. Отдельно проверяются имена табличных частей и собственных действий. Ошибка называет причину и конфликтующее имя.

Имя типа `string` значения не раскрывает, поэтому проходит проверку типов, а набор накопленных ключей после него расширяется до `string`. Повторы такого набора тогда ловит `commit()`; явно указанные стандартные имена по-прежнему отклоняются.

## Проверки при сборке

`commit()` сообщает обо всех проблемах описания сразу, а не по первой. Он проверяет:

- Имена объектов, полей, табличных частей и действий: lowerCamelCase латиницей без `_`, не длиннее 60 символов, не ключевые слова SQLite (из них строятся таблицы и колонки). Имена полей не повторяются и не совпадают со стандартными, имя табличной части не совпадает с именем поля.
- Ссылка указывает на справочник или документ из конфигурации. Границы и длины согласованы: минимум не больше максимума, у денег границы целые. Ресурс регистра оборотов число или сумма.
- Составное поле соответствует [правилам объявления](#составное-поле); способ ввода задан только ему и только как `solid`.
- Начальное значение задано строковому невычисляемому полю и входит в его перечень, если перечень есть.
- Обработчик проведения задан только у документа. У собственного действия есть обработчик, а имя не совпадает со стандартным.
- Ограничение итога задано только у регистра оборотов, называет существующие измерения без повторов, существующий ресурс и конечное наименьшее значение; имена ограничений не повторяются.
- Представление по ссылке задано только у справочника и называет существующее обязательное поле-ссылку с заданной целью. Части представления называют существующие поля и колонки, формат даты применим только к дате и дате со временем.
- Форма ссылается на существующие поля и табличные части. Элемент входит не больше чем в одну группу и не бывает одновременно скрыт и выведен в группу, группа не пуста, `guid` и `deletedAt` в группы не выводятся, обязательное поле, которое заполняет пользователь, не скрыто, режим создания задан не больше одного раза.
- Подключения элементов формы и формы объектов соответствуют правилам разделов [«Элементы формы»](#элементы-формы) и [«Формы объекта»](#формы-объекта).
- Стандартные поля добавлены: вызван `withStandardFields()`.

`commitConfiguration` дополнительно проверяет, что имена объектов одного вида не повторяются и в представлениях нет циклов ссылок с заданными целями.

## Проверка входных данных

По описанию строится Effect Schema (`src/server/metadata/schema.ts`):

- `inputSchema(description)` описывает входные данные записи объекта: поля, которые заполняет пользователь, и табличные части. Поля, которые заполняет платформа (`guid`, `deletedAt`, `number`, `posted`, `recorder`, `lineNumber`), в схему не входят;
- `actionInputSchema(description, action)` описывает входные данные собственного действия;
- `fieldsSchema(fields)` и `fieldSchema(field)` описывают набор полей и одно поле.

Обязательное поле должно быть передано, обязательная строка не бывает пустой. Необязательное поле можно пропустить или передать `null`. Сообщения об ошибках на русском языке.

## Страницы конфигурации

Список и форма объекта строятся по его описанию. Экран, который к ним не сводится, например рабочее место, конфигурация объявляет страницей. Серверу нужны имя и заголовок для меню и прав, клиент получает компонент при сборке; через `/api/metadata` компонент не передаётся.

### Как добавить страницу

1. Создайте объявление `*.page.ts` и компонент `*.page-component.tsx` с общим началом имени внутри `src/configuration`.
2. В объявлении экспортируйте один билдер `page(...)` с уникальным именем и заголовком, компонент экспортируйте по умолчанию.
3. Объекты указывайте через `Objects.<вид>.<имя>`, данные читайте и меняйте хуками web SDK. Право страницы настройте по [правилам доступа](authorization.md).
4. Проверьте типы и импорты командой `npm run typecheck`, запустите приложение в режиме проверки и откройте `/page/<имя>` под пользователем с нужным правом.

Минимальная пара файлов выводит список непроведённых пробных документов:

```ts
// src/configuration/pages/sample-workplace.page.ts: объявление
import { page } from '../../server/ui/pages.js';

export const SampleWorkplace = page('sampleWorkplace').title('Пробное рабочее место');
```

```tsx
// src/configuration/pages/sample-workplace.page-component.tsx: компонент, экспорт по умолчанию
import { Page, RecordTable, useRecordList } from '../../web/sdk';
import { Objects } from '../objects.generated';

export default function SampleWorkplacePage() {
    const documents = Objects.document.sample;
    const list = useRecordList(documents, { permanentFilter: [{ field: 'posted', operator: 'equals', value: false }] });
    return (
        <Page title="Пробное рабочее место">
            <RecordTable object={documents} list={list} columns={['number', 'date', 'item']} />
        </Page>
    );
}
```

### Контракт и граница импортов

- Объявление отделено от компонента, потому что сервер собирает `src/configuration` без React и DOM. Файлы `*.tsx` каталога конфигурации исключены из серверной сборки и проверяются настройками клиента.
- Имя страницы подчиняется правилам имён объектов и не повторяется. Оно входит в адрес `/page/<имя>` и в ключ права.
- Генератор проверяет парность файлов: объявление без компонента и компонент без объявления останавливают генерацию с названием файла. В режиме слежения нарушение только попадает в журнал, потому что файлы пары создаются по одному. Экспорт ровно одного билдера и имя сервер проверяет при запуске и останавливается с `MetadataError`.
- Страница не импортирует значения из файлов объектов: файл объекта тянет билдеры, Effect, обработчики действий и политики с чтением базы, и серверный код попал бы в сборку клиента. Объект страница указывает ссылкой `Objects.<вид>.<имя>` из `objects.generated.ts`. Тип ссылки выведен из билдера импортом только типа, а вид и имя берутся из пути обращения, который компилятор сверяет с билдерами. Поэтому генератору не нужно разбирать исходники, чтобы узнать имена объектов.
- Из клиента страница импортирует только web SDK. Границу проверяет скрипт `scripts/configuration-imports-check.ts`, который `npm run typecheck` запускает перед проверкой типов: импорт внутреннего модуля `src/web`, значения из серверного кода или файла объекта останавливает проверку с названием файла и строки. Компилятор запрещать импорты по каталогам не умеет, поэтому проверка вынесена в скрипт.
- Клиент получает от сервера только имена и заголовки доступных страниц.

Полный образец в `src/configuration/pages/sample-workplace.page-component.tsx` показывает непроведённые пробные документы и кнопку «Провести» для выбранной строки.

## Элементы формы

Стандартная форма выводит поля и табличные части из описания объекта. Блок с собственной логикой, например итог по табличной части или поле ввода с кнопкой, конфигурация объявляет элементом формы. Как у страницы, у него есть объявление для сервера и компонент для клиента.

### Как добавить элемент

1. Создайте пару `*.form-element.ts` и `*.form-element-component.tsx` с общим началом имени внутри `src/configuration`.
2. В объявлении экспортируйте один результат `defineFormComponent(...)` с уникальным именем и местом подключения. React-компонент экспортируйте по умолчанию из соседнего файла.
3. Для замены ввода укажите `override` со ссылкой на объект и именем `field` либо `tablePart`. Для дополнительного блока укажите `insert` со ссылкой на объект, заголовком группы `group` и необязательным `after`.
4. Данные и механизмы формы получайте через SDK. Проверьте типы и импорты командой `npm run typecheck`, затем работу компонента на форме.

Блок итога объявляет место подключения рядом со своим компонентом:

```ts
import { defineFormComponent } from '../../server/metadata/form-elements.js';
import { Objects } from '../objects.generated.js';

export const SampleTotal = defineFormComponent({
    name: 'sampleTotal',
    insert: { object: Objects.document.sample, group: 'Строки и итог', after: 'lines' },
});
```

Замена таблицы объявляется так же:

```ts
export const SamplePayments = defineFormComponent({
    name: 'samplePayments',
    override: { object: Objects.document.sample, tablePart: 'payments' },
});
```

### Контракт элемента

| Настройка | Назначение и ограничения |
|---|---|
| `name` | Уникальное имя по правилам имён объектов; по нему клиент находит компонент |
| `override.object` | Типизированная ссылка `Objects` на справочник или документ |
| `override.field` или `override.tablePart` | Ровно одно существующее место ввода; скрытое место и поле, заполняемое платформой, недопустимы |
| `insert.object`, `insert.group` | Объект и существующая группа с единственным объявлением этого заголовка |
| `insert.after` | Поле или часть в этой группе; без настройки блок вставляется в начало |
| `attachments` | Массив подключений вместо одиночного `override` или `insert`; типы каждого места проверяются отдельно |

Один компонент может объявить несколько мест подключения. Вставки в одно место идут в порядке файлов реестра. Блок занимает всю ширину группы и в обход полей не входит. Замена сохраняет место, подпись и остановку обхода исходного поля или части. Две замены одного места отклоняются при запуске. Настроек компонентов в `.form(...)` нет: там остаются поля, части, группы, подписи, скрытие и режим открытия.

Объявление и компонент разделены, чтобы сервер проверял подключения без React, DOM и web SDK: объявление импортирует только `defineFormComponent` и ссылки `Objects`, файлы объектов ему доступны как типы. При запуске сервер применяет подключения к копии раскладки, проверяет результат и отдаёт готовую форму клиенту.

Блок вставки читает данные хуками `useFormData` и `useFormValue`. Замена поля получает `LaidOutInputProperties`: `InputProperties` и компоновку поля с названием и обязательностью ([«Компоновка полей»](web-sdk/components.md#компоновка-полей)). Замена части получает `TablePartInputProperties`: описание, строки, обработчик изменения, недоступность, ссылку для фокуса и возврат обхода назад. Строки остаются в форме при переключении представления, полную таблицу компонент выводит через `TablePart`, проверка колонок работает и без смонтированных ячеек. Хуки и компоненты перечислены в [«Web SDK»](web-sdk.md#состав).

Элемент на месте поля ввода должен поддерживать обе компоновки поля, потому что компоновку выбирает группа, а не элемент. Поэтому его компонент собирается функцией SDK `fieldInput({ stacked, fluid })` из двух компонентов; обычный компонент на месте поля не соберётся. Запись клиентского реестра создаёт `formElementModule`, и компилятор сверяет компонент с местами подключения из объявления. Вид места (`field`, `tablePart` или `group`) выводится из типа результата `defineFormComponent`, запись реестра пишет генератор `scripts/metadata-generate.ts`. Элемент на месте табличной части и блок вставки собираются любым компонентом.

Права у компонента нет: он виден там, где видна форма, а чтение данных и действия проверяются по правам объектов. К форме Ant Design и к API напрямую компонент не обращается. Реестр компонентов подключает стандартная форма, а не SDK: импорт реестра из SDK создал бы цикл зависимостей.

### Ограничения интерфейса

Элемент может сделать недоступной для изменения всю форму, отдельное поле или табличную часть и скрыть действие. Для этого он объявляет ограничения хуком [`useFormRestrictions`](web-sdk/hooks.md#ограничения-формы) и может ничего не выводить. Условие вычисляет компонент, а не описание объекта: оно может зависеть от состояния записи, значений формы и данных других объектов.

Ограничения управляют только интерфейсом и не меняют права и единый эндпоинт: скрытое на форме действие по-прежнему выполняется через `/api/perform`, а запрет изменения записи задаёт [политика записи](write-policies.md).

Условие в примере зависит от сохранённого комментария. Если взять вводимое значение, форма заблокируется после первой набранной буквы и не даст сохранить комментарий. Это фрагмент компонента, импорты SDK и `Objects` опущены.

```tsx
// Элемент, который управляет состоянием формы и ничего не выводит
export default function SampleLock() {
    const form = useFormData(Objects.document.sample);
    const locked = (form.saved?.comment ?? null) !== null;
    useFormRestrictions(Objects.document.sample, locked ? { readOnly: true, hiddenActions: ['post'] } : {});
    return null;
}
```

Пробные элементы стоят на форме пробного документа. Блок «Итого до скидки» под табличной частью «Строки» показывает сумму колонки «Сумма». Поле «Комментарий» заменено полем ввода с кнопкой, которая подставляет текст «Проверено». Компонент оплаты переключает одно поле суммы и таблицу, итог оплаты пересчитывается из строк. Элемент блокировки не даёт изменить и провести с формы документ с записанным комментарием и сообщает об этом строкой под полями.

## Формы объекта

Стандартные список и форма записи строятся по описанию объекта. Если этого мало, конфигурация заменяет экран целиком собственной формой объекта. Как страница и элемент формы, она состоит из объявления для сервера и компонента для клиента.

### Что выбрать

| Что нужно изменить | Средство |
|---|---|
| Порядок и группы полей, подписи, скрытие, режим создания | `.form(...)` в описании объекта ([«Переопределение формы»](interface.md#переопределение-формы)) |
| Блок в группе, ввод поля или табличной части | [Элемент формы](#элементы-формы) |
| Раскладка или поведение формы целиком, другой список | Форма объекта |

Форма объекта нужна, когда меньшие средства не справляются: раскладку она берёт на себя, и последующие изменения стандартной формы её уже не затрагивают. Элементы формы и `.form(...)` продолжают действовать внутри неё, если она выводит поля стандартными частями SDK.

### Виды форм

У объекта три формы, каждую можно заменить отдельно:

| Вид `kind` | Что заменяет | Свойства компонента | Объекты |
|---|---|---|---|
| `list` | Список объекта | `ListFormProperties`: `object` | Все виды объектов |
| `record` | Форму существующей записи | `RecordFormProperties`: `object`, `view`, `record`, `reload`, `presentation` | Справочники и документы |
| `new` | Форму новой записи | `NewFormProperties`: `object`, `view`, `presentation`, необязательное `initial` | Справочники и документы |

Собственная форма записи не заменяет форму новой записи, и наоборот: непереопределённый вид остаётся стандартным. `initial` содержит значения новой записи от того, кто открыл форму, например наименование, введённое в поле ссылки ([«Ссылки»](interface.md#ссылки)). Модальность видом формы не является: форма записи и форма новой записи получают в `presentation` место показа, `page` (вкладка) или `dialog` (модальное окно), и сами решают, менять ли раскладку. Список показывается только во вкладке. Типы свойств описаны в [«Функциях и типах»](web-sdk/functions-and-types.md#типы), а выбор формы и обмен с областью окна в разделе [«Выбор формы и место показа»](interface.md#выбор-формы-и-место-показа).

### Как заменить форму

1. Выберите вид формы и объект: справочник или документ для `record` и `new`, любой объект для `list`.
2. Создайте пару `*.object-form.ts` и `*.object-form-component.tsx` с общим началом имени внутри `src/configuration`.
3. В объявлении экспортируйте один результат `defineObjectForm({ object, kind })`, где `object` ссылка `Objects.<вид>.<имя>`. Компонент экспортируйте по умолчанию, его свойства должны соответствовать виду формы.
4. В форме записи и форме новой записи подключите контракт с областью окна: вызовите `useRecordForm` либо `useRecordFormContract` ([«Хуки»](web-sdk/hooks.md#контракт-формы-записи)). Без него область показывает ошибку вместо формы.
5. Выполните `npm run typecheck`, запустите приложение и откройте форму во вкладке и, если она открывается в окне, в окне.

Образец заменяет форму новой записи пробного документа:

```ts
// src/configuration/object-forms/sample-new.object-form.ts
import { defineObjectForm } from '../../server/metadata/object-forms.js';
import { Objects } from '../objects.generated.js';

export const SampleNew = defineObjectForm({ object: Objects.document.sample, kind: 'new' });
```

```tsx
// src/configuration/object-forms/sample-new.object-form-component.tsx
export default function SampleNewForm(properties: NewFormProperties) {
    if (properties.presentation === 'dialog') return <StandardRecordForm {...properties} />;
    return <SampleNewPage {...properties} />;
}
```

В окне форма возвращает стандартную, во вкладке выводит подсказку над группами (импорты и `SampleNewPage` опущены, полный файл лежит рядом с объявлением). Ветвление стоит до `useRecordForm`, правило описано в [«Компонентах»](web-sdk/components.md#стандартная-форма-и-её-части).

### Контракт объявления

`defineObjectForm` принимает `object` (типизированная ссылка `Objects`) и `kind` (`list`, `record` или `new`). Файл экспортирует ровно одно объявление. Сервер читает его без клиентских модулей, поэтому `*.object-form.ts` импортирует только `defineObjectForm` и ссылки `Objects`.

Проверки разделены по исполнителю:

| Кто проверяет | Что проверяется |
|---|---|
| Генератор | У объявления есть компонент и наоборот. Нарушение останавливает генерацию, в режиме слежения только попадает в журнал |
| Сервер при запуске | Ровно одно объявление в файле, известный вид, существующий объект, у объекта есть форма записи для `record` и `new`, вид не объявлен дважды. Нарушение останавливает запуск с `MetadataError` и названием файла |
| Компилятор | Свойства компонента соответствуют виду формы. Границу импортов проверяет `scripts/configuration-imports-check.ts` в составе `npm run typecheck` |
| Область окна во время работы | Форма записи подключила контракт ровно один раз; иначе вместо формы показана ошибка |

Дважды объявленный вид отклоняется: клиент не знал бы, какой из двух компонентов показать.

## Обнаружение объектов конфигурации

В исполняемом файле исходников `.ts` нет, поэтому объекты, страницы, элементы формы и формы объектов обнаруживаются при сборке. Скрипт `scripts/metadata-generate.ts` (`npm run metadata:generate`) находит файлы объектов `src/configuration/**/*.{catalog,document,register,information-register}.ts`, а также файлы [страниц](#страницы-конфигурации), [элементов формы](#элементы-формы) и [форм объектов](#формы-объекта) и генерирует в `src/configuration` пять файлов:

| Файл | Кому нужен | Содержимое |
|---|---|---|
| `configuration.generated.ts` | серверу | Импорт каждого файла объекта и каждого объявления страницы, элемента формы и формы объекта целиком, списки `configurationModules`, `pageModules`, `formElementModules` и `objectFormModules` с путём файла и его экспортом, объект прав `Rights`, построенный из модулей объектов и страниц (раздел [«Права (RBAC)»](authorization.md)) |
| `objects.generated.ts` | клиенту | Ссылки на объекты `Objects` для страниц и элементов формы; файлы объектов импортируются только как типы |
| `pages.generated.ts` | клиенту | Реестр страниц: объявление и компонент каждой страницы |
| `form-elements.generated.ts` | клиенту | Реестр элементов формы: объявление и компонент каждого элемента |
| `object-forms.generated.ts` | клиенту | Реестр форм объектов: запись каждой формы создаёт `objectFormModule(файл, объявление, компонент)`, и компилятор сверяет свойства компонента с видом формы |

- Сгенерированные файлы исключены из git и помечены комментарием «не редактировать вручную». `dev`, `build` и `typecheck` сначала запускают генерацию, поэтому в новом клоне или worktree файлы появляются сами.
- В `npm run dev` скрипт работает с флагом `--watch`: при появлении, удалении или переименовании файла объекта, страницы, элемента формы или формы объекта реестры обновляются, `tsc --watch` пересобирает сервер, `node --watch` перезапускает его, Vite обновляет клиент. Файл перезаписывается, только если его текст изменился.
- Ссылки на объекты и реестры компонентов лежат в разных файлах: реестр импортирует компоненты, а компоненты импортируют ссылки на объекты. В одном файле возник бы циклический импорт, и при загрузке компонента ссылки могли бы быть ещё не определены.

### Сборка описаний при запуске

Платформа читает только сгенерированный реестр. Сервис метаданных извлекает билдер из каждого модуля объекта: экспорт должен содержать ровно один билдер, вид которого совпадает с суффиксом файла. Объявления компонентов формы собираются отдельно, их подключения применяются перед проверкой описаний объектов, исходные билдеры не меняются. Объявления форм объектов (`objectFormModules`) проверяются в той же загрузке, когда известны все объекты, и их проблемы сообщаются вместе с остальными.

После проверки модулей сервис добавляет стандартные поля через `withStandardFields()` и вызывает `commitConfiguration`. Описания собираются один раз до приёма запросов и неизменны до перезапуска. `commit(configuration)` собирает один объект в окружении билдеров, `commitConfiguration(builders)` собирает и проверяет все объекты вместе. Обе операции возвращают Effect, результат состоит из неизменяемых `ObjectDescription`.

Нарушение соглашения о файлах или ошибка описания останавливает запуск с `MetadataError`: сообщение называет файл или объект, место и суть проблемы. Проблемы файлов сообщаются до проверки описаний, иначе некорректный экспорт породил бы вторичные ошибки в проверке ссылок. Готовые описания отдаёт `MetadataService`: `objects` возвращает все объекты, `find(kind, name)` один объект или `undefined`.

## Пробные объекты

Пробные объекты служат образцами объявления и ручной проверки возможностей платформы. Они лежат рядом с прикладными объектами и бизнес-правил магазина не описывают.

| Образец | Что демонстрирует |
|---|---|
| `catalogs/sample.catalog.ts` | Числовое поле для подсказок, цель ссылки документа |
| `catalogs/sample-delegate.catalog.ts` | Представление справочника по ссылке |
| `documents/sample.document.ts` | Ссылки шапки и строк, вычисления, составное представление, раскрытие частей, собственное действие и проведение в регистр (отрицательное количество уменьшает итог). Составные поля: «Куда оплачено» и «Отметка» вводятся текстом, «Срок» (дата либо строка) требует выбора типа |
| `documents/sample-selection.document.ts` | Общие колонки с дополнительным примечанием, выбор строк документа-источника через SDK |
| `registers/sample.register.ts` | Движения пробного документа, ограничение «количество по элементу не меньше нуля», составные измерения |
| `information-registers/sample.information-register.ts` | Ключ из двух измерений и ресурсы разных видов |
| `information-registers/sample-composite.information-register.ts` | Составное поле в ключе и ресурсе; у ресурса текстовый ввод отключён через `inputMode('solid')` |
| `pages/sample-workplace.*` | Собственная страница со списком и действием проведения |
| `form-elements/sample-*` | Итог текущих строк, собственное поле ввода, ограничения формы и выбор строк |
| `object-forms/sample-new.*` | Собственная форма новой записи пробного документа: стандартная в модальном окне, с подсказкой над группами во вкладке |
| `object-forms/shift-new.*` | Форма новой смены: во вкладке стандартная, в окне только дата, кнопки сотрудников и кнопки «Открыть» и «Отменить» |

Пути указаны относительно `src/configuration`. Общие колонки объявлены в `sample-lines.ts`: строки вычисляют сумму после скидки, шапка документа их итог. Выбор строк использует `RecordTablePart` и SDK формы, просмотр по ссылке раскрывает часть целевого документа. Образцы удобно читать вместе с [«Web SDK»](web-sdk.md).
