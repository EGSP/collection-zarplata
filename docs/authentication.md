# Вход в приложение

Пользователь входит по PIN, который однозначно определяет его учётную запись. Сервер выдаёт токены в cookie, клиент обновляет их при истечении срока. Права вошедшего описаны в разделе [«Права доступа»](authorization.md).

На экране входа также видна [отметка тестовой среды](interface.md#отметка-тестовой-среды), если сервер сообщает `testEnvironment: true`. Она занимает отдельное место под формой и не требует сессии.

## Протокол входа и выхода

Все запросы используют метод `POST`. Успешный ответ: `204` без тела, токены приходят только в `Set-Cookie`.

| Адрес | Входные данные | Результат | Ошибки |
|---|---|---|---|
| `/api/authentication/login` | JSON `{ "pin": "1234" }`. PIN передаётся строкой из 4–12 цифр | Создаёт новую сессию и устанавливает обе cookie | `400`: неверный формат PIN; `401`: PIN не найден или пользователь отключён; `429`: адрес временно заблокирован |
| `/api/authentication/refresh` | Cookie `refreshToken`; тело не требуется | Однократно расходует refresh-токен и заменяет обе cookie новой парой. При [автовходе](build-and-launch.md#автовход) вместо отказа выдаёт токены тестового пользователя автовхода | `401`: токен отсутствует, истёк, отозван или неизвестен; пользователь отсутствует или отключён |
| `/api/authentication/logout` | Cookie `refreshToken`; тело не требуется | Завершает сессию предъявленного действующего refresh-токена и удаляет обе cookie | Отсутствующий или отозванный токен допускается: повторный выход тоже возвращает `204` |

### Cookie и сроки действия

Обе cookie имеют флаги `HttpOnly` и `SameSite=Strict`. Если сервер определяет протокол запроса как HTTPS, он добавляет `Secure`.

| Cookie | Где браузер отправляет её | Срок по умолчанию | Переменная окружения |
|---|---|---|---|
| `accessToken` | `/api` и вложенные адреса | 15 минут | `ACCESS_TOKEN_LIFETIME_SECONDS` |
| `refreshToken` | `/api/authentication` и вложенные адреса | Семь дней | `REFRESH_TOKEN_LIFETIME_SECONDS` |

Переменные задают срок токена и его cookie в секундах. Пустая или отсутствующая переменная оставляет значение по умолчанию; иное значение должно быть положительным целым числом в безопасном диапазоне JavaScript, иначе запуск останавливается.

[API данных](single-endpoint.md) перед выполнением действий проверяет подпись и срок access-токена, активность пользователя и действительность сессии. Отсутствующий или недействительный токен даёт `401`.

### Ограничение попыток входа

Сервер считает ответы `401` при входе отдельно для каждого IP-адреса. Первая ошибка открывает окно на 15 минут. Пятая ошибка в окне ещё получает `401`, а следующие попытки до конца окна получают `429`; новое окно блокировка не начинает. Успешный вход сбрасывает счётчик, ошибки формата PIN (`400`) его не увеличивают.

Счётчик живёт в памяти процесса и пропадает при перезапуске. Адрес берётся из соединения: заголовкам прокси, которые передаёт клиент, сервер не доверяет.

## Как устроена сессия

Каждый вход создаёт запись `platform_sessions` с постоянным UUID. Access-токен содержит `sessionGuid`, а строка refresh-токена в `platform_tokens` ссылается на ту же сессию. UUID не зависит от устройства и сам по себе не разрешает вход. Отдельная cookie для UUID не нужна.

При переходе на эту схему прежние access-токены без `sessionGuid` и refresh-токены без связи с сессией получают `401`. Пользователь повторно вводит PIN. Старые токены в список сессий не попадают; время их первоначального входа не восстанавливается.

Access-токен подписан ключом, производным от `pinHmacSecret`, и связан с записью refresh-токена в базе. Одной действительной подписи мало: сервер проверяет, что сессия не отозвана и не истекла. Поэтому после обновления или выхода прежний access-токен перестаёт приниматься.

Обновление сохраняет UUID сессии, отзывает прежнюю запись токена и создаёт новую пару в одной транзакции, так что два одновременных обновления одним refresh-токеном не могут оба завершиться успешно.

База хранит SHA-256 refresh-токенов и HMAC-SHA-256 от PIN с ключом `pinHmacSecret`, без исходных значений. HMAC одного PIN с тем же ключом всегда одинаков, поэтому уникальный индекс позволяет найти пользователя по PIN и запрещает одинаковые PIN у разных пользователей. Пользователи, роли и сессии лежат в служебных таблицах платформы.

Из-за `HttpOnly` клиент не читает токены и судит о сессии по ответам сервера. При `401` на запрос данных он обновляет токены и один раз повторяет запрос:

- одновременные запросы страницы ждут одного общего обновления, потому что refresh-токен одноразовый;
- если токены уже заменил соседний запрос, выполняется только повтор;
- повтор делается и после `401` от самого обновления: cookie могла заменить другая вкладка.

Сессия считается завершённой, только если повтор тоже вернул `401`.

Ответы входа, обновления токенов и повторных запросов также сообщают [версии сервера](versions.md#обновление-открытой-страницы). Предложение обновить страницу доступно до входа и не меняет состояние сессии.

При открытии приложения состояние сессии неизвестно, пока ответ сервера не подтвердит вход или его отсутствие. Ошибка сети сама по себе не ведёт на экран входа. Если запрос выхода не удался, клиент сохраняет прежнее состояние: удалить cookie с `HttpOnly` он не может.

## Как создать первого пользователя

Для обычного запуска с файловой базой и пустой таблицей пользователей. Расположение и обязательные поля файла настроек описаны в разделе [«Сборка и запуск»](build-and-launch.md).

1. Добавьте в `collection-zarplata.settings.json` поле `initialUser` с непустым именем и PIN из 4–12 цифр. Например:

   ```json
   "initialUser": { "name": "Администратор", "pin": "482915" }
   ```

   Это фрагмент файла настроек: остальные поля остаются. Без `roles` пользователь получает все роли конфигурации; чтобы ограничить их, добавьте список имён, например `"roles": ["administrator"]`. Неизвестная роль останавливает запуск.

2. Запустите приложение. На пустой таблице сервер создаст пользователя, сохранит HMAC PIN и назначит роли. На непустой `initialUser` пользователя не создаёт и не меняет, но формат поля и имена ролей всё равно проверяются.
3. Войдите с этим PIN и проверьте доступ.

Не удаляйте `initialUser` и не ограничивайте его `roles`: при каждом запуске сервер загружает [первичные данные](initial-data.md) от имени этого пользователя, без него запуск останавливается. Пользователя создаёт модуль первичных данных, а хеш PIN и поиск по PIN берёт у сервиса входа.

Сохраняйте `pinHmacSecret`: после его замены прежние хеши PIN не подходят для входа, и PIN придётся назначить заново.

## Как создать и изменить пользователя

В разделе «Администрирование → Учётные записи → Пользователи» откройте «Создать», заполните имя и роли и нажмите «Записать». Затем нажмите «Установить PIN» и задайте от 4 до 12 цифр. До установки PIN новая учётная запись не разрешает вход. Начальные нули значимы; PIN не должен совпадать с PIN другого пользователя, в том числе отключённого.

Список использует общий поиск, отборы, сортировку и страницы справочников. Нажатие на запись открывает отдельную вкладку. На вкладке «Данные пользователя» стандартная форма записывает имя, дату отключения и табличную часть ролей. Роли выбираются из текущей конфигурации. Прежнюю роль, удалённую из конфигурации, можно оставить или снять; назначить её заново нельзя. Сотрудники магазина и учётные записи являются разными записями.

Доступ задаётся схемой встроенного справочника `Users`: чтение и изменение данных, группы `account` (имя) и `authorization` (дата отключения и роли), отдельные поля, действия и функции. Для установки PIN нужно разрешение действия `setPin`, для просмотра сессий функция `sessions`, для отключения одной сессии действие `revokeSession`; варианты ролей читает функция `roleOptions`. Полный доступ администратора включает эти разрешения, если более точное правило их не запрещает.

Заполненная дата «Отключён с» запрещает вход сразу, независимо от значения даты. Очистка даты включает учётную запись. Отключение и установка PIN отзывают прежние сессии; включение их не восстанавливает. Изменение ролей действует при следующей проверке прав без повторного входа. Не отключайте начального пользователя и не меняйте его PIN без согласованной правки `initialUser`: первичные данные используют эту запись при запуске.

PIN передаётся только действию установки. PIN и HMAC не являются полями справочника и отсутствуют в метаданных полей, `get/list`, представлениях и функциях даже при полном доступе. Журнал записывает изменения публичных данных; для установки PIN только факт `pinChanged`, без значения и HMAC.

## Устройство встроенного справочника

Пользователи описаны обычным `catalog('users')` в платформе, без прикладного справочника магазина. Описание включено в общий реестр до проверки форм и ссылок. Общий диспетчер выполняет `list/get/save`, проверку схемы, политики, доступ к полям и журналирование. Компоненты новой и существующей формы подключены обычными `*.object-form.ts` в конфигурации. Они используют `useRecordForm`, `RecordFormPage`, стандартные поля, табличную часть и `ActionDialog`; собственного CRUD и отдельного реестра UI для пользователей нет.

Адаптер хранения сохраняет существующие `platform_users` и `platform_user_roles`. Представления `catalog_users` и `catalog_users_roles` публикуют только поля справочника для общих запросов. UUID, хеши PIN, назначения ролей, токены и сессии при подключении адаптера не переносятся и не заменяются. Новые учётные записи до установки PIN получают случайное недействующее значение в служебной колонке HMAC.

## API пользователей

Цель [API данных](single-endpoint.md): `{ "kind": "catalog", "name": "users" }`. Прежняя отдельная цель `platform.users` удалена. Существующие ссылки следует заменить на `/catalog/users/<guid>`; UUID записей сохраняются.

| Операция | Вход (`payload`) | Результат |
|---|---|---|
| Действие `list` | Общие параметры страницы, поиска, отбора и сортировки | Общая страница `{ items, total, page, pageSize, presentations }` |
| Действие `get` | `{ guid }` | Публичная запись `{ guid, deletedAt, name, disabledAt, roles: [{ role }], $access }` |
| Действие `save` | `{ guid?, fields: { name, disabledAt, roles: [{ role }] } }` | Записанная публичная запись. Защищённые поля проверяет общий конвейер; при обновлении их можно пропустить |
| Действие `setPin` | `{ guid, pin }` | `null`; установка HMAC и отзыв всех сессий пользователя |
| Функция `sessions` | `{ guid }` | Массив `{ guid, createdAt, lastConnectedAt, refreshedAt }` действующих сессий |
| Функция `roleOptions` | `{}` | Массив `{ name, title, all }` ролей конфигурации |
| Действие `revokeSession` | `{ guid, sessionGuid }` | `null`; отзыв одной сессии и связанных токенов |

Функции вызываются свойством `function`, действия свойством `action`. Функции не изменяют данные и не пишут журнал. Все вызовы проходят общий расчёт прав. Применяется общая защита результатов обработчиков при частично скрытых данных, описанная в [правах доступа](authorization.md#полномочия-обработчиков).

Удаление, пометка удаления, импорт и подбор для пользователей не предусмотрены. Стандартное `deletedAt` всегда равно `null`, для отключения служит `disabledAt`. Неверный формат, пустое имя и неизвестные роли дают `400`, повтор PIN `409`, отсутствие права `403`, неизвестная запись или операция `404`. Ошибка откатывает весь пакет, включая предшествующие изменения.

Пример создания записи (PIN устанавливается следующим действием по полученному `guid`):

```json
{
  "target": { "kind": "catalog", "name": "users" },
  "action": "save",
  "payload": { "fields": { "name": "Кассир", "disabledAt": null, "roles": [{ "role": "seller" }] } }
}
```

## Как проверить обновление токенов

Нужна пустая база в памяти и короткие сроки. В PowerShell:

```powershell
$env:ACCESS_TOKEN_LIFETIME_SECONDS = '20'
$env:REFRESH_TOKEN_LIFETIME_SECONDS = '90'
npm run start:check -- --test-pin=482915 --port=3101
```

Войдите с PIN `482915`. Через 20 секунд следующий запрос данных обновит токены без повторного ввода PIN. Если после последней выдачи токенов оставить приложение без запросов дольше 90 секунд, обновление и повтор получат `401`, и приложение покажет экран входа. Каждое успешное обновление заново отсчитывает срок refresh-токена.

После остановки приложения удалите переменные из оболочки:

```powershell
Remove-Item Env:ACCESS_TOKEN_LIFETIME_SECONDS
Remove-Item Env:REFRESH_TOKEN_LIFETIME_SECONDS
```

## Просмотр и отключение сессий

Нажатие на имя в списке пользователей открывает отдельную вкладку приложения с собственным адресом и вкладками «Данные пользователя» и «Сессии». Список сессий показывает полный UUID в колонке «ID», время входа, последнего успешного подключения к защищённому API и последней выдачи токенов. При входе все три времени совпадают. Вкладка обновляется каждые 15 секунд; кнопка «Обновить» перечитывает её сразу. Вкладки одного профиля браузера используют общие cookie и одну сессию.

Просмотр требует разрешения функции `catalog.users.functions.sessions`, отключение разрешения действия `catalog.users.actions.revokeSession`. Для пользователя без права записи кнопка отключения недоступна. Отключение выбранной сессии не затрагивает остальные; следующий запрос с её токенами получает `401`. Истёкшие и отозванные сессии скрыты. Выход, отключение пользователя и смена PIN также отзывают соответствующие сессии. Журнал хранит UUID отключённой сессии без токенов и их хешей.

Пользователи открываются общими представлениями справочника: список `/catalog/users`, новая запись `/catalog/users/new`, существующая `/catalog/users/<guid>`. Форма использует стандартный контракт записи: ввод сохраняется при переключении вкладок, закрытие спрашивает подтверждение, после создания адрес заменяется на UUID. Кнопка «Записать» и Ctrl+S оставляют форму открытой. Escape сначала закрывает открытый выбор или окно PIN, затем форму. Установка PIN происходит в отдельном общем окне действия, которое очищается после закрытия.
