# Вход в приложение

Пользователь входит по PIN, который однозначно определяет его учётную запись. Сервер выдаёт токены в cookie, клиент обновляет их при истечении срока. Права вошедшего описаны в разделе [«Права доступа»](authorization.md).

## Протокол входа и выхода

Все запросы используют метод `POST`. Успешный ответ: `204` без тела, токены приходят только в `Set-Cookie`.

| Адрес | Входные данные | Результат | Ошибки |
|---|---|---|---|
| `/api/authentication/login` | JSON `{ "pin": "1234" }`. PIN передаётся строкой из 4–12 цифр | Создаёт новую сессию и устанавливает обе cookie | `400`: неверный формат PIN; `401`: PIN не найден или пользователь отключён; `429`: адрес временно заблокирован |
| `/api/authentication/refresh` | Cookie `refreshToken`; тело не требуется | Однократно расходует refresh-токен и заменяет обе cookie новой парой. При [автовходе](build-and-launch.md#автовход) вместо отказа выдаёт токены тестового пользователя автовхода | `401`: токен отсутствует, истёк, отозван или неизвестен; пользователь отсутствует или отключён |
| `/api/authentication/logout` | Cookie `refreshToken`; тело не требуется | Отзывает предъявленный refresh-токен и удаляет обе cookie | Отсутствующий или отозванный токен допускается: повторный выход тоже возвращает `204` |

### Cookie и сроки действия

Обе cookie имеют флаги `HttpOnly` и `SameSite=Strict`. Если сервер определяет протокол запроса как HTTPS, он добавляет `Secure`.

| Cookie | Где браузер отправляет её | Срок по умолчанию | Переменная окружения |
|---|---|---|---|
| `accessToken` | `/api` и вложенные адреса | 15 минут | `ACCESS_TOKEN_LIFETIME_SECONDS` |
| `refreshToken` | `/api/authentication` и вложенные адреса | Семь дней | `REFRESH_TOKEN_LIFETIME_SECONDS` |

Переменные задают срок токена и его cookie в секундах. Пустая или отсутствующая переменная оставляет значение по умолчанию; иное значение должно быть положительным целым числом в безопасном диапазоне JavaScript, иначе запуск останавливается.

[API данных](single-endpoint.md) перед выполнением действий проверяет подпись и срок access-токена, активность пользователя и действительность сессии. Отсутствующий или недействительный токен даёт `401`.

### Ограничение попыток входа

Сервер считает ответы `401` при входе отдельно для каждого IP-адреса. Первая ошибка открывает окно на 15 минут. Пятая ошибка в окне ещё получает `401`, а следующие попытки до конца окна получают `429`; новое окно блокировка не начинает. Успешный вход сбрасывает счётчик, ошибки формата PIN (`400`) его не увеличивают.

Счётчик живёт в памяти процесса и пропадает при перезапуске. Адрес берётся из соединения: заголовкам прокси, которые передаёт клиент, сервер не доверяет.

## Как устроена сессия

Access-токен подписан ключом, производным от `pinHmacSecret`, и связан с записью refresh-токена в базе. Одной действительной подписи мало: сервер проверяет, что сессия не отозвана и не истекла. Поэтому после обновления или выхода прежний access-токен перестаёт приниматься.

Обновление отзывает прежнюю запись и создаёт новую пару в одной транзакции, так что два одновременных обновления одним refresh-токеном не могут оба завершиться успешно.

База хранит SHA-256 refresh-токенов и HMAC-SHA-256 от PIN с ключом `pinHmacSecret`, без исходных значений. HMAC одного PIN с тем же ключом всегда одинаков, поэтому уникальный индекс позволяет найти пользователя по PIN и запрещает одинаковые PIN у разных пользователей. Пользователи, роли и сессии лежат в служебных таблицах платформы.

Из-за `HttpOnly` клиент не читает токены и судит о сессии по ответам сервера. При `401` на запрос данных он обновляет токены и один раз повторяет запрос:

- одновременные запросы страницы ждут одного общего обновления, потому что refresh-токен одноразовый;
- если токены уже заменил соседний запрос, выполняется только повтор;
- повтор делается и после `401` от самого обновления: cookie могла заменить другая вкладка.

Сессия считается завершённой, только если повтор тоже вернул `401`.

При открытии приложения состояние сессии неизвестно, пока ответ сервера не подтвердит вход или его отсутствие. Ошибка сети сама по себе не ведёт на экран входа. Если запрос выхода не удался, клиент сохраняет прежнее состояние: удалить cookie с `HttpOnly` он не может.

## Как создать первого пользователя

Для обычного запуска с файловой базой и пустой таблицей пользователей. Расположение и обязательные поля файла настроек описаны в разделе [«Сборка и запуск»](build-and-launch.md).

1. Добавьте в `collection-zarplata.settings.json` поле `initialUser` с непустым именем и PIN из 4–12 цифр. Например:

   ```json
   "initialUser": { "name": "Администратор", "pin": "482915" }
   ```

   Это фрагмент файла настроек: остальные поля остаются. Без `roles` пользователь получает все роли конфигурации; чтобы ограничить их, добавьте список имён, например `"roles": ["administrator"]`. Неизвестная роль останавливает запуск.

2. Запустите приложение. На пустой таблице сервер создаст пользователя, сохранит HMAC PIN и назначит роли. На непустой `initialUser` пользователя не создаёт и не меняет, но формат поля и имена ролей всё равно проверяются.
3. Войдите с этим PIN и проверьте доступ.

Не удаляйте `initialUser` и не ограничивайте его `roles`: при каждом запуске сервер загружает [первичные данные](initial-data.md) от имени этого пользователя, без него запуск останавливается. Пользователя создаёт модуль первичных данных, а хеш PIN и поиск по PIN берёт у сервиса входа.

Сохраняйте `pinHmacSecret`: после его замены прежние хеши PIN не подходят для входа, и PIN придётся назначить заново.

## Как проверить обновление токенов

Нужна пустая база в памяти и короткие сроки. В PowerShell:

```powershell
$env:ACCESS_TOKEN_LIFETIME_SECONDS = '20'
$env:REFRESH_TOKEN_LIFETIME_SECONDS = '90'
npm run start:check -- --test-pin=482915 --port=3101
```

Войдите с PIN `482915`. Через 20 секунд следующий запрос данных обновит токены без повторного ввода PIN. Если после последней выдачи токенов оставить приложение без запросов дольше 90 секунд, обновление и повтор получат `401`, и приложение покажет экран входа. Каждое успешное обновление заново отсчитывает срок refresh-токена.

После остановки приложения удалите переменные из оболочки:

```powershell
Remove-Item Env:ACCESS_TOKEN_LIFETIME_SECONDS
Remove-Item Env:REFRESH_TOKEN_LIFETIME_SECONDS
```
