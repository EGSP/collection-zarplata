# Вход в приложение

Пользователь входит по PIN, который однозначно определяет его учётную запись. Сервер выдаёт токены в cookie, а клиент обновляет их при истечении срока доступа. Здесь описаны протокол входа для разработчика, устройство сессии и создание первого пользователя для администратора. Права вошедшего пользователя описаны в разделе [«Права доступа»](authorization.md).

## Протокол входа и выхода

Все запросы используют метод `POST`. Успешный ответ имеет статус `204` и не содержит тела; токены передаются только через `Set-Cookie`.

| Адрес | Входные данные | Результат | Ошибки |
|---|---|---|---|
| `/api/authentication/login` | JSON `{ "pin": "1234" }`. PIN передаётся строкой из 4–12 цифр | Создаёт новую сессию и устанавливает обе cookie | `400`: неверный формат PIN; `401`: PIN не найден или пользователь отключён; `429`: адрес временно заблокирован |
| `/api/authentication/refresh` | Cookie `refreshToken`; тело не требуется | Однократно расходует refresh-токен и заменяет обе cookie новой парой | `401`: токен отсутствует, истёк, отозван или неизвестен; пользователь отсутствует или отключён |
| `/api/authentication/logout` | Cookie `refreshToken`; тело не требуется | Отзывает предъявленный refresh-токен и удаляет обе cookie | Отсутствующий или уже отозванный токен допускается: повторный выход также возвращает `204` |

### Cookie и сроки действия

Обе cookie имеют флаги `HttpOnly` и `SameSite=Strict`. Если сервер определяет протокол запроса как HTTPS, он добавляет `Secure`.

| Cookie | Где браузер отправляет её | Срок по умолчанию | Переменная окружения |
|---|---|---|---|
| `accessToken` | `/api` и вложенные адреса | 15 минут | `ACCESS_TOKEN_LIFETIME_SECONDS` |
| `refreshToken` | `/api/authentication` и вложенные адреса | Семь дней | `REFRESH_TOKEN_LIFETIME_SECONDS` |

Переменные задают срок токена и его cookie в секундах. Если переменная отсутствует или пуста, действует значение по умолчанию. Иное значение должно быть положительным целым числом в безопасном диапазоне JavaScript; неверное значение останавливает запуск.

[API данных](single-endpoint.md) проверяет access-токен до выполнения действий: его подпись и срок, активность пользователя, принадлежность и действительность сессии. Отсутствующий или недействительный токен даёт `401`.

### Ограничение попыток входа

Сервер учитывает ответы `401` при входе по каждому IP-адресу. Первая ошибка открывает окно на 15 минут. После пяти ошибок в этом окне следующие попытки получают `429` до его окончания. Пятая ошибка ещё возвращает `401`; блокировка не начинает новое 15-минутное окно. Успешный вход сбрасывает счётчик, а ошибки формата PIN (`400`) его не увеличивают.

Счётчик хранится в памяти процесса и исчезает при перезапуске. Адрес берётся из соединения: сервер не доверяет переданным клиентом заголовкам прокси.

## Как устроена сессия

Access-токен подписан ключом, производным от `pinHmacSecret`, и связан с записью refresh-токена в базе. Поэтому одной действительной подписи недостаточно: сервер проверяет, что сессия не отозвана и не истекла. Обновление отзывает прежнюю запись и создаёт новую пару токенов в одной транзакции. Два одновременных обновления одним refresh-токеном не могут оба завершиться успешно. После обновления или выхода прежний access-токен тоже перестаёт приниматься.

База хранит SHA-256 refresh-токенов и HMAC-SHA-256 от PIN с ключом `pinHmacSecret`, без исходных значений. HMAC одного PIN с тем же ключом всегда одинаков: уникальный индекс позволяет найти пользователя по PIN и запрещает одинаковые PIN у разных пользователей. Пользователи, назначения ролей и записи сессий находятся в служебных таблицах платформы.

Клиент не читает токены из-за `HttpOnly` и узнаёт о сессии по ответам сервера. При `401` на запрос данных он обновляет токены и один раз повторяет исходный запрос. Одновременные запросы одной страницы ждут общего обновления; если токены уже заменил соседний запрос, выполняется только повтор. Даже после `401` от обновления клиент делает повтор: cookie могла заменить другая вкладка. Сессия считается завершённой, только если повтор тоже вернул `401`.

При открытии приложения состояние сессии неизвестно, пока запрос к серверу не подтвердит вход или его отсутствие. Ошибка сети сама по себе не переводит пользователя на экран входа. Если запрос выхода не удался, клиент сохраняет прежнее состояние: самостоятельно удалить cookie с `HttpOnly` он не может.

## Как создать первого пользователя

Инструкция предназначена для обычного запуска с файловой базой и пустой таблицей пользователей. Расположение и обязательные поля локального файла настроек описаны в разделе [«Сборка и запуск»](build-and-launch.md).

1. Добавьте в `collection-zarplata.settings.json` поле `initialUser` с непустым именем и PIN из 4–12 цифр. Например:

   ```json
   "initialUser": { "name": "Администратор", "pin": "482915" }
   ```

   Это фрагмент существующего объекта настроек; остальные поля должны остаться в файле. Без `roles` пользователь получает все роли конфигурации. Чтобы ограничить их, добавьте список имён, например `"roles": ["administrator"]`, если такая роль описана в конфигурации. Неизвестная роль останавливает запуск.

2. Запустите приложение. На пустой таблице сервер создаст пользователя, сохранит HMAC PIN и назначит роли. На непустой таблице `initialUser` не создаёт и не меняет пользователя. Формат поля и имена ролей проверяются и в этом случае.
3. Войдите с указанным PIN и убедитесь, что пользователь получил ожидаемый доступ.
4. Удалите `initialUser` из файла настроек после успешной проверки. Учётная запись останется в базе, а открытый PIN больше не будет храниться в файле.

После создания пользователей сохраняйте `pinHmacSecret`: его замена делает прежние хеши PIN непригодными для входа и требует переназначения PIN.

## Как проверить обновление токенов

Для ручной проверки используйте пустую базу в памяти и короткие сроки. В PowerShell:

```powershell
$env:ACCESS_TOKEN_LIFETIME_SECONDS = '20'
$env:REFRESH_TOKEN_LIFETIME_SECONDS = '90'
npm run start:check -- --test-pin=482915 --port=3101
```

Войдите с PIN `482915`. После истечения 20 секунд следующий запрос данных должен вызвать обновление токенов и завершиться без повторного ввода PIN. Затем оставьте приложение без запросов на время, превышающее 90 секунд после последней выдачи токенов: при следующем запросе обновление и повтор получат `401`, и приложение покажет экран входа. Каждое успешное обновление заново отсчитывает срок refresh-токена.

После остановки приложения удалите временные значения из окружения текущей оболочки:

```powershell
Remove-Item Env:ACCESS_TOKEN_LIFETIME_SECONDS
Remove-Item Env:REFRESH_TOKEN_LIFETIME_SECONDS
```
