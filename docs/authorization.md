# Права доступа

При [открытии записи по правилу](metadata.md#правило-открытия-записи) сервер проверяет права чтения. Условия отказа описаны в [контракте операции](single-endpoint.md#разрешение-цели-открытия).

Конфигурация описывает дерево доступа к данным и обработчикам. Роли и пользовательские настройки используют одни узлы; диспетчер, интерфейс и административный редактор рассчитывают итог одинаково. Правила, зависящие от состояния документов, остаются отдельными [политиками](write-policies.md).

## Иерархическая схема

### Как объявить группы и назначить доступ

Группы доступа не зависят от раскладки формы. Например, продажа объявляет группу `financial` («Финансы») для сумм, оплат и финансовых колонок товаров. Перенос контрола в другую группу формы прав не меняет.

```ts
const saleAccess = accessSchema(Sale)
    .level('full')
    .group('financial', 'deny')
    .field('paid', 'read');

role('salesObserver').access(saleAccess);
```

Эта роль читает и изменяет продажу и вызывает её обработчики, но не видит финансовую группу; исключение открывает только поле «Оплачено». Имена полей, табличных частей, групп, действий и функций проверяет TypeScript. Колонка части записывается как `goods.discount`.

Для объявления группы используется `accessSchema(object).defineGroup(name, fields, title)`. Схему подключают к объекту методом `.withAccess(schema)`, после чего имя группы входит в его тип. `.internal(...fields)` отмечает внутренние поля: их нет в публичных метаданных, ответах и редакторе даже при полном доступе. Фиксированное объявление внутреннего поля пользовательскими настройками не отменяется.

### Узлы и уровни

| Метод схемы | Узел и уровни |
|---|---|
| `.level(level)` | Объект: `inherit`, `deny`, `read`, `edit`; сокращение `full` даёт также вызовы |
| `.fields(level)` | Все данные: `inherit`, `deny`, `read`, `edit` |
| `.group(name, level)` | Независимая группа полей, те же уровни данных |
| `.field(name, level)` | Поле, часть или колонка части, те же уровни данных |
| `.actions(level)`, `.functions(level)` | Группы вызовов: `inherit`, `deny`, `allow` |
| `.action(name, level)`, `.function(name, level)` | Конкретный обработчик: `inherit`, `deny`, `allow` |
| `.post(level)` | Проведение и отмена проведения документа: `inherit`, `deny`, `allow` |
| `.import(level)` | Импорт записей справочника (узел `actions.import`): `inherit`, `deny`, `allow` |
| `accessSchema().page(page, level)` | Открытие страницы (узел `actions.open`): `inherit`, `deny`, `allow` |
| `accessSchema().platform(section, operation, level)` | Операция платформы (узел `actions.<имя>`): `inherit`, `deny`, `allow` |

Редактирование включает чтение. Чтение или редактирование данных само по себе не разрешает вызов обработчиков; импорт справочника тоже требует собственного узла `import`, право записи его не даёт. `inherit` удаляет собственное решение узла из расчёта; если разрешающего предка нет, действует запрет. Полный доступ допускает исключения на любых более точных узлах.

### Наследование и сочетание ролей

Итог определяет наиболее точная явная настройка: поле перекрывает часть и группу, группа перекрывает общую настройку данных, та перекрывает объект. На одном уровне точности запрет сильнее разрешения; среди разрешений редактирование сильнее чтения. При одинаковом решении источник выбирается по стабильному порядку путей. Поэтому порядок назначения ролей результата не меняет, а полная роль не стирает явный запрет поля другой роли.

При запуске `grantAll()` задаёт `full` на каждом корне схемы, включая объекты, страницы и служебные разделы. Если у одной роли на корне объекта задано чтение, а у другой полный доступ, пользователь может записывать данные. Более точный запрет на поле или операцию сохраняет приоритет.

Настройки редактируемой роли из базы заменяют объявленное в коде решение на том же узле. Настройка `inherit` позволяет наследовать родителя вместо исходного решения. Роли с `.readOnly()` при каждом запуске получают настройки из конфигурации. Пользовательские настройки участвуют в общем расчёте вместе с ролями с тем же приоритетом по точности узла.

Продавцу и управляющему разрешена функция продажи `figures`. Она нужна сводке за период и ленте продавца. Вложенный вызов функции рассрочки `figures` также проверяет право пользователя на её вызов.

## Полномочия обработчиков

Один билдер используется и без привязки к объекту:

```ts
const extension = accessSchema()
    .object(Sale, access => access.field('paid', 'edit'))
    .object(SaleInstallment, access => access.level('edit').post('allow'));

// В объявлении действия или функции:
// .access(extension).handle(handler)
```

До исполнения проверяется право вызова. Затем к пользовательскому доступу добавляется фиксированная схема обработчика. Прямой пользовательский запрет не блокирует разрешение из расширения. Расширение действует только в текущей серверной цепочке, не записывается в назначения и не приходит от клиента. Вложенные действия и функции проверяют свои права вызова и могут добавить только собственные объявленные полномочия. Инициатор и общая транзакция сохраняются.

Чтения `ReadonlyDatabase` проверяются по происхождению запросов `query(object)`: выбранные поля, отборы и сортировки. Произвольный SQL без такого описания в обработчике отклоняется. `Database` и возможность записи не появляются у функции: ограничения типов из [метаданных](metadata.md#функции-объектов) продолжают действовать. Политики и проверки бизнес-правил расширением не отключаются.

Расширение может объявить и платформа. Импорт справочника (`import`) на время вызова разрешает изменять поля этого справочника и читать и записывать регистр сведений «Внешние связи» (`informationRegister.externalLinks`). Пользователю достаточно права на импорт `Rights.catalog.<имя>.import`: права записи справочника и регистра ему не нужны. Расширение задаёт функция `importAccess` в [модуле импорта](https://github.com/EGSP/collection-zarplata/blob/main/src/server/data/import.ts), диспетчер подключает его для действия `import`.

Расширение не является разрешением раскрывать данные. Если у объекта обработчика есть скрытые поля или серверная цепочка прочитала данные, недоступные самому пользователю, внешнее действие возвращает только `{ "completed": true }`; его записи подтверждаются. Функция с непустым результатом в такой ситуации получает 403, функция без результата может завершиться. Это консервативная граница для произвольных результатов JavaScript: переименование скрытого поля или расчёт производного значения его не раскрывают. Внутри цепочки разрешённые данные доступны вызывающему обработчику. Пользовательские ответы общего API всегда отбираются по исходным правам.

## Чтение и сохранение

`get`, `list` и результаты записи не содержат недоступных значений. Для публичных полей запись содержит карту `$access`: `deny`, `read` или `edit`. Например, `$access.amount = "deny"` и отсутствие `amount` отличаются от доступного `amount = null`. Недоступная целиком часть не возвращает даже число строк. Внутренние поля отсутствуют и в карте.

Отбор и сортировка по скрытому полю получают 403; общий поиск использует только доступные колонки. Представление частично недоступного объекта, поиск по нему и правило переадресации открытия отключены; представления ссылок на такие объекты также не раскрываются. Журнал целиком недоступен, если пользователь не может читать какое-либо поле конфигурации: произвольные старые изменения не выдаются в обход текущих прав.

При обновлении пропущенное недоступное поле берётся из текущей записи. Переданное прежнее значение допустимо, новое даёт 403 до записи. Колонки частей сравниваются по строкам; изменение числа строк при защищённых колонках отклоняется. Вычисляемые и служебные поля заполняет сервер; при создании недоступного поля используется постоянное значение `.default(...)` или правило вида из [карты начальных значений](metadata.md#начальные-значения-полей). Effect выполняется при подготовке формы для доступного поля. Отсутствие обязательного значения без серверного заполнения остаётся ошибкой входных данных.

Отказ содержит `code: "ACCESS_DENIED"`, `target`, `path`, `required`, `actual`, `chain` и совместимый ключ `right`. Текст называет поле и группу; цепочка показывает вложенные вызовы. Значения полей и SQL не включаются. Ошибка откатывает всю транзакцию, включая предыдущие операции пакета. Сообщение прикладной проверки, использовавшей скрытые данные, заменяется безопасным отказом раскрытия результата.

## Права

### Проверка прав объектов

`Rights.<вид>.<имя>.read/write/post`, у справочника ещё `import`, а также `actions` и `functions` сохраняются как типизированные ссылки для существующих политик и интерфейса. Их проверяет тот же расчёт дерева: отдельного плоского механизма разрешений для данных нет. `read` означает наличие доступных данных, `write` наличие редактируемого поля, `post` узел проведения `actions.post`, `import` узел импорта `actions.import`. Узел права определяет функция `rightAccessPath`. Детальную запись всегда дополнительно проверяет общий конвейер полей.

### Права страниц и платформы

| Право | Ключ | Назначение |
|---|---|---|
| `Rights.page.<имя>.open` | `page.<имя>.open` | Видимость страницы конфигурации в описаниях интерфейса и возможность открыть её адрес |
| `Rights.platform.journal.read` | `platform.journal.read` | Чтение журнала изменений всех объектов |
| `Rights.platform.documents.repost` | `platform.documents.repost` | [Перепроведение](single-endpoint.md#перепроведение-документов) всех проведённых документов |
| `Users` через `accessSchema` | `catalog.users` | Данные встроенного справочника, группы `account` и `authorization`, отдельные поля и колонки ролей |
| Действия и функции `Users` | `catalog.users.actions.*`, `catalog.users.functions.*` | Установка PIN и отзыв сессии; чтение сессий и вариантов ролей |
| `Rights.platform.authorization.write` | `platform.authorization.write` | Изменение пользовательских и ролевых настроек узлов |
| `Rights.platform.authorization.read` | `platform.authorization.read` | Просмотр полного дерева прав, числа пользователей и всех ролей-оснований |
| `Rights.platform.backups.read` | `platform.backups.read` | Просмотр [резервных копий](backup.md#api-и-права): список, диск, расписание, идущие копии |
| `Rights.platform.backups.write` | `platform.backups.write` | Создание и прерывание резервных копий |

- Право открыть страницу не даёт прав на данные, которые она читает или изменяет: для них нужны права объектов.
- Журнал показывает изменения всех объектов, поэтому его чтение не следует из права чтения объекта.
- Перепроведение заменяет движения документов всех видов без политик проведения, поэтому право `post` отдельных документов его не разрешает.
- Резервная копия содержит всю базу, поэтому её просмотр и создание не следуют из прав объектов. В дереве прав они стоят в узле «Платформа» под заголовком «Резервные копии»; роль администратора получает их вместе с остальными.

### Объект Rights

Конфигурация ссылается на права через `Rights`: `Rights.catalog.employees.read`, `Rights.document.shift.post`, `Rights.catalog.employees.actions.dismiss`, `Rights.document.saleInstallment.functions.figures`. У права есть ключ (`catalog.employees.write`), по ключам проверка и сравнивает права.

Генератор реестра строит `Rights` в `configuration.generated.ts` из модулей объектов и объявлений страниц. Тип `Rights` выводится из типов билдеров, поэтому право несуществующего объекта, действия или страницы не компилируется. Порядок генерации описан в разделе [«Метаданные»](metadata.md).

## Роли

### Как добавить роль

Объекты, действия и страницы, к которым роль даёт доступ, должны быть уже объявлены.

1. В [описании ролей конфигурации](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/roles.ts) добавьте билдер в экспортируемый массив `roles`. Задайте уникальное имя и название для интерфейса.
2. Подключите схему через `.access(...)`. В схеме задайте доступ к объектам через `.object(...)`, открытие страниц через `.page(...)` и операции платформы через `.platform(...)`. Для полного доступа на всех корнях используйте `.grantAll()`.
3. Для страницы добавьте право страницы и права на её операции с данными. Если собственное действие обращается к другим объектам через диспетчер, добавьте права на эти вложенные операции.

Например, эта роль открывает страницу резервных копий и просматривает список.

```ts
role('backupObserver')
    .title('Просмотр резервных копий')
    .readOnly()
    .access(accessSchema()
        .page(Backups, 'allow')
        .platform('backups', 'read', 'allow'));
```

Это упрощённый пример: в реальном файле сохраняйте остальные роли массива.

После правки проверьте типы и перезапустите приложение. Для проверки запустите режим памяти с пользователем, у которого только новая роль ([«Сборка и запуск»](build-and-launch.md)). Разрешённые операции должны выполняться, а прямой запрос к запрещённой операции получать 403. У страницы отдельно проверьте видимость и доступ к данным.

### Контракт роли

| Объявление | Поведение |
|---|---|
| `role(name)` | Создаёт роль с указанным именем |
| `.title(title)` | Задаёт название для интерфейса; без него используется имя роли |
| `.access(schema)` | Добавляет типизированную схему объектов, страниц и операций платформы |
| `.readOnly()` | Фиксирует права роли в конфигурации; роль по-прежнему можно назначать пользователям |
| `.grantAll()` | Даёт полный доступ на всех корнях схемы, включая появившиеся позже |

Имя роли пишется латиницей в lowerCamelCase и не повторяется. Неверное имя или повтор останавливают запуск до приёма запросов. Билдеры описаны в [модуле ролей](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/roles.ts).

Пользователю можно назначить несколько ролей; решения их узлов сочетаются по точности и описанному выше приоритету. Исходная схема объекта также участвует в расчёте; текущая конфигурация использует её для групп, без общих разрешений. Без роли, исходного разрешения объекта и пользовательских настроек действует запрет. Конфигурация содержит роли:

| Имя | Название и права |
|---|---|
| `seller` | «Продавец». Открывает и закрывает смены, оформляет продажи, рассрочки, отвесы, возвраты и сертификаты. Применяет купоны и выбирает приёмники оплат из существующих записей. Принимает взносы и оформляет оплату банком. Открывает рабочее место, зарплату и сводку, в том числе кассовую |
| `manager` | «Управляющий». Выполняет операции продавца, закрывает собственные рассрочки и периоды, ведёт справочники купонов и приёмников оплат, сверяет движения регистра «Поступления денег», ставит отметки сверки кассовых дней |
| `administrator` | «Администратор». Получает полный доступ на корнях схемы, в том числе к действию сверки кассового дня. Роль включает учётные записи, права доступа и резервные копии |

Все три роли имеют фиксированные права. Продавцу доступны взносы и оплата банка, а закрытие собственной рассрочки и периода выполняет управляющий или администратор. При записи даты закрытия собственной рассрочки через API сервер проверяет то же право, что при вызове действия «Закрыть». У продавца есть чтение купонов и приёмников оплат. Правила закрытия описаны в разделах [«Рассрочка по продаже»](accounting-rules.md#рассрочка-по-продаже) и [«Закрытие периода»](accounting-rules.md#закрытие-периода).

Отметки [сверки кассовых дней](accounting-rules/cash-summary.md#сверка-кассового-дня) ставят управляющий и администратор через отдельное действие. Документ записывается только в рамках этого действия. Продавец просматривает отметки и историю сверки, но не меняет их.

Роли назначаются в [карточке пользователя](authentication.md#как-создать-и-изменить-пользователя), первому пользователю из настроек и тестовым пользователям режима памяти. Порядок тестового запуска описан в разделе [«Сборка и запуск»](build-and-launch.md). Право управления пользователями позволяет назначить в том числе полный доступ, поэтому его следует выдавать только администраторам учётных записей.

## Как посмотреть доступ пользователей

Войдите как администратор и откройте «Администрирование → Учётные записи → Права доступа». Полный доступ роли даёт права `Rights.page.accessRights.open` и `Rights.platform.authorization.read`.

Оставьте верхний пикер пустым и выберите узел в дереве. Панель «Пользователи и роли» покажет итоговый уровень каждой активной учётной записи и каждой роли, включая запреты. Для подсистем и групп меню панель показывает охват дочерних узлов. Узлы раскрываются стрелкой. Поиск по названию или ключу оставляет совпадения и раскрывает путь к ним.

Дерево сохраняет подсистемы и группы из конфигурации. Внутри объектов находятся группы полей, отдельные поля, табличные части, действия и функции. Объекты и страницы вне меню собраны в «Прочем», а служебные операции в «Платформе».

### Как считаются пользователи

В режиме обзора число рядом с узлом показывает, сколько активных пользователей имеют доступ хотя бы к одной конечной настройке внутри него. Пользователь учитывается один раз, даже если разрешение дают несколько ролей или объект повторяется в меню. Охват подсистемы или группы меню считается по уникальным конечным настройкам. Счётчики используют тот же расчёт разрешений, что и серверная проверка.

Политики записи, закрытый период и права на вложенные операции могут дополнительно ограничить действие над конкретной записью.

### API дерева и объяснения

Действия идут через [API данных](single-endpoint.md) с целью `{ "kind": "platform", "name": "authorization" }`. Оба требуют `platform.authorization.read`. Без этого права ответ 403, без входа ответ 401. Фильтрация метаданных по прикладным правам просматривающего пользователя к этому дереву не применяется.

| Действие | Вход (`payload`) | Ответ |
|---|---|---|
| `tree` | Не требуется | `{ nodes, subjects }`. Дерево со счётчиками и варианты пикера |
| `explain` | `{ key: string }` | `{ key, subjects }`. Итоговый доступ активных пользователей и объявленных ролей на выбранный узел |

Узел дерева содержит `key`, `title`, `count`, `address` и `children`. Ключ обозначает место в дереве. У повтора объекта другой ключ и тот же адрес настройки `{ kind, name, path }`. У подсистем и групп меню адрес равен `null`.

Варианты пикера содержат `subjectKind`, `subject` и `title`. В объяснении каждая строка дополнена полем `access`. У узла схемы это уровень и источник, у группы меню это количество доступных и общее количество конечных настроек (`allowed` и `total`).

Отсутствующий или нестроковый ключ даёт 400, неизвестный узел или действие 404. Ответы строятся на текущих назначениях. У отключённых пользователей можно открыть настройки через пикер, но в обзоре и счётчиках они не участвуют.

Пример объяснения подсистемы:

```json
{
  "target": { "kind": "platform", "name": "authorization" },
  "action": "explain",
  "payload": { "key": "subsystem.sales" }
}
```

## Проверка прав

### Почему права проверяются при выполнении операции

Все операции [API данных](single-endpoint.md) приходят на один маршрут, а объект и действие определяет тело запроса. Поэтому проверку выполняет [диспетчер](https://github.com/EGSP/collection-zarplata/blob/main/src/server/data/data.service.ts) после поиска цели, перед каждой операцией, в том числе вложенной.

Права с ролями сравнивает единый [RightsGuardPlatform](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights-guard.platform.ts). Его вызывают диспетчер, проверка отдельных маршрутов и отбор описаний интерфейса. Проверки из кода конфигурации диспетчер тоже передаёт ему, поэтому конфигурация роли пользователя сама не читает.

Вложенная операция выполняется от имени того же пользователя и учитывает только действующие в серверной цепочке явные расширения обработчиков. При отказе API возвращает 403 и откатывает транзакцию всего запроса, включая предшествующие операции пакета. Неизвестные объект и действие возвращают 404 независимо от прав.

Роли пользователя хранятся в табличной части `catalog_users_roles`. Настройки узлов ролей и пользователей хранятся в `platform_access_settings`, расширения обработчиков задаются в коде.

- Изменение кода роли действует после перезапуска; административные настройки узлов учитываются со следующей операции без повторного входа.
- Имя роли, удалённой из конфигурации, прав не даёт. Поэтому при переименовании роли обновите назначения пользователям.
- Платформа читает назначения из базы при каждой проверке, внутри операции через дескриптор текущей транзакции. Права не хранятся в токене, поэтому смена ролей действует без повторного входа.

### Как проверить право в коде конфигурации

Диспетчер проверяет право на действие целиком. Если запрет зависит от данных, его проверяет политика записи, собственное действие или обработчик проведения. Например, документ записывает любой пользователь с правом `write`, а менять отдельное поле может только обладатель особого права. Без проверки в коде запрет обошёл бы прямой запрос `save`.

Функции [модуля проверки прав](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/current-user-rights.ts) возвращают Effect и принимают права из объекта `Rights`:

| Функция | Результат |
|---|---|
| `hasRight(right)` | `true`, если право есть у пользователя, иначе `false`; отсутствие права ошибкой не считается |
| `requireRight(...rights)` | Ничего не возвращает, если есть все права; иначе прерывает действие ошибкой `RightsDeniedError` с первым недостающим правом |

Отказ `requireRight` не отличается от отказа диспетчера: 403 с ключом права в поле `right` и откат транзакции всего запроса. Для запрета с прикладной причиной используйте `hasRight` и ошибку `DataPolicyError` со своим текстом.

Проверка относится к пользователю, отправившему запрос; во вложенном действии это тот же пользователь, у запроса без пользователя прав нет. Роли читаются при каждом вызове, поэтому их изменение действует со следующей проверки.

Ограничения использования:

- Сервис проверки приходит через окружение Effect, поэтому функции работают только в политике записи, собственном действии, обработчике проведения и вызываемом ими коде.
- Обращайтесь к `Rights` внутри обработчика, а не при загрузке модуля: объект прав строится из модулей объектов и к их загрузке ещё не готов.
- Тип `Rights` выводится из типов объектов, поэтому обработчик с `Rights` не должен участвовать в выводе типа своего объекта, иначе проверка типов сообщит о циклической ссылке. Политику объявляйте отдельной константой с явным типом `Policy<…>`. Обработчику действия или проведения в цепочке объявления объекта укажите тип результата: `(input): Effect.Effect<unknown, unknown, unknown> => …`.

```ts
import { Effect } from 'effect';
import { requireRight } from '../../server/authorization/current-user-rights.js';
import type { Policy } from '../../server/metadata/index.js';
import { Rights } from '../configuration.generated.js';

export const sampleCommentRightPolicy: Policy<{ readonly comment: string | null }> = {
    name: 'sample-comment-right',
    save: ({ existingRecord, proposedRecord }) => Effect.gen(function* () {
        if (existingRecord === null || existingRecord.comment === proposedRecord.comment) return;
        yield* requireRight(Rights.document.sample.actions.acceptLines);
    }),
};
```

[Политика пробного документа](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/policies/sample-comment-right.ts): комментарий записанного документа меняет только пользователь с правом на действие «Принять строки». Создание документа с комментарием она не ограничивает.

### Как защитить отдельный маршрут

Для маршрута вне API данных используйте декоратор `@RequireRights(Rights.…)` из [модуля Nest-проверки](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights-guard.nest.ts):

1. Импортируйте `AuthenticationModule` и `AuthorizationModule` в модуль контроллера.
2. Укажите в `@RequireRights(...)` все права маршрута или контроллера; список не может быть пустым.
3. Учтите, что декоратор метода заменяет список прав контроллера целиком.

Декоратор проверяет вход, затем передаёт права в `RightsGuardPlatform` через `RightsGuardNest`. Нужны все перечисленные права, при нехватке маршрут отвечает 403. Подключение проверки без прав считается ошибкой разработчика.

### Как права влияют на интерфейс

`GET /api/metadata` отбирает описания по тем же правам, что и выполнение операций. Объект без права чтения в ответ не входит, у форм остаются только разрешённые действия, а недоступные объекты и страницы убираются и из схемы оболочки.

Без права `open` страницы нет в меню, а её адрес показывает «не найдено». Если право открыть есть, а права на нужный объект нет, запрос данных получает отказ сервера. Скрытие помогает построить интерфейс по правам, но защищает сервер: его проверка действует и при прямом запросе к API. Отбор реализован в [сервисе описаний интерфейса](https://github.com/EGSP/collection-zarplata/blob/main/src/server/ui/ui.service.ts).


## Как изменить настройки в интерфейсе

Выберите пользователя или роль в верхнем пикере. У каждого узла с правом рядом с названием появится тег настройки. Нажмите его и выберите новый вариант. Под вариантами меню указано, какое право действует и в каком узле оно задано. Для фиксированных ролей эта информация доступна в подсказке. Очистите пикер, чтобы вернуться к обзору.

Справа от «Наследовать» серый тег показывает, какое право действует на этом узле. Если подходящего назначения нет, итоговый тег показывает «Запрет», а подсказка поясняет, что доступ закрыт по умолчанию. Названия узлов с наследованием приглушены.

Фиолетовый ромб показывает, что в поддереве есть явные назначения или изменения доступа либо что уровень самого узла отличается от базового. Для пользователя базовый уровень учитывает его роли и общую схему без персональных настроек. Для роли учитывается её описание в конфигурации без сохранённых правок.

У полей и их групп доступны «Наследовать», «Запрет», «Чтение» и «Редактирование». У корня объекта есть также «Полный доступ». У действий, функций, открытия страниц и операций платформы вместо уровней доступа к данным доступно разрешение вызова. Состав вариантов и возможность записи определяет сервер.

Операции цели `platform.authorization`:

| Действие | Payload | Право |
|---|---|---|
| `settings` | Необязательные `subjectKind` (`"role"` или `"user"`) и `subject` | `platform.authorization.read` |
| `saveSettings` | `subjectKind`, `subject`, `kind`, `name`, `path`, `level` | `platform.authorization.write` |

Оба действия возвращают варианты назначения, признаки `readOnly` и `editable`, а также настройки узлов `selected`, допустимые уровни `levels` и итог `effective` с уровнем и источником и признак отличия от базового уровня `differsFromBaseline`. Сервер проверяет цель, узел, уровень и существование назначения. Неизвестные свойства и пути расширений обработчиков отклоняются с 400. Изменение фиксированной роли возвращает 403 с кодом `roleReadOnly`. Фиксированные расширения и внутренние поля в редактор не входят. Изменение административных настроек сбрасывает метаданные текущего клиента.

## Доступ к встроенному справочнику пользователей

`Users` из `src/server/users/object.ts` подключается к `accessSchema` тем же способом, что прикладные справочники. Группа `account` содержит имя, `authorization` дату отключения и роли; отдельная колонка имеет путь `roles.role`. Сервер применяет общую проверку `writableInput` и к прямому `save`: пропуск защищённых данных сохраняет прежнее значение, изменение даёт 403 до адаптера хранения. Группы не зависят от вкладок формы.

`setPin`, `revokeSession`, `sessions` и `roleOptions` объявляют пустые расширения: вызов не добавляет пользователю полномочий на другие объекты. Первые два являются действиями, вторые функциями. Разрешение редактирования данных не разрешает их автоматически. PIN и HMAC отсутствуют в публичной схеме, поэтому полный доступ не открывает их через чтение, метаданные, функции или журнал. Служебные таблицы читает только доверенный адаптер платформы, а обработчики конфигурации по-прежнему получают проверяемый `ReadonlyDatabase`.

Продавцу доступна функция `sale.periodFigures`, которую используют сводки. Форма возврата получает условия и план через `refund.settlementTerms`. Самостоятельные вызовы функций `refund.figures` и `refund.refundPlan` доступны администратору.
