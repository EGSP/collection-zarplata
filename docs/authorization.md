# Права (RBAC)

Конфигурация задаёт роли как наборы прав, а платформа проверяет права пользователя перед выполнением действий. Разработчик конфигурации выбирает разрешённые операции и описывает роли; разработчик платформы подключает проверку к новым маршрутам.

## Права

### Права объектов

Каждый объект конфигурации получает стандартные права своего вида, а каждое собственное действие получает отдельное право. Объявлять права вручную не требуется. Соответствие действий и прав задано в [модуле прав](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights.ts):

| Право | Виды объектов | Разрешённые действия |
|---|---|---|
| `read` | справочник, документ, регистр сведений | `list`, `get` |
| `read` | регистр движений | `list`, `totals` |
| `write` | справочник | `save`, `markDeleted`, `unmarkDeleted`, `import` |
| `write` | документ | `save`, `markDeleted`, `unmarkDeleted` |
| `write` | регистр сведений | `save`, `delete` |
| `post` | документ | `post`, `unpost` |
| `actions.<имя>` | справочник, документ | собственное действие с этим именем |

Право записи документа не включает проведение и его отмену: для них требуется `post`. Право на собственное действие разрешает вызвать его обработчик; вложенные операции через диспетчер требуют своих прав. Условие, которое зависит от данных записи, конфигурация [проверяет в своём коде](#как-проверить-право-в-коде-конфигурации).

### Права страниц и платформы

| Право | Ключ | Назначение |
|---|---|---|
| `Rights.page.<имя>.open` | `page.<имя>.open` | Видимость страницы конфигурации в описаниях интерфейса и возможность открыть её адрес |
| `Rights.platform.journal.read` | `platform.journal.read` | Чтение журнала изменений всех объектов |
| `Rights.platform.documents.repost` | `platform.documents.repost` | [Перепроведение](single-endpoint.md#перепроведение-документов) всех проведённых документов |

Право открыть страницу не даёт прав на данные, которые она читает или изменяет. Для этих операций нужны права соответствующих объектов. Чтение журнала тоже назначается отдельно и не следует из права чтения объекта. Перепроведение заменяет движения документов всех видов без политик проведения, поэтому право `post` отдельных документов его не разрешает.

### Объект Rights

В конфигурации права указываются через `Rights`, например `Rights.catalog.employees.read`, `Rights.document.shift.post` или `Rights.catalog.employees.actions.dismiss`. У каждого права есть ключ, например `catalog.employees.write`; проверка сравнивает права по ключам.

Генератор реестра включает в `configuration.generated.ts` построение `Rights` из модулей объектов и объявлений страниц. TypeScript выводит тип `Rights` из типов билдеров: ссылка на право несуществующего объекта, действия или страницы приводит к ошибке компиляции. Порядок генерации описан в разделе [«Метаданные»](metadata.md).

## Роли

### Как добавить роль

Для новой роли уже должны быть объявлены объекты, действия и страницы, доступ к которым она разрешает.

1. В [описании ролей конфигурации](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/roles.ts) добавьте билдер в экспортируемый массив `roles`. Задайте уникальное имя и название для интерфейса.
2. Перечислите права через `grant(...)`. Для роли с полным доступом используйте `grantAll()`: она получит и права, которые появятся в конфигурации позже.
3. Если роль открывает страницу, включите право страницы и права на нужные ей операции с данными. Если собственное действие обращается к другим объектам через диспетчер, включите права на эти вложенные операции.

Например, роль для чтения сотрудников и смен описывается так:

```ts
import { role } from '../server/authorization/roles.js';
import { Rights } from './configuration.generated.js';

export const roles = [
    role('administrator').title('Администратор').grantAll(),
    role('reader')
        .title('Только чтение')
        .grant(Rights.catalog.employees.read, Rights.document.shift.read),
];
```

Это пример состава ролей; при добавлении роли сохраняйте остальные элементы существующего массива.

После правки проверьте типы и перезапустите приложение. Для проверки ограниченного доступа запустите приложение в режиме памяти с пользователем, которому назначена только новая роль, как описано в разделе [«Сборка и запуск»](build-and-launch.md). Убедитесь, что разрешённые операции выполняются, а прямой запрос к запрещённой операции получает 403. Для страницы отдельно проверьте её видимость и доступ к данным.

### Контракт роли

| Объявление | Поведение |
|---|---|
| `role(name)` | Создаёт роль с указанным именем |
| `.title(title)` | Задаёт название для интерфейса; без него используется имя роли |
| `.grant(...rights)` | Добавляет перечисленные права к уже заданным |
| `.grantAll()` | Даёт все права, включая права будущих объектов, действий, страниц и платформы |

Имя роли пишется латиницей в lowerCamelCase: начинается со строчной буквы и содержит только буквы и цифры. Имена ролей не повторяются. Неверное имя или повтор останавливают запуск до приёма запросов. Контракт билдеров описан в [модуле ролей](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/roles.ts).

Пользователю можно назначить несколько ролей; его права являются объединением их прав. У пользователя без ролей прав нет. Конфигурация содержит следующие роли:

| Имя | Название и права |
|---|---|
| `administrator` | «Администратор»: полный доступ, включая будущие объекты и действия |
| `seller` | «Продавец»: рабочее место продавца; чтение прикладных справочников и запись физических лиц; чтение, запись и проведение смен, продаж, отвесов, возвратов и рассрочек по продажам; закрытие смены, выкуп отвеса, оформление рассрочки из продажи, продажа с рассрочкой и взнос рассрочки по продаже; чтение справочника «Ставки по рассрочке»; чтение регистров продаж, расчётов с покупателями, поступлений денег и рассрочек по продажам; открытие страниц «Зарплата» и «Сводка за период», чтение закрытий периода и действия «Расчёт зарплаты» и «Сводка за период». Права закрыть рассрочку и закрыть период у роли нет. Приёмники оплат роль читает, но не изменяет |
| `reader` | «Только чтение»: явно перечисленные права чтения, в том числе справочника «Ставки по рассрочке», и открытия рабочего места продавца |
| `sampleEditor` | «Запись пробного документа»: запись пробного документа без права на его собственное действие |
| `sampleDocumentReader` | «Чтение пробного документа без справочников»: чтение пробного документа и пробного регистра без пробных справочников; на ней проверяется показ ссылок на недоступный объект |

Продавцу не разрешены закрытие рассрочки, закрытие периода и пробные объекты. Политика рассрочки проверяет право закрытия и при прямом `save` с датой закрытия: право записи не позволяет обойти запрет. Условие об ответственном сотруднике и остальные правила рассрочки описаны в [«Правилах учёта»](accounting-rules.md#рассрочка-по-продаже), правила закрытия периода в разделе [«Закрытие периода»](accounting-rules.md#закрытие-периода).

Роли назначаются при создании первого пользователя из настроек и тестовых пользователей режима памяти. Параметры назначения описаны в разделах [«Вход в приложение»](authentication.md) и [«Сборка и запуск»](build-and-launch.md).

## Проверка прав

### Почему права проверяются при выполнении операции

Все операции [API данных](single-endpoint.md) поступают на один маршрут. Объект и действие определяются телом запроса, поэтому проверка выполняется в диспетчере после поиска цели. Единый механизм сравнения прав с ролями пользователя реализован в [RightsGuardPlatform](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights-guard.platform.ts); его вызывают диспетчер, проверка отдельных маршрутов и отбор описаний интерфейса. Ему же диспетчер передаёт проверки из кода конфигурации, поэтому конфигурация не читает роли пользователя сама.

[Диспетчер](https://github.com/EGSP/collection-zarplata/blob/main/src/server/data/data.service.ts) проверяет право перед каждой операцией, в том числе вложенной. Вложенная операция выполняется от имени того же пользователя. Например, право вызвать собственное действие не разрешает ему читать другой справочник через диспетчер, если у пользователя нет права чтения этого справочника. При отказе API возвращает 403 и откатывает транзакцию всего запроса, включая предшествующие операции пакета. Неизвестные объект конфигурации и действие объекта возвращают 404 независимо от прав пользователя.

Связь пользователя с ролями хранится в таблице `platform_user_roles` по именам ролей; сами наборы прав задаёт конфигурация. Изменение состава роли действует на всех её пользователей после перезапуска. Если роль удалена из конфигурации, оставшееся в базе имя не даёт прав. Поэтому переименование роли требует обновления её назначений пользователям.

При каждой проверке платформа читает назначения ролей из базы. Внутри операции чтение использует дескриптор текущей транзакции и видит те же данные, что и действие. Права не хранятся в токене: изменение назначения ролей учитывается при следующей проверке без повторного входа.

### Как проверить право в коде конфигурации

Диспетчер проверяет право на действие целиком. Если запрет зависит от данных, его проверяет политика записи, собственное действие или обработчик проведения. Например, документ записывает каждый пользователь с правом `write`, а изменить в нём отдельное поле может только пользователь с особым правом. Без такой проверки пользователь с правом записи обошёл бы запрет прямым запросом `save`.

Функции [модуля проверки прав](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/current-user-rights.ts) возвращают Effect и принимают права из объекта `Rights`:

| Функция | Результат |
|---|---|
| `hasRight(right)` | `true`, если право есть у пользователя, иначе `false`; отсутствие права ошибкой не считается |
| `requireRight(...rights)` | Завершается без значения, если у пользователя есть все перечисленные права. Иначе прерывает действие ошибкой `RightsDeniedError` с первым недостающим правом |

Отказ `requireRight` не отличается от отказа диспетчера: API возвращает 403 с ключом права в поле `right` и откатывает транзакцию всего запроса. Для запрета с прикладной причиной вместо него используйте `hasRight` и ошибку `DataPolicyError` со своим текстом.

Проверка относится к пользователю, который отправил запрос. Во вложенном действии это тот же пользователь, что и во внешнем; у запроса без пользователя прав нет. Роли читаются при каждом вызове в транзакции действия, поэтому изменение ролей действует со следующей проверки.

Сервис проверки диспетчер передаёт через окружение Effect, поэтому функции работают только в политике записи, собственном действии, обработчике проведения и коде, который они вызывают. Обращайтесь к `Rights` внутри обработчика, а не при загрузке модуля: объект прав строится из модулей объектов конфигурации и к моменту их загрузки ещё не готов.

Тип `Rights` выводится из типов объектов, поэтому обработчик с обращением к `Rights` не должен участвовать в выводе типа своего объекта. Иначе проверка типов сообщает, что объект и `Rights` ссылаются сами на себя. Политику объявляйте отдельной константой с явным типом `Policy<…>`. Обработчику собственного действия или проведения, записанному в цепочке объявления объекта, укажите тип результата: `(input): Effect.Effect<unknown, unknown, unknown> => …`.

```ts
import { Effect } from 'effect';
import { requireRight } from '../../server/authorization/current-user-rights.js';
import type { Policy } from '../../server/metadata/index.js';
import { Rights } from '../configuration.generated.js';

export const sampleCommentRight: Policy<{ readonly comment: string | null }> = {
    name: 'sample-comment-right',
    save: ({ existingRecord, proposedRecord }) => Effect.gen(function* () {
        if (existingRecord === null || existingRecord.comment === proposedRecord.comment) return;
        yield* requireRight(Rights.document.sample.actions.acceptLines);
    }),
};
```

Это [политика пробного документа](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/policies/sample-comment-right.ts): комментарий записанного документа меняет только пользователь с правом на действие «Принять строки». Создание документа с комментарием она не ограничивает.

### Как защитить отдельный маршрут

Для маршрута вне API данных используйте декоратор `@RequireRights(Rights.…)` из [модуля Nest-проверки](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights-guard.nest.ts):

1. Импортируйте `AuthenticationModule` и `AuthorizationModule` в модуль контроллера.
2. Укажите в `@RequireRights(...)` все права, которые требуются для маршрута или контроллера. Список должен быть непустым.
3. Если на контроллере уже задан список прав, учитывайте, что декоратор метода заменяет его целиком.

Декоратор сначала проверяет вход, затем передаёт перечисленные права в `RightsGuardPlatform` через `RightsGuardNest`. Пользователь должен иметь каждое из них. При недостатке прав маршрут отвечает 403. Подключение Nest-проверки без прав считается ошибкой разработчика.

### Как права влияют на интерфейс

`GET /api/metadata` отбирает описания по тем же правам, которые использует выполнение операций. Объект без права чтения не входит в ответ; из действий формы остаются только разрешённые. Страница включается только при наличии права её открыть. Недоступные объекты и страницы убираются и из схемы оболочки.

Без права `open` страницы нет в меню, а её адрес показывает «не найдено». Если право открыть страницу есть, но нужного права на объект нет, запрос данных получает отказ сервера. Отбор описаний и скрытие кнопок помогают построить интерфейс по правам пользователя; проверка операции на сервере действует и при прямом запросе к API. Реализация отбора находится в [сервисе описаний интерфейса](https://github.com/EGSP/collection-zarplata/blob/main/src/server/ui/ui.service.ts).
