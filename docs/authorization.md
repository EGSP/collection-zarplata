# Права (RBAC)

При [открытии существующей записи](interface.md#открытие-существующей-записи) операция `platform.records.resolveOpening` проверяет чтение исходной записи и каждой цели правила. Отсутствие чтения конечной продажи даёт 403, без открытия исходной рассрочки. Режим оригинала (`original: true`, в адресе `?original=1`) пропускает правило, но требует чтения исходной записи.

Конфигурация описывает роли как наборы прав, платформа проверяет права пользователя перед каждой операцией. Разработчик конфигурации составляет роли; разработчик платформы подключает проверку к новым маршрутам.

## Права

### Права объектов

Права не объявляются вручную: объект получает стандартные права своего вида, а каждое собственное действие получает отдельное право. Соответствие действий и прав задано в [модуле прав](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights.ts):

| Право | Виды объектов | Разрешённые действия |
|---|---|---|
| `read` | справочник, документ | `list`, `get`, `lookup` |
| `read` | регистр сведений | `list`, `get` |
| `read` | регистр движений | `list`, `totals` |
| `write` | справочник | `save`, `markDeleted`, `unmarkDeleted`, `import` |
| `write` | документ | `save`, `markDeleted`, `unmarkDeleted` |
| `write` | регистр сведений | `save`, `delete` |
| `post` | документ | `post`, `unpost` |
| `actions.<имя>` | справочник, документ | собственное действие с этим именем |

- Право записи документа не включает проведение и его отмену: для них нужно `post`.
- Право на собственное действие разрешает вызвать только его обработчик; вложенные операции через диспетчер требуют своих прав.
- Условие, которое зависит от данных записи, конфигурация [проверяет в своём коде](#как-проверить-право-в-коде-конфигурации).

### Права страниц и платформы

| Право | Ключ | Назначение |
|---|---|---|
| `Rights.page.<имя>.open` | `page.<имя>.open` | Видимость страницы конфигурации в описаниях интерфейса и возможность открыть её адрес |
| `Rights.platform.journal.read` | `platform.journal.read` | Чтение журнала изменений всех объектов |
| `Rights.platform.documents.repost` | `platform.documents.repost` | [Перепроведение](single-endpoint.md#перепроведение-документов) всех проведённых документов |
| `Rights.platform.users.read` | `platform.users.read` | Чтение служебного справочника пользователей и вариантов ролей без секретов |
| `Rights.platform.users.write` | `platform.users.write` | Создание и изменение учётных записей, назначение ролей, смена PIN и отключение |
| `Rights.platform.authorization.read` | `platform.authorization.read` | Просмотр полного дерева прав, числа пользователей и всех ролей-оснований |
| `Rights.platform.backups.read` | `platform.backups.read` | Просмотр [резервных копий](backup.md#api-и-права): список, диск, расписание, идущие копии |
| `Rights.platform.backups.write` | `platform.backups.write` | Создание и прерывание резервных копий |

- Право открыть страницу не даёт прав на данные, которые она читает или изменяет: для них нужны права объектов.
- Журнал показывает изменения всех объектов, поэтому его чтение не следует из права чтения объекта.
- Перепроведение заменяет движения документов всех видов без политик проведения, поэтому право `post` отдельных документов его не разрешает.
- Резервная копия содержит всю базу, поэтому её просмотр и создание не следуют из прав объектов. В дереве прав они стоят в узле «Платформа» под заголовком «Резервные копии»; роль администратора получает их вместе с остальными.

### Объект Rights

Конфигурация ссылается на права через `Rights`: `Rights.catalog.employees.read`, `Rights.document.shift.post`, `Rights.catalog.employees.actions.dismiss`. У права есть ключ (`catalog.employees.write`), по ключам проверка и сравнивает права.

Генератор реестра строит `Rights` в `configuration.generated.ts` из модулей объектов и объявлений страниц. Тип `Rights` выводится из типов билдеров, поэтому право несуществующего объекта, действия или страницы не компилируется. Порядок генерации описан в разделе [«Метаданные»](metadata.md).

## Роли

### Как добавить роль

Объекты, действия и страницы, к которым роль даёт доступ, должны быть уже объявлены.

1. В [описании ролей конфигурации](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/roles.ts) добавьте билдер в экспортируемый массив `roles`. Задайте уникальное имя и название для интерфейса.
2. Перечислите права через `grant(...)`. Роли с полным доступом подойдёт `grantAll()`: она получит и права, которые появятся позже.
3. Для страницы добавьте право страницы и права на её операции с данными. Если собственное действие обращается к другим объектам через диспетчер, добавьте права на эти вложенные операции.

Роль для чтения сотрудников и смен:

```ts
import { role } from '../server/authorization/roles.js';
import { Rights } from './configuration.generated.js';

export const roles = [
    role('administrator').title('Администратор').grantAll(),
    role('reader')
        .title('Только чтение')
        .grant(Rights.catalog.employees.read, Rights.document.shift.read),
];
```

Это упрощённый пример: в реальном файле сохраняйте остальные роли массива.

После правки проверьте типы и перезапустите приложение. Для проверки запустите режим памяти с пользователем, у которого только новая роль ([«Сборка и запуск»](build-and-launch.md)). Разрешённые операции должны выполняться, а прямой запрос к запрещённой операции получать 403. У страницы отдельно проверьте видимость и доступ к данным.

### Контракт роли

| Объявление | Поведение |
|---|---|
| `role(name)` | Создаёт роль с указанным именем |
| `.title(title)` | Задаёт название для интерфейса; без него используется имя роли |
| `.grant(...rights)` | Добавляет перечисленные права к уже заданным |
| `.grantAll()` | Даёт все права, включая права будущих объектов, действий, страниц и платформы |

Имя роли пишется латиницей в lowerCamelCase и не повторяется. Неверное имя или повтор останавливают запуск до приёма запросов. Билдеры описаны в [модуле ролей](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/roles.ts).

Пользователю можно назначить несколько ролей: его права объединяют права всех ролей. Без ролей прав нет. Конфигурация содержит роли:

| Имя | Название и права |
|---|---|
| `administrator` | «Администратор»: полный доступ, включая будущие объекты и действия |
| `accessAuditor` | «Просмотр прав доступа»: открытие страницы «Права доступа», полное дерево и объяснение доступа пользователей. Не разрешает чтение прикладных данных и изменение учётных записей |
| `seller` | «Продавец»: рабочее место продавца; чтение прикладных справочников и запись физических лиц; чтение, запись и проведение смен, продаж, отвесов, возвратов и рассрочек по продажам; закрытие смены, выкуп отвеса, продажа с рассрочкой, взнос рассрочки по продаже, изменение продажи вместе с рассрочками и отмена продажи; чтение справочника «Ставки по рассрочке»; чтение регистров продаж, расчётов с покупателями, поступлений денег и рассрочек по продажам; открытие страниц «Зарплата» и «Сводка за период», чтение закрытий периода и действия «Расчёт зарплаты» и «Сводка за период». Права закрыть рассрочку и закрыть период у роли нет. Приёмники оплат роль читает, но не изменяет |
| `reader` | «Только чтение»: явно перечисленные права чтения, в том числе справочника «Ставки по рассрочке», и открытия рабочего места продавца |
| `sampleEditor` | «Запись пробного документа»: запись пробного документа без права на его собственное действие |
| `sampleDocumentReader` | «Чтение пробного документа без справочников»: чтение пробного документа и пробного регистра без пробных справочников; на ней проверяется показ ссылок на недоступный объект |

Продавцу не разрешены закрытие рассрочки, закрытие периода и пробные объекты. Политика рассрочки проверяет право закрытия и при прямом `save` с датой закрытия, поэтому право записи запрет не обходит. Правила рассрочки, в том числе условие об ответственном сотруднике, описаны в [«Правилах учёта»](accounting-rules.md#рассрочка-по-продаже), правила закрытия периода: [«Закрытие периода»](accounting-rules.md#закрытие-периода).

Роли назначаются в [карточке пользователя](authentication.md#как-создать-и-изменить-пользователя), первому пользователю из настроек и тестовым пользователям режима памяти. Порядок тестового запуска описан в разделе [«Сборка и запуск»](build-and-launch.md). Право управления пользователями позволяет назначить в том числе полный доступ, поэтому его следует выдавать только администраторам учётных записей.

## Как посмотреть доступ пользователей

Откройте «Администрирование → Учётные записи → Права доступа». Нужны право страницы `Rights.page.accessRights.open` и право данных `Rights.platform.authorization.read`; готовая роль `accessAuditor` содержит оба. Полный доступ администратора тоже разрешает просмотр.

Дерево повторяет подсистемы и их группы из `src/configuration/shell.ts`: например, «Продажи → Документы → Продажа → Чтение». В него входят справочники, документы, регистры движений и сведений, страницы и служебные права платформы. Объекты и страницы вне меню собраны в «Прочем», служебные права в «Платформе». Используется полная схема конфигурации без отбора по правам просматривающего. Число в скобках есть у каждого узла, включая `(0)`.

Стрелка раскрывает дочерние узлы. Нажатие на название открывает справа два независимо прокручиваемых списка: «Пользователи» и «Роли». У права показаны активные пользователи и все их роли-основания, а отдельный список ролей включает все разрешающие роли конфигурации, даже никому не назначенные. У объекта, группы или подсистемы показаны доступные каждому пользователю и каждой роли права; раскройте строку права у пользователя, чтобы увидеть основания. Роль с полным доступом помечена словами «полный доступ». Поиск по названию подсистемы, группы, объекта, права или ключу отбирает совпадения и раскрывает путь к ним. Если найден объект, видны все его дочерние права.

### Как считаются пользователи

Источник подсчёта: активные учётные записи входа и назначенные им роли, те же, что в [справочнике пользователей](authentication.md#как-создать-и-изменить-пользователя). Справочник сотрудников в подсчёте не участвует. У конечного права пользователь учитывается один раз, даже если его разрешают несколько ролей. У объекта или группы считается объединение пользователей дочерних прав, поэтому счётчики детей не складываются.

Объект, включённый в несколько групп или подсистем, показан в каждом месте. Его повтор не увеличивает число пользователей подсистемы и не дублирует право в её объяснении. Счётчик дерева относится к пользователям; число ролей показано отдельно в заголовке списка ролей и не зависит от наличия пользователей.

Отключённые учётные записи исключены. Назначение роли, которой больше нет в конфигурации, прав не даёт. Полный доступ разрешает все конечные права и учитывается один раз в каждом узле. Счётчики и объяснение используют тот же механизм сравнения прав с ролями, что и проверка выполнения операций.

Например, Иван имеет роли чтения и записи продаж, Анна только чтения, а Пётр с обеими ролями отключён. Если других пользователей с доступом нет, у чтения будет `(2)`, у записи `(1)`, у объекта «Продажа» `(2)`. Дополнительная роль чтения Ивана счётчик не увеличит, но появится в объяснении вторым основанием.

Экран объясняет разрешения по ролям. Политики записи, закрытый период и права на вложенные операции могут дополнительно ограничить действие над конкретной записью. Редактирование состава прав ролей на этом экране не предусмотрено.

### API дерева и объяснения

Действия идут через [API данных](single-endpoint.md) с целью `{ "kind": "platform", "name": "authorization" }`. Оба требуют `platform.authorization.read`; без него ответ `403`, без входа `401`. Чтение дерева не требует прав на перечисленные объекты и возвращает полный состав метаданных сервера, независимо от обычного отбора `GET /api/metadata`. Это право открывает сведения о доступе других пользователей ко всем объектам, поэтому назначайте его тем, кому разрешён такой просмотр.

| Действие | Вход (`payload`) | Ответ |
|---|---|---|
| `tree` | Не требуется | `{ nodes: AccessNode[] }`: полное дерево со счётчиками |
| `explain` | `{ key: string }` | `{ node, users, roles }`: выбранный узел без `children`, пользователи с доступом и разрешающие роли конфигурации |

Узел: `{ key, title, count, right, children }`. `right` содержит ключ конечного права, у объекта или группы `null`; у листа `children: []`. `key` обозначает место в дереве и берётся из ответа `tree`: у повторов объекта разные ключи, но одинаковые `right`. Например, `right: "document.sale.read"` обозначает право чтения продажи, а подсистема продаж имеет `key: "subsystem.sales"`.

У пользователей в объяснении поля `{ guid, name, rights }`; право описывается как `{ key, title, roles }`, где `key` является ключом права, `title` содержит путь от подсистемы, а роли как `{ name, title, all }`. Отдельный массив `roles` содержит `{ name, title, all, rights }`; его `rights` перечисляет разрешённые права выбранного узла в виде `{ key, title }`, независимо от назначения роли пользователям.

Отсутствующий или нестроковый ключ даёт `400`, неизвестный узел или действие `404`. Нулевой узел остаётся в дереве; его объяснение возвращает `users: []`, но `roles` может быть непустым. PIN, HMAC, сессии и отключённые пользователи в ответы не входят. Чтение ничего не записывает в журнал. Каждый ответ строится в транзакции на текущих назначениях; последующие изменения ролей или состояния пользователя учитываются при следующем запросе.

Пример объяснения подсистемы:

```json
{
  "target": { "kind": "platform", "name": "authorization" },
  "action": "explain",
  "payload": { "key": "subsystem.sales" }
}
```

## Проверка прав

### Почему права проверяются при выполнении операции

Все операции [API данных](single-endpoint.md) приходят на один маршрут, а объект и действие определяет тело запроса. Поэтому проверку выполняет [диспетчер](https://github.com/EGSP/collection-zarplata/blob/main/src/server/data/data.service.ts) после поиска цели, перед каждой операцией, в том числе вложенной.

Права с ролями сравнивает единый [RightsGuardPlatform](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights-guard.platform.ts). Его вызывают диспетчер, проверка отдельных маршрутов и отбор описаний интерфейса. Проверки из кода конфигурации диспетчер тоже передаёт ему, поэтому конфигурация роли пользователя сама не читает.

Вложенная операция выполняется от имени того же пользователя: право вызвать действие не разрешает читать другой справочник без права его чтения. При отказе API возвращает 403 и откатывает транзакцию всего запроса, включая предшествующие операции пакета. Неизвестные объект и действие возвращают 404 независимо от прав.

Роли пользователя хранятся в таблице `platform_user_roles` по именам; наборы прав задаёт конфигурация.

- Изменение состава роли действует после перезапуска.
- Имя роли, удалённой из конфигурации, прав не даёт. Поэтому при переименовании роли обновите назначения пользователям.
- Платформа читает назначения из базы при каждой проверке, внутри операции через дескриптор текущей транзакции. Права не хранятся в токене, поэтому смена ролей действует без повторного входа.

### Как проверить право в коде конфигурации

Диспетчер проверяет право на действие целиком. Если запрет зависит от данных, его проверяет политика записи, собственное действие или обработчик проведения. Например, документ записывает любой пользователь с правом `write`, а менять отдельное поле может только обладатель особого права. Без проверки в коде запрет обошёл бы прямой запрос `save`.

Функции [модуля проверки прав](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/current-user-rights.ts) возвращают Effect и принимают права из объекта `Rights`:

| Функция | Результат |
|---|---|
| `hasRight(right)` | `true`, если право есть у пользователя, иначе `false`; отсутствие права ошибкой не считается |
| `requireRight(...rights)` | Ничего не возвращает, если есть все права; иначе прерывает действие ошибкой `RightsDeniedError` с первым недостающим правом |

Отказ `requireRight` не отличается от отказа диспетчера: 403 с ключом права в поле `right` и откат транзакции всего запроса. Для запрета с прикладной причиной используйте `hasRight` и ошибку `DataPolicyError` со своим текстом.

Проверка относится к пользователю, отправившему запрос; во вложенном действии это тот же пользователь, у запроса без пользователя прав нет. Роли читаются при каждом вызове, поэтому их изменение действует со следующей проверки.

Ограничения использования:

- Сервис проверки приходит через окружение Effect, поэтому функции работают только в политике записи, собственном действии, обработчике проведения и вызываемом ими коде.
- Обращайтесь к `Rights` внутри обработчика, а не при загрузке модуля: объект прав строится из модулей объектов и к их загрузке ещё не готов.
- Тип `Rights` выводится из типов объектов, поэтому обработчик с `Rights` не должен участвовать в выводе типа своего объекта, иначе проверка типов сообщит о циклической ссылке. Политику объявляйте отдельной константой с явным типом `Policy<…>`. Обработчику действия или проведения в цепочке объявления объекта укажите тип результата: `(input): Effect.Effect<unknown, unknown, unknown> => …`.

```ts
import { Effect } from 'effect';
import { requireRight } from '../../server/authorization/current-user-rights.js';
import type { Policy } from '../../server/metadata/index.js';
import { Rights } from '../configuration.generated.js';

export const sampleCommentRightPolicy: Policy<{ readonly comment: string | null }> = {
    name: 'sample-comment-right',
    save: ({ existingRecord, proposedRecord }) => Effect.gen(function* () {
        if (existingRecord === null || existingRecord.comment === proposedRecord.comment) return;
        yield* requireRight(Rights.document.sample.actions.acceptLines);
    }),
};
```

[Политика пробного документа](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/policies/sample-comment-right.ts): комментарий записанного документа меняет только пользователь с правом на действие «Принять строки». Создание документа с комментарием она не ограничивает.

### Как защитить отдельный маршрут

Для маршрута вне API данных используйте декоратор `@RequireRights(Rights.…)` из [модуля Nest-проверки](https://github.com/EGSP/collection-zarplata/blob/main/src/server/authorization/rights-guard.nest.ts):

1. Импортируйте `AuthenticationModule` и `AuthorizationModule` в модуль контроллера.
2. Укажите в `@RequireRights(...)` все права маршрута или контроллера; список не может быть пустым.
3. Учтите, что декоратор метода заменяет список прав контроллера целиком.

Декоратор проверяет вход, затем передаёт права в `RightsGuardPlatform` через `RightsGuardNest`. Нужны все перечисленные права, при нехватке маршрут отвечает 403. Подключение проверки без прав считается ошибкой разработчика.

### Как права влияют на интерфейс

`GET /api/metadata` отбирает описания по тем же правам, что и выполнение операций. Объект без права чтения в ответ не входит, у форм остаются только разрешённые действия, а недоступные объекты и страницы убираются и из схемы оболочки.

Без права `open` страницы нет в меню, а её адрес показывает «не найдено». Если право открыть есть, а права на нужный объект нет, запрос данных получает отказ сервера. Скрытие помогает построить интерфейс по правам, но защищает сервер: его проверка действует и при прямом запросе к API. Отбор реализован в [сервисе описаний интерфейса](https://github.com/EGSP/collection-zarplata/blob/main/src/server/ui/ui.service.ts).
