# Версии

У приложения две независимые версии вида `x.y.z`: версия платформы (сервер, клиент, SDK) и версия конфигурации (объекты, роли и правила магазина). По номерам видно, можно ли открыть базу новой или старой сборкой без потери данных. Страница описывает правила номеров, проверку при запуске и порядок выпуска релиза.

## Что означают числа

| Число | Когда растёт |
|---|---|
| `x` | Изменение серьёзно ломает совместимость с прежними версиями |
| `y` | Изменение требует миграции базы |
| `z` | Исправления и прочие изменения, не затрагивающие структуру базы |

Любое изменение структуры относится к `y`, в том числе автоматически добавляемые колонки и таблицы: база, записанная новой сборкой, содержит элементы, которых не знает старая, и старая сборка на ней не запустится. Версии платформы и конфигурации повышаются отдельно: часть, которая не менялась, сохраняет номер.

Версия повышается в коммите релиза, а не в рабочих ветках. Иначе параллельные ветки конфликтовали бы из-за одного и того же номера.

## Где задаются и где видны версии

Версии заданы константами в коде, а не в `package.json`: исполняемому файлу этот файл недоступен.

| Часть | Константа | Файл |
|---|---|---|
| Платформа | `platformVersion` | [`src/server/versions/versions.ts`](https://github.com/EGSP/collection-zarplata/blob/main/src/server/versions/versions.ts) |
| Конфигурация | `configurationVersion` | [`src/configuration/version.ts`](https://github.com/EGSP/collection-zarplata/blob/main/src/configuration/version.ts) |

Каждая константа содержит поле `version` и поле `compatibleFrom`. Текущие значения: обе версии `1.0.0`, `compatibleFrom` тоже `1.0.0`.

Глобальный `MetadataModule` экспортирует токен `VersionInformation` с одним `useValue`-провайдером. Его поля `platform` и `configuration` содержат версии с границами совместимости, `current` содержит пару строк для HTTP-ответов. Контроллер состояния, синхронизация базы и interceptor получают эти сведения через `@Inject(VersionInformation)`. Обычные константы остаются доступны без Nest для сборки клиента, упаковщика и раннего вывода журнала до создания контейнера DI.

Версии показаны в таких местах:

- на экране входа и внизу развёрнутой боковой панели показаны версии сборки клиента (в свёрнутой полосе иконок их нет); они встроены при сборке и не зависят от доступности и версии сервера;
- первой строкой журнала запуска, до проверки базы, поэтому они видны и при отказе запуска;
- в ответе открытого запроса `GET /api/health`:

  ```json
  { "status": "ok", "versions": { "platform": "1.0.0", "configuration": "1.0.0" }, "testEnvironment": true }
  ```

- в имени архива комплекта: скрипт `npm run build:executable` в конце печатает `collection-zarplata_portable_platform-<x.y.z>_configuration-<x.y.z>.zip`. Сам архив собирают вручную.

## Обновление открытой страницы

После обновления сервера открытая вкладка может продолжать работать со старым клиентом. При любом различии версии платформы или конфигурации, включая `z` и откат сервера, поверх приложения появляется окно «Вышло обновление». Оно работает и на экране входа.

Кнопка «Обновить страницу» перезагружает вкладку. Несохранённые изменения при этом теряются, поэтому окно можно закрыть и сначала закончить работу. После закрытия предложение не повторяется для той же пары версий сервера. Другая пара версий снимает отказ и показывает окно снова. Если сервер вернулся к версиям клиента, запись об обновлении удаляется, а открытое окно закрывается. Состояние хранится только в памяти каждой вкладки.

### Как клиент получает версии сервера

Глобальный `VersionsInterceptor`, зарегистрированный через `APP_INTERCEPTOR`, добавляет в ответы контроллеров API заголовок `x-application-versions` с JSON:

```json
{ "platform": "1.0.0", "configuration": "1.0.0" }
```

Заголовок устанавливается до вызова обработчика и сохраняется в ответах без тела и при ошибках внутри обработки запроса. Отказы guard'ов, например `401` без сессии на запрос метаданных, происходят раньше interceptor и заголовка не содержат. Это допустимо: открытый `GET /api/health` сообщает версии и без входа. Хук Fastify для передачи версий не используется.

Перехватчики axios читают заголовок у запросов данных, входа, обновления токенов и повторов запросов. Отсутствующий или некорректный заголовок и отсутствие ответа при ошибке сети не меняют запись об обновлении. Тело ответа `/api/health` само по себе не используется для сравнения.

Простаивающая вкладка дополнительно запрашивает `GET /api/health` при фокусе окна, возврате вкладки из фона (`visibilitychange`) и восстановлении сети (`online`). На все эти события действует один предел: не больше одной проверки в минуту. Отдельного опроса по таймеру нет. Проверка не требует входа и не меняет состояние сессии.

## Что значит compatibleFrom

`compatibleFrom` задаёт самую раннюю версию части, чью базу принимает сборка. База более ранней версии могла пройти не все миграции, цепочка от неё не проверялась, поэтому её нужно сначала обновить промежуточным релизом.

Для текущих сборок обе части совместимы только с `1.0.0`. База от сборок, выпущенных до введения версий, не содержит записи о версиях и принимается: её проверяют обычные проверки снимка структуры и журнала миграций.

`compatibleFrom` повышают в коммите релиза, когда миграции от старых версий удалены или перестали поддерживаться.

## Проверка при запуске

В базе хранится таблица `platform_versions` ([служебные таблицы](database.md#служебные-таблицы)): одна строка с версиями сборки, которая последней открыла базу. Проверка выполняется до сверки структуры, чтобы старая сборка назвала причину, а не жаловалась на незнакомые миграции. Платформа и конфигурация проверяются раздельно.

| Условие | Результат |
|---|---|
| Строки версий нет (база от сборки без версий) | База принимается |
| Числа `x.y` в базе новее, чем в сборке | Запуск останавливается |
| Версия в базе раньше `compatibleFrom` | Запуск останавливается |
| Различие только в `z`, в любую сторону | База принимается |

Различие в `z` допустимо в обе стороны, потому что такие изменения не затрагивают структуру: исправление можно откатить на прежнюю сборку.

Тексты отказов:

- «База записана более новой версией: платформа 1.2.0, в этой сборке 1.1.0. Обновите программу». Вместо «платформа» может стоять «конфигурация».
- «База записана слишком старой версией: платформа 0.9.0, эта сборка совместима начиная с 1.0.0. Сначала запустите промежуточный релиз».

Версии базы обновляются в той же транзакции, что и снимок структуры. Ошибка синхронизации откатывает обе записи. Подробнее о синхронизации: [«База данных»](database.md#версии-базы-и-запуск).

## Как выпустить релиз

Релизом считается коммит в `main`, отмеченный git-тегом с версией. Версию меняет только коммит релиза.

1. Определите, какие части изменились, и по правилам выше повысьте номер платформы, конфигурации или обеих. При повышении `x` или `y` следующие числа сбросьте в `0`.
2. При необходимости повысьте `compatibleFrom` в той же константе.
3. Проверьте поле `version` у новых миграций: у платформенных оно равно версии платформы в релизе, у конфигурационных версии конфигурации, всегда вида `x.y.0`. Проверка при запуске отклоняет `z`, отличное от нуля.
4. Создайте коммит релиза.
5. Поставьте на коммит аннотированный тег. Тег ставится на каждый релиз, который ломает совместимость или требует миграции. Аннотация содержит сведения о совместимости и нужных миграциях: журнал изменений в проекте не ведётся.

   ```bash
   git tag -a platform-1.3.0 -m "Платформа 1.3.0. Требуется миграция 20261101_example. Базы платформы 1.0.0 и новее открываются."
   ```

   Имя тега составляют из части и версии: `platform-1.3.0` или `configuration-1.3.0`. Если изменились обе части, на один коммит ставятся два тега.
6. Выполните `npm run build:executable`, соберите комплект и назовите архив по строке, которую напечатал скрипт.

## Версия миграции

Каждая миграция схемы указывает `part` (`platform` или `configuration`) и `version`: версию этой части, в релизе которой появилась миграция. Контракт полей описан в разделе [«База данных»](database.md#файлы-миграций).
