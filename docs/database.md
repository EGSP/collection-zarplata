# База данных

Приложение хранит данные во встраиваемой базе Turso через пакет `@tursodatabase/database` версии `0.8.0`. Страница предназначена для разработчика серверной части: объясняет владение соединением и транзакциями, описывает физическую структуру и показывает, как подготовить миграцию или типизированную выборку. Контракты действий над записями находятся в разделе [«API данных»](single-endpoint.md).

## Работа с базой в приложении

Приложение использует одно соединение на процесс. Фабрика провайдера Nest открывает файл из настроек запуска и при необходимости создаёт его каталог. В режиме проверки она открывает пустую базу в памяти. Сервисы получают одинаковый интерфейс в обоих режимах; данные базы в памяти исчезают после остановки приложения. `DatabaseService` закрывает соединение при завершении работы. Провайдер самого соединения остаётся внутри модуля базы.

Бизнес-логика обращается к сервису `Database` в окружении Effect. Он передаёт SQL и параметры драйверу раздельно, возвращает результат в Effect и преобразует ошибки выполнения в `DatabaseError`. Запрос может дополнительно содержать преобразование строки; ошибки этого преобразования также становятся ошибками чтения базы.

Транзакцией владеет драйвер. Внешний вызов `Database.transaction` открывает `transactionAsync(...).immediate()` и передаёт дескриптор транзакции в окружение Effect. Чтения и записи внутри неё, в том числе во вложенных действиях, используют этот дескриптор. Вложенный вызов `transaction` продолжает текущую транзакцию: отдельного подтверждения или отката у него нет.

Драйвер подтверждает транзакцию после успешного завершения работы и откатывает её при ошибке или прерывании. После прерывания приложение ждёт завершения отката. Нативная блокировка удерживает соединение до подтверждения или отката, поэтому запросы вне транзакции ждут её завершения и не видят промежуточные изменения. Отдельный семафор Effect и режим конкурентной записи `BEGIN CONCURRENT` не используются.

### Драйвер

Прикладной код работает через `Database`, а не напрямую с драйвером. Основные операции обёртки:

| Операция | Результат и гарантия |
|---|---|
| `get(query)` | Первая строка либо `undefined` |
| `all(query)` | Массив всех выбранных строк |
| `run(query)` | Число изменённых строк и идентификатор последней вставленной строки |
| `transaction(work)` | Результат работы после подтверждения; при ошибке изменения откатываются |

Обёртка использует асинхронные вызовы драйвера `get`, `all`, `run` и его дескриптор транзакции. Драйвер подключается через нативную привязку Node.js; требования к её включению в поставку описаны в разделе [«Поставка»](delivery.md).

## Структура БД

После открытия соединения и загрузки метаданных платформа строит желаемую структуру и синхронизирует её до начала приёма запросов. Все таблицы создаются в режиме `STRICT`: база проверяет физический тип записываемых значений. Описание объектов задаётся [метаданными](metadata.md), а физическая структура выводится из него.

### Таблицы объектов

| Вид данных | Имя таблицы | Первичный ключ |
|---|---|---|
| Справочник | `catalog_<имя>` | `guid` |
| Документ | `document_<имя>` | `guid` |
| Регистр движений | `register_<имя>` | `recorderDocument`, `recorderGuid`, `lineNumber` |
| Регистр сведений | `informationRegister_<имя>` | Все измерения в порядке объявления |
| Табличная часть | `<таблица объекта>_<имя части>` | `ownerGuid`, `lineNumber` |

Регистратор движения занимает две колонки: `recorderDocument` хранит имя документа, `recorderGuid` хранит GUID записи. Табличные части хранятся отдельно от основной строки объекта.

Индексы создаются для пометки удаления справочника или документа, номера документа, периода регистра движений, измерений и ссылок. В табличных частях индексируются ссылки.

### Служебные таблицы

| Таблица | Назначение |
|---|---|
| `platform_schema` | JSON-снимок применённой структуры |
| `platform_migrations` | Идентификаторы и время применения миграций |
| `platform_journal` | [Журнал действий](journal.md) |
| `platform_users` | Пользователи и данные для входа |
| `platform_user_roles` | Связь пользователя с именами ролей |
| `platform_tokens` | Токены доступа |

Служебные таблицы входят в то же описание структуры и создаются в режиме `STRICT`. Журнал индексируется по времени, объекту, пользователю и цепочке запроса; токены индексируются по пользователю. Правила входа и ролей описаны в разделах [«Вход в приложение»](authentication.md) и [«Права (RBAC)»](authorization.md).

### Синхронизация и миграции

При запуске платформа сравнивает желаемую структуру с сохранённым снимком. Новые таблицы, колонки и индексы добавляются автоматически. Новая колонка в существующей таблице допускает `NULL`, чтобы сохранить старые строки; обязательность нового реквизита проверяется при записи. Физическое ограничение `NOT NULL` с заполнением старых строк требует явной миграции.

Удаление таблицы или колонки, изменение физического типа, первичного ключа либо существующего индекса требует миграции. Переименование считается удалением старого элемента и добавлением нового: платформа не угадывает перенос данных. Если неприменённые миграции не покрывают все такие изменения, запуск останавливается с перечнем недостающих изменений.

Платформа выполняет неприменённые миграции по порядку, добавляет недостающие безопасные элементы, проверяет фактическую структуру и записывает новый снимок. Эти операции и отметки о миграциях выполняются в одной транзакции. Ошибка SQL или несовпадение таблиц, колонок, типов, ключей, режима `STRICT` либо индексов откатывает эту транзакцию и останавливает запуск. Уже применённая миграция повторно не выполняется.

Запуск также останавливается, если в базе есть прикладные таблицы без снимка структуры, повреждён снимок, отсутствует журнал миграций при существующем снимке, применены неизвестные текущей сборке миграции или нарушен порядок их применения. Произвольная существующая база не принимается за новую: для неё нужна отдельная миграция.

## Как подготовить миграцию

Инструкция применяется, когда изменение метаданных затрагивает существующие данные или физические ограничения. Для простого добавления таблицы, колонки или индекса достаточно автоматической синхронизации с условиями, описанными выше.

1. Получите перечень изменений, которые остановили запуск. Используйте их точные ключи в `changes` миграции.
2. Создайте файл в `src/server/schema/migrations`, экспортирующий `SchemaMigration`. Задайте новый `id` после последней миграции и SQL-команды, которые приводят прежнюю структуру к желаемой, сохраняя нужные данные.
3. Импортируйте миграцию в `src/server/schema/migrations/index.ts` и добавьте её в реестр по возрастанию `id`. Статический реестр входит и в исполняемый файл.
4. Проверьте миграцию на копии базы с прежней структурой. После запуска проверьте перенесённые значения; повторный запуск должен пройти без повторного выполнения миграции. Пустая база не проверяет перенос старых данных.
5. Перед обновлением рабочей базы остановите приложение и сохраните резервную копию её файла. Затем запустите новую сборку. При ошибке синхронизации сервер не начинает принимать запросы.

Пример переноса значения из `comment` в `note` иллюстрирует формат миграции; таблица `catalog_sample` должна существовать в исходной базе:

```ts
import type { SchemaMigration } from './index.js';

export const renameComment: SchemaMigration = {
    id: '20260929_rename_comment',
    changes: ['catalog_sample.comment: удалить колонку'],
    statements: [
        'ALTER TABLE catalog_sample ADD COLUMN note TEXT',
        'UPDATE catalog_sample SET note = comment',
        'ALTER TABLE catalog_sample DROP COLUMN comment',
    ],
};
```

### Файлы миграций

| Свойство | Контракт |
|---|---|
| `id` | Уникальный идентификатор вида `YYYYMMDD_имя`; после даты допустимы строчные латинские буквы, цифры и `_`, первый символ имени является буквой. Реестр упорядочен лексикографически |
| `changes` | Массив точных ключей разрешённых изменений из сообщения об остановке запуска |
| `statements` | Массив SQL-команд без пользовательских значений; выполняются по порядку в общей транзакции |
| `prepare(previous, desired)` | Необязательная чистая функция, которая возвращает `changes` и `statements` для снимков конкретной базы и заменяет ими статический план |

`prepare` не обращается к базе и вызывается до открытия транзакции миграции. Она нужна, например, для изменения стандартного поля во всех справочниках установленной конфигурации без ручного перечисления таблиц. Полученный план проходит ту же проверку покрытия изменений, что и статический план.

## Хранение значений

| Значение поля | Хранение |
|---|---|
| Строка, обычная ссылка, GUID | `TEXT`; ссылка содержит GUID, идентификаторы записей создаются как UUIDv7 |
| Полная ссылка | `TEXT` с JSON-объектом `{ kind, name, guid }` |
| Дата | `TEXT` в формате `YYYY-MM-DD` |
| Дата со временем | `TEXT` в формате ISO 8601 с часовым поясом |
| Деньги | `INTEGER`, целое число копеек |
| Целое число | `INTEGER` |
| Дробное число | `REAL` |
| Логическое значение | `INTEGER`, `0` или `1` |

При чтении записей логические поля преобразуются в `boolean`, полные ссылки в объекты. Деньги остаются целым числом копеек. Обычный SQL-запрос возвращает хранимые значения; типизированный запрос применяет преобразования полей.

## Типизированные выборки объектов

Запросы прикладных таблиц строятся через `query` из `src/server/database/sql.builder.ts`. Он принимает билдер объекта конфигурации, сохраняет связь имён полей, значений условий и результата в типах и сразу формирует SQL с отдельными параметрами для `Database`. Сервисы с динамическими объектами передают описание метаданных; имена и значения в этом случае проверяются при построении запроса.

```ts
const closing = yield* database.get(query(PeriodClosing).select({
    columns: ['closedThrough'],
    where: [{ column: 'posted', operator: '=', value: true }],
    orderBy: [{ column: 'closedThrough', direction: 'DESC' }],
    limit: 1,
}));
```

В примере билдер `PeriodClosing` объявляет поле `closedThrough`; запрос читает его у последнего по этой дате проведённого документа. При отсутствии подходящего документа `get` возвращает `undefined`.

| Настройка | Контракт |
|---|---|
| `columns` | Имена объявленных или стандартных логических полей, включая `recorder`. Без параметра выбираются все поля строки; пустой перечень и повторы отклоняются |
| `where` | Условия `{ column, operator, value }`, соединённые через `AND`. Вложенные группы `{ any: [...] }` и `{ all: [...] }` означают `OR` и `AND`; пустая группа отклоняется |
| `orderBy` | Массив колонок с направлением `ASC` или `DESC` |
| `limit` | Неотрицательное безопасное целое число; без параметра число строк не ограничивается |
| `offset` | Неотрицательное безопасное целое число, число пропускаемых строк |

Имена полей, отбора и сортировки проверяются по метаданным, включая вызовы из JavaScript. Неизвестная настройка, строка вместо условия и строковое значение логического поля отклоняются до исполнения SQL. Допустимы операторы `=`, `!=`, `<`, `<=`, `>`, `>=`, `LIKE` и `IN`. Логическое поле, полная ссылка и регистратор допускают только `=`, `!=` и `IN`. `LIKE` принимает строковый шаблон для строки, даты или даты со временем и сохраняет правила SQL; поиск по показанному тексту списка использует [действующие правила API](single-endpoint.md#поиск-по-колонкам-и-представлению).

`IN` принимает непустой массив значений того же поля. Для `null` допустимы только `=` и `!=`, преобразуемые в `IS NULL` и `IS NOT NULL`; `null` можно искать и в обязательном поле, поскольку старые строки после добавления колонки могут содержать незаполненное значение. SQL сохраняет обычные правила сравнения с `NULL`: неравенство заполненному значению не включает строки с `NULL`.

Табличные части в выборку объекта не входят, поскольку хранятся отдельно. `query(Sale).tablePart('goods')` возвращает билдер строк части: её поля вместе с `ownerGuid` и `lineNumber`. Он поддерживает те же операции, отбор, сортировку и страницу. При чтении полной записи платформа убирает эти два служебных ключа из строк части.

## Подсчёт, группировка и запись

Все операции используют имена логических полей. Значения условий и записи проверяются по схеме поля перед переводом в хранение. Одно отображение в `src/server/database/field-storage.ts` задаёт столбцы, преобразование значения и восстановление результата; из него же строятся колонки, ключи и индексы прикладной схемы.

| Операция | Контракт |
|---|---|
| `select(options)` | Типизированная выборка для `Database.get/all` |
| `count({ where })` | Запрос для `Database.get`, результат `{ total: number }`; считает строки по тому же отбору без страницы |
| `sums({ groupBy, sums, where, orderBy, limit, offset })` | Выборка для `Database.get/all`: поля группировки и суммы под именами суммируемых полей. Отбор применяется до группировки, страница после неё. Суммировать можно только числа и деньги |
| `insert(values)` | Запрос для `Database.run`; обязательные поля должны быть заполнены, пропущенные необязательные поля становятся `NULL` |
| `update(values, where)` | Меняет только переданные поля выбранных строк; пустые значения или пустой отбор отклоняются |
| `remove(where)` | Удаляет выбранные строки; пустой отбор отклоняется |
| `maximumNumber(column)` | Запрос для `Database.get`, результат `{ maximum: number \| null }`; числовой максимум строки или числа через `CAST AS INTEGER`, используется нумерацией документов |

`sums` требует непустой список сумм и список группировки, который может быть пустым. Поля не повторяются и не входят одновременно в группировку и суммы. По умолчанию результат упорядочен по группировке; явная сортировка допускает только поля результата. Без группировки пустой набор возвращает одну строку с нулевыми суммами, с группировкой не возвращает строк. Функция [`totals`](metadata.md#чтение-итога-из-конфигурации) сохраняет правила округления итогов регистров и использует этот же запрос.

Регистратор передаётся целиком во всех операциях:

```ts
const byDocument = query(Sales).sums({
    groupBy: ['recorder'],
    sums: ['amount'],
    where: [{ column: 'recorder', operator: '=', value: { document: 'sale', guid } }],
});
```

Результат содержит `recorder: { document, guid }` и `amount: number`. Для равенства должны совпасть оба столбца регистратора; для неравенства достаточно отличия одного. Группировка и сортировка раскрывают поле в оба столбца, не требуя их имён от вызывающего кода. Это возможность внутреннего билдера; [контракт списка API](single-endpoint.md#регистры-движений) сохраняет свой набор допустимых сортировок.

Билдер не исполняет SQL и не открывает транзакцию. Изменяющие запросы платформы выполняются внутри существующего диспетчера с проверками прав, политик, ограничений и записью журнала. Конфигурация читает через билдер, а изменяет записи через действия; прямой `Database.run` для неё запрещён. Ошибка действия откатывает всю транзакцию.

Прежняя отдельная функция `selectTyped` удалена: вызовы переведены на `query(object).select(options)`. Функции с физическим именем таблицы в том же модуле используются для служебных таблиц пользователей, токенов и журнала. Самостоятельного конструктора SQL под билдером прикладных запросов нет.

## Ограничения Turso, которые учитываем

Платформа использует обычные таблицы `STRICT` и последовательные транзакции одного соединения. Доступ нескольких процессов к одному файлу и конкурентная запись не входят в описанную модель приложения. Ограничения нативной поставки вынесены в раздел [«Поставка»](delivery.md).

Для резервного копирования сохраните копию файла остановленной базы. При выборе возможностей Turso следует сверяться с документацией установленной версии драйвера: совместимость с SQLite не означает поддержку любого её API.
