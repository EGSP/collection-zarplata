# База данных

Приложение хранит данные во встраиваемой базе Turso (пакет `@tursodatabase/database` версии `0.8.0`). Страница для разработчика серверной части: как устроены соединение и транзакции, какова физическая структура, как подготовить миграцию и построить типизированный запрос. Контракты действий над записями описаны в разделе [«API данных»](single-endpoint.md).

## Работа с базой в приложении

На процесс приходится одно соединение. Фабрика провайдера Nest открывает файл из настроек запуска, при необходимости создаёт его каталог, а в режиме проверки открывает пустую базу в памяти (после остановки данные исчезают). Сервисы получают одинаковый интерфейс в обоих режимах. `DatabaseService` закрывает соединение при завершении работы; провайдер самого соединения остаётся внутри модуля базы.

Бизнес-логика обращается к сервису `Database` в окружении Effect. Он передаёт драйверу SQL и параметры раздельно и преобразует ошибки выполнения в `DatabaseError`. Запрос может содержать преобразование строки: его ошибки тоже становятся ошибками чтения базы.

| Операция | Результат и гарантия |
|---|---|
| `get(query)` | Первая строка либо `undefined` |
| `all(query)` | Массив всех выбранных строк |
| `run(query)` | Число изменённых строк и идентификатор последней вставленной строки |
| `transaction(work)` | Результат работы после подтверждения; при ошибке изменения откатываются |

Прикладной код работает через `Database`, а не напрямую с драйвером. Исключение составляет снимок для резервной копии: его пишет рабочий поток со своим соединением только для чтения (раздел [«Резервное копирование»](backup.md#как-устроено-копирование)). Драйвер подключается через нативную привязку Node.js; требования к её включению в поставку описаны в разделе [«Поставка»](delivery.md).

### Транзакции

Транзакцией владеет драйвер. Внешний `Database.transaction` открывает `transactionAsync(...).immediate()` и передаёт дескриптор в окружение Effect, поэтому все чтения и записи внутри неё, в том числе во вложенных действиях, идут через него. Вложенный `transaction` продолжает текущую транзакцию и своего подтверждения или отката не имеет.

Драйвер подтверждает транзакцию при успехе и откатывает при ошибке или прерывании; после прерывания приложение дожидается отката. Нативная блокировка удерживает соединение до конца транзакции: запросы вне неё ждут и не видят промежуточных изменений. Поэтому отдельный семафор Effect и режим `BEGIN CONCURRENT` не нужны и не используются.

## Структура БД

После открытия соединения и загрузки [метаданных](metadata.md) платформа выводит из них желаемую структуру и синхронизирует базу до начала приёма запросов. Все таблицы создаются в режиме `STRICT`: база проверяет физический тип записываемых значений.

### Таблицы объектов

| Вид данных | Имя таблицы | Первичный ключ |
|---|---|---|
| Справочник | `catalog_<имя>` | `guid` |
| Документ | `document_<имя>` | `guid` |
| Регистр движений | `register_<имя>` | `recorderDocument`, `recorderGuid`, `lineNumber` |
| Регистр сведений | `informationRegister_<имя>` | Все измерения в порядке объявления |
| Табличная часть | `<таблица объекта>_<имя части>` | `ownerGuid`, `lineNumber` |

Регистратор движения занимает две колонки: `recorderDocument` хранит имя документа, `recorderGuid` хранит GUID записи.

Индексы создаются для пометки удаления справочника или документа, номера документа, периода регистра движений, измерений и ссылок; в табличных частях индексируются ссылки. Составное поле индексируется, если служит измерением или содержит ссылочный вариант; индекс включает его столбцы в порядке сортировки.

Составное измерение регистра сведений входит в первичный ключ одним столбцом `<имя>_key`. Остальные его столбцы допускают `NULL`, а Turso требует `NOT NULL` для столбцов первичного ключа.

### Служебные таблицы

Служебные таблицы входят в то же описание структуры и тоже создаются в режиме `STRICT`.

| Таблица | Назначение |
|---|---|
| `platform_schema` | JSON-снимок применённой структуры |
| `platform_backup_settings` | [Расписание резервных копий](backup.md#как-изменить-расписание): одна строка `id = 1`, JSON `schedule`, число `keep` и время `updatedAt`; отсутствие строки означает начальные настройки файла |
| `platform_migrations` | Идентификаторы и время применения миграций |
| `platform_versions` | [Версии](versions.md) платформы и конфигурации сборки, последней открывшей базу: одна строка `id = 1`, поля `platform` и `configuration` |
| `platform_journal` | [Журнал действий](journal.md); индексы по времени, объекту, пользователю и цепочке запроса |
| `platform_users` | Пользователи и данные для входа |
| `platform_user_roles` | Связь пользователя с именами ролей |
| `platform_tokens` | Токены доступа; индекс по пользователю |

Правила входа и ролей описаны в разделах [«Вход в приложение»](authentication.md) и [«Права (RBAC)»](authorization.md).

### Синхронизация и миграции

При запуске платформа сравнивает желаемую структуру с сохранённым снимком.

| Изменение | Что происходит |
|---|---|
| Новая таблица, колонка или индекс | Добавляется автоматически |
| Удаление таблицы или колонки, смена физического типа, первичного ключа или существующего индекса | Требует миграции |
| Переименование | Считается удалением старого элемента и добавлением нового: перенос данных платформа не угадывает |

Новая колонка в существующей таблице допускает `NULL`, чтобы сохранить старые строки; обязательность нового реквизита проверяется при записи. Физическое `NOT NULL` с заполнением старых строк требует явной миграции.

Если неприменённые миграции не покрывают все изменения, требующие миграции, запуск останавливается с перечнем недостающих.

Платформа выполняет неприменённые миграции по порядку, добавляет недостающие безопасные элементы, проверяет фактическую структуру и записывает новый снимок. Всё это вместе с отметками о миграциях происходит в одной транзакции. Ошибка SQL или несовпадение таблиц, колонок, типов, ключей, режима `STRICT` либо индексов откатывает её и останавливает запуск. Применённая миграция повторно не выполняется.

Запуск останавливается и в таких случаях:

- в базе есть прикладные таблицы без снимка структуры;
- снимок повреждён;
- при существующем снимке нет журнала миграций;
- применены миграции, неизвестные текущей сборке, или нарушен порядок их применения;
- версии в базе несовместимы со сборкой ([см. ниже](#версии-базы-и-запуск)).

Произвольная существующая база за новую не принимается: для неё нужна отдельная миграция.

### Версии базы и запуск

Если таблица `platform_versions` уже есть, версии проверяются до сверки структуры. Платформа и конфигурация сравниваются с записанными в базе раздельно. Запуск останавливается, когда `x.y` в базе новее, чем в сборке, или когда версия в базе раньше `compatibleFrom` сборки. Различие только в `z` допустимо в обе стороны. База без строки версий, оставшаяся от сборок без версий, принимается. Версии сборки записываются в транзакции синхронизации вместе со снимком. Правила номеров и тексты отказов описаны в разделе [«Версии»](versions.md).

## Как подготовить миграцию

Нужна, когда изменение метаданных затрагивает существующие данные или физические ограничения. Для простого добавления таблицы, колонки или индекса достаточно автоматической синхронизации.

1. Получите перечень изменений, остановивших запуск. Их точные ключи пойдут в `changes` миграции.
2. Создайте в `src/server/schema/migrations` файл, экспортирующий `SchemaMigration`: новый `id` после последней миграции, `part`, `version` и SQL-команды, которые приводят прежнюю структуру к желаемой с сохранением нужных данных.
3. Укажите `part` (`platform` или `configuration`: какая часть потребовала миграции) и `version` вида `x.y.0`: версию этой части в ближайшем релизе. Миграция меняет структуру, поэтому повышает как минимум `y`; ненулевой `z` останавливает запуск. Сам номер повышается в коммите релиза, как описано в разделе [«Версии»](versions.md#как-выпустить-релиз).
4. Импортируйте миграцию в `src/server/schema/migrations/index.ts` и добавьте в реестр по возрастанию `id`. Статический реестр входит и в исполняемый файл.
5. Проверьте на копии базы с прежней структурой: перенесённые значения должны сохраниться, повторный запуск не должен выполнять миграцию снова. Пустая база перенос старых данных не проверяет.
6. Перед обновлением рабочей базы остановите приложение и сохраните копию её файла, затем запустите новую сборку. При ошибке синхронизации сервер не начинает принимать запросы.

Пример переноса значения из `comment` в `note` показывает формат; таблица `catalog_sample` должна существовать в исходной базе:

```ts
import type { SchemaMigration } from './index.js';

export const renameComment: SchemaMigration = {
    id: '20260929_rename_comment',
    part: 'platform',
    version: '1.1.0',
    changes: ['catalog_sample.comment: удалить колонку'],
    statements: [
        'ALTER TABLE catalog_sample ADD COLUMN note TEXT',
        'UPDATE catalog_sample SET note = comment',
        'ALTER TABLE catalog_sample DROP COLUMN comment',
    ],
};
```

### Файлы миграций

| Свойство | Контракт |
|---|---|
| `id` | Уникальный идентификатор вида `YYYYMMDD_имя`; в имени допустимы строчные латинские буквы, цифры и `_`, первый символ буква. Реестр упорядочен лексикографически |
| `part` | Часть приложения, изменение которой потребовало миграции: `platform` или `configuration` |
| `version` | Версия этой части, в релизе которой появилась миграция, вида `x.y.0`; запуск проверяет `z = 0` |
| `changes` | Точные ключи разрешённых изменений из сообщения об остановке запуска |
| `statements` | SQL-команды без пользовательских значений; выполняются по порядку в общей транзакции |
| `prepare(previous, desired)` | Необязательная чистая функция: по снимкам конкретной базы возвращает `changes` и `statements` вместо статического плана |

`prepare` не обращается к базе и вызывается до открытия транзакции миграции. Она нужна, например, чтобы изменить стандартное поле во всех справочниках установленной конфигурации без ручного перечисления таблиц. Её план проходит ту же проверку покрытия изменений, что и статический.

## Хранение значений

| Значение поля | Хранение |
|---|---|
| Строка, обычная ссылка, GUID | `TEXT`; ссылка содержит GUID, идентификаторы записей создаются как UUIDv7 |
| Полная ссылка | `TEXT` с JSON-объектом `{ kind, name, guid }` |
| Дата | `TEXT` в формате `YYYY-MM-DD` |
| Дата со временем | `TEXT` в формате ISO 8601 с часовым поясом |
| Деньги | `INTEGER`, целое число копеек |
| Целое число | `INTEGER` |
| Дробное число | `REAL` |
| Логическое значение | `INTEGER`, `0` или `1` |
| Составное поле | Несколько столбцов с общим началом имени, см. ниже |

Обычный SQL-запрос возвращает хранимые значения, а типизированный применяет преобразования полей: логические поля становятся `boolean`, полные ссылки и составные значения становятся объектами. Деньги остаются целым числом копеек.

### Столбцы составного поля

[Составное поле](metadata.md#составное-поле) `<имя>` хранит тип варианта отдельно от значения, а значение в столбце того же физического типа, что у обычного поля. Поэтому числа сравнивает SQL без разбора JSON, а строка «100» и число 100 не совпадают.

| Столбец | Содержимое |
|---|---|
| `<имя>_type` | Тип варианта: `string`, `number`, `money`, `date`, `dateTime`, `boolean` или `reference`. `NOT NULL` у обязательного поля |
| `<имя>_integer` | Значение целого числа, суммы или логического варианта |
| `<имя>_real` | Значение дробного числа |
| `<имя>_text` | Значение строки, даты или даты со временем |
| `<имя>_target`, `<имя>_guid` | Цель ссылки в виде `catalog/<имя объекта>` и GUID записи; общие для всех ссылочных вариантов |
| `<имя>_key` | Только у измерения: значение одной строкой, например `string:100` или `reference:catalog/sample:<guid>` |

Столбцы значения создаются только для способов хранения, которые нужны объявленным вариантам. У записи заполнены тип и столбцы выбранного варианта, остальные равны `NULL`; запись значения другого типа очищает прежние столбцы. Незаполненное поле хранит `NULL` во всех столбцах. Имена полей не содержат `_`, поэтому столбцы составного поля не совпадают со столбцами других полей.

Добавление варианта добавляет недостающие столбцы обычной синхронизацией. Удаление варианта, значения которого есть в базе, требует миграции данных: иначе чтение такой строки завершится ошибкой.

## Типизированные выборки объектов

Запросы прикладных таблиц строятся через `query` из `src/server/database/sql.builder.ts`. Он принимает билдер объекта конфигурации, связывает в типах имена полей, значения условий и результат и сразу формирует SQL с отдельными параметрами для `Database`. Сервисы с динамическими объектами передают описание метаданных; имена и значения тогда проверяются при построении запроса.

```ts
const closing = yield* database.get(query(PeriodClosing).select({
    columns: ['closedThrough'],
    where: [{ column: 'posted', operator: '=', value: true }],
    orderBy: [{ column: 'closedThrough', direction: 'DESC' }],
    limit: 1,
}));
```

Запрос читает `closedThrough` у последнего по этой дате проведённого документа `PeriodClosing`. Если такого документа нет, `get` возвращает `undefined`.

| Настройка | Контракт |
|---|---|
| `columns` | Имена объявленных или стандартных логических полей, включая `recorder`. Без параметра выбираются все поля строки; пустой перечень и повторы отклоняются |
| `where` | Условия `{ column, operator, value }`, соединённые через `AND`. Группы `{ any: [...] }` и `{ all: [...] }` означают `OR` и `AND` и могут быть вложенными; пустая группа отклоняется |
| `orderBy` | Массив колонок с направлением `ASC` или `DESC` |
| `limit` | Неотрицательное безопасное целое число; без параметра строки не ограничиваются |
| `offset` | Неотрицательное безопасное целое число, число пропускаемых строк |

Имена полей, отбора и сортировки проверяются по метаданным, в том числе при вызове из JavaScript. До исполнения SQL отклоняются неизвестная настройка, строка вместо условия и строковое значение логического поля.

Операторы:

- `=`, `!=`, `<`, `<=`, `>`, `>=`, `LIKE`, `IN`;
- логическое поле, полная ссылка и регистратор допускают только `=`, `!=` и `IN`;
- `LIKE` принимает строковый шаблон для строки, даты или даты со временем и сохраняет правила SQL; поиск по показанному тексту списка работает по [правилам API](single-endpoint.md#поиск-по-колонкам-и-представлению);
- `IN` принимает непустой массив значений того же поля;
- для `null` допустимы только `=` и `!=`, они превращаются в `IS NULL` и `IS NOT NULL`. `null` можно искать и в обязательном поле: после добавления колонки старые строки могут быть незаполненными. Неравенство заполненному значению не включает строки с `NULL`, как в SQL.

Составное поле сравнивается вместе с типом: `{ type: 'number', value: 100 }`. Равенство требует совпадения типа и значения либо типа, цели и GUID. Упорядоченные операторы сравнивают значения внутри указанного простого типа и не выбирают строки других типов; со ссылочным и логическим значением они отклоняются, `LIKE` недоступен. Сортировка раскрывает поле в столбцы типа, значений, цели и GUID в этом порядке, группировка использует все его столбцы.

Табличные части в выборку объекта не входят, они хранятся отдельно. `query(Sale).tablePart('goods')` возвращает билдер строк части: её поля вместе с `ownerGuid` и `lineNumber`, с теми же операциями, отбором, сортировкой и страницей. При чтении полной записи платформа убирает эти два служебных ключа из строк части.

## Подсчёт, группировка и запись

Все операции используют имена логических полей. Значения условий и записи проверяются по схеме поля до перевода в хранение. Столбцы, преобразование значения и восстановление результата задаёт одно отображение в `src/server/database/field-storage.ts`; из него же строятся колонки, ключи и индексы прикладной схемы.

| Операция | Контракт |
|---|---|
| `select(options)` | Типизированная выборка для `Database.get/all` |
| `count({ where })` | Запрос для `Database.get`, результат `{ total: number }`; считает строки по тому же отбору без страницы |
| `sums({ groupBy, sums, where, orderBy, limit, offset })` | Запрос для `Database.get/all`: поля группировки и суммы под именами суммируемых полей. Отбор применяется до группировки, страница после. Суммировать можно только числа и деньги |
| `insert(values)` | Запрос для `Database.run`; обязательные поля должны быть заполнены, пропущенные необязательные становятся `NULL` |
| `update(values, where)` | Меняет только переданные поля выбранных строк; пустые значения или пустой отбор отклоняются |
| `remove(where)` | Удаляет выбранные строки; пустой отбор отклоняется |
| `maximumNumber(column)` | Запрос для `Database.get`, результат `{ maximum: number \| null }`: числовой максимум строки или числа через `CAST AS INTEGER`; используется нумерацией документов |

Правила `sums`:

- нужен непустой список сумм; список группировки может быть пустым;
- поля не повторяются и не входят одновременно в группировку и суммы;
- по умолчанию результат упорядочен по группировке; явная сортировка допускает только поля результата;
- без группировки пустой набор даёт одну строку с нулевыми суммами, с группировкой строк нет.

Функция [`totals`](metadata.md#чтение-итога-из-конфигурации) использует этот же запрос и сохраняет правила округления итогов регистров.

Регистратор передаётся целиком во всех операциях:

```ts
const byDocument = query(SalesNetOfReturns).sums({
    groupBy: ['recorder'],
    sums: ['amount'],
    where: [{ column: 'recorder', operator: '=', value: { document: 'sale', guid } }],
});
```

Результат содержит `recorder: { document, guid }` и `amount: number`. Для равенства должны совпасть оба столбца регистратора, для неравенства достаточно отличия одного. Группировка и сортировка сами раскрывают поле в оба столбца. Это возможность внутреннего билдера: [контракт списка API](single-endpoint.md#регистры-движений) сохраняет свой набор допустимых сортировок.

Билдер не исполняет SQL и не открывает транзакцию. Изменяющие запросы платформы выполняются внутри существующего диспетчера с проверками прав, политик и ограничений и записью журнала; ошибка действия откатывает всю транзакцию. Конфигурация читает через билдер, а изменяет записи через действия: прямой `Database.run` для неё запрещён.

Функции с физическим именем таблицы в том же модуле служат для таблиц пользователей, токенов и журнала. Самостоятельного конструктора SQL под билдером прикладных запросов нет; прежняя функция `selectTyped` удалена в пользу `query(object).select(options)`.

## Ограничения Turso

Платформа использует обычные таблицы `STRICT` и последовательные транзакции одного соединения. Доступ нескольких процессов к одному файлу и конкурентная запись в модель приложения не входят. Ограничения нативной поставки описаны в разделе [«Поставка»](delivery.md).

Для резервной копии сохраните файл остановленной базы. Возможности Turso сверяйте с документацией установленной версии драйвера: совместимость с SQLite не означает поддержку любого её API.
