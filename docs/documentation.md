# Документация

Эта страница задаёт правила для авторов документации и объясняет, как приложение показывает её по адресу `/docs/`. Исходники страниц хранятся в `docs` в формате Markdown: один текст читается и в репозитории, и на сайте.

## Правила изложения

Перед созданием или переработкой документации прочитайте навык [documentation-directions](https://github.com/EGSP/collection-zarplata/blob/main/.agents/skills/documentation-directions/SKILL.md). Его копия для Claude находится в [`.claude/skills`](https://github.com/EGSP/collection-zarplata/blob/main/.claude/skills/documentation-directions/SKILL.md); обе копии обновляются вместе. Русскоязычные тексты следуют правилу [russian-style-v2](https://github.com/EGSP/collection-zarplata/blob/main/.agents/skills/russian-style-v2/SKILL.md).

Каждый самостоятельный блок отвечает одной потребности читателя:

| Тип блока | Потребность читателя |
|---|---|
| Учебный пример (tutorial) | Освоить навык на подготовленном примере |
| Инструкция (how-to) | Выполнить рабочую задачу |
| Объяснение (explanation) | Понять предмет, связи и причины решений |
| Справочник (reference) | Найти точные сведения |

Блоки разных типов могут находиться на одной странице, но отделяются содержательными заголовками. Все четыре типа на каждой странице не требуются.

Название кратко отражает назначение страницы. У содержания есть граница: справочник API раскрывает доступные действия, форматы и гарантии, а устройство обработчиков относится к архитектурному объяснению и комментариям к коду. Общие правила предшествуют особенностям частей или видов объектов. Сопоставимые темы описываются с сопоставимой подробностью; объём накопленного текста не определяет место темы в структуре.

Деталь реализации включается, если она влияет на использование или объясняет существенное решение в рамках страницы. Для дальнейшего изучения внутреннего устройства даётся ссылка на отвечающий за него модуль. Условия, гарантии и ограничения описываются в самой документации, а не заменяются ссылками на код.

Редакторская переработка объединяет разрозненные правила, убирает повторы и выравнивает глубину описания. Одной расстановки заголовков недостаточно. Текст называет конкретные действия и последствия, без дежурных вступлений, общих оценок и повторных выводов.

Критерий проверки инструкции и справочника: читатель может найти ответ на свою задачу, не изучая предварительно внутреннее устройство системы. При сокращении сохраняются действующие контракты и существенные ограничения; сомнительные утверждения сверяются с кодом. Ссылки и используемые якоря сохраняются либо обновляются вместе с текстом.

## Как добавить или обновить раздел

Для работы нужны исходники проекта и установленные зависимости. Изменения документации ведутся в той же ветке, что и описываемые изменения кода.

1. Определите читателя, тему и вопросы страницы. Разделите ответы по [потребностям читателя](#правила-изложения).
2. Для нового раздела архитектуры создайте `docs/<имя>.md` и добавьте строку в корневой `ARCHITECTURE.md` в формате `- [Название](docs/<имя>.md)`. Настройку меню менять не нужно. Для существующего раздела измените его файл.
3. Если раздел описывает код, укажите его пути в списке [`covers`](#связь-разделов-с-кодом). Новый модуль добавьте в список соответствующего раздела.
4. Если изменились формулы, округление, условия или запреты магазина, обновите [«Правила учёта»](accounting-rules.md) в той же ветке. Новый документ конфигурации получает там подраздел со своими правилами. Состав полей, формы и механизмы платформы описываются в архитектуре.
5. Проверьте входящие ссылки перед переименованием страницы или заголовка. Обновите ссылки либо сохраните совместимый якорь.
6. Перед отчётом запустите `npm run docs:check`. Прочитайте каждый названный раздел с пометкой «раздел не изменён» и обновите его, если изменилось описанное поведение. Исправьте ошибки шаблонов `covers`.
7. [Соберите сайт](#сборка-сайта), проверьте страницу, навигацию, схемы и ссылки. Сопоставьте итоговый текст с исходным: существенные условия и ограничения должны сохраниться.

В документацию не включаются секреты и данные магазина: сайт доступен без входа в приложение.

## Файлы и оглавление

| Элемент | Правило |
|---|---|
| Файл раздела архитектуры | `docs/<имя>.md`; имя латиницей в kebab-case |
| Заголовки | Один заголовок первого уровня называет страницу; второй уровень задаёт подразделы, которые попадают в меню сайта |
| Оглавление архитектуры | Корневой `ARCHITECTURE.md`, одна строка со ссылкой на каждый раздел |
| Правила учёта | `docs/accounting-rules.md`; отдельная группа меню перед архитектурой, вне оглавления `ARCHITECTURE.md` |
| Ссылка на документацию | Относительный путь к файлу, при необходимости с якорем: `[«Web SDK»](interface.md#web-sdk)` |
| Ссылка на код вне `docs` | Ссылка на файл в репозитории: `https://github.com/EGSP/collection-zarplata/blob/main/<путь>` |

Якорь заголовка строится по правилу GitHub: строчные буквы, знаки препинания удалены, пробелы заменены дефисами. В [настройке сайта](https://github.com/EGSP/collection-zarplata/blob/main/docs/.vitepress/config.ts) заменено стандартное правило VitePress, которое превращает «й» в «и». Поэтому относительная ссылка на подраздел ведёт к одному заголовку и на сайте, и на GitHub.

Схемы записываются блоком кода `mermaid` в тексте раздела. Сайт отображает их плагином Mermaid, GitHub поддерживает такие блоки сам. Отдельный файл картинки не требуется, и схема изменяется вместе с объясняющим её текстом.

Подписи узлов и стрелок берутся в кавычки: кириллица и знаки препинания без кавычек могут нарушить разбор. Подпись должна быть короткой; вторая строка отделяется тегом `<br/>`. Пояснения располагаются текстом под схемой. Настройка сайта выводит подписи текстом SVG, а не вложенным HTML: иначе стили сайта обрезали бы нижний край подписи в две строки.

## Связь разделов с кодом

Раздел перечисляет описываемый код в служебном заголовке в начале файла. `covers` содержит шаблоны путей от корня проекта, по одному на строке:

```markdown
---
covers:
  - src/server/data/**
  - scripts/metadata-generate.ts
---
```

Список в одну строку, например `covers: [a, b]`, не поддерживается и считается ошибкой. Раздел без своего кода, например «Принципы», не нуждается в `covers`.

Шаблон выбирается по тому, изменение какого кода должно напомнить о разделе. Слишком широкий шаблон включает раздел в отчёт при посторонних правках и затрудняет поиск нужной документации. Один файл может относиться к нескольким разделам.

| Проверка | Поведение |
|---|---|
| Область проверки | Файлы `docs/*.md`; страницы за пределами этого списка не проверяются |
| База сравнения | `main`; другую ветку задаёт `npm run docs:check -- --base=feat/data/perform` |
| Состав изменений | Коммиты после расхождения с базовой веткой, незакоммиченные правки и новые файлы |
| Изменение описываемого кода | Отчёт называет раздел, изменённые файлы и то, менялся ли файл раздела |
| Шаблон без совпадений | Ошибка, которая останавливает `docs:check` и `typecheck` |
| Код без соответствующего раздела | В отчёт не попадает; связь нового модуля с документацией указывает автор |
| База сравнения недоступна | Проверка сообщает, что изменения не сравнивались; укажите существующую базовую ветку |

Изменённый код сам по себе не делает документацию устаревшей. Поэтому наличие затронутого раздела не останавливает проверку: автор решает, меняет ли правка описанное поведение. Шаблон без совпадений означает, что связь с кодом не работает, например после переноса или удаления модуля. Его нужно исправить либо удалить.

Формат и сравнение реализованы в [скрипте проверки документации](https://github.com/EGSP/collection-zarplata/blob/main/scripts/documentation-check.ts). `npm run typecheck` запускает тот же скрипт.

## Сборка сайта

Чтобы просматривать изменения во время редактирования, выполните:

```bash
npm run docs:dev
```

Откройте `http://localhost:5174/docs/`. Страница обновляется при изменении файлов; сервер приложения для этого не нужен.

Чтобы проверить готовый сайт, выполните:

```bash
npm run build:docs
```

Сборка создаёт `dist/docs` и останавливается, если внутренняя ссылка ведёт на несуществующий файл документации. Якоря внутри страниц и ссылки на код нужно проверить отдельно. После успешной сборки запущенный сервер приложения показывает результат по адресу `/docs/`.

Полная команда `npm run build` собирает документацию вместе с сервером и клиентом. При запуске `npm run dev` сайт собирается один раз и отдаётся через сервер; прокси Vite направляет `/docs` на него, как и `/api`. Для просмотра последующих правок повторите `npm run build:docs` либо используйте `npm run docs:dev`. Общий порядок запуска описан в разделе [«Сборка и запуск»](build-and-launch.md).

## Как устроен сайт

VitePress заранее преобразует Markdown в сайт. Он использует Vite, уже применяемый для клиента. Навигация и поиск по тексту формируются при сборке; поиск работает в браузере по включённому в сборку индексу. Оформление остаётся стандартным для сайта документации.

Меню архитектуры строится из корневого `ARCHITECTURE.md`, а подразделы берутся из заголовков второго уровня в файлах страниц. Правила учёта образуют отдельную группу перед архитектурой, поскольку описывают прикладные правила магазина. Это место задано в [настройке VitePress](https://github.com/EGSP/collection-zarplata/blob/main/docs/.vitepress/config.ts).

## Раздача по адресу /docs

Сервер приложения отдаёт сайт из `dist/docs` при запуске из исходников или из ресурсов исполняемого файла при [поставке](delivery.md). Адрес `/docs` перенаправляется на `/docs/`. Страницу можно открыть и без расширения `.html`.

Для документации выделен маршрут `/docs/*`. Он точнее общего маршрута клиента приложения, который возвращает клиентскую страницу для адресов вкладок. Поэтому неизвестный адрес документации получает страницу сайта «не найдено» с кодом 404. Если сайт не собран и страницы 404 тоже нет, сервер возвращает текстовое сообщение с предложением выполнить `npm run build:docs`.

Документация доступна без входа. Cookie доступа отправляется только на `/api` (раздел [«Вход в приложение»](authentication.md)), поэтому сервер не получает её при обращении к `/docs`. Раздача реализована в [модуле документации](https://github.com/EGSP/collection-zarplata/blob/main/src/server/documentation/documentation.module.ts).

В левой панели приложения над кнопкой «Выйти» расположена кнопка «Документация», видимая каждому вошедшему пользователю. Она открывает `/docs/` в новой вкладке браузера: собственные меню и оформление сайта иначе повторяли бы каркас приложения.
