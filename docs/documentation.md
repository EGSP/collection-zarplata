# Документация

Страницы лежат в `docs` в формате Markdown: один текст читается и в репозитории, и на сайте, который приложение показывает по адресу `/docs/`. Здесь описаны правила для авторов, сборка сайта и его раздача.

## Правила изложения

Перед созданием или переработкой страниц прочитайте навык [documentation-directions](https://github.com/EGSP/collection-zarplata/blob/main/.agents/skills/documentation-directions/SKILL.md). Его копия для Claude лежит в [`.claude/skills`](https://github.com/EGSP/collection-zarplata/blob/main/.claude/skills/documentation-directions/SKILL.md); обе копии обновляются вместе. Русский текст пишется по правилу [russian-style-v2](https://github.com/EGSP/collection-zarplata/blob/main/.agents/skills/russian-style-v2/SKILL.md).

Каждый блок отвечает одной потребности читателя:

| Тип блока | Потребность читателя |
|---|---|
| Учебный пример (tutorial) | Освоить навык на подготовленном примере |
| Инструкция (how-to) | Выполнить рабочую задачу |
| Объяснение (explanation) | Понять предмет, связи и причины решений |
| Справочник (reference) | Найти точные сведения |

Блоки разных типов можно держать на одной странице под содержательными заголовками. Все четыре типа на каждой странице не нужны.

- Название кратко отражает назначение страницы. У содержания есть граница: справочник API раскрывает действия, форматы и гарантии, а устройство обработчиков относится к архитектурному объяснению и комментариям в коде.
- Общие правила идут раньше особенностей частей или видов объектов. Сопоставимые темы описываются с сопоставимой подробностью: объём накопленного текста не определяет место темы.
- Деталь реализации включается, если влияет на использование или объясняет существенное решение. Для изучения внутреннего устройства даётся ссылка на модуль. Условия, гарантии и ограничения описываются в самой документации, а не заменяются ссылками на код.
- Переработка объединяет разрозненные правила, убирает повторы и выравнивает глубину. Одной расстановки заголовков недостаточно. Текст называет действия и последствия, без вступлений, общих оценок и повторных выводов.

Инструкция и справочник проверяются так: читатель находит ответ на свою задачу, не изучая внутреннее устройство системы. При сокращении сохраняются действующие контракты и существенные ограничения, сомнительные утверждения сверяются с кодом. Ссылки и якоря сохраняются либо обновляются вместе с текстом.

## Как добавить или обновить раздел

Изменения документации ведутся в той же ветке, что и изменения описываемого кода. Нужны исходники и установленные зависимости.

1. Определите читателя, тему и вопросы страницы. Разделите ответы по [потребностям читателя](#правила-изложения).
2. Для нового раздела архитектуры создайте `docs/<имя>.md` и добавьте в корневой `ARCHITECTURE.md` строку `- [Название](docs/<имя>.md)`. Меню настраивать не нужно. Существующий раздел правится в его файле.
3. Если раздел описывает код, перечислите пути в [`covers`](#связь-разделов-с-кодом). Новый модуль добавьте в список соответствующего раздела.
4. Если изменились формулы, округление, условия или запреты магазина, обновите [«Правила учёта»](accounting-rules.md) в той же ветке. Новый документ конфигурации получает там подраздел со своими правилами. Состав полей, формы и механизмы платформы описываются в архитектуре.
5. Перед переименованием страницы или заголовка проверьте входящие ссылки: обновите их или сохраните совместимый якорь.
6. Перед отчётом запустите `npm run docs:check`. Прочитайте каждый раздел с пометкой «раздел не изменён» и обновите его, если описанное поведение изменилось. Исправьте ошибки шаблонов `covers`.
7. [Соберите сайт](#сборка-сайта) и проверьте страницу, навигацию, схемы и ссылки. Сопоставьте итоговый текст с исходным: существенные условия и ограничения должны сохраниться.

Секреты и данные магазина в документацию не включаются: сайт доступен без входа в приложение.

## Файлы и оглавление

| Элемент | Правило |
|---|---|
| Файл раздела архитектуры | `docs/<имя>.md`; имя латиницей в kebab-case |
| Дочерняя страница | `docs/<раздел>/<имя>.md`; для большой темы, которую удобнее читать частями |
| Заголовки | Один заголовок первого уровня называет страницу; второй уровень задаёт подразделы, они попадают в меню сайта |
| Оглавление архитектуры | Корневой `ARCHITECTURE.md`: одна строка со ссылкой на каждый раздел; дочерние страницы идут под строкой раздела с отступом в два пробела |
| Правила учёта | `docs/accounting-rules.md`; отдельная группа меню перед архитектурой, вне `ARCHITECTURE.md`. Дочерняя страница «Правила редактирования продаж» (`docs/sale-editing-rules.md`) подключена в [настройке сайта](https://github.com/EGSP/collection-zarplata/blob/main/docs/.vitepress/config.ts) |
| Ссылка на документацию | Относительный путь к файлу, при необходимости с якорем: `[«Хуки»](web-sdk/hooks.md#чтение-данных)` |
| Ссылка на код вне `docs` | `https://github.com/EGSP/collection-zarplata/blob/main/<путь>` |

Якорь строится по правилу GitHub: строчные буквы, знаки препинания удалены, пробелы заменены дефисами. [Настройка сайта](https://github.com/EGSP/collection-zarplata/blob/main/docs/.vitepress/config.ts) заменяет стандартное правило VitePress, которое превращает «й» в «и». Поэтому относительная ссылка на подраздел ведёт к одному заголовку и на сайте, и на GitHub.

Схема записывается блоком кода `mermaid` прямо в тексте раздела: сайт рисует её плагином Mermaid, GitHub поддерживает такие блоки сам. Отдельный файл картинки не нужен, схема меняется вместе с объясняющим текстом.

Подписи узлов и стрелок берутся в кавычки: кириллица и знаки препинания без них могут нарушить разбор. Подпись короткая, вторая строка отделяется тегом `<br/>`, пояснения идут текстом под схемой. Сайт выводит подписи текстом SVG, а не вложенным HTML: иначе стили сайта обрезали бы нижний край подписи в две строки.

## Связь разделов с кодом

Раздел перечисляет описываемый код в служебном заголовке в начале файла. `covers` содержит шаблоны путей от корня проекта, по одному на строке:

```markdown
---
covers:
  - src/server/data/**
  - scripts/metadata-generate.ts
---
```

Список в одну строку (`covers: [a, b]`) не поддерживается и считается ошибкой. Разделу без своего кода, например «Принципы», `covers` не нужен.

Шаблон выбирается по тому, изменение какого кода должно напомнить о разделе. Слишком широкий шаблон попадает в отчёт при посторонних правках и мешает искать нужную документацию. Один файл может относиться к нескольким разделам.

| Проверка | Поведение |
|---|---|
| Область проверки | Файлы `docs/**/*.md`, включая дочерние страницы; каталог `.vitepress` не проверяется |
| База сравнения | `main`; другую ветку задаёт `npm run docs:check -- --base=feat/data/perform` |
| Состав изменений | Коммиты после расхождения с базой, незакоммиченные правки и новые файлы |
| Изменён описываемый код | Отчёт называет раздел, изменённые файлы и то, менялся ли файл раздела |
| Шаблон без совпадений | Ошибка, она останавливает `docs:check` и `typecheck` |
| Код без раздела | В отчёт не попадает; связь нового модуля с документацией указывает автор |
| База недоступна | Проверка сообщает, что изменения не сравнивались; укажите существующую ветку |

Изменённый код сам по себе не делает документацию устаревшей, поэтому затронутый раздел не останавливает проверку: автор решает, менялось ли описанное поведение. Шаблон без совпадений означает, что связь с кодом не работает, например после переноса или удаления модуля. Его нужно исправить или удалить.

Формат и сравнение реализует [скрипт проверки](https://github.com/EGSP/collection-zarplata/blob/main/scripts/documentation-check.ts). `npm run typecheck` запускает тот же скрипт.

## Сборка сайта

Для просмотра правок во время редактирования выполните `npm run docs:dev` и откройте `http://localhost:5174/docs/`. Страница обновляется при изменении файлов, сервер приложения не нужен.

Чтобы проверить готовый сайт, выполните `npm run build:docs`. Сборка создаёт `dist/docs` и останавливается, если внутренняя ссылка ведёт на несуществующий файл документации. Якоря внутри страниц и ссылки на код проверяйте отдельно. После сборки запущенный сервер приложения показывает результат по адресу `/docs/`.

`npm run build` собирает документацию вместе с сервером и клиентом. `npm run dev` собирает сайт один раз и отдаёт его через сервер, а прокси Vite направляет `/docs` на сервер, как и `/api`. Последующие правки смотрите через `npm run build:docs` или `npm run docs:dev`. Общий порядок запуска описан в разделе [«Сборка и запуск»](build-and-launch.md).

## Как устроен сайт

Сайт собирает VitePress на том же Vite, что и клиент. Навигация и поиск формируются при сборке; поиск работает в браузере по включённому в сборку индексу. Оформление стандартное.

Меню архитектуры строится из корневого `ARCHITECTURE.md`, подразделы берутся из заголовков второго уровня в файлах страниц. Дочерние страницы стоят под своим разделом после его подразделов. Правила учёта образуют отдельную группу перед архитектурой, их дочерняя страница «Правила редактирования продаж» стоит под ними, потому что описывают прикладные правила магазина; место задано в [настройке VitePress](https://github.com/EGSP/collection-zarplata/blob/main/docs/.vitepress/config.ts).

## Раздача по адресу /docs

Сервер отдаёт сайт из `dist/docs` при запуске из исходников или из ресурсов исполняемого файла при [поставке](delivery.md). Адрес `/docs` перенаправляется на `/docs/`, страницу можно открыть и без расширения `.html`.

Для документации выделен маршрут `/docs/*`. Он точнее общего маршрута клиента, который на адреса вкладок возвращает клиентскую страницу. Поэтому неизвестный адрес документации получает страницу сайта «не найдено» с кодом 404. Если сайт не собран и страницы 404 нет, сервер отвечает текстом с предложением выполнить `npm run build:docs`.

Документация доступна без входа: cookie доступа уходит только на `/api` (раздел [«Вход в приложение»](authentication.md)), и сервер не получает её при обращении к `/docs`. Раздачу реализует [модуль документации](https://github.com/EGSP/collection-zarplata/blob/main/src/server/documentation/documentation.module.ts).

В левой панели приложения над кнопкой «Выйти» стоит кнопка «Документация», видимая каждому вошедшему пользователю. Она открывает `/docs/` в новой вкладке: собственные меню и оформление сайта иначе повторяли бы каркас приложения.
