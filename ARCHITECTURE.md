# Архитектура

Приложение для учёта зарплаты и продаж магазина. Этот документ описывает технические решения; назначение и возможности — в [PRODUCT.md](PRODUCT.md).

## Принципы

- **Модельно-ориентированная разработка (MDD).** Прикладные объекты (справочники, документы, регистры) описываются декларативно. По описанию платформа строит структуру БД, API, права, валидацию и формы.
- **Платформа отделена от конфигурации.** Платформа — это механизмы: хранение, единый API, права, журнал, SDUI. Конфигурация — это прикладные объекты и роли конкретного магазина. Новый объект добавляется одним файлом конфигурации без ручной регистрации.
- **Один процесс, один исполняемый файл.** NestJS обслуживает API и раздаёт собранный фронтенд. Файл БД лежит рядом с исполняемым файлом.
- **Effect только в бизнес-логике.** Роутинг, контроллеры и DI остаются на Nest. Effect управляет ходом выполнения: ошибками, транзакциями, контекстом действия, композицией операций.
- **Полные имена.** В идентификаторах, действиях, маршрутах и полях используются полные слова без сокращений: `parameters`, а не `params`; `configuration`, а не `config`. Допустимы только общепринятые аббревиатуры: `guid`, `API`, `UI`, `SQL`, `JSON`.

## Метаданные

### Виды объектов

| Вид | Назначение | Функция описания |
|---|---|---|
| Справочник | Условно-постоянные данные: сотрудники, номенклатура, точки | `catalog(name)` |
| Документ | Событие с датой, номером и статусом «проведён / не проведён» | `document(name)` |
| Регистр | Строки, которые документ записывает при проведении; по ним считаются обороты | `register(name)` |
| Регистр сведений | Текущие независимые значения по уникальному набору измерений | `informationRegister(name)` |

Регистры поддерживаются платформой. Нужны ли они в конкретной задаче, решает конфигурация. Строка регистра (движение) всегда ссылается на документ-регистратор. Один документ может записать несколько строк, например по одной на каждого сотрудника смены. При повторном проведении старые строки документа удаляются и записываются заново, поэтому проведение идемпотентно.

Пока поддерживаются только регистры оборотов: ресурсы строк суммируются. Регистры остатков с видом движения «приход / расход» добавим, когда они понадобятся.

Регистр сведений имеет отдельный вид `informationRegister`. У него нет документа-регистратора, периода, номера строки, `guid` и пометки удаления. Все измерения обязательны и вместе определяют запись; ресурсы содержат её значения и допускают все прикладные виды полей, включая строки и ссылки. Периодичность и история значений не поддерживаются. История действий доступна в общем журнале.

### Независимые сведения

Один файл `*.information-register.ts` экспортирует билдер регистра. Например, пробный регистр описан так:

```ts
import { informationRegister } from '../../server/metadata/index.js';
import { Sample } from '../catalogs/sample.catalog.js';

export const SampleInformation = informationRegister('sample')
    .title('Пробный регистр сведений')
    .dimension('source', (field) => field.string().title('Источник').maximumLength(100))
    .dimension('externalObject', (field) => field.string().title('Внешний объект').maximumLength(100))
    .resource('description', (field) => field.string().title('Описание').maximumLength(500))
    .resource('item', (field) => field.reference(() => Sample).title('Элемент справочника'));
```

Обязательность измерений добавляет сам билдер, в том числе в выведенный тип записи. `commit()` требует хотя бы одно измерение и один ресурс. Порядок ключа совпадает с порядком объявления измерений. При синхронизации создаётся таблица `informationRegister_<имя>` с составным первичным ключом по измерениям и ограничением `NOT NULL` для каждого измерения. База не допускает двух строк с одним ключом; запись при конфликте ключа заменяет только ресурсы. Индексы измерений позволяют искать сведения по части ключа. Политики `.policy(...)` проверяют сохранение и физическое удаление; форм, табличных частей и собственных действий у этого вида объекта нет.

### Описание объекта

Объект описывается цепочкой вызовов билдера. Билдер собирает описание объекта из полей, табличных частей, действий и формы; описание создаётся при вызове `commit()`. Код билдеров находится в `src/server/metadata`.

```ts
import { Effect } from 'effect';
import { catalog, document, movements, register } from '../../server/metadata/index.js';
import { Positions } from './positions.catalog.js';
import { closedPeriodByDocumentDate } from '../policies/closed-period.js';
import { preventPostedDocumentDeletion } from '../policies/posted-document-deletion.js';

export const Employees = catalog('employees')
    .title('Сотрудники')
    .field('position', (field) => field.reference(Positions).title('Должность'))
    .field('hiredAt', (field) => field.date().title('Дата приёма').required())
    .field('rate', (field) => field.money().title('Ставка').minimum(0))
    .tablePart('contacts', (part) => part
        .title('Контакты')
        .field('kind', (field) => field.string().title('Вид').required().maximumLength(20))
        .field('value', (field) => field.string().title('Значение')))
    .action('dismiss', (action) => action          // собственное действие
        .title('Уволить')
        .input((input) => input.field('dismissedAt', (field) => field.date().required()))
        .handle((input) => Effect.log(input.dismissedAt)))
    .form((form) => form                           // необязательное переопределение формы
        .group('Основное', ['name', 'position'])
        .hide('rate'));

export const Accruals = register('accruals')
    .title('Начисления')
    .dimension('employee', (field) => field.reference(Employees))
    .resource('amount', (field) => field.money().required());

export const Shift = document('shift')
    .title('Смена')
    .tablePart('staff', (part) => part
        .field('employee', (field) => field.reference(Employees).required())
        .field('amount', (field) => field.money().required()))
    .policy(closedPeriodByDocumentDate())
    .policy(preventPostedDocumentDeletion())
    .posting((record) => Effect.succeed([                 // обработчик проведения
        movements(Accruals, record.staff.map((line) => ({ employee: line.employee, amount: line.amount }))),
    ]));
```

- Файл конфигурации экспортирует **билдер**, а не готовое описание. `commit()` в файлах конфигурации не вызывается.
- Билдеры неизменяемы: каждый вызов возвращает новый билдер.
- Платформенный сервис метаданных получает билдеры всех объектов из сгенерированного реестра. Перед сборкой он добавляет стандартные поля вида объекта методом `withStandardFields()`.
- Затем сервис вызывает `commit(configuration)`, где `configuration` — билдеры всех объектов, или `commitConfiguration(builders)` для всех объектов сразу. `commit()` проверяет описание и собирает из него неизменяемое описание объекта (`ObjectDescription`), с которым работает остальная платформа. Результат — `Effect`; при ошибках он завершается `MetadataError` со списком всех найденных проблем.
- Ссылки на другие объекты передаются самими билдерами (`field.reference(Positions)`), а не строками. Если файлы импортируют друг друга по кругу, цель передаётся функцией: `field.reference(() => Employees)`. Ссылаться можно на справочники и документы.
- Каждый вызов `.field(...)`, `.tablePart(...)`, `.dimension(...)` и `.resource(...)` расширяет тип билдера, поэтому TypeScript выводит тип записи из цепочки без отдельной генерации типов: `RecordOf<typeof Employees>`. Стандартные поля известны заранее по виду объекта и тоже входят в тип. Обязательное поле имеет тип значения, необязательное — значение или `null`, табличная часть — массив строк.
- Обработчик проведения `.posting(...)` есть только у документа. Он получает сохранённую запись документа с табличными частями и возвращает Effect со строками регистров. Строки одного регистра собирает `movements(Регистр, строки)`: тип строки выводится из билдера регистра, поэтому TypeScript отклоняет неизвестные измерения и ресурсы. `period` строки можно не указывать — платформа подставит дату документа; регистратор и номер строки платформа заполняет сама. Обработчику, как и собственному действию, доступны из окружения Effect `ActionContext`, `ActionDispatcher`, `Database` для чтения и `Metadata` — описания объектов конфигурации. Изменения через прямой вызов `Database.run` запрещены; для вложенной записи используется `ActionDispatcher`.
- Собственные действия выполняет диспетчер после проверки прав и входных данных. Имя действия попадает в тип билдера, поэтому право на него доступно переменной `Rights.catalog.employees.actions.dismiss`. Переопределение формы применяется при построении описаний форм (раздел «Интерфейс (SDUI)»). `.policy(...)` привязывает к объекту именованную проверку: она получает действие, прежнюю и предлагаемую запись и выполняется до изменения данных.

### Поля

Полная ссылка на запись содержит `kind` (`catalog` или `document`), `name` объекта конфигурации и `guid` записи. Функция `objectReference` собирает её из известной цели и GUID. Поле `field.reference()` принимает такую ссылку; поле с заданной целью `field.reference(Объект)` сохраняет прежний формат GUID, поскольку цель уже есть в метаданных. Оба вида полей показывают представление записи и открывают её карточку по общему правилу формирования адресов. В таблицах это наименование справочника или представление документа, в полях ввода — выбор записи с кнопкой открытия. Без права чтения целевого объекта представление не запрашивается: показывается «Нет доступа».

| Поле | Значение в записи | Свойства |
|---|---|---|
| `field.string()` | строка | `minimumLength`, `maximumLength` |
| `field.number()` | число | `minimum`, `maximum`, `integer` |
| `field.money()` | целое число копеек | `minimum`, `maximum` в копейках |
| `field.date()` | строка `YYYY-MM-DD` | |
| `field.dateTime()` | строка ISO 8601 с часовым поясом | |
| `field.boolean()` | логическое значение | |
| `field.reference(Объект)` | `guid` объекта; цель задана в метаданных | |
| `field.reference()` | `{ kind, name, guid }`, ссылка на любой справочник или документ | |

У всех полей есть `title` и `required`. Табличные части и входные данные действий состоят из тех же полей. Поля регистра делятся на измерения (`.dimension`) — разрезы, по которым строки отбирают и группируют, — и ресурсы (`.resource`) — числа или деньги, которые суммируются. У регистра должен быть хотя бы один ресурс.

### Проверка повторов имён в типах

Методы билдера отклоняют повтор литерального имени при проверке типов. Для полей объекта проверяются также совпадения со стандартными полями его вида. Измерения и ресурсы регистра используют общий набор имён. Поля табличной части и входных данных действия проверяются внутри своей части или действия, поэтому одинаковое имя в разных частях допустимо. Отдельно проверяются повторы имён самих табличных частей и собственных действий.

Ограничение сохраняет тип имени и добавляет в ошибку текст причины, например `имя поля повторяется` или `имя поля совпадает со стандартным полем`, вместе с конфликтующим именем. Оно не меняет состояние билдера и поведение при выполнении.

Имя типа `string` не раскрывает конкретное значение, поэтому проходит проверку типов. После такого объявления накопленный набор ключей тоже может расшириться до `string`, и проверка повторов этого набора остаётся за `commit()`. Проверка стандартных полей выполняется отдельно и продолжает отклонять явно указанные стандартные имена. Все проверки сборки описания сохраняются, включая проверку имён, полученных во время выполнения.

### Проверки при сборке

`commit()` сообщает обо всех проблемах описания сразу:
- имена объектов, полей, табличных частей и действий — lowerCamelCase латиницей без `_`, не длиннее 60 символов и не совпадают с ключевыми словами SQLite: из них строятся имена таблиц и колонок;
- имена полей не повторяются и не совпадают со стандартными полями; имя табличной части не совпадает с именем поля;
- ссылка указывает на справочник или документ, который есть в конфигурации;
- границы и длины согласованы: минимум не больше максимума, у денег границы целые;
- имя собственного действия не совпадает со стандартным, у действия задан обработчик;
- обработчик проведения задан только у документа;
- форма ссылается на существующие поля и табличные части; элемент входит не больше чем в одну группу, не бывает одновременно скрыт и выведен в группу; группа не пуста; `guid` и `deletedAt` не выводятся в группы; обязательное поле, которое заполняет пользователь, не скрыто; режим создания записи задан не больше одного раза;
- собственный элемент формы объявлен в файле `*.form-element.ts`; полем ввода он назначен существующему полю, которое пользователь заполняет на форме: не табличной части, не скрытому полю и не полю, которое заполняет платформа; одному полю назначен один элемент;
- стандартные поля добавлены, то есть вызван `withStandardFields()`.

`commitConfiguration` дополнительно проверяет, что имена объектов одного вида не повторяются.

### Проверка входных данных

По описанию строится Effect Schema (`src/server/metadata/schema.ts`):
- `inputSchema(description)` — входные данные записи объекта: поля, которые заполняет пользователь, и табличные части. Поля, которые заполняет платформа (`guid`, `deletedAt`, `number`, `posted`, `recorder`, `lineNumber`), в схему не входят;
- `actionInputSchema(description, action)` — входные данные собственного действия;
- `fieldsSchema(fields)` и `fieldSchema(field)` — схема набора полей и одного поля.

Обязательное поле должно быть передано, а обязательная строка не может быть пустой. Необязательное поле можно пропустить или передать `null`. Сообщения об ошибках — на русском.

### Стандартные поля

Стандартного поля `code` у справочников нет. Запись определяется GUID, а пользователю показывается наименование. Миграция `20261007_remove_catalog_code` удаляет прежнюю стандартную колонку и её индексы из существующих справочников, сохраняя GUID, остальные поля и внешние связи. Если прикладная конфигурация самостоятельно объявляет поле с именем `code`, миграция сохраняет это поле.

У каждого вида объектов есть свой набор стандартных полей. Он задан в одном месте — `src/server/metadata/standard-fields.ts`:
- у справочников: `guid`, `deletedAt`, `name`;
- у документов: `guid`, `deletedAt`, `number`, `date`, `posted`;
- у регистров движений: `recorder` — документ-регистратор (`{ document, guid }`), `period` — дата и время строки, `lineNumber` — номер строки среди строк того же регистратора. Своего `guid` и пометки удаления у строки регистра нет: её определяют регистратор и номер строки.

Список может уточняться по ходу работы. `guid` генерируется как UUIDv7: такие идентификаторы упорядочены по времени, поэтому новые записи добавляются в конец индекса, а не в случайные его места.

### Пометка удаления

Справочники и документы физически не удаляются. Пометкой служит поле `deletedAt`: если дата заполнена, объект помечен на удаление. Кто поставил пометку, фиксирует журнал. Сведения удаляются физически по измерениям, а движения удаляются при отмене проведения.

### Обнаружение объектов конфигурации

Во время работы исполняемого файла исходники `.ts` недоступны, поэтому объекты, страницы и элементы формы обнаруживаются на этапе сборки. Скрипт `scripts/metadata-generate.ts` (`npm run metadata:generate`) находит файлы объектов `src/configuration/**/*.{catalog,document,register,information-register}.ts`, файлы страниц (подраздел «Страницы конфигурации») и файлы элементов формы (подраздел «Элементы формы») и генерирует в `src/configuration` четыре файла:

| Файл | Кому нужен | Содержимое |
|---|---|---|
| `configuration.generated.ts` | серверу | Импорт каждого файла объекта и каждого объявления страницы и элемента формы целиком, списки `configurationModules`, `pageModules` и `formElementModules` с путём файла и его экспортом, объект прав `Rights`, построенный из модулей объектов и страниц (раздел «Права (RBAC)») |
| `objects.generated.ts` | клиенту | Ссылки на объекты `Objects` для страниц и элементов формы; файлы объектов импортируются только как типы |
| `pages.generated.ts` | клиенту | Реестр страниц: объявление и компонент каждой страницы |
| `form-elements.generated.ts` | клиенту | Реестр элементов формы: объявление и компонент каждого элемента |

- Сгенерированные файлы исключены из git и помечены комментарием, что вручную их не редактируют. Команды `dev`, `build` и `typecheck` сначала запускают генерацию, поэтому в новом клоне или worktree файлы появляются сами.
- В `npm run dev` скрипт работает с флагом `--watch`: при появлении, удалении или переименовании файла объекта или страницы реестры обновляются, `tsc --watch` пересобирает сервер, `node --watch` перезапускает его, а Vite обновляет клиент. Файл перезаписывается, только если его текст изменился.
- Ссылки на объекты и реестры компонентов лежат в разных файлах. Реестр импортирует компоненты страниц или элементов, а компоненты импортируют ссылки на объекты: в одном файле получился бы циклический импорт, и при загрузке компонента ссылки могли бы быть ещё не определены.
- Скрипт выполняется Node без сборки: Node 24 сам удаляет аннотации типов. Поэтому в скриптах допустим только стираемый синтаксис TypeScript, это проверяет `scripts/tsconfig.json` с `erasableSyntaxOnly`.

Платформа читает только сгенерированный реестр. Сервис метаданных (`MetadataService` в глобальном модуле `MetadataModule`) при запуске сервера:
1. извлекает билдер из экспорта каждого файла и проверяет соглашение: файл экспортирует ровно один билдер, а его вид совпадает с суффиксом файла (`*.catalog.ts` — `catalog(...)` и т. д.). Кроме билдера файл может экспортировать другие значения;
2. так же извлекает билдеры элементов формы из файлов объявлений и составляет перечень их имён;
3. добавляет стандартные поля методом `withStandardFields()`;
4. собирает описания через `commitConfiguration`, передавая перечень элементов формы для проверки форм.

Если нарушено соглашение о файлах или в описании есть ошибки, запуск останавливается с `MetadataError`, где перечислены все проблемы: файл или объект, место в описании и суть ошибки. Готовые описания сервис отдаёт платформе: `objects` — все объекты, `find(kind, name)` — один объект.

### Страницы конфигурации

Интерфейс объекта строится по его описанию: список и форма. Экран, который к ним не сводится, например рабочее место, конфигурация объявляет страницей. Страница состоит из двух файлов с общим началом имени:

```ts
// src/configuration/pages/sample-workplace.page.ts — объявление
import { page } from '../../server/ui/pages.js';

export const SampleWorkplace = page('sampleWorkplace').title('Пробное рабочее место');
```

```tsx
// src/configuration/pages/sample-workplace.page-component.tsx — компонент, экспорт по умолчанию
import { ActionButton, Page, RecordTable, useRecordList } from '../../web/sdk';
import { Objects } from '../objects.generated';

export default function SampleWorkplacePage() {
    const documents = Objects.document.sample;
    const list = useRecordList(documents, { permanentFilter: [{ field: 'posted', operator: 'equals', value: false }] });
    return (
        <Page title="Пробное рабочее место">
            <RecordTable object={documents} list={list} columns={['number', 'date', 'item']} />
        </Page>
    );
}
```

- Объявление отделено от компонента. Сервер собирает `src/configuration` без React и DOM, а имя и заголовок страницы нужны ему для меню и прав. Файлы `*.tsx` каталога конфигурации исключены из серверной сборки и проверяются настройками клиента.
- Имя страницы подчиняется правилам имён объектов и не повторяется. Оно входит в адрес `/page/<имя>` и в ключ права.
- Генератор находит страницы по именам файлов и сам проверяет парность: объявление без компонента и компонент без объявления останавливают генерацию с названием файла. В режиме слежения нарушение только выводится в журнал, а реестры остаются прежними: файлы страницы создаются по одному. Экспорт объявления (ровно один билдер страницы) и имя страницы сервер проверяет при запуске и останавливается с `MetadataError`.
- Страница не импортирует значения из файлов объектов. Файл объекта тянет за собой билдеры, Effect, обработчики действий и политики с чтением базы: такой импорт включил бы серверный код в сборку клиента. Объект страница указывает ссылкой `Objects.<вид>.<имя>` из `objects.generated.ts`. Тип ссылки выведен из билдера импортом только типа, а вид и имя во время работы берутся из пути обращения, который компилятор сверяет с билдерами. Поэтому генератору по-прежнему не нужно разбирать исходники, чтобы узнать имена объектов.
- Из клиента страница импортирует только web SDK. Границу проверяет скрипт `scripts/configuration-imports-check.ts`, который `npm run typecheck` запускает перед проверкой типов: импорт внутреннего модуля `src/web`, импорт значения из серверного кода или файла объекта останавливают проверку с названием файла и строки. Компилятор запрещать импорты по каталогам не умеет, поэтому проверка вынесена в скрипт.
- Описание страницы сервером в виде JSON отклонено: компонент попадает в клиент при сборке, а не через `/api/metadata`. Сервер сообщает клиенту только имена и заголовки доступных страниц.

Пробная страница «Пробное рабочее место» показывает непроведённые пробные документы и кнопку «Провести» для выбранной строки.

### Элементы формы

Стандартная форма выводит поля и табличные части из описания объекта. Блок с собственной логикой, например итог по табличной части или поле ввода с кнопкой, конфигурация объявляет элементом формы. Как и страница, элемент состоит из двух файлов с общим началом имени:

```ts
// src/configuration/form-elements/sample-total.form-element.ts — объявление
import { formElement } from '../../server/metadata/form-elements.js';

export const SampleTotal = formElement('sampleTotal');
```

```tsx
// src/configuration/form-elements/sample-total.form-element-component.tsx — компонент, экспорт по умолчанию
import { FieldDisplay, useFormValue } from '../../web/sdk';
import { Objects } from '../objects.generated';

export default function SampleTotal() {
    const lines = useFormValue(Objects.document.sample, 'lines');
    const total = lines.reduce((sum, line) => sum + (line.amount ?? 0), 0);
    return <FieldDisplay field={{ kind: 'money', target: null }} value={total} />;
}
```

- У объявления есть только имя. Оно подчиняется правилам имён объектов и не повторяется среди элементов. Место на форме задаёт переопределение формы объекта (подраздел «Переопределение формы»), поэтому один элемент можно поставить на формы разных объектов.
- Обнаружение, парность файлов и граница импортов устроены так же, как у страниц: генератор находит пары файлов, сервер при запуске проверяет экспорт объявления, скрипт проверки импортов разрешает компоненту только web SDK и типы серверного кода.
- Права у элемента нет: он виден там, где видна форма, а доступ к данным проверяется по правам объектов.
- Элемент не обращается к форме Ant Design и к API напрямую. Значения формы и запись он получает из SDK (`useFormData`, `useFormValue`, раздел «Web SDK»). Иначе смена устройства формы в платформе ломала бы элементы конфигурации.
- Сервер называет в описании формы только имя элемента и его место. Компонент клиент находит по имени в реестре `form-elements.generated.ts`. Реестр подключает стандартная форма, а не SDK: компоненты элементов сами импортируют SDK, и импорт реестра из SDK замкнул бы модули в кольцо.

Пробные элементы стоят на форме пробного документа: блок «Итого» под табличной частью «Строки» показывает сумму колонки «Сумма», а поле «Комментарий» заменено собственным полем ввода с кнопкой, которая подставляет текст «Проверено».

### Пробные объекты

Пока прикладных объектов нет, платформу проверяют на пробных объектах: справочнике `src/configuration/catalogs/sample.catalog.ts`, документе `src/configuration/documents/sample.document.ts` и регистре `src/configuration/registers/sample.register.ts`. Документ ссылается на справочник в шапке и в табличной части, а при проведении записывает строки табличной части в регистр. На его форме стоят пробные элементы формы из `src/configuration/form-elements/`.

## База данных

Используется **Turso** — SQLite-совместимая встраиваемая база, переписанная на Rust. Проект находится в статусе бета: часть возможностей SQLite ещё не реализована.

### Драйвер

Пакет `@tursodatabase/database` (версия 0.8 на сентябрь 2026). Основные вызовы:
- `connect(path)` открывает файл БД и создаёт его, если файла нет;
- `db.prepare(sql)` асинхронно готовит запрос; `run`, `get`, `all`, `iterate` выполняют его и возвращают промисы. Для разовых запросов есть `db.get(sql, ...parameters)`, `db.all(...)`, `db.run(...)`;
- `db.exec(sql)` выполняет SQL без результата, например DDL;
- `db.pragma(...)` выполняет PRAGMA.
- `db.transactionAsync(async (transaction) => { ... }).immediate()` удерживает соединение до подтверждения или отката и передаёт дескриптор для запросов внутри транзакции.

Драйвер использует нативные привязки для Node.js; есть и сборка на WebAssembly.

### Типизированные выборки объектов

Прикладной код вызывает `selectTyped` из `src/server/data/typed-select.ts`, передавая билдер объекта и настройки выборки. Имя таблицы определяется по виду и имени объекта. Имена колонок, отбора и сортировки проверяются по объявленным и стандартным полям; тип значения отбора связан с выбранным полем. Например:

```ts
const closing = yield* database.get(selectTyped(PeriodClosing, {
    columns: ['closedThrough'],
    where: [{ column: 'posted', operator: '=', value: true }],
    orderBy: [{ column: 'closedThrough', direction: 'DESC' }],
    limit: 1,
}));
```

Готовый запрос выполняют обычные `Database.get` и `Database.all`: тип строки выводится из выбранных колонок. Без `columns` возвращаются все поля таблицы объекта. Табличные части хранятся отдельно и в эту строку не входят. Регистратор не поддерживается в колонках, отборе и сортировке, поскольку занимает две колонки; без перечня колонок он тоже исключён из результата регистра.

Запрос сохраняет преобразование строки, которое методы чтения применяют внутри операции базы. Логические значения возвращаются как `boolean`, полные ссылки как объекты, деньги как целое число копеек. Те же преобразования используются при чтении обычных записей и табличных частей. Условия переводятся в хранимые значения до построения SQL, включая логические поля и полные ссылки. Ошибка преобразования возвращается как ошибка чтения базы. Конструктор SQL остаётся независимым от метаданных; обычные запросы продолжают возвращать хранимые строки.

### Работа с базой в приложении

- **Одно соединение на процесс.** Turso не поддерживает доступ к одному файлу из нескольких процессов, а нам это и не требуется: приложение работает одним процессом.
- **Соединение открывает провайдер-фабрика Nest.** Фабрика по настройкам запуска открывает файл базы, создав его каталог при необходимости, или пустую базу в памяти (`connect(':memory:')`). `DatabaseService` получает уже открытое соединение и закрывает его при остановке приложения; остальные сервисы работают с базой через него и о режиме не знают. Сам провайдер соединения из модуля базы не экспортируется.
- **Сервис `Database` на Effect** оборачивает драйвер: вызовы драйвера превращаются в `Effect`, ошибки — в `DatabaseError` (`Data.TaggedError`).
- **Транзакцией владеет драйвер.** Действие открывает `transactionAsync(...).immediate` и передаёт его дескриптор в окружение Effect. Все чтения и записи действия, включая вложенные вызовы, идут через этот дескриптор. Драйвер подтверждает транзакцию после успешного завершения действия и откатывает при ошибке или прерывании. Прерывание ждёт завершения отката, прежде чем соединение снова считается свободным.
- **Порядок запросов задаёт нативная блокировка соединения.** Драйвер удерживает её на всё время транзакции. Другая транзакция, отдельная запись или чтение вне неё ждёт завершения текущей транзакции и не видит промежуточные изменения. Запросы внутри транзакции выполняются на её дескрипторе. Отдельный семафор Effect для этого порядка не нужен.
- **Таблицы создаются как `STRICT`.** В таком режиме база проверяет типы колонок при записи, а не принимает любые значения, как обычная SQLite-таблица.
- **Конкурентная запись (MVCC, `BEGIN CONCURRENT`) не включается.** Она в статусе бета, а при двух пользователях очереди транзакций достаточно.

### Ограничения Turso, которые учитываем

- нет таблиц `WITHOUT ROWID`;
- нет `VACUUM`;
- только кодировка UTF-8;
- в JavaScript-драйвере нет `backup()`, поэтому резервная копия делается копированием файла.

### Структура БД

Для изменения стандартных полей во всех объектах миграция может предоставить `prepare(previous, desired)`. Чистая функция получает сохранённый и желаемый снимки структуры и возвращает план `changes` и `statements`, который заменяет одноимённые свойства миграции. Это позволяет обработать справочники конкретной базы, не перечисляя имена объектов вручную. План строится до транзакции, проверяется на покрытие разрушающих изменений и исполняется вместе с записью нового снимка. Повторно применённая миграция не выполняется.

- `SchemaService` после инициализации соединения и метаданных строит желаемую структуру и завершает синхронизацию до начала приёма запросов. `catalog_<имя>`, `document_<имя>` и `register_<имя>` содержат поля объектов; `<таблица объекта>_<имя части>` содержит строки табличной части с ключом `(ownerGuid, lineNumber)`. У справочников и документов первичный ключ — `guid`; у регистра — `(recorderDocument, recorderGuid, lineNumber)`. Значение `recorder` разложено на две колонки. Ссылки и даты хранятся как `TEXT`, деньги, целые числа и логические значения — как `INTEGER`, дробные числа — как `REAL`.
- Тем же описанием создаются служебные таблицы `platform_schema` (снимок), `platform_migrations` (применённые миграции), `platform_journal`, `platform_users`, `platform_user_roles` (связь пользователя с именами ролей) и `platform_tokens`. Все таблицы создаются в режиме `STRICT`. Индексы создаются для номера документа, пометки удаления, измерений и ссылок, периода регистра, а также для поиска по журналу и токенам.
- Применённая структура хранится JSON-снимком в `platform_schema`. При запуске платформа сравнивает с ним текущие метаданные. Новые таблицы, колонки и индексы добавляются автоматически. Новая колонка в существующей таблице допускает `NULL`, чтобы сохранить старые строки; обязательность нового реквизита проверяется при записи. Если нужна физическая обязательность с заполнением старых строк, используйте миграцию.
- Удаление таблицы или колонки, изменение типа, первичного ключа либо существующего индекса требует миграции. Переименование определяется как удаление старой и добавление новой колонки. Без подходящей миграции запуск останавливается с перечнем изменений. После выполнения SQL платформа проверяет фактические таблицы, типы колонок и индексы; ошибка откатывает транзакцию вместе с записью снимка и отметками миграций.

#### Файлы миграций

Файл в `src/server/schema/migrations` экспортирует значение типа `SchemaMigration` с `id` вида `YYYYMMDD_имя`, массивом `changes` и массивом SQL-команд `statements`. Например, для переноса значения в колонку с новым именем миграция сначала добавляет колонку, переносит данные запросом `UPDATE`, затем удаляет старую колонку. Ключи `changes` следует брать из сообщения об остановке запуска. Файл импортируется в `migrations/index.ts`, где миграции перечислены в возрастающем порядке `id`: статический реестр попадает и в исполняемый файл.

```ts
import type { SchemaMigration } from './index.js';

export const renameComment: SchemaMigration = {
    id: '20260929_rename_comment',
    changes: ['catalog_sample.comment: удалить колонку'],
    statements: [
        'ALTER TABLE catalog_sample ADD COLUMN note TEXT',
        'UPDATE catalog_sample SET note = comment',
        'ALTER TABLE catalog_sample DROP COLUMN comment',
    ],
};
```

Платформа выполняет неприменённые миграции по порядку, затем добавляет недостающие безопасные элементы и записывает снимок в той же транзакции. `platform_migrations` фиксирует `id` только после успешного выполнения. При следующем запуске тот же файл повторно не выполняется. SQL миграции относится к конкретной установленной структуре; перед изменением рабочей базы сделайте резервную копию её файла.

### Хранение значений

- Деньги — целые числа в копейках.
- Дата и время — строки ISO 8601 с явным учётом часового пояса.
- `guid` — строка UUIDv7.

## Единый эндпоинт

Все операции с данными клиент выполняет через `POST /api/perform`:

```json
{
    "target": { "kind": "catalog", "name": "employees" },
    "action": "save",
    "payload": { "guid": "…", "fields": { "name": "…" } }
}
```

В теле можно передать массив операций. Массив выполняется в одной транзакции.

Диспетчер выполняет стандартные действия всех видов объектов и собственные действия справочников и документов. Контракт записи и чтения справочников и документов приведён ниже; контракт сведений описан отдельно. Ответ на одиночную операцию — её результат; ответ на пакет — массив результатов в исходном порядке. Пустой пакет отклоняется. Для действий без входных данных `payload` можно опустить.

- `save`: `payload: { "fields": { "name": "…", "active": true, "lines": [] } }` создаёт запись; `guid` в `payload` обновляет существующую. В `fields` передаются все заполняемые пользователем поля и все табличные части. Отсутствующие необязательные поля сохраняются как `null`. Обновление заменяет строки табличных частей и сохраняет пометку удаления.
- `get`, `markDeleted`, `unmarkDeleted`: `payload: { "guid": "…" }`. `get` возвращает запись с табличными частями. Действия пометки возвращают обновлённую запись.
- `list`: `payload: { "filter": [{ "field": "name", "operator": "contains", "value": "образец" }], "sort": [{ "field": "name", "direction": "ascending" }], "page": 1, "pageSize": 50 }`. Все свойства необязательны; размер страницы от 1 до 500. Способы сравнения и направления сортировки (`ascending`, `descending`) те же, что в описании списка (раздел «Формат описаний»); способ, недопустимый для вида поля, отклоняется. `equals` и `notEquals` с `null` проверяют, заполнено ли поле. `contains` ищет буквальную подстроку без учёта регистра: клиент не добавляет `%`, а введённые `%` и `_` считаются обычными символами. Для строк, чисел, сумм, дат и дат со временем значение отбора передаётся строкой. Поиск идёт по отображаемому значению: число с десятичной запятой, сумма в рублях с двумя цифрами копеек, дата `ДД.ММ.ГГГГ`, дата со временем `ДД.ММ.ГГГГ ЧЧ:ММ` по часовому поясу сервера. Пробельные разделители разрядов чисел и сумм не учитываются ни в значении, ни в запросе. Незаполненное поле не совпадает с подстрокой. Для этого сервер читает подходящие по остальным условиям записи порциями и отбирает подстроку до подсчёта `total` и выбора страницы. Поля отбора и сортировки должны принадлежать объекту. Ответ содержит `items`, `total`, `page`, `pageSize`. При равенстве значений сортировки порядок стабилизируется по `guid`, у регистра движений по регистратору и номеру строки, у регистра сведений по всем измерениям.
- `post`, `unpost`: `payload: { "guid": "…" }`, возвращают документ. Описаны в подразделе «Документы и проведение».
- Собственное действие получает `payload` по своим полям `.input(...)` и возвращает результат обработчика. Обработчик может получить из окружения Effect `ActionContext`, `ActionDispatcher`, `Database` и `Metadata`; вложенный вызов диспетчера получает новый `actionGuid` и наследует `traceGuid` и `userGuid`. Записи обработчик изменяет вложенными действиями через диспетчер: только так изменения попадают в журнал.
- Журнал читается через тот же эндпоинт с целью `{ "kind": "platform", "name": "journal" }`. Действия описаны в подразделе «Чтение журнала».

У пробного справочника `sample` есть действия для ручной проверки собственных и вложенных действий. `inspect` принимает `guid`, вызывает вложенное чтение записи и возвращает её вместе с идентификатором пользователя, трассы и исходного действия. `duplicate` принимает `guid` и создаёт копию записи вложенным `save`; в журнале строка копии ссылается на строку `duplicate` через `parentActionGuid`.

Ошибка входных данных возвращает HTTP 400 с `error` и `fields`. В `fields` перечислены пути полей от начала операции через точку, например `payload.fields.name` или `payload.fields.lines.0.text` для поля первой строки табличной части. Отсутствие права возвращает 403 с `error` и ключом недостающего права в `right`, неизвестный объект, действие или запись — 404. Ошибка базы возвращает 500 без текста SQL и параметров.

Отдельная строка `search` в `payload` действия `list` ищет буквальную подстроку в любой колонке из описания списка. Пустая строка отключает поиск; значение другого типа даёт 400. Поиск соединяется с условиями `filter` через «и». Сервер сначала применяет SQL-отбор, затем читает кандидатов порциями по 500 строк, проверяет оставшиеся условия и поиск, считает общее число совпадений и выбирает страницу в заданном порядке сортировки. Соседние колонки не склеиваются; скрытые GUID и пометка удаления не участвуют в поиске. Строки, числа, суммы и даты используют общий формат отображения, логические значения ищутся по словам «Да» и «Нет».

Ссылки, полные ссылки и регистратор ищутся по общему представлению записи: наименование справочника либо заголовок, номер и дата документа. Перед чтением целевого объекта сервер проверяет право чтения. Связанные записи загружаются пакетами по целевым объектам, не более 500 ссылок на пакет; каждая ссылка читается один раз за запрос. Отсутствующие и недоступные записи не дают совпадения. Ответ `list` также содержит `presentations`: словарь представлений только выбранной страницы, где ключ является JSON-массивом `[kind, name, guid]`, а значение равно тексту либо `null`, если доступного текста нет. Клиент показывает эти представления вместо названий из кеша, поэтому отображение соответствует серверному поиску.

Описания объектов и форм клиент получает через `GET /api/metadata`. Маршрут требует входа и возвращает только доступные пользователю объекты, действия и страницы.

### Стандартные действия

| Действие | Справочник | Документ | Регистр движений | Смысл |
|---|:-:|:-:|:-:|---|
| `list` | + | + | + | Список с фильтрами, сортировкой и страницами |
| `get` | + | + | | Один объект со всеми полями и табличными частями |
| `save` | + | + | | Запись объекта: новый без `guid`, существующий с `guid` |
| `markDeleted` | + | + | | Установить пометку удаления |
| `unmarkDeleted` | + | + | | Снять пометку удаления |
| `post` | | + | | Провести документ: записать движения регистров |
| `unpost` | | + | | Отменить проведение: удалить движения |

Регистры движений напрямую не изменяются: их записывают только документы при проведении. Остальные стандартные действия для регистра движений возвращают 404 с объяснением.

### Действия регистра сведений

Цель операции: `{ "kind": "informationRegister", "name": "sample" }`. Доступны четыре стандартных действия:

| Действие | `payload` | Результат |
|---|---|---|
| `get` | `{ "dimensions": { "source": "system", "externalObject": "one" } }` | Все измерения и ресурсы; отсутствующая запись даёт 404 |
| `list` | Обычные `filter`, `sort`, `page`, `pageSize` | Страница сведений; можно отбирать по одному измерению |
| `save` | `{ "fields": { "source": "system", "externalObject": "one", "description": "Описание", "item": "<guid>" } }` | Созданная либо обновлённая запись |
| `delete` | `{ "dimensions": { "source": "system", "externalObject": "one" } }` | `{ "dimensions": { "source": "system", "externalObject": "one" }, "deleted": true }`; отсутствующая запись даёт 404 |

Каждый ключ передаётся целиком. Порядок свойств JSON значения не имеет. Пропущенное, null или пустое строковое измерение, неверный тип либо неизвестное имя поля дают 400. Значения 0 и false допустимы для измерений соответствующих видов. Посторонние свойства оболочки, в том числе технический guid, также отклоняются. `save` заменяет все ресурсы: пропущенные необязательные ресурсы становятся `null`, а обязательные нужно передать. Технического идентификатора для обновления нет: другой набор измерений создаёт другую запись. Чтобы перенести сведения на другой ключ, вызывающий код удаляет старую запись и создаёт новую в одном пакете или собственном действии. Стабильный порядок списка при одинаковой сортировке задают все измерения.

`get` и `list` требуют `Rights.informationRegister.<имя>.read`, `save` и `delete` требуют `write`. Те же действия доступны через `ActionDispatcher` в бизнес-логике; вложенная запись, прикладные проверки и журнал используют транзакцию внешнего действия. Отказ в праве или ошибка откатывают всю цепочку. Пробное действие справочника `checkInformationRollback` создаёт объект и сведения, затем возвращает ошибку 400: ни одна из записей и ни одна строка журнала не сохраняются.

Политика `save` получает прежнюю запись (либо `null`) и предлагаемую, политика `delete` получает существующую запись в `record`. При удалении сведения исчезают физически, а журнал сохраняет измерения в `targetKey` и значения полей до удаления в `changes`; значения после удаления равны `null`. У строки журнала сведений `targetGuid` равен `null`. `history` принимает `targetKey` с полным набором измерений для отбора истории одной записи. Без ключа возвращает историю всего регистра. Новая nullable-колонка журнала добавляется обычной синхронизацией и сохраняет прежние строки.

### Документы и проведение

- **Нумерация.** Номер и признак проведения заполняет платформа, во входных данных `save` их нет. Новый документ получает наибольший номер своего вида плюс один, дополненный нулями до шести знаков: `000001`, `000002`. Номер выдаётся внутри изменяющей транзакции, а они выполняются по очереди, поэтому два документа не получат один номер. Нумерация сквозная, без разбиения по годам и префиксов.
- **Проведение.** `post` отмечает документ проведённым, удаляет его прежние движения во всех регистрах и записывает строки, которые вернул обработчик проведения. Поэтому повторное проведение не дублирует движения. Удаляются строки всех регистров, а не только тех, куда пишет обработчик: при других данных документа обработчик может перестать писать в регистр. Строки проверяются по описанию регистра так же, как входные данные записи; ошибка возвращает 400 и отменяет проведение вместе с транзакцией. Номера строк сквозные внутри регистра для одного документа. Документ без обработчика проведения тоже можно провести: движений у него нет.
- **Отмена проведения.** `unpost` удаляет движения документа и снимает признак проведения.
- **Шаги проведения.** Правила «провести» и «отменить проведение» заданы один раз в модуле `data/posting.ts` и собраны из шагов. Шаг — функция от состояния документа (описание и запись с табличными частями) к новому состоянию: проверка пометки удаления, установка признака проведения или пометки удаления, удаление строк регистров, запись строк регистров, перечитывание записи. Шаг, меняющий признак, сам обновляет запись в состоянии, поэтому между шагами документ не перечитывается. Проведение читает документ из базы дважды: в начале и после обработчика проведения, который через вложенные действия может изменить сам документ. Действия `post`, `unpost`, `markDeleted`, `unmarkDeleted` и завершение `save` собраны из составных шагов проведения и отмены проведения; политики проверяются диспетчером перед запуском этих действий. Журнал пишет диспетчер по всему действию, а не шаги (раздел «Журнал действий»).
- **Запись проведённого документа.** `save` проведённого документа заново записывает его движения, чтобы они соответствовали новым данным. Признак проведения сохраняется.
- **Пометка удаления.** Платформенное действие при пометке проведённого документа отменяет его проведение, чтобы помеченный документ не влиял на обороты. Политика пробных документов запрещает такую пометку до явной отмены проведения. Снятие пометки документ не проводит. Документ с пометкой удаления провести нельзя, `post` возвращает 400.
- **Строки регистра.** `list` регистра возвращает строки с регистратором `{ "document": "…", "guid": "…" }`, периодом, номером строки, измерениями и ресурсами. Отбор по регистратору принимает такое же значение: `{ "field": "recorder", "operator": "equals", "value": { "document": "sample", "guid": "…" } }`. Регистратор хранится в двух колонках. Оба способа сравнения выполняются в SQL: `equals` — двумя условиями через `AND`, `notEquals` — группой `recorderDocument != ? OR recorderGuid != ?`. Сортировать по регистратору нельзя.

### Собственные действия

Объект может объявить собственные действия в метаданных: входные данные и обработчик на Effect. Право на действие объявлять не нужно: каждое собственное действие получает своё право автоматически. Они вызываются через тот же эндпоинт: `"action": "dismiss"`.

### Выполнение действия

1. Nest-контроллер принимает запрос и передаёт тело диспетчеру. Больше контроллер ничего не делает; отдельный фильтр переводит ошибки в HTTP.
2. Диспетчер находит объект и действие в реестре метаданных.
3. Бизнес-гвард `RightsGuardPlatform` проверяет право пользователя на это действие; без права операция завершается ошибкой 403.
4. Входные данные проверяются Effect Schema, построенной из описания полей.
5. Открывается транзакция.
6. Перед изменением объекта выполняются обработчики политик конфигурации, объявленные для выбранного действия.
7. Выполняется действие.
8. В журнал записывается строка о действии, если действие изменяющее.
9. Транзакция фиксируется. При ошибке откатываются и данные, и журнал.

Шаги 2–9 — это Effect-программа. Ошибки описаны через `Data.TaggedError` и в одном месте переводятся в HTTP-ответы.
Перед шагом 2 сервер проверяет access-токен и передаёт `userGuid` вошедшего пользователя в контекст действия. Выполняются все шаги. Транзакция в текущей реализации открывается на весь запрос до шага 2, поэтому отказ в праве на одну операцию пакета откатывает и предыдущие операции.

## Вход в приложение

- `POST /api/authentication/login` принимает `{ "pin": "1234" }` и возвращает новую пару токенов в cookie. PIN содержит от 4 до 12 цифр и однозначно определяет пользователя.
- `POST /api/authentication/refresh` однократно расходует refresh-токен и заменяет обе cookie. `POST /api/authentication/logout` отзывает refresh-токен и удаляет cookie. Эти запросы не требуют тела.
- Оба токена передаются в cookie с флагами `HttpOnly` и `SameSite=Strict`; при HTTPS включается `Secure`. Cookie access доступна на `/api`, refresh — только на `/api/authentication`.
- Access-токен подписан производным от секрета настроек ключом и действует 15 минут. `POST /api/perform` проверяет его подпись, срок, активность пользователя и неотозванную сессию; отсутствие или недействительность токена даёт 401. Refresh-токен действует семь дней. После обновления или выхода прежний access-токен перестаёт работать вместе с прежней сессией.
- Сроки действия токенов и их cookie задают переменные окружения `ACCESS_TOKEN_LIFETIME_SECONDS` и `REFRESH_TOKEN_LIFETIME_SECONDS` в секундах; без них действуют 15 минут и семь дней. Значение, которое не является положительным целым числом, останавливает запуск. Короткие сроки нужны для проверки обновления токенов без ожидания настоящего истечения: `ACCESS_TOKEN_LIFETIME_SECONDS=20 REFRESH_TOKEN_LIFETIME_SECONDS=90 npm run start:check -- --test-pin=482915 --port=3101`.
- Refresh-токены хранятся в БД в виде хеша. При обновлении старый refresh-токен отзывается и выдаётся новый, поэтому украденный и уже использованный токен повторно не сработает.
- PIN не хранится в открытом виде. В таблице пользователей лежит HMAC-SHA-256 от PIN с секретным ключом из файла настроек. Такой хеш при одинаковом PIN всегда одинаков, поэтому пользователя можно найти по уникальному индексу.
- После пяти неверных PIN с одного адреса сервер блокирует вход с него на 15 минут и отвечает 429. Счётчик хранится в памяти процесса и сбрасывается при перезапуске. Адрес берётся из соединения, клиентским заголовкам прокси сервер не доверяет.
- Пользователи, их роли и токены хранятся в служебных таблицах платформы.
- Первого пользователя можно создать через одноразовое поле `initialUser` в локальном файле настроек: `{ "name": "Имя", "pin": "PIN" }`. При запуске с пустой таблицей пользователей сервер записывает его с HMAC PIN и назначает ему роли из необязательного списка `roles`: `{ "name": "Имя", "pin": "PIN", "roles": ["administrator"] }`. Без списка первый пользователь получает все роли конфигурации. Роль, которой нет в конфигурации, останавливает запуск. После успешного запуска удалите `initialUser` из файла: существующий пользователь сохраняется в базе, а PIN больше не лежит в настройках. На непустой базе поле не создаёт и не меняет пользователя. Секрет `pinHmacSecret` после создания пользователя менять нельзя без переназначения его PIN.

## Права (RBAC)

### Права

Права не объявляются вручную: их даёт сам объект конфигурации. Соответствие действий и прав задано один раз в `src/server/authorization/rights.ts`:

| Право | Виды объектов | Действия |
|---|---|---|
| `read` | справочник, документ, регистр сведений | `list`, `get` |
| `read` | регистр движений | `list` |
| `write` | справочник, документ | `save`, `markDeleted`, `unmarkDeleted` |
| `write` | регистр сведений | `save`, `delete` |
| `post` | документ | `post`, `unpost` |
| `actions.<имя>` | справочник, документ | собственное действие с этим именем |

Чтение журнала — отдельное право платформы `Rights.platform.journal.read`: журнал показывает изменения всех объектов.

Страница конфигурации даёт право `Rights.page.<имя>.open` с ключом `page.<имя>.open`. Оно управляет только видимостью: без него страницы нет в меню и в ответе `GET /api/metadata`, а её адрес показывает «не найдено». Доступ к данным, которые страница читает и изменяет, проверяет единый эндпоинт по правам объектов. Поэтому страница, открытая без права на объект, покажет отказ сервера, а не данные.

Конфигурация указывает права переменными объекта `Rights`, а не строками: `Rights.catalog.employees.read`, `Rights.document.shift.post`, `Rights.catalog.employees.actions.dismiss`. Объект строит генератор реестра в `configuration.generated.ts` из модулей объектов и объявлений страниц, а его тип TypeScript выводит из типов билдеров. Право несуществующего объекта, действия или страницы — ошибка компиляции. У права есть ключ, например `catalog.employees.write`; права сравниваются по ключу.

### Роли

Роли описываются билдерами в `src/configuration/roles.ts`:

```ts
import { role } from '../server/authorization/roles.js';
import { Rights } from './configuration.generated.js';

export const roles = [
    role('administrator').title('Администратор').grantAll(),
    role('reader').title('Только чтение').grant(Rights.catalog.employees.read, Rights.document.shift.read),
];
```

- `grant(...)` добавляет роли права. `grantAll()` даёт все права, включая права объектов, действий и страниц, которые появятся позже.
- Имя роли — lowerCamelCase латиницей, имена не повторяются. Ошибка в описании ролей останавливает запуск.
- Связь пользователя с ролями хранится в таблице `platform_user_roles` именами ролей. Состав прав роли берётся из конфигурации, поэтому изменение роли действует на всех её пользователей после перезапуска. Имя роли, которой больше нет в конфигурации, прав не даёт.
- Права пользователя — объединение прав его ролей. У пользователя без ролей прав нет.
- Роли назначаются пользователям при их создании при запуске: первому пользователю из настроек (раздел «Вход в приложение») и тестовым пользователям режима памяти (раздел «Сборка и запуск»). Сейчас в конфигурации две роли для пробных объектов: `administrator` и `reader`.

### Проверка прав

- Права проверяет **бизнес-гвард** `RightsGuardPlatform` — единственный механизм, который сравнивает права с ролями пользователя. Цель операции единого эндпоинта известна только из тела запроса, поэтому проверка выполняется в диспетчере, а не на маршруте.
- Диспетчер вызывает гвард перед каждой операцией, в том числе вложенной. Вложенное действие проверяется по правам того же пользователя: право на собственное действие не даёт доступа к объектам, которые оно читает или изменяет через диспетчер. Отказ возвращает 403 и откатывает транзакцию запроса.
- Роли пользователя читаются из базы при каждой проверке через дескриптор текущей транзакции. В токене права не хранятся.
- Неизвестные объект и действие дают 404 независимо от прав.
- Для маршрутов вне единого эндпоинта есть декоратор `@RequireRights(Rights.…)`. Он подключает проверку входа и Nest-гвард `RightsGuardNest`, который передаёт права маршрута тому же `RightsGuardPlatform` и при отказе отвечает 403. Модуль контроллера импортирует `AuthenticationModule` и `AuthorizationModule`.
- `GET /api/metadata` отбирает описания тем же гвардом: объект без права чтения в ответ не входит, а из действий формы остаются только разрешённые. Страница входит в ответ только при праве её открыть. Из схемы оболочки недоступные объекты и страницы тоже убираются.

## Политики записи

Прикладные ограничения задаёт конфигурация через `.policy(...)` в описании объекта. У политики есть необязательные обработчики `save`, `post`, `unpost`, `markDeleted`, `unmarkDeleted` и `delete`: отсутствие обработчика не ограничивает соответствующее действие. Проверка `save` получает существующую запись (`null` у новой) и предлагаемую; проверки проведения получают существующий документ, а проверки пометки и физического удаления получают существующую запись. Для каждого изменяющего действия диспетчер строит команду с аргументами политик и эффектом выполнения. Общий конвейер читает запись, строит команду без изменяющих запросов, вызывает все применимые политики, исполняет команду и записывает результат в журнал. Только журнал после выполнения сравнивает исходную и полученную записи для списка изменённых полей; политика получает состояния, нужные её действию, до изменения базы. Все шаги идут в одной транзакции. Ошибка политики возвращает 409 с объяснением и откатывает весь пакет операций. Чтение политик не вызывает. Прямое изменение движений недоступно; сохранение и физическое удаление сведений вызывают политики.

Пробный пример закрытия периода состоит из документа «Закрытие периода» и переиспользуемой политики конфигурации. Поле «Закрыто по» содержит календарную дату включительно; дата самого документа показывает, когда закрытие оформили. Политика читает максимальную границу среди проведённых и не помеченных на удаление закрытий. Она подключена к пробному документу по его стандартной дате: при сохранении проверяет прежнюю и предлагаемую даты, при остальных изменениях — дату существующей записи. Если закрытий нет, запись разрешена. Прикладные объекты с другой учётной датой могут использовать тот же механизм с собственным извлекателем дат. Другая политика запрещает помечать проведённый документ на удаление; она подключена к пробному документу и к документу закрытия. Конкретный порядок повторного открытия периода ещё требует решения; пока граница меняется при отмене проведения или изменении документов закрытия.

Собственное действие, вызывающее `save` или `post` через `ActionDispatcher`, проходит те же проверки. В окружении собственных действий, обработчиков проведения и политик `Database` разрешает только чтение; попытка выполнить прямой изменяющий SQL прерывает и откатывает транзакцию. Платформенные шаги проведения продолжают пользоваться полным доступом к базе.

## Журнал действий

### Контекст действия

При каждом входящем запросе создаётся контекст действия — Effect-сервис `ActionContext`:

| Поле | Смысл |
|---|---|
| `userGuid` | Пользователь, запустивший исходное действие |
| `traceGuid` | Общий идентификатор цепочки действий одного запроса |
| `actionGuid` | Идентификатор текущего действия |
| `parentActionGuid` | Действие, которое вызвало текущее; пусто у исходного |

Контекст передаётся через окружение Effect, пробрасывать его параметрами не нужно. Если одно действие вызывает другое (например, проведение документа запускает пересчёт), вложенный вызов проходит через диспетчер и получает новый `actionGuid`. `traceGuid` и `userGuid` наследуются, поэтому любое вложенное действие приводит к пользователю, который начал цепочку.

### Запись журнала

Одно логическое действие над объектом даёт **одну** строку журнала, сколько бы полей ни изменилось:

| Колонка | Содержимое |
|---|---|
| `guid` | Идентификатор записи |
| `occurredAt` | Время действия |
| `userGuid`, `traceGuid`, `actionGuid`, `parentActionGuid` | Из контекста действия |
| `targetKind`, `targetName`, `targetGuid`, `targetKey` | Объект и запись: guid справочника или документа либо измерения сведений |
| `action` | `save`, `post`, `markDeleted`, собственное действие и т. д. |
| `changes` | JSON с изменёнными полями: `{ "поле": { "before": …, "after": … } }`, включая изменения табличных частей. Для нового объекта — все заполненные поля |

Журнал пишется в той же транзакции, что и данные: откат пакета или ошибка вложенного действия удаляют и строки журнала. Действие, завершившееся ошибкой, строки не оставляет. Чтение данных (`get`, `list`) не журналируется.

- **Стандартные изменяющие действия** (`save`, `markDeleted`, `unmarkDeleted`, `post`, `unpost`) журналирует диспетчер. Перед действием он читает запись, после действия сравнивает её с записью, которую вернуло действие. Поэтому одна строка содержит все изменения действия, сколько бы запросов оно ни выполнило: пометка удаления проведённого документа даёт одну строку с изменениями `deletedAt` и `posted`. Движения регистров в `changes` не входят: их определяет проведение, а оно видно по `posted` и по действию `post`.
- **Табличная часть** записывается в `changes` целиком: списки строк до и после действия. У строк нет собственного идентификатора, поэтому сопоставить отдельные строки до и после замены нельзя.
- **Новый объект** получает в `changes` все заполненные поля и непустые табличные части со значением `before`, равным `null`. `guid` в `changes` не входит, он хранится в `targetGuid`.
- **Действие без изменений**, например запись тех же значений, тоже даёт строку с пустым `changes`: пользователь выполнил действие, и журнал это фиксирует.
- **Собственное действие** даёт строку с пустыми `targetGuid` и `changes` (`null`). Платформа не знает, что изменил обработчик: изменения записей видны в строках вложенных действий, а строка собственного действия связывает их с вызовом. Строку получает и собственное действие, которое только читает данные, например `inspect`.
- `occurredAt` — время начала действия. Вложенные действия завершаются и записывают строки раньше родителя, но по времени начала идут после него.

Таблица `platform_journal` имеет индексы по времени, по объекту, по пользователю и по трассе. Прежняя структура таблицы, которая не заполнялась, заменяется миграцией `20260929_journal_columns`.

### Чтение журнала

Журнал читается через `POST /api/perform` с целью `{ "kind": "platform", "name": "journal" }`. Строки возвращаются с колонками таблицы; `changes` и `targetKey` возвращаются разобранными JSON. Чтение журнала само в журнал не записывается.

| Действие | `payload` | Результат |
|---|---|---|
| `history` | `targetKind`, `targetName`, необязательный `targetGuid` или `targetKey`, `page`, `pageSize` | История записи или, без ключа, всех записей объекта |
| `userActions` | `userGuid`, `page`, `pageSize` | Действия пользователя, включая вложенные |
| `trace` | `traceGuid` | Дерево цепочки: `{ traceGuid, actions }` |

`history` и `userActions` возвращают страницу `{ items, total, page, pageSize }` с теми же ограничениями, что `list`, новые действия первыми. Действия, начатые в одну миллисекунду, упорядочиваются по порядку записи строк. `trace` возвращает внешние операции запроса в порядке выполнения; у каждой в `children` лежат вложенные действия. Действие, родитель которого строки не оставил, становится корнем. Неизвестный объект в `history` и неизвестное действие журнала дают 404, неверный guid — 400.

## Интерфейс (SDUI)

- Сервер отдаёт JSON-описания форм и списков: поля, типы, ссылки на справочники, табличные части, группы, порядок обхода, доступные действия с учётом прав.
- Вместе с ними сервер отдаёт схему оболочки: подсистемы, их группы, объекты и страницы в группах. Состав меню задаёт конфигурация, а не клиент.
- Экран, который не сводится к списку или форме, конфигурация объявляет страницей: её компонент входит в сборку клиента, а сервер отдаёт только её имя и заголовок. См. «Страницы конфигурации».
- Описание по умолчанию строится из метаданных. В метаданных его можно переопределить: сгруппировать поля, скрыть поле, изменить подпись.
- Клиент рендерит описание через реестр виджетов: каждому виду поля соответствуют поле ввода и компонент отображения на Ant Design.
- Правила проверки (обязательность, границы, длина) входят в описание формы, и клиент проверяет по ним ввод до отправки. Окончательную проверку выполняет сервер.
- Из Refine используется ядро `@refinedev/core`: ресурсы, маршрутизация, хуки данных. Компоненты форм и списков — собственные, на Ant Design.
- Экраны собираются из web SDK (`src/web/sdk`): стандартные форма записи и список объекта и собственные экраны конфигурации используют одни и те же компоненты и хуки. См. «Web SDK».
- Refine подключается через собственный data provider, который переводит свои методы в вызовы `/api/perform`.
- Лёгкие вычисления клиент выполняет сам. Сложные оформляются собственным действием на сервере.

### Формат описаний

`GET /api/metadata` требует входа и возвращает `{ "objects": [...], "pages": [...], "shell": {...} }`: объекты конфигурации, которые пользователь вправе читать, и страницы, которые он вправе открывать, в порядке файлов реестра, а также схему оболочки (подраздел «Схема оболочки»). Страница описана именем и заголовком: `{ "name", "title" }`. Типы формата лежат в `src/server/ui/descriptions.ts`. В этом файле нет импортов Nest и Effect, поэтому клиент импортирует его напрямую. Описания строятся в `src/server/ui/views.ts` из тех же метаданных, что таблицы базы и схемы проверки входных данных, поэтому набор полей и правила проверки на форме совпадают с тем, что примет сервер. Полные описания строятся один раз при первом запросе, отбор по правам выполняется при каждом запросе.

Описание объекта (`ObjectView`): `kind`, `name`, `title`, `form` и `list`. У регистров `form` равен `null`: их строки записывают только документы.

Описание формы (`FormView`):

| Свойство | Содержимое |
|---|---|
| `fields` | Поля на форме в порядке объявления: `name`, `title`, `kind`, `target` (объект ссылки), `readOnly`, `rules`, `inputElement` — имя собственного элемента на месте поля ввода либо `null` |
| `tableParts` | Табличные части: `name`, `title`, `columns` — поля строки в том же формате |
| `groups` | Раскладка: `{ title, elements }`. Строка в `elements` — имя поля или табличной части, объект `{ element }` — собственный элемент конфигурации. Каждое поле и каждая табличная часть входят ровно в одну группу |
| `traversal` | Порядок обхода с клавиатуры: имена редактируемых полей и табличных частей. Собственных элементов групп в нём нет |
| `actions` | Действия формы: `name`, `title`, `standard`, `input` — поля входных данных собственного действия |
| `creationMode` | Режим, в котором форма новой записи открывается по умолчанию: `tab` — во вкладке, `dialog` — в модальном окне |

- `rules` содержит правила проверки: `required`, `minimumLength`, `maximumLength`, `minimum`, `maximum`, `integer`. Обязательная строка не может быть пустой. Значение денег и их границы указаны в копейках.
- `readOnly` получают поля, которые заполняет платформа: `number` и `posted` документа. Они показываются на форме, но не входят в порядок обхода. `guid` и `deletedAt` на форму не выводятся.
- Стандартные действия справочника — `save`, `markDeleted`, `unmarkDeleted`; у документа к ним добавляются `post` и `unpost`. За ними идут собственные действия объекта. В описание попадают только действия, на которые у пользователя есть право; форму без `save` клиент показывает только для просмотра.

Описание списка (`ListView`):

Над списком есть поле «Поиск» с очисткой, отдельно от условий отбора. Введённый текст применяется через 300 мс после последнего изменения, а очистка без задержки убирает только поиск. Применение поиска возвращает список на первую страницу, сохраняя отборы и сортировку. Клиент передаёт текст в `search` действия `list`.

| Свойство | Содержимое |
|---|---|
| `columns` | Поля записи, кроме стандартных `guid` и `deletedAt`; `role` различает измерения (`dimension`) и ресурсы (`resource`) |
| `filters` | Отборы: поле и допустимые способы сравнения `operators` |
| `sortable` | Поля, по которым можно сортировать; регистратор не сортируется |
| `defaultSort` | Сортировка при открытии: справочник по наименованию, документ по дате и номеру от новых к старым, движения по периоду от новых к старым, сведения по измерениям в порядке объявления |
| `deletionMark` | У записей есть пометка удаления; клиент показывает её признаком строки, а не колонкой |

Способы сравнения зависят от вида поля: у строк — `contains`, `equals` и `notEquals`; у чисел, денег, дат и дат со временем — `equals`, `notEquals`, `greater`, `greaterOrEqual`, `less`, `lessOrEqual` и `contains`; у логических значений, ссылок и регистратора — `equals` и `notEquals`. `contains` ищет подстроку без учёта регистра, а `%` и `_` в ней — обычные символы. Общий модуль формата значений рядом с форматом описаний используется клиентом для отображения и сервером для поиска: правило перевода копеек в рубли, десятичная запятая и вид даты задаются один раз. Для `contains` интерфейс предлагает свободный текстовый ввод, в том числе части даты или суммы; при переходе к точному сравнению или обратно прежнее значение очищается. Соответствие видов полей и способов сравнения задано в формате описаний (`filterOperators`), и действие `list` принимает те же способы, поэтому отбор из описания всегда можно передать в `list` без перевода.

### Переопределение формы

По умолчанию форма состоит из одной группы без заголовка: поля в порядке объявления, затем табличные части. `.form(...)` в описании объекта меняет раскладку:

```ts
.form((form) => form
    .group('Основное', ['item', 'date', 'number'])
    .group('Строки документа', ['lines', SampleTotal])
    .hide('posted')
    .title('comment', 'Примечание')
    .input('comment', SampleComment)
    .creation('dialog'))
```

- `group(title, elements)` выводит поля и табличные части группой с заголовком. Группы идут в порядке объявления, элементы внутри группы — в указанном порядке. Элементы, не попавшие ни в одну группу, собираются после групп в группу без заголовка.
- `hide(name)` убирает поле или табличную часть с формы и из порядка обхода.
- `title(name, title)` меняет подпись на форме; в списке остаётся подпись из описания поля.
- Порядок обхода следует за раскладкой групп, поэтому перестановка групп и элементов меняет и его.
- Собственный элемент формы (подраздел «Элементы формы») указывается билдером из файла объявления. В группе он стоит наравне с полями и табличными частями, занимает всю ширину группы и в порядок обхода не входит. Вне группы элемент поставить нельзя.
- `input(field, element)` назначает элемент полем ввода для поля. На форме он заменяет виджет вида поля, а поле остаётся на своём месте в раскладке и в порядке обхода, с той же подписью и проверкой. Реестр виджетов при этом не меняется: в списке и в отборе поле выводится стандартным виджетом.
- Элемент назначается полю в метаданных, а не выбирается клиентом по имени поля: раскладка и порядок обхода строятся на сервере, и `commit()` проверяет их целиком.
- `creation(mode)` задаёт режим создания записи: `tab` открывает форму новой записи во вкладке, `dialog` — в модальном окне поверх списка. Без вызова запись создаётся во вкладке. Это умолчание, а не запрет: место вызова может указать режим само (команда открытия записи в разделе «Web SDK»), а адрес `/<вид>/<имя>/new` всегда открывает вкладку. На существующие записи режим не действует. Режим задаётся один раз. В окне создаются записи справочников «Номенклатура» и «Физические лица»: полей на их формах немного.

Переопределение действует только на форму. Ошибки переопределения обнаруживает `commit()` при запуске (раздел «Проверки при сборке»).

### Схема оболочки

Оболочка состоит из подсистем, подсистема из групп, группа из ссылок на объекты и страницы конфигурации. Схема описывается билдером в `src/configuration/shell.ts`:

```ts
import { shell } from '../server/ui/shell.js';
import { Employees } from './catalogs/employees.catalog.js';
import { Shift } from './documents/shift.document.js';
import { ShiftWorkplace } from './pages/shift-workplace.page.js';

export const applicationShell = shell()
    .subsystem('masterData', (subsystem) => subsystem
        .title('НСИ')
        .group('Справочники', [Employees])
        .group('Документы', [Shift])
        .group('Рабочие места', [ShiftWorkplace]));
```

- Подсистемы, группы и пункты группы показываются в порядке описания. Объекты и страницы стоят в группе в общем порядке. Имя подсистемы отличает её от остальных, пользователь видит заголовок.
- Объект и страница указываются импортированными билдерами, а не строками. Один объект или страницу можно указать в нескольких группах и подсистемах: содержимое подсистемы — список ссылок.
- Вся проверка выполняется типами при `npm run typecheck`: значение, которое не является билдером объекта или страницы, и повтор имени подсистемы не компилируются. Имена подсистем накапливаются в параметре типа билдера оболочки. При запуске сервера схема не проверяется.
- Объект, не указанный в схеме, в окнах подсистем не показывается, но его список открывается по адресу, а форма записи — по ссылке из другой записи. Страница, не указанная в схеме, открывается по адресу. Предупреждений об этом нет: объект или страница могли быть скрыты намеренно.
- Файл схемы один, путь к нему постоянный, поэтому генератор реестра его не ищет: сервер импортирует его напрямую, как файл ролей.

В ответе `GET /api/metadata` схема лежит в свойстве `shell`: `{ "subsystems": [{ "name", "title", "groups": [{ "title", "items": [{ "kind", "name" }] }] }] }`. У пункта-страницы `kind` равен `page`, у объекта это его вид. Сервер оставляет в схеме только объекты, которые пользователь вправе читать, и страницы, которые он вправе открывать. Группа без таких пунктов, в том числе пустая в конфигурации, и подсистема без групп в ответ не попадают. Заголовок объекта клиент берёт из его описания в `objects`, заголовок страницы — из `pages`.

### Каркас клиента

Все модальные окна сохраняют открытое состояние и введённые значения при нажатии на затемнённую область вокруг окна. Это правило задано один раз в общем провайдере Ant Design и действует также на новые окна. Окно закрывается крестиком, клавишей Esc или переходом из самого окна; кнопки «Отмена» и «Выполнить» сохраняют своё назначение. Пока собственное действие выполняется, окно его входных данных не закрывается: Esc отключён, крестик и «Отмена» недоступны. После отказа сервера окно остаётся открытым с ошибками полей и снова допускает закрытие.

Каркас — это сессия, data provider, приложение Refine, ресурсы которого строятся из описаний объектов, список подсистем из схемы оболочки и вкладки открытых окон. Формы и списки объектов работают поверх него и описаны в подразделах «Web SDK», «Реестр виджетов», «Ссылки», «Списки» и «Формы».

#### Сессия и запросы к API

- Все запросы приложения идут через один экземпляр axios (`src/web/common/api.ts`). Ошибка запроса приводится к `ApiError`: статус HTTP, текст сервера, а для единого эндпоинта ещё пути полей с ошибками проверки (`fields`) и ключ недостающего права (`right`). Если ответ не получен, статус равен 0.
- Токены лежат в `HttpOnly`-cookie, поэтому клиент не видит ни их, ни срок их действия и судит о сессии по ответам сервера. Ответ 401 принимает перехватчик axios (`src/web/authentication/session.ts`): он обновляет токены запросом `POST /api/authentication/refresh` и повторяет исходный запрос. Вызывающий код получает ответ повтора, поэтому истёкший access-токен не виден ни TanStack Query, ни интерфейсу.
- Обновление токенов одно на всю страницу. Refresh-токен одноразовый: если бы каждый запрос, получивший 401, обновлял токены сам, сервер принял бы только первое обновление. Одновременные запросы ждут общего обновления. Запрос запоминает номер пары токенов, с которой отправлен; если к приходу ответа 401 пара уже заменена, запрос только повторяется.
- Сессия считается завершённой, когда 401 вернул и повтор запроса. Отказ в самом обновлении её ещё не завершает: токены могла заменить соседняя вкладка, у которой общие cookie.
- Состояние сессии хранится в TanStack Store: `unknown` — приложение только открыто, `active` — сервер принял запрос пользователя, `ended` — сервер отказал после обновления токенов либо пользователь вышел. По состоянию auth provider Refine отвечает на проверку входа. Отдельного запроса «кто я» у сервера нет, поэтому при открытии приложения состояние выясняет загрузка описаний объектов.
- При завершении сессии данные и описания объектов удаляются из кеша TanStack Query: следующий вошедший пользователь не увидит данных предыдущего.

#### Data provider

Refine называет ресурс одной строкой, а сервер различает объекты по виду и имени. Имя ресурса состоит из вида и имени объекта через точку: `catalog.sample`. Методы data provider (`src/web/data-provider/data-provider.ts`) переводятся в действия единого эндпоинта:

| Метод Refine | Действие | Входные данные |
|---|---|---|
| `getList` | `list` | Отбор, сортировка и страница; условие отбора с текстом поиска передаётся параметром `search` |
| `getOne` | `get` | `id` — `guid` записи |
| `getMany` | пакет действий `get` | `ids`: перечень `guid`; одновременные вызовы уходят одним запросом |
| `create` | `save` без `guid` | `variables` — значения полей и табличные части, как в `payload.fields` |
| `update` | `save` с `guid` | `id` и `variables`; запись заменяется целиком |
| `deleteOne` | `markDeleted` | `id` — `guid` записи |
| `custom` | любое, в том числе собственное | `url` — ресурс и действие через косую черту: `document.sample/post`, `platform.journal/history`; `payload` — входные данные действия |

- Запись возвращается в том виде, в каком её отдал сервер. Её идентификатор — `guid`; поля `id`, принятого в Refine, у записей нет.
- Операторы отбора Refine переводятся в способы сравнения сервера: `eq` — `equals`, `ne` — `notEquals`, `gt` — `greater`, `gte` — `greaterOrEqual`, `lt` — `less`, `lte` — `lessOrEqual`, `contains` — `contains`. Операторы `null` и `nnull` становятся сравнением с `null`. Группа `and` раскрывается в общий список условий. Группа `or` и остальные операторы завершаются ошибкой: молча пропущенное условие показало бы лишние записи.
- В режиме страниц `server` запрашивается одна страница. В режимах `client` и `off` Refine ждёт все записи сразу, и data provider читает их страницами по 500 записей, пока не получит все.
- Метод HTTP в `custom` значения не имеет: единый эндпоинт принимает только `POST`.

#### Ресурсы, подсистемы и адреса

- Ресурсы Refine строятся из ответа `GET /api/metadata`: один ресурс на объект конфигурации. Ресурсы плоские, без ресурсов-групп: один объект может стоять в нескольких группах схемы оболочки, поэтому меню строится из схемы, а не из ресурсов.
- Слева показан список подсистем из схемы оболочки. Нажатие на подсистему открывает модальное окно с её группами. Пункт группы — ссылка на список объекта или на страницу конфигурации; переход по ней закрывает окно. Слева от названия пункта стоит иконка: у объекта по его виду (справочник, документ, регистр оборотов, регистр сведений), у страницы собственная. Иконку выбирает клиент по виду пункта.
- Подсистема не подсвечивается по открытой странице: страница объекта не принадлежит одной подсистеме.
- Адреса: `/<вид>/<имя>` открывает список объекта, например `/catalog/sample`; `/<вид>/<имя>/new` и `/<вид>/<имя>/<guid>` открывают форму записи; `/page/<имя>` открывает страницу конфигурации; `/` открывает главный экран. Главный экран пуст: объекты пользователь открывает из окон подсистем. Список, форма и страница конфигурации открываются во вкладках, см. «Вкладки открытых окон».
- Страница конфигурации открывается, если её имя есть и в ответе сервера, и в реестре страниц клиента (`pages.generated.ts`). Неизвестное имя и страница без права показывают «не найдено»: для клиента они неразличимы. Пока страница не задала заголовок сама, вкладка показывает заголовок из объявления.
- Всё приложение закрыто проверкой входа. Без сессии на его месте показывается экран входа, а адрес не меняется: отдельного адреса у экрана входа нет. Поэтому после входа открывается та же страница, в том числе когда сессия истекла посреди работы. После явного выхода открывается главный экран: следующим может войти другой пользователь.
- Раскладка показывает страницы вкладок только после загрузки описаний объектов. Пока они загружаются, виден признак ожидания; при ошибке — сообщение с кнопкой повтора.
- Refine получает общий с приложением клиент TanStack Query. Запросы не повторяются сами ни при возврате в окно или восстановлении сети, ни после отказа сервера. Проверка входа Refine на время своего запроса убирает приложение с экрана, и её повтор закрыл бы все вкладки. Отказ в праве или в проверке данных от повтора не изменится.
- Уведомления Refine выводятся компонентом уведомлений Ant Design, их встроенные заголовки переведены на русский язык. Описанием ошибки служит текст сервера. Отправка сведений об использовании на сервер Refine отключена.

#### Вкладки открытых окон

Открытые списки, формы и страницы конфигурации остаются вкладками, как окна в 1С (`src/web/tabs/`). Над страницей стоит полоса вкладок. Первая вкладка — главный экран: на ней иконка без заголовка, закрыть её нельзя.

- Вкладку определяет путь адреса. Поэтому отдельной команды «открыть вкладку» нет: ссылка из окна подсистемы, из списка или из другой записи, прямой адрес и кнопки браузера «Назад» и «Вперёд» меняют адрес, а набор вкладок выводится из него. Адрес с новым путём открывает вкладку, адрес с путём открытой вкладки делает её активной. Новая вкладка встаёт сразу за активной.
- Строка запроса принадлежит вкладке: в ней список хранит сортировку, отбор и страницу. Скрытая вкладка помнит свою строку запроса. При возврате на вкладку, в том числе по ссылке без строки запроса, адрес браузера приводится к запомненному.
- Страницы всех вкладок остаются смонтированными, неактивные скрыты. Так вкладка сохраняет несохранённые значения формы, отбор, текст поиска и страницу списка. Если бы страница пересоздавалась при переключении, ввод терялся бы.
- Общих маршрутов у приложения нет: каждая вкладка раскладывает страницы по своему адресу, а не по адресу браузера. Поэтому скрытый список не реагирует на адрес активной вкладки и не меняет его.
- Всё, что действует на приложение в целом, страница включает только на активной вкладке. Так устроены сочетания клавиш формы: иначе Esc закрыл бы все открытые формы сразу.
- Страница обращается не к вкладке, а к ближайшей области окна (`src/web/window/`): области она сообщает заголовок, несохранённые изменения, изменённую и созданную запись, у неё узнаёт, видна ли пользователю, и её просит закрыться. Реализаций области две: вкладка и модальное окно с формой записи. Каждая сама решает, что значит обращение. Поэтому страница, в том числе форма записи, не зависит от того, в чём показана.
- У области может быть рамка: собственные места для заголовка и кнопок действий. У вкладки рамки нет, и каркас страницы выводит заголовок и кнопки над содержимым. У модального окна рамка есть: заголовок с отметками состояния стоит в шапке окна, кнопки в его нижней части.
- Модальное окно с формой записи (`src/web/forms/record-dialog.tsx`) открывает команда открытия записи SDK в режиме окна. Адреса у окна нет: вкладки выводятся из адреса, и адрес окна открыл бы вкладку. Поэтому окно после перезагрузки страницы не восстанавливается. После создания записи окно закрывается и отдаёт её `guid` коду, который его открыл.
- Окно принадлежит области, со страницы которой открыто, и регистрируется в ней вложенной областью: закрытие вкладки, выход и закрытие страницы браузера учитывают несохранённые изменения в окне. Окно выводится в слой страницы вкладки: затемнение закрывает только страницу, а полоса вкладок и список подсистем остаются доступны. Окно видно, только пока активна его вкладка; при возврате на вкладку оно показано снова с введёнными значениями. Форма в окне может открыть следующее окно, оно вкладывается в первое.
- Крестик окна, Esc и кнопка «Закрыть» спрашивают то же подтверждение, что и вкладка. Esc обрабатывает форма, а не окно Ant Design: она отличает закрытие списка выбора от закрытия окна.
- Несохранённые изменения область узнаёт через проверки: функции, которые читают признак в момент вызова. Форма сбрасывает признак сразу после записи и тут же закрывает область, а признак в состоянии React к этому моменту ещё не обновился бы. Проверок в области может быть несколько; область изменена, если изменён хотя бы один участник. Вложенная область регистрируется в родительской одной проверкой. Так же области вкладок регистрируются в общем наборе приложения, по которому спрашивается подтверждение перед выходом и перед закрытием вкладки браузера.
- Подтверждение перед закрытием спрашивает область. Крестик в полосе вкладок стоит вне области, поэтому вызывает команду закрытия, которую область вкладки передала набору вкладок.
- Страница сообщает области заголовок, и он становится заголовком вкладки. У списка это заголовок объекта. У формы это представление записи, у новой записи заголовок объекта с пометкой «(новый)»; после записи заголовок меняется на представление. У страницы конфигурации это заголовок из объявления, пока она не задала свой.
- Вкладка закрывается крестиком, форма также кнопкой «Закрыть» и клавишей Esc. Активной становится соседняя слева вкладка, а если её нет, главный экран. В истории браузера адрес закрытой вкладки заменяется адресом новой активной.
- Набор вкладок хранится в памяти страницы. После перезагрузки открыты главный экран и вкладка текущего адреса. Вкладки стоят под проверкой входа и при завершении сессии закрываются: следующий вошедший пользователь не увидит вкладок и данных предыдущего.

### Web SDK

Web SDK (`src/web/sdk`) — набор компонентов, хуков и типов платформы, из которого собираются экраны клиента. У него одна точка входа, `src/web/sdk/index.ts`. Всё, что из неё экспортировано, считается публичным контрактом клиента; остальные модули `src/web` остаются внутренними и могут меняться. Стандартные форма записи (`src/web/forms/`) и список объекта (`src/web/lists/`) собраны из SDK и служат образцами собственных экранов.

- SDK состоит из функциональных компонентов React и хуков, экран пишется обычным JSX. Базовых классов для наследования нет: клиент построен на хуках, а классовый компонент вызывать их не может. Описания интерфейса билдерами тоже нет.
- В SDK входит только то, что знает о платформе: данные, права, описания объектов, область окна, фокус. Раскладку, типографику и прочие элементы без такой связи экран берёт из Ant Design напрямую, обёртки для них не пишутся.
- Иконки экран берёт из реестра `Icons` (`src/web/sdk/icons.tsx`) по смыслу действия, а не по рисунку: `<Icons.open />`, `<Icons.add />`. Реестр сопоставляет смыслу значок Ant Design, поэтому одно действие выглядит одинаково на всех экранах, а рисунок меняется в одном месте. Пакет `@ant-design/icons` импортирует только реестр. Если нужного смысла в нём нет, в реестр добавляют запись. У иконки без подписи рядом есть название для чтения с экрана и подсказка: так оформлена кнопка перехода к записи у поля ссылки.
- Хуки данных SDK служат единственным путём к API для кода вне платформы: хуки Refine и `/api/perform` такой код напрямую не вызывает. Так сброс сохранённых ответов сервера и показ ошибок остаются в одном месте.
- Если экрану не хватает элемента или хука и он пригодится другим экранам, его добавляют в SDK, а не пишут на месте.

| Что нужно экрану | Что даёт SDK |
|---|---|
| Описание объекта, доступное пользователю | `useObjectView` |
| Объект конфигурации с типами записи и действий | типы `ObjectReference`, `RecordCondition`, `RecordSort`, `FieldName`; сами ссылки лежат в `Objects` из `objects.generated.ts` |
| Страница списка с отбором, поиском, сортировкой и номером страницы, постоянный отбор экрана | `useRecordList` |
| Запись по `guid` | `useRecord` |
| Выполнение действия | `useAction` |
| Представление записи по ссылке | `useReferencePresentation`, `recordPresentation` |
| Область окна, в которой показана страница: заголовок, закрытие, признак активности, сообщения об изменённой и о созданной записи, несохранённые изменения | `useWindowTitle`, `useWindowScope`, `useUnsavedChanges` |
| Открытие формы записи во вкладке или в модальном окне | `useOpenRecord` |
| Адреса списка объекта, формы записи и страницы конфигурации | `objectPath`, `recordPath`, `newRecordPath`, `pagePath` |
| Каркас страницы с заголовком, отметками состояния и кнопками | `Page` |
| Поле ввода и отображение значения по виду поля | `FieldInput`, `FieldDisplay` |
| Ссылка на запись | `RecordLink` |
| Группа полей с подписями и ошибками, табличная часть | `FieldGroup`, `TablePart` |
| Данные формы для элемента на ней: описание объекта, записанное состояние, признак «только просмотр», изменение значения поля | `useFormData` |
| Текущее значение поля или строки табличной части вместе с несохранённым вводом | `useFormValue` |
| Поставщик данных формы для собственного экрана с формой | `FormDataProvider` |
| Обход полей с клавиатуры | `useFieldTraversal` |
| Таблица записей с сортировкой и страницами, выбором колонок и строки; отбор и поиск списка | `RecordTable`, `ListFilters`, `ListSearch` |
| Кнопка действия и окно его входных данных | `ActionButton`, `ActionDialog` |
| Иконка по смыслу: добавление, открытие, удаление, вид объекта | `Icons` |

- Хуки списка и записи отдают условия отбора и сортировку в формате действия `list`, тех же типов, что в описании списка. Типы Refine в контракт SDK не входят.
- Объект хуки и компоненты принимают двумя способами. Описание с сервера (`ObjectView`) типов записи не несёт: записи имеют общий тип, имена полей и действий — строки. Так работают стандартные список и форма. Ссылка на объект `Objects.<вид>.<имя>` несёт тип строки списка, тип записи и имена стандартных и собственных действий, выведенные из билдера. По ней компилятор проверяет имена колонок `RecordTable`, поля сортировки и постоянного отбора `useRecordList` вместе с типом значения, имя действия у `ActionButton` и `useAction`, а `useRecord` и `useRecordList` возвращают записи точного типа. Опечатка в имени не собирается.
- Хуки области окна обращаются к ближайшей области и вне области завершаются ошибкой. Экран не знает, вкладка это или модальное окно: `useWindowScope` отдаёт признак активности, закрытие с подтверждением и сообщения об изменённой и о созданной записи, `useWindowTitle` задаёт заголовок. `useUnsavedChanges` можно вызвать на одном экране несколько раз, по разу на каждую часть со своим признаком изменений. Каркас `Page` сообщает области свой заголовок; свойство `windowTitle` задаёт другой заголовок области или отключает его. Заголовок, отметки и кнопки каркас выводит в рамку области, если она есть, иначе над содержимым.
- `useOpenRecord` отдаёт команду открытия формы записи. Команда принимает объект, `guid` записи либо `null` для новой записи и необязательный режим: `tab` или `dialog`. Без режима новая запись открывается в режиме создания из описания формы (`creationMode`), существующая во вкладке. В режиме вкладки команда переходит по адресу записи. В режиме окна она возвращает итог, когда окно закрыто: `guid` записи, которую в окне записали или над которой выполнили действие, либо `null`, если окно закрыто без записи. Режим указывает место вызова, а конфигурация задаёт только умолчание: общего состояния «как открывать записи объекта» нет, потому что страницы всех вкладок смонтированы одновременно, и результат зависел бы от порядка их монтирования.
- `hasOpenDialog` сообщает, открыто ли модальное окно поверх экрана. Экран передаёт свой корневой элемент: окно, в котором показан сам экран, поверх него не лежит и не учитывается. Иначе форма в модальном окне сочла бы себя закрытой собственным окном и отключила бы свои сочетания клавиш.
- `useRecordList` принимает постоянный отбор экрана, например «только непроведённые». Он действует вместе с отбором пользователя, в отбор пользователя не входит и им не снимается.
- `RecordTable` по настройке выводит только перечисленные колонки и показывает выбор строки. Выбор хранит экран: таблица сообщает о нём и показывает выбранной строку, которую получила.
- `useRecordList` по настройке хранит состояние списка в адресе вкладки. Адрес у вкладки один, поэтому так может работать только один список на экране; остальные хранят состояние в памяти.
- `useAction` показывает уведомление об успехе и об отказе сервера и после успеха помечает устаревшими сохранённые ответы сервера о данных. Отказ завершает вызов ошибкой `ApiError`, по которой экран отмечает поля из перечня `fields`.
- Кнопка действия получает объект, запись и имя действия. Она не выводится, если действия нет в описании формы объекта: сервер оставляет там только действия, на которые у пользователя есть право. Не выводится и действие, неприменимое к записи в её состоянии: из пары «Пометить на удаление» и «Снять пометку удаления» применимо одно, отмена проведения применима только к проведённому документу. Во время запроса кнопка недоступна. Если у собственного действия есть входные данные, кнопка сначала открывает окно с их полями; экран может передать входные данные сам, тогда окно не открывается.
- Стандартное действие кнопка выполняет над записью по её `guid`. Действие `save` кнопка сама не выполняет: значения полей знает только форма. Для таких случаев экран заменяет выполнение своим, а кнопка сохраняет проверку прав, окно входных данных и признак ожидания. Так устроена стандартная форма: перед действием она записывает несохранённые изменения.
- Контракт поля ввода SDK публикует из реестра виджетов без изменений: значение, обработчик изменения, недоступность, приём фокуса. На нём держатся обход с клавиатуры и проверка ввода. Собственный элемент на месте поля ввода соблюдает этот же контракт.
- Данные формы элемент получает хуками, а не свойствами. `useFormData` отдаёт описание объекта, записанное состояние, признак «только просмотр» и функцию изменения значения; элемент перерисовывается, когда форма записана или перечитана. `useFormValue` отдаёт текущее значение одного поля или строки табличной части вместе с несохранённым вводом и перерисовывает элемент только при изменении этого значения. У поля, которого на форме нет или которое заполняет платформа, возвращается значение из записанного состояния.
- Оба хука принимают ссылку на объект `Objects.<вид>.<имя>`: по ней запись и имена полей получают точные типы. Элемент со ссылкой, поставленный на форму другого объекта, завершается ошибкой: типы записи были бы неверны. Без ссылки элемент подходит форме любого объекта, а запись имеет общий тип.
- Изменение значения через `useFormData` форма учитывает как ввод пользователя: оно считается несохранённым, сразу проверяется по правилам поля с показом ошибки под ним и уходит в `save` вместе с остальными значениями. Изменить можно редактируемое поле формы или строки табличной части; имя другого поля завершает вызов ошибкой. На форме только для просмотра значение не меняется.
- `FormDataProvider` стоит внутри формы Ant Design и снаружи групп полей. Стандартная форма передаёт ему реестр компонентов элементов конфигурации; без поставщика `FieldGroup` выводит поле виджетом его вида, а элемент группы пропускает.

### Реестр виджетов

Формы и списки о видах полей сами ничего не знают: компонент для поля они берут из реестра виджетов (`src/web/widgets/registry.tsx`). Реестр сопоставляет каждому виду поля (`FieldKind`) два компонента. Поле ввода служит для ввода или выбора значения. Компонент отображения выводит значение текстом там, где его нельзя изменить: в ячейке списка и на форме у полей только для чтения.

| Вид поля | Поле ввода | Отображение |
|---|---|---|
| `string` | Текстовое поле; пустое поле отдаёт `null`, а не пустую строку | Текст |
| `number` | Поле для числа; при правиле `integer` дробную часть ввести нельзя | Число с разделителями разрядов |
| `money` | Поле для суммы в рублях с двумя знаками после запятой | Рубли с двумя знаками после запятой |
| `date` | Выбор даты в календаре | `ДД.ММ.ГГГГ` |
| `dateTime` | Выбор даты и времени | `ДД.ММ.ГГГГ ЧЧ:ММ` по часовому поясу браузера |
| `boolean` | Флажок | «Да» или «Нет» |
| `reference` | Выбор записи другого объекта с поиском и кнопка перехода к выбранной записи | Представление записи со ссылкой на её форму |
| `guid` | Нет: значение заполняет платформа | Текст |
| `recorder` | Нет: значение заполняет платформа | Представление документа со ссылкой на его форму |

- Реестр обязан перечислить все виды полей, и это проверяется типами. Если на сервере появится новый вид поля, клиент не соберётся, пока для него не добавлена пара компонентов.
- Значение остаётся в формате сервера на всём пути: деньги в копейках, даты строками ISO, ссылка в виде `guid`, отсутствие значения в виде `null`. В привычный человеку вид значение переводит само поле ввода, и оно же переводит введённое обратно. Поэтому значения формы уходят в `save`, а значение отбора в `list` без преобразования, и общего слоя преобразования нет.
- Все поля ввода принимают один набор свойств, принятый для элементов формы Ant Design: значение, обработчик изменения, признак недоступности, а также описание поля. Поэтому одно и то же поле ввода стоит в шапке формы, в ячейке табличной части, в условии отбора списка и в окне входных данных собственного действия.
- Каждое поле ввода умеет принять фокус по команде извне. Этим пользуется форма, когда ставит фокус в первое поле новой записи; на этом же будет построен обход с клавиатуры.
- Правила проверки Ant Design строятся из `rules` описания поля в одном месте (`src/web/widgets/validation.ts`): обязательность, длина строки, границы числа, целочисленность. Значение проверяется в формате сервера, поэтому граница суммы сравнивается в копейках, а в сообщении называется в рублях.

### Ссылки

Поле вида `reference` хранит `guid` записи другого объекта. Пользователю `guid` ничего не говорит, поэтому вместо него всегда выводится представление записи: текст, по которому человек её узнаёт. У записи справочника это наименование, у документа: «<заголовок объекта> № <номер> от <дата>». Общий модуль представлений (`src/server/ui/reference-presentation.ts`) используется сервером и клиентом, поэтому в поле ссылки, в ячейке списка, в колонке регистратора и в заголовке формы запись называется одинаково. Список получает готовые представления со своей страницей, а вне списка клиент читает записи по ссылкам.

- Вне списка клиенту нужны записи по списку `guid`. Чтения, начатые за один проход отрисовки, уходят на сервер одним пакетом действий `get`, общим для всех объектов страницы. Это делает метод `getMany` data provider. В ячейках списка отдельное чтение не выполняется: представления страницы имеют приоритет перед кешем записей.
- Прочитанная запись хранится в общем кеше запросов и в течение минуты повторно не запрашивается. Изменение записи самим пользователем сбрасывает сохранённые ответы раньше.
- Пакет выполняется целиком или не выполняется вовсе. Для ссылок это допустимо: записи физически не удаляются, поэтому чтение по сохранённой ссылке всегда находит запись, а объекты без права чтения клиент не запрашивает.
- Поле ввода ссылки представляет собой выпадающий список с поиском. По введённому тексту оно запрашивает у сервера записи целевого объекта: у справочника ищет текст в наименовании, у документа в номере. Предлагаются первые 20 записей в порядке сортировки объекта по умолчанию; помеченные на удаление не предлагаются. Запрос уходит, только когда список открыт.
- Уже сделанная ссылка на помеченную запись остаётся в силе: поле показывает её представление, хотя выбрать её заново нельзя.
- Если целевого объекта нет в описаниях, у пользователя нет права его читать. Тогда записи не запрашиваются, вместо представления написано «Нет доступа», а выбрать другую запись в поле нельзя.

### Списки

Страница `/<вид>/<имя>` показывает список объекта (`src/web/lists/`). Он собран из SDK: хук списка читает страницу, а поиск, отбор и таблица записей показывают и меняют её состояние. Список строится только по описанию списка, поэтому новый объект конфигурации получает его без изменений клиента.

- Колонки берутся из `columns`, при открытии действует сортировка `defaultSort`. Щелчок по заголовку колонки из `sortable` сортирует список по ней и заменяет прежнюю сортировку, повторный щелчок меняет направление.
- Над таблицей пользователь составляет отбор из условий: поле из `filters`, способ сравнения из `operators` этого поля и значение. Значение вводится в поле ввода из реестра виджетов. Условия соединяются через «и», условие без значения не применяется.
- Отдельное поле «Поиск» ищет фрагмент в любой видимой колонке вместе с условиями отбора. Ввод применяется с задержкой и возвращает первую страницу; очистка сохраняет отборы. Общее число строк, страницы и сортировка относятся к найденному набору.
- Под таблицей переключаются страницы и размер страницы: 20, 50 или 100 записей, по умолчанию 50.
- Сортировку, отбор, текст поиска и номер страницы Refine хранит в адресе страницы (`syncWithLocation`). Поэтому адрес с отбором можно сохранить в закладки, а после перезагрузки страницы список открывается в прежнем состоянии. Текст поиска Refine хранить не умеет, поэтому он записывается в отбор отдельным условием с именем поля `$search`; data provider передаёт его серверу параметром `search`, а не условием. Пока вкладка списка открыта, список своё состояние не теряет. Строка запроса не различает типы, и число после разбора адреса возвращается строкой. Поэтому router provider приложения (`src/web/application/router-provider.ts`) приводит значения отбора к виду поля по описанию списка.
- Запись, помеченная на удаление, остаётся в списке: в первой колонке стоит значок пометки, текст строки бледнее обычного. У проведённого документа в первой колонке стоит значок проведения.
- Двойной щелчок по строке или щелчок по ссылке в первой колонке открывает форму записи. Если первая колонка сама содержит ссылку, она открывает целевую запись; двойной щелчок по строке открывает её владельца. Кнопка «Создать» есть, если в описании формы есть действие `save`. Она открывает запись командой SDK без указания режима: форма открывается во вкладке или в окне поверх списка, как задано в конфигурации объекта. Запись, созданная в окне, появляется в списке сама, адрес и набор вкладок при этом не меняются. Меню в конце строки ставит или снимает пометку удаления, если это действие есть среди действий формы.
- Списки обоих видов регистров доступны только для просмотра: в них нет кнопки «Создать», меню в строках и перехода к форме. У движений в колонке регистратора стоит представление документа, которое открывает его форму; у сведений отображаются измерения и ресурсы.

### Формы

У записи есть собственный адрес: `/<вид>/<имя>/new` открывает форму новой записи, `/<вид>/<имя>/<guid>` открывает форму существующей (`src/web/forms/`). По адресу форма открывается в отдельной вкладке: на запись ведут ссылки из списков, из строк регистров и из других форм. Ту же форму команда открытия записи SDK показывает в модальном окне поверх страницы; так создаётся запись объекта, у которого в конфигурации задан режим создания в окне (подразделы «Переопределение формы» и «Вкладки открытых окон»). У обоих видов регистров формы нет, и их адреса форм показывают страницу «не найдено». Если сервер запись не отдал, на месте формы показывается его сообщение и кнопка возврата в список.

Страница вкладки только разбирает адрес. Чтение существующей записи с признаком ожидания и сообщением об отказе сервера вынесено в отдельный компонент, который от адреса не зависит: что предложить пользователю при отказе, ему передаёт вызывающий код. Поэтому форму существующей записи показывает и модальное окно: при отказе оно предлагает закрыться.

- Форма собрана из SDK. Значения и ошибки полей хранит форма Ant Design, а загрузку, запись и действия выполняют хуки данных SDK. Отдельно форма помнит записанное состояние: запись в том виде, в каком её последним вернул сервер. По нему выводятся заголовок, отметки «Помечен на удаление» и «Проведён» и поля только для чтения, к нему применяются действия.
- Группы выводятся в порядке описания: группа с заголовком блоком с заголовком, группа без заголовка без рамки. Табличная часть занимает всю ширину формы.
- Собственный элемент конфигурации в группе занимает всю её ширину и свойств не получает. Элемент, назначенный полю, стоит на месте поля ввода: значение и обработчик изменения ему передаёт элемент формы Ant Design, как и виджету, поэтому подпись, ошибку проверки и отметку «Сервер отклонил значение» показывает форма. Значения и записанное состояние элементы читают из данных формы SDK, а изменение значения элементом форма считает несохранённым так же, как ввод пользователя. На форме только для просмотра поля ввода и кнопки Ant Design внутри элемента недоступны: недоступность им передаёт форма.
- В форме новой записи обязательный флажок снят, а обязательные дата и время равны текущему моменту: так заполняется дата нового документа. Остальные поля пусты, в том числе поля только для чтения: номер документа сервер назначает при записи.
- Форма без действия `save` в описании открывается только для просмотра.
- До отправки форма проверяет значения по правилам из описания. Сообщение показывается под полем, а в табличной части у ячейки; пока есть ошибки, запрос не отправляется. Если сервер ответил 400, поля из его перечня `fields` отмечаются ошибкой «Сервер отклонил значение», а текст сервера показывается уведомлением: отдельного текста на каждое поле сервер не присылает. Ответы 403 и 409 показываются уведомлением с текстом сервера. При любой ошибке введённые значения остаются на форме.
- Значение ячейки табличной части лежит в форме по пути «табличная часть, номер строки, поле». Сервер называет поле с ошибкой таким же путём (`payload.fields.lines.0.text`), поэтому его ошибки сопоставляются с полями напрямую.
- Действие `save` заменяет запись целиком, а на форме есть не все её поля: переопределение `.hide(...)` убирает поле из описания формы. Поэтому в `save` отправляется загруженная запись, в которой значения полей формы заменены введёнными. Иначе запись обнулила бы скрытые поля. Поля, которые заполняет платформа, сервер во входных данных пропускает.
- Кнопки действий строятся из `actions` описания, поэтому действие без права на форме не появляется. Из пары «Пометить на удаление» и «Снять пометку удаления» показывается применимое, «Отменить проведение» показывается только у проведённого документа. В форме новой записи доступны только «Записать» и «Провести».
- Все действия, кроме «Записать», применяются к записанному состоянию. При несохранённых изменениях форма сначала записывает их и только затем выполняет действие, двумя последовательными запросами: у новой записи до ответа на запись нет `guid`, который нужен действию. Если действие после успешной записи отклонено, запись остаётся сохранённой.
- После каждого изменения записи на сервере форма сообщает области окна её `guid`, а после создания записи сообщает об этом отдельно. Что делать дальше, решает область. Вкладка формы новой записи получает адрес существующей записи, форма остаётся открытой, и повторное открытие этой записи находит ту же вкладку. Модальное окно после создания записи закрывается. В истории браузера адрес новой записи заменяется, поэтому кнопка «Назад» к пустой форме не возвращает. Форма новой записи у объекта одна: кнопка «Создать» при уже открытой новой форме возвращает к ней.
- Собственное действие доступно для записанной записи. Если у него есть входные данные, кнопка действия открывает окно с полями из того же реестра виджетов. После выполнения запись читается с сервера заново: действие могло её изменить.
- После любого изменяющего действия сохранённые ответы сервера о данных помечаются устаревшими: открытые списки и ссылки перечитываются сразу, остальные при следующем открытии. Сбрасываются ответы обо всех объектах, потому что проведение меняет строки регистров, а собственное действие может изменить любые записи.
- Переключение вкладок данные формы не теряет, поэтому подтверждение спрашивается только при закрытии вкладки формы с несохранёнными изменениями: крестиком, кнопкой «Закрыть» или клавишей Esc. Отказ оставляет вкладку открытой. Выход из приложения закрывает все вкладки и спрашивает подтверждение, если несохранённые изменения есть хотя бы на одной. При закрытии вкладки или окна браузера подтверждение показывает сам браузер; оно тоже учитывает все вкладки приложения, потому что изменения могут быть на скрытой форме.
- Табличная часть сделана отдельным компонентом, который получает только её описание и не зависит от остальной формы. Форма знает свои поля ввода и табличные части по именам и может перевести фокус на любое имя из порядка обхода `traversal`.

### Работа с клавиатуры

Форма обходит редактируемые поля по порядку `traversal` из описания: Enter переводит фокус вперёд, Shift+Enter назад. Поля только для чтения в обход не входят. На границе шапки обратный обход останавливается в первом поле.

Собственный элемент, назначенный полю, участвует в обходе на месте этого поля и получает фокус в новой записи, если поле первое в порядке: для этого он принимает фокус по контракту поля ввода. Кнопка внутри элемента по Enter срабатывает сама, как и остальные кнопки формы. Собственный элемент в группе без назначенного поля в порядок обхода не входит: контракта поля ввода он соблюдать не обязан.

При переходе в пустую табличную часть форма добавляет первую строку и ставит фокус в её первую ячейку. Внутри строки обход идёт по колонкам описания. После последней ячейки Enter переходит в первую ячейку следующей строки, а если её ещё нет, добавляет строку. Shift+Enter из первой ячейки возвращает в последнюю ячейку предыдущей строки, а из первой строки в предыдущее поле формы. Ссылки на поля ячеек учитываются по устойчивым ключам строк, поэтому удаление строки не меняет адреса полей остальных строк.

Открытый список выбора или календарь обрабатывает Enter и Esc сам: Enter выбирает значение, Esc закрывает выбор. Следующее нажатие работает с формой. Во время составного ввода текста переходы не выполняются.

Сочетания TanStack Hotkeys действуют на форме активной вкладки: Ctrl+S записывает её, Ctrl+Enter проводит документ и закрывает вкладку только после успеха, Esc закрывает вкладку с обычным подтверждением при несохранённых изменениях. В форме, показанной в модальном окне, сочетания действуют так же и закрывают окно, а в формах под окном не действуют. Esc, которую обработала форма, до обработчика Ant Design не доходит: иначе то же нажатие закрыло бы только что открытое окно подтверждения. Сочетания вызывают те же действия, что кнопки, и доступны только при наличии действия в описании формы. Поэтому пользователь без права записи не может записать форму сочетанием клавиш. Окна подтверждения и входных данных собственных действий получают клавиши сами; действия записи за ними не запускаются. Повторное нажатие во время запроса не запускает второе действие.

Обход полей и учёт фокуса входят в SDK (`useFieldTraversal`), поэтому собственный экран с формой получает тот же обход; значения хранятся в форме Ant Design, серверные данные в TanStack Query. Табличная часть использует таблицу Ant Design с собственным обходом ячеек, без замены остальных частей формы.

## Сборка и запуск

| Команда | Что делает |
|---|---|
| `npm run dev` | Режим разработки: генератор реестров следит за файлами объектов и страниц, `tsc --watch` собирает сервер, `node --watch` перезапускает его при изменениях, Vite раздаёт клиент на порту 5173 и проксирует `/api` на Nest |
| `npm run build` | Генерация реестров конфигурации, сборка сервера (`tsc`) в `dist/server` и клиента (Vite) в `dist/web` |
| `npm run build:executable` | На Windows x64 собирает сервер и клиент, затем создаёт `dist/executable/collection-zarplata.exe` |
| `npm start` | Запуск собранного приложения: Nest отдаёт API и клиент на порту из файла настроек |
| `npm run start:check` | Сборка и запуск на пустой базе в памяти без файла настроек, для ручной проверки. Дополнительные параметры передаются после `--`: `npm run start:check -- --test-pin=482915 --port=3101` |
| `npm run typecheck` | Генерация реестров, проверка импортов страниц конфигурации, проверка типов и правил Effect для сервера, скриптов и клиента |
| `npm run metadata:generate` | Генерация реестров конфигурации: объектов и страниц |

- Сервер компилируется самим `tsc` (TypeScript 7), без Nest CLI.
- Сервер использует ES-модули (`"type": "module"`), поэтому относительные импорты пишутся с расширением `.js`.
- Конфигурации TypeScript: `tsconfig.base.json` — общие правила и плагин Effect; `tsconfig.json` — сервер и конфигурация без компонентов страниц и сгенерированных файлов клиента; `scripts/tsconfig.json` — служебные скрипты, только проверка; `src/web/tsconfig.json` — клиент, компоненты страниц конфигурации и сгенерированные файлы клиента.
- Настройки запуска читаются из `collection-zarplata.settings.json`. При запуске `.exe` файл должен лежать рядом с ним; при `npm start` и `npm run dev` — в корне проекта. Образец — `collection-zarplata.settings.example.json`. Отсутствие файла или неверные значения останавливают запуск с сообщением об ошибке.
- Поля настроек: `host` — адрес интерфейса, `port` — порт от 1 до 65535, `databasePath` — путь к файлу базы относительно каталога настроек (допустим и абсолютный путь), `pinHmacSecret` — секрет длиной не меньше 32 символов для HMAC PIN и подписи access-токенов. Заполните секрет случайным значением, например сгенерируйте 32 байта командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` на машине сборки. Настоящий секрет хранится только в локальном файле настроек; этот файл исключён из Git. Для создания первого пользователя временно добавьте `initialUser`, как описано в разделе «Вход в приложение». В режиме разработки оставляйте порт 3000, на который Vite направляет запросы `/api`.
- Параметры запуска передаются в виде `--имя=значение` после `main.js` или имени `.exe`. Неизвестный параметр или неверное значение останавливают запуск.
  - `--database=memory` открывает пустую базу в памяти. Файл настроек в этом режиме не читается: сервер слушает `127.0.0.1`, порт по умолчанию 3100, секрет HMAC создаётся случайным при каждом запуске. Данные, пользователи и токены исчезают после остановки процесса, о чём сервер предупреждает в журнале при запуске. Таблицы создаёт синхронизация структуры, как на новом файле базы. `--database=file` — обычный режим, он действует без параметра.
  - `--test-pin=<4–12 цифр>` в режиме памяти создаёт при запуске тестового пользователя с этим PIN и всеми ролями конфигурации. Роли можно ограничить: `--test-pin=111111:reader` или `--test-pin=111111:reader,cashier`. Параметр можно повторять, чтобы создать нескольких пользователей с разными PIN; неизвестная роль или повтор PIN останавливают запуск. Вне режима памяти параметр останавливает запуск: он создал бы постоянного пользователя в рабочей базе.
  - `--port=<1–65535>` заменяет порт из настроек в любом режиме. Порт сервера выбирает отдельный провайдер-фабрика: значение параметра, если он передан, иначе порт из настроек.

## Инструменты разработки

- **Проверка кода.** После изменений код проверяется командой `effect-tsgo` из пакета `@effect/tsgo`. Она выполняет проверку типов TypeScript 7 и выдаёт диагностики Effect Language Service. Плагин `@effect/language-service` подключён в `tsconfig.json`.
- **Исходники Effect в репозитории.** Репозиторий Effect подключён через `git subtree` в `repos/effect` и служит справочником по API и примерам. Код из `repos/` не импортируется и не редактируется. Обновление:

  ```bash
  git subtree pull --prefix=repos/effect https://github.com/Effect-TS/effect.git main --squash
  ```

## Поставка

- Для сборки на Windows x64 нужен Node.js 24.8 или новее, npm и установленные зависимости (`npm ci`). Выполните `npm run build:executable`, скопируйте `dist/executable/collection-zarplata.exe` в каталог поставки, рядом создайте `collection-zarplata.settings.json` по образцу и запустите `.exe`. На целевой машине Node.js и `node_modules` не нужны.
- Используется Node SEA: esbuild собирает NestJS и зависимости в один сценарий, Vite собирает клиент, SEA встраивает сценарий, файлы клиента и нативный модуль Turso в копию Node.js. При запуске нативный модуль извлекается в каталог `%TEMP%/collection-zarplata/` по хешу содержимого. Файлы клиента отдаются непосредственно из ресурсов исполняемого файла.
- Проверен также `bun build --compile`: он собрал каркас после исключения необязательных интеграций NestJS, но полученный файл не смог загрузить нативный модуль `@tursodatabase/database`. Поэтому для этой поставки выбран Node SEA.
- Файл БД создаётся по пути `databasePath` из настроек. По умолчанию в образце он лежит рядом с исполняемым файлом.
- Резервная копия — копия файла БД.


## Импорт из универсальной XML-выгрузки 1С

Стандартное действие `import` доступно справочникам и требует права записи. Тело `payload` содержит `externalSystem` и непустой список `items` (до 500 элементов). Каждый элемент содержит `sourceObject`, `externalIdentifier` и `fields`; ответ возвращает `externalIdentifier`, `guid` и `status` (`created` или `updated`) в исходном порядке.

В конфигурации регистр сведений `externalLinks` хранит уникальную тройку «внешняя система, вид объекта источника, внешний идентификатор» и ресурс «ссылка на запись». Импорт читает связь, записывает справочник и новую связь через вложенные действия диспетчера. Все действия используют одну транзакцию, права пользователя, политики записи и журнал. При повторной загрузке переданные пользовательские поля заменяются, пропущенные необязательные очищаются. Ошибка элемента отменяет всю порцию. Если связь ведёт в другой справочник, импорт останавливается. Несколько внешних адресов одной записи можно создать обычным действием записи регистра сведений.

Конфигурация может ограничить строковое поле вызовом `.choices(['Мужской', 'Женский'])`. Список копируется и становится неизменяемым; сборка метаданных отклоняет пустой список, пустые строки и повторы. Сервер проверяет принадлежность значения списку при записи и отборе, форма показывает выпадающий список с возможностью очистки необязательного поля. Тип хранения остаётся строковым. ФИО справочника `physicalPersons` хранится в стандартном `name`, подпись формы заменена на «ФИО». Справочник `nomenclature` собственных полей не имеет: название позиции хранится в стандартном `name`.

Инструмент импорта написан на Go и находится в `tools/1c-xml-import`, описание запуска и формата сопоставления в его README.md. Он использует стандартную библиотеку Go и собирается без cgo в исполняемый файл, не зависящий от системных библиотек. Сборка основного приложения Go не требует. Локальный инструмент передаёт PIN через скрытый ввод или переменную окружения, использует cookie и обновляет доступ при ответе 401. Для удалённого сервера требуется HTTPS. Файл читается потоком, в памяти находятся один выбранный объект XML и текущая порция. Ранее подтверждённые порции сохраняются при ошибке; повторный запуск безопасно обновляет их.

Полные ссылки хранятся в колонках TEXT как JSON в устойчивом порядке `kind`, `name`, `guid`; API возвращает объект, а не JSON-строку. Это правило действует также для табличных частей, измерений, ресурсов и условий отбора. Регистр внешних связей содержит ресурс `record` такого типа. Миграция `20261007_external_record_reference` переносит прежние `targetObject` и `recordGuid` в этот ресурс до удаления колонок, сохраняя внешние ключи. Пробный справочник содержит полную ссылку в реквизите и табличной части для проверки общего механизма.
