# Архитектура

Приложение для учёта зарплаты и продаж магазина. Этот документ описывает технические решения; назначение и возможности — в [PRODUCT.md](PRODUCT.md).

## Принципы

- **Модельно-ориентированная разработка (MDD).** Прикладные объекты (справочники, документы, регистры) описываются декларативно. По описанию платформа строит структуру БД, API, права, валидацию и формы.
- **Платформа отделена от конфигурации.** Платформа — это механизмы: хранение, единый API, права, журнал, SDUI. Конфигурация — это прикладные объекты и роли конкретного магазина. Новый объект добавляется одним файлом конфигурации без ручной регистрации.
- **Один процесс, один исполняемый файл.** NestJS обслуживает API и раздаёт собранный фронтенд. Файл БД лежит рядом с исполняемым файлом.
- **Effect только в бизнес-логике.** Роутинг, контроллеры и DI остаются на Nest. Effect управляет ходом выполнения: ошибками, транзакциями, контекстом действия, композицией операций.
- **Полные имена.** В идентификаторах, действиях, маршрутах и полях используются полные слова без сокращений: `parameters`, а не `params`; `configuration`, а не `config`. Допустимы только общепринятые аббревиатуры: `guid`, `API`, `UI`, `SQL`, `JSON`.

## Стек

| Слой | Технологии |
|---|---|
| База данных | Turso (встраиваемая, файл рядом с приложением) |
| Бэкенд | NestJS (вероятно, на Fastify, как в `miracle/back-nest`), Effect 3 в бизнес-логике |
| Валидация | Effect Schema на сервере |
| Фронтенд | React, Refine, Ant Design, TanStack Query (входит в Refine), TanStack Store, TanStack Hotkeys, сборка Vite |
| Пакеты | npm, один `package.json` |
| Поставка | один исполняемый файл |

## Структура проекта

Серверный код разделён на доменные модули, как в проектах `miracle/back-nest` и `XIP/xip/server`.

```
src/
  server/
    main.ts
    app.module.ts
    database/         подключение к Turso, транзакции
    metadata/         DSL описания объектов, реестр объектов конфигурации
    schema/           сверка метаданных со структурой БД, миграции
    data/             единый эндпоинт perform, диспетчер действий, стандартные действия
    authorization/    RBAC: права из метаданных, бизнес-гвард
    authentication/   пользователи, вход по PIN, сессии
    journal/          журнал действий и трассировка
    ui/               построение описаний форм и списков (SDUI)
    settings/         настройки запуска: путь к БД, порт
    common/
  configuration/
    catalogs/         *.catalog.ts
    documents/        *.document.ts
    registers/        *.register.ts
    roles.ts
    configuration.generated.ts   генерируется, вручную не редактируется
  web/                клиент: React + Refine + Ant Design
```

## Метаданные

### Виды объектов

| Вид | Назначение | Функция описания |
|---|---|---|
| Справочник | Условно-постоянные данные: сотрудники, номенклатура, точки | `defineCatalog` |
| Документ | Событие с датой, номером и статусом «проведён / не проведён» | `defineDocument` |
| Регистр | Движения, которые записывает документ при проведении; нужны для остатков и оборотов | `defineRegister` |

Регистры поддерживаются платформой. Нужны ли они в конкретной задаче, решает конфигурация. Движения регистра всегда ссылаются на документ-регистратор. При повторном проведении старые движения документа удаляются и записываются заново, поэтому проведение идемпотентно.

### Описание объекта

Примерная форма описания:

```ts
export const Employees = defineCatalog({
    name: 'employees',
    title: 'Сотрудники',
    fields: {
        position: field.reference('catalog', 'positions', { title: 'Должность' }),
        hiredAt: field.date({ title: 'Дата приёма', required: true }),
    },
    actions: {
        dismiss: defineAction({ input: ..., handler: ... }),
    },
    form: { ... },          // необязательное переопределение формы
    policies: [ ... ],      // необязательные политики записи
});
```

Типы записей и права TypeScript выводит из описания через `as const`, поэтому отдельная генерация типов не нужна.

### Стандартные поля

У каждого вида объектов есть свой набор стандартных полей, заданный в одном месте платформы. Предварительно:
- у всех объектов: `guid`, `deletedAt`;
- у справочников: `code`, `name`;
- у документов: `number`, `date`, `posted`.

Окончательный список формируется по ходу работы. `guid` генерируется как UUIDv7: такие идентификаторы упорядочены по времени, поэтому новые записи добавляются в конец индекса, а не в случайные его места.

### Пометка удаления

Физически объекты не удаляются. Пометкой служит поле `deletedAt`: если дата заполнена, объект помечен на удаление. Кто поставил пометку, фиксирует журнал.

### Обнаружение объектов конфигурации

Во время работы исполняемого файла исходники `.ts` недоступны, поэтому объекты обнаруживаются на этапе сборки. Скрипт `npm run metadata:generate` находит файлы `src/configuration/**/*.{catalog,document,register}.ts` и генерирует `configuration.generated.ts` с импортами и реестром. В режиме разработки скрипт работает в watch-режиме. Платформа читает только сгенерированный реестр.

## База данных

Используется **Turso** — SQLite-совместимая встраиваемая база, переписанная на Rust. Проект находится в статусе бета: часть возможностей SQLite ещё не реализована.

### Драйвер

Пакет `@tursodatabase/database` (версия 0.7 на сентябрь 2026). Основные вызовы:
- `connect(path)` открывает файл БД и создаёт его, если файла нет;
- `db.prepare(sql)` готовит запрос; `run`, `get`, `all`, `iterate` выполняют его и возвращают промисы;
- `db.exec(sql)` выполняет SQL без результата, например DDL;
- `db.pragma(...)` выполняет PRAGMA.

Драйвер использует нативные привязки для Node.js; есть и сборка на WebAssembly.

### Работа с базой в приложении

- **Одно соединение на процесс.** Turso не поддерживает доступ к одному файлу из нескольких процессов, а нам это и не требуется: приложение работает одним процессом.
- **Сервис `Database` на Effect** оборачивает драйвер: вызовы драйвера превращаются в `Effect`, ошибки — в `DatabaseError` (`Data.TaggedError`).
- **Транзакции выполняются по очереди.** Соединение одно, а вызовы драйвера асинхронные, поэтому две транзакции без упорядочивания перемешали бы свои запросы внутри одного `BEGIN … COMMIT`. Изменяющие транзакции выполняются через `Effect.Semaphore` с одним разрешением и начинаются с `BEGIN IMMEDIATE`. Текущая транзакция передаётся через окружение Effect, поэтому вложенные действия выполняются в ней же, а не открывают новую.
- **Чтения** выполняются вне очереди транзакций.
- **Построитель SQL собственный.** Таблицы строятся из метаданных во время работы, поэтому запросы тоже собираются по метаданным: тонкий слой над `prepare` с параметрами, без конкатенации значений в текст SQL.
- **Таблицы создаются как `STRICT`.** В таком режиме база проверяет типы колонок при записи, а не принимает любые значения, как обычная SQLite-таблица.
- **Конкурентная запись (MVCC, `BEGIN CONCURRENT`) не включается.** Она в статусе бета, а при двух пользователях очереди транзакций достаточно.

### Ограничения Turso, которые учитываем

- нет таблиц `WITHOUT ROWID`;
- нет `VACUUM`;
- только кодировка UTF-8;
- в JavaScript-драйвере нет `backup()`, поэтому резервная копия делается копированием файла.

### Структура БД

- Структура БД строится из метаданных.
- Безопасные изменения (новая таблица, колонка, индекс) применяются автоматически при старте.
- Разрушающие изменения (удаление или переименование колонки, смена типа) требуют явного файла миграции. Без него приложение не запускается и сообщает, какое изменение требует миграции.
- Применённая структура хранится снимком в служебной таблице; при старте платформа сравнивает с ним текущие метаданные.

### Хранение значений

- Деньги — целые числа в копейках.
- Дата и время — строки ISO 8601 с явным учётом часового пояса.
- `guid` — строка UUIDv7.

## Единый эндпоинт

Все операции с данными клиент выполняет через `POST /api/perform`:

```json
{
    "target": { "kind": "catalog", "name": "employees" },
    "action": "save",
    "payload": { "guid": "…", "fields": { "name": "…" } }
}
```

В теле можно передать массив операций. Массив выполняется в одной транзакции.

Описания объектов и форм клиент получает через `GET /api/metadata`.

### Стандартные действия

| Действие | Справочник | Документ | Регистр | Смысл |
|---|:-:|:-:|:-:|---|
| `list` | + | + | + | Список с фильтрами, сортировкой и страницами |
| `get` | + | + | | Один объект со всеми полями и табличными частями |
| `save` | + | + | | Запись объекта: новый без `guid`, существующий с `guid` |
| `markDeleted` | + | + | | Установить пометку удаления |
| `unmarkDeleted` | + | + | | Снять пометку удаления |
| `post` | | + | | Провести документ: записать движения регистров |
| `unpost` | | + | | Отменить проведение: удалить движения |

Регистры напрямую не изменяются: их записывают только документы при проведении.

### Собственные действия

Объект может объявить собственные действия в метаданных: входные данные, право и обработчик на Effect. Они вызываются через тот же эндпоинт: `"action": "dismiss"`.

### Выполнение действия

1. Nest-контроллер принимает запрос и передаёт тело диспетчеру. Больше контроллер ничего не делает.
2. Диспетчер находит объект и действие в реестре метаданных.
3. Бизнес-гвард проверяет права пользователя на это действие.
4. Входные данные проверяются Effect Schema, построенной из описания полей.
5. Открывается транзакция.
6. Выполняются политики записи конфигурации (`canWrite`, `beforeWrite`).
7. Выполняется действие.
8. В журнал записывается строка о действии.
9. Транзакция фиксируется. При ошибке откатываются и данные, и журнал.

Шаги 2–9 — это Effect-программа. Ошибки описаны через `Data.TaggedError` и в одном месте переводятся в HTTP-ответы.

## Вход в приложение

- Пользователь входит по PIN. PIN однозначно определяет пользователя, поэтому PIN уникален.
- PIN не хранится в открытом виде. В таблице пользователей лежит HMAC-SHA-256 от PIN с секретным ключом из файла настроек. Такой хеш детерминирован, поэтому пользователя можно найти по уникальному индексу.
- Короткий PIN легко перебрать, поэтому число неудачных попыток ограничивается: после нескольких ошибок вход временно блокируется.
- После входа сервер создаёт сессию и выдаёт её идентификатор в cookie с флагом `HttpOnly`. Сессии хранятся в БД.
- Пользователи и их роли хранятся в служебных таблицах платформы.

## Права (RBAC)

- Права генерируются из метаданных: `Rights.catalog.employees.read`, `Rights.catalog.employees.write`, `Rights.document.shift.post`, права на собственные действия.
- Роли описываются в `src/configuration/roles.ts` через `defineRole({ name, rights: [Rights.…] })`. Права указываются переменными, а не строками.
- Права проверяет **бизнес-гвард** — шаг диспетчера перед выполнением каждой операции, в том числе вложенной. Цель операции известна только из тела запроса, поэтому проверка выполняется в диспетчере, а не на маршруте.
- Для маршрутов вне единого эндпоинта предусмотрен декоратор `@RequireRights(Rights.…)` с обычным гвардом, который использует ту же проверку.

## Политики записи

Прикладные ограничения в платформу не встроены. Перед любым изменением объекта платформа вызывает политики, объявленные в конфигурации. Пример — закрытие периода:
- в конфигурации есть документ «Закрытие периода», который пользователь создаёт после расчёта зарплаты;
- политика запрещает изменять документы с датой не позже последнего проведённого закрытия;
- расчёты и проверка прав могут читать дату последнего закрытия из того же документа.

## Журнал действий

### Контекст действия

При каждом входящем запросе создаётся контекст действия — Effect-сервис `ActionContext`:

| Поле | Смысл |
|---|---|
| `userGuid` | Пользователь, запустивший исходное действие |
| `traceGuid` | Общий идентификатор цепочки действий одного запроса |
| `actionGuid` | Идентификатор текущего действия |
| `parentActionGuid` | Действие, которое вызвало текущее; пусто у исходного |

Контекст передаётся через окружение Effect, пробрасывать его параметрами не нужно. Если одно действие вызывает другое (например, проведение документа запускает пересчёт), вложенный вызов проходит через диспетчер и получает новый `actionGuid`. `traceGuid` и `userGuid` наследуются, поэтому любое вложенное действие приводит к пользователю, который начал цепочку.

### Запись журнала

Одно логическое действие над объектом даёт **одну** строку журнала, сколько бы полей ни изменилось:

| Колонка | Содержимое |
|---|---|
| `guid` | Идентификатор записи |
| `occurredAt` | Время действия |
| `userGuid`, `traceGuid`, `actionGuid`, `parentActionGuid` | Из контекста действия |
| `targetKind`, `targetName`, `targetGuid` | Объект, над которым выполнено действие |
| `action` | `save`, `post`, `markDeleted`, собственное действие и т. д. |
| `changes` | JSON с изменёнными полями: `{ "поле": { "before": …, "after": … } }`, включая изменения табличных частей. Для нового объекта — все заполненные поля |

Журнал пишется в той же транзакции, что и данные. Чтение данных не журналируется.

По журналу можно получить:
- история объекта — отбор по `targetKind`, `targetName`, `targetGuid`;
- действия пользователя — отбор по `userGuid`;
- цепочка «кто что запустил» — отбор по `traceGuid` и построение дерева по `parentActionGuid`.

## Интерфейс (SDUI)

- Сервер отдаёт JSON-описания форм и списков: поля, типы, ссылки на справочники, табличные части, группы, порядок обхода, доступные действия с учётом прав.
- Описание по умолчанию строится из метаданных. В метаданных его можно переопределить: сгруппировать поля, скрыть поле, изменить подпись.
- Клиент рендерит описание через реестр виджетов «тип поля → компонент Ant Design».
- Правила проверки (обязательность, границы, длина) входят в описание формы, и клиент проверяет по ним ввод до отправки. Окончательную проверку выполняет сервер.
- Refine подключается через собственный data provider, который переводит свои методы в вызовы `/api/perform`.
- Лёгкие вычисления клиент выполняет сам. Сложные оформляются собственным действием на сервере.

### Работа с клавиатуры

- Enter переходит к следующему полю, Shift+Enter — к предыдущему. Порядок обхода берётся из описания формы.
- После последнего поля шапки фокус переходит в табличную часть. В ней Enter переходит к следующей ячейке, а в конце строки создаёт новую строку.
- Глобальные сочетания: Ctrl+S — записать, Ctrl+Enter — провести и закрыть, Esc — закрыть форму. Окончательный набор уточним.
- Реализация: TanStack Hotkeys и собственный менеджер фокуса формы. Клиентское состояние (открытые формы, фокус) хранится в TanStack Store, серверные данные — в TanStack Query.
- Табличную часть, скорее всего, придётся написать самим поверх Ant Design: стандартная редактируемая таблица не даёт готового перехода между ячейками и добавления строк с клавиатуры.

## Поставка

- Результат сборки — один исполняемый файл. Собранный фронтенд встраивается в него.
- Рядом с исполняемым файлом лежат файл БД и файл настроек.
- Резервная копия — копия файла БД.
- Инструмент сборки исполняемого файла выбирается после создания структуры проекта. При выборе нужно проверить упаковку нативного модуля драйвера Turso.
