# Инструкция для агентов

Назначение проекта описано в [PRODUCT.md](PRODUCT.md), архитектура в [docs](docs), её оглавление в [ARCHITECTURE.md](ARCHITECTURE.md).

## Язык и стиль текстов

В начале каждого разговора, до первого ответа, прочитай [communication-style](.agents/skills/communication-style/SKILL.md) и [russian-style-v2](.agents/skills/russian-style-v2/SKILL.md). Пиши на русском: в чате, документации, issues, коммитах, комментариях кода и сообщениях пользователю.

Идентификаторы, имена веток и типы коммитов (`feat`, `fix` и другие) пиши латиницей.

## Документация

Обновляй документацию вместе с описанным в ней кодом. Перед её созданием или переработкой прочитай [documentation-directions](.agents/skills/documentation-directions/SKILL.md).

Навыки `communication-style`, `russian-style-v2` и `documentation-directions` хранятся в `.agents/skills` и `.claude/skills`. При изменении навыка обновляй обе копии.

Новый раздел архитектуры добавляй файлом в `docs` и строкой в `ARCHITECTURE.md`. Правила ведения разделов описаны в [документации](docs/documentation.md).

Перед отчётом запусти:

```bash
npm run docs:check
```

Команда сопоставляет изменённый код с разделами архитектуры. Прочитай разделы с пометкой «раздел не изменён» и исправь их, если поведение изменилось. Новый модуль добавь в `covers` описывающего его раздела.

Формулы, округление, условия и запреты магазина хранятся в [правилах учёта](docs/accounting-rules.md). Обновляй их в той же ветке, что и конфигурацию. Для нового документа конфигурации добавляй подраздел с его бизнес-правилами; устройство платформы, поля и раскладка форм описываются отдельно.

## Ветки и worktree

Работай в отдельной локальной ветке и своём `.worktrees/<агент>`, например `.worktrees/codex`. Это действует и при работе одного агента. Основной каталог принадлежит пользователю и остаётся на `main`: не меняй там файлы и не переключай ветку. Прямые коммиты в `main` запрещены.

Если своего worktree ещё нет, создай его один раз:

```bash
git worktree add .worktrees/codex -b docs/agents/comments main
```

Для существующей ветки опусти `-b`. Затем переключай ветки внутри worktree через `git switch`. Перед первой проверкой и сборкой выполни `npm install`. Каталог `.worktrees/` исключён из git; удаляй worktree только по просьбе пользователя.

### Временные инструкции

Договорённости, которые действуют только на время текущей работы, записывай в `TEMPORARY.md` в корне своего worktree: как запущен сервер, какие решения пользователь принял по ходу задачи. Если файл есть, прочитай его в начале разговора вместе с этой инструкцией и следуй ему. Файл исключён из git.

Перед коммитом очисти `TEMPORARY.md`: перенеси устойчивые решения в документацию или код, остальное удали. Иначе договорённости завершённой задачи перейдут в следующую.

Субагенты работают в той же ветке и worktree, без создания или переключения веток. Распредели между ними файлы, чтобы правки не пересекались. Коммит и отправку выполняет основной агент после одобрения пользователя.

### Имена веток и коммитов

Имя ветки имеет вид `<тип>/<область>/<тема>` в kebab-case. Для issue начинай тему с его номера:

```text
docs/agents/communication
feat/sales/57-goods-columns
```

| Тип | Назначение |
|---|---|
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `chore` | Сборка, зависимости, инструменты |
| `docs` | Только документация |
| `refactor` | Перестройка кода без изменения поведения |

Сообщение коммита: `<тип>(<область>): описание на русском`.

```text
feat(database): очередь транзакций на Semaphore
```

Переиспользовать ветку можно после полного вливания в `main`. Проверь её наличие в `git branch --merged main`, затем переведи на текущий `main`:

```bash
git switch <ветка>
git reset --hard main
```

## Задачи (issues)

Задачи ведутся в `EGSP/collection-zarplata`. Работай в ветке, указанной в конце issue.

Перед началом проверь зависимости из строки «Нужно до начала работ»:

```bash
git fetch origin
git branch -r --merged origin/main
```

В списке должны быть ветки всех зависимостей. Если какой-либо нет, работу не начинай. Закрытый issue сам по себе не подтверждает вливание.

При возможности оставь в issue комментарий о начале работы: ветка и краткий план. Замечания и переписку между агентами веди в issue соответствующей задачи.

Перед созданием issue целиком прочитай [шаблон](.github/ISSUE_TEMPLATE/task.md), в том числе при создании через CLI. Следуй записанным в задаче решениям; отклонения объясняй в отчёте.

Назначай задаче одну-две метки:

| Метка | Смысл |
|---|---|
| `бэкенд` | Сервер |
| `фронтенд` | Клиент |
| `инструменты` | Сборка, окружение, зависимости, служебные скрипты |
| `документация` | Только документация |

## Завершение работы и вливание в main

Проверь изменения и представь результат пользователю. Коммит создавай только после явного одобрения подготовленных правок: просьба выполнить задачу сама по себе его не разрешает.

После одобрения создай коммит и отправь ветку в `origin`. Если работа велась по issue, оставь итоговый комментарий и закрой задачу.

В `main` ветку вливает пользователь после своей проверки. Pull request не используются.

### Отчёт о работе

Отчёт в чате и итоговый комментарий должны быть понятны без переписки и следовать [communication-style](.agents/skills/communication-style/SKILL.md). Опиши результат, подтверди проверку и объясни существенные отклонения от задачи.

Укажи ветку и состояние работы: подготовлены ли правки, создан ли коммит, отправлена ли ветка и влита ли она в `main`.

## Правила кода

Используй полные слова в идентификаторах, действиях, маршрутах и полях: `parameters`, `configuration`. Допустимы общепринятые сокращения: `guid`, `API`, `UI`, `SQL`, `JSON`.

### Комментарии в коде

Комментируй новый и изменяемый код: поясняй назначение, использование и причины решений. Ориентируйся на соседние файлы, [SQL-конструктор](src/server/database/sql.builder.ts) и [работу с базой данных](src/server/database/database.effect.ts).

Обновляй комментарии вместе с поведением кода.

## Effect

Используй Effect 4 только в бизнес-логике. Роутинг, контроллеры и DI остаются на NestJS.

Разрешены core-модули из корня пакета:

```ts
import { Effect, Layer, Schema, Semaphore } from 'effect';
```

Или импортируй отдельный модуль:

```ts
import * as Effect from 'effect/Effect';
```

Подпакеты-каталоги вроде `effect/ai`, `effect/http` и `effect/sql` не используются, хотя входят в пакет.

Пакеты `@effect/*` не устанавливай, кроме `@effect/tsgo` для проверки кода. Исключения из этих ограничений требуют явного решения пользователя.

## Проверка после изменений

Автотесты и тестовые фреймворки в проект не добавляются. Проверяй поведение сам через API и интерфейс.

После каждого изменения кода запускай:

```bash
npm run typecheck
```

Команда использует `effect-tsgo` (TypeScript 7 с Effect Language Service). Исправляй ошибки и предупреждения типов и Effect, не подавляя их. Подробная диагностика доступна через `npm run diagnostics`.

Если затронут сервер или клиент, выполни сборку, запуск и ручную проверку. Для этого используй:

```bash
npm run start:check -- --test-pin=482915 --port=3101
```

Команда собирает сервер и клиент и запускает их без файла настроек. База находится в памяти: при запуске в ней только тестовый пользователь, после остановки данные исчезают. Отдельный файл базы и очистка не нужны; локальные настройки не меняй.

Тестовый пользователь получает все роли. Для проверки ограниченных прав добавь второго:

```text
--test-pin=111111:reader
```

Выбирай порт, отличный от `3000` и `5173`. Сервер и режим разработки запускай в фоне.

После проверки заверши свои процессы и убедись, что занятые ими порты свободны. На Windows дочерние `node`, `vite` и `tsc` могут остаться после остановки фоновой задачи.

Подробности находятся в разделе [«Сборка и запуск»](docs/build-and-launch.md).

## Исходники внешних библиотек

В `repos/` через `git subtree` подключены исходники библиотек. Сверяй API и приёмы с ними, а не с догадками или веб-поиском. Не меняй эти файлы без явной просьбы и не импортируй их в приложение: используй установленные пакеты.

Перед использованием Effect читай `repos/effect/packages/effect/src`, `repos/effect/LLMS.md` и `repos/effect/ai-docs`.
