# Инструкция для агентов

Проект документируется на русском языке. Если для изменяемой части проекта есть документация, её нужно обновить вместе с кодом. Архитектура ведётся файлами каталога `docs` по правилам раздела [«Документация»](docs/documentation.md): новый раздел добавляется файлом и строкой оглавления в ARCHITECTURE.md.

Перед созданием или редакторской переработкой документации прочитай навык [documentation-directions](.agents/skills/documentation-directions/SKILL.md). Копия для Claude лежит в `.claude/skills/documentation-directions/SKILL.md`; обе копии обновляются вместе.

Перед отчётом о работе запусти `npm run docs:check`. Команда называет разделы архитектуры, код которых изменён в ветке. Прочитай каждый раздел, у которого указано «раздел не изменён», и обнови его, если изменилось описанное в нём поведение. Новый модуль добавь в шаблоны `covers` раздела, который его описывает.

Архитектура описана в каталоге [docs](docs), оглавление — в [ARCHITECTURE.md](ARCHITECTURE.md); назначение и возможности — в [PRODUCT.md](PRODUCT.md).

Бизнес-правила магазина записаны в разделе [«Правила учёта»](docs/accounting-rules.md): формулы, округление, условия и запреты. Если меняешь такое правило в конфигурации, исправь раздел в той же ветке. Новый документ конфигурации добавляет в раздел подраздел со своими правилами. Поведение платформы, состав полей и раскладку форм в раздел не пиши.

## Язык и стиль текстов

Все тексты проекта пишутся на русском языке по правилу [russian-style-v2](.claude/skills/russian-style-v2/SKILL.md): документация, issues и комментарии в них, описания коммитов, комментарии в коде, сообщения об ошибках для пользователя. Прочитай правило до начала работы. Копия лежит также в `.agents/skills/russian-style-v2/SKILL.md` для агентов, которые ищут навыки там; при изменении правила обнови обе копии.

Идентификаторы в коде, имена веток и метки типа коммита (`feat`, `fix` и т. п.) пишутся латиницей.

## Ветки и worktree

- Вся работа ведётся в отдельных локальных ветках. Прямые коммиты в `main` запрещены.
- Коммит создаётся только после явного одобрения пользователем подготовленных изменений. До одобрения агент оставляет правки незакоммиченными, проверяет их и предоставляет результат для просмотра. Просьба выполнить работу сама по себе не означает одобрения коммита.
- Имя ветки: `<тип>/<область>/<тема>` латиницей в kebab-case, например `feat/database/transactions`, `fix/authentication/refresh-rotation`, `docs/agents/workflow`.
  - `feat` — новая возможность;
  - `fix` — исправление ошибки;
  - `chore` — сборка, зависимости, инструменты;
  - `docs` — только документация;
  - `refactor` — изменение структуры кода без изменения поведения.
- Основной агент работает в своём worktree `.worktrees/<агент>`, названном по имени агента: `.worktrees/codex`, `.worktrees/claude`. Это правило действует всегда, даже если сейчас работает только один агент. Основной каталог репозитория остаётся на `main` и принадлежит пользователю: агент в нём не переключает ветки и не меняет файлы. Каталог `.worktrees/` исключён из git.
- Субагенты работают в той же ветке и worktree, что и основной агент. Отдельные ветки и worktree для подзадач они не создают и не переключают текущую ветку. Основной агент распределяет между ними файлы или области правок, чтобы избежать одновременного изменения одного участка. Коммит и отправку ветки выполняет основной агент после одобрения пользователя.
- Если worktree основного агента ещё нет, он создаёт его один раз и дальше переключает в нём ветки обычной командой `git switch`:

  ```bash
  git worktree add .worktrees/claude -b docs/agents/comments main
  ```

  Для существующей ветки её имя указывается без `-b`. В новом worktree нет `node_modules`, поэтому перед проверкой и сборкой в нём выполняется `npm install`. Удаляет worktree командой `git worktree remove .worktrees/<агент>` только пользователь или агент по его просьбе.
- Ветку можно переиспользовать, если она уже полностью влита в `main` (`git branch --merged main` её показывает). Перед новой работой переведи её на текущий `main`: `git switch <ветка> && git reset --hard main`.
- Сообщения коммитов: `<тип>(<область>): описание на русском`, например `feat(database): очередь транзакций на Semaphore`. Описание на русском обязательно.

## Завершение работы и вливание в main

- Pull request не используются.
- Когда работа готова, агент:
  1. проверяет её: `npm run typecheck`, сборка, запуск и ручная проверка, если затронуты сервер или клиент;
  2. предоставляет пользователю подготовленные изменения и результат проверки; до явного одобрения коммит не создаёт;
  3. после одобрения создаёт коммит, отправляет ветку в `origin` и оставляет её без вливания в `main`;
  4. пишет в issue комментарий по правилу «Отчёт о работе»: имя ветки, что сделано, как проверено, что изменилось по сравнению с описанием задачи;
  5. закрывает issue.
- Ветки в `main` вливает пользователь после своей проверки.
- Переписка между агентами идёт в комментариях к issues: замечания к работе пишутся в её issue.

### Отчёт о работе

Правило действует для отчёта пользователю в чате и для комментария к issue при завершении работы. Читатель отчёта оценивает результат на уровне архитектуры и поведения системы, а не читает код.

- Начинай с результата: что теперь умеет система. Одно-два предложения.
- Объясняй, как решение работает, связным текстом, а не списком. Описывай поведение и решения: что происходит при запуске, при добавлении файла, при ошибке.
- Не перечисляй файлы, классы, методы, команды и параметры. Имя из кода упоминай, только если без него читатель не сможет действовать, например имя ветки.
- Выделяй жирным и оформляй кодом умеренно: выделение не заменяет объяснения.
- Отдельным абзацем опиши, что сделано сверх задачи или иначе, чем в ней, и почему.
- Проверку описывай простыми словами: что проверено и какой получен результат, а не какие команды запускались.
- Замечания, которые не относятся к задаче, но важны для проекта, выноси в конец коротким списком.
- Имя ветки и то, что она не влита в `main`, указывай в конце.

Пример начала хорошего отчёта:

> Задача выполнена: объекты конфигурации теперь подключаются автоматически, а платформа при запуске получает их готовые описания.
>
> Как это работает. Каждый справочник, документ или регистр описывается отдельным файлом в каталоге конфигурации. Перед сборкой служебный скрипт находит эти файлы и составляет из них реестр. В режиме разработки скрипт следит за каталогом: новый файл сразу попадает в реестр, и сервер перезапускается сам.

## Задачи (issues)

- Задачи ведутся в GitHub Issues репозитория `EGSP/collection-zarplata`.
- В каждом issue указано имя ветки. Работа ведётся в ветке с этим именем.
- В разделе «Нужно до начала работ» перечислены issues, ветки которых должны быть влиты в `main` раньше. Закрытый issue означает только, что работа завершена, а не что ветка влита. Проверь вливание командой `git fetch origin && git branch -r --merged origin/main`: в списке должны быть ветки всех зависимостей. Если хотя бы одной нет, работу не начинай.
- Если есть возможность, агент комментирует issue:
  - при начале работы — ветка и краткий план;
  - при завершении — по порядку из раздела «Завершение работы и вливание в main».
- Новые issues создаются по шаблону `.github/ISSUE_TEMPLATE/task.md`. Правила постановки задачи записаны в самом шаблоне: прочитай его целиком, даже если создаёшь issue командой, а не через веб-форму.
- Исполнитель следует решениям из раздела «Решения и архитектура» задачи. Отступление от них он объясняет в отчёте.
- На issue ставится одна-две метки, не больше.

## Правила кода

- В идентификаторах, действиях, маршрутах и полях используются полные слова без сокращений: `parameters`, а не `params`; `configuration`, а не `config`. Допустимы только общепринятые аббревиатуры: `guid`, `API`, `UI`, `SQL`, `JSON`.
- Effect используется только в бизнес-логике. Роутинг, контроллеры и DI остаются на NestJS.

### Экраны клиента и web SDK

- Экран клиента собирается из web SDK и импортирует платформу только из его точки входа `src/web/sdk/index.ts`. Остальные модули `src/web` для экрана внутренние. Состав SDK описан в разделе [«Web SDK»](docs/interface.md#web-sdk) архитектуры.
- Собственный экран конфигурации оформляется страницей: объявление `*.page.ts` и компонент `*.page-component.tsx` в `src/configuration`. Объект страница указывает ссылкой `Objects.<вид>.<имя>` и не импортирует значения из файлов объектов и серверного кода, только типы. Границу импортов проверяет `npm run typecheck`. Правила описаны в подразделе [«Страницы конфигурации»](docs/metadata.md#страницы-конфигурации) архитектуры.
- Собственный блок на стандартной форме оформляется элементом формы: объявление `*.form-element.ts` и компонент `*.form-element-component.tsx` в `src/configuration`. На форму его ставит `.form(...)` объекта: в группу либо полем ввода конкретного поля. К компоненту относятся те же правила импортов, что и к странице. Значения формы и запись он получает только из SDK, а не из формы Ant Design. Правила описаны в подразделе [«Элементы формы»](docs/metadata.md#элементы-формы) архитектуры.
- Хуки данных Refine и `/api/perform` экран напрямую не вызывает: данные он читает и изменяет хуками SDK.
- Если экрану не хватает элемента или хука и он пригодится другим экранам, его добавляют в SDK, а не пишут на месте. Вместе с ним обновляется таблица раздела [«Web SDK»](docs/interface.md#web-sdk).
- Раскладку, типографику и прочие элементы без связи с платформой экран берёт из Ant Design напрямую: обёртки для них в SDK не пишутся.
- Иконки берутся из реестра `Icons` web SDK по смыслу действия: `<Icons.open />`, а не значок из `@ant-design/icons`. Этот пакет импортирует только реестр `src/web/sdk/icons.tsx`. Если нужного смысла в реестре нет, в него добавляют запись.

### Комментарии в коде

Код служит документацией сам по себе: прочитав модуль, разработчик должен понять не только что делает каждая часть, но и почему она устроена именно так, не заглядывая в документацию архитектуры и историю коммитов. Комментарии пишутся на русском языке по правилу russian-style-v2.

Каждый экспортируемый класс, интерфейс, тип, функция и константа получает JSDoc-комментарий `/** … */`. Он объясняет назначение и контракт: что сущность принимает и возвращает, в каких случаях завершается ошибкой, какие условия должен соблюдать вызывающий код. Члены интерфейсов и публичные методы комментируются, если их смысл не очевиден из имени и типа. Если назначение исчерпывающе выражено именем и типом, комментарий не пишется: он только повторил бы имя другими словами.

У модуля или главного класса модуля есть вводный JSDoc, который описывает роль модуля в системе и ключевое решение, на котором он построен. Например, в сервисе базы данных такой комментарий объясняет, почему одно соединение требует очереди транзакций, а в модуле событий сессии — почему шина живёт в памяти и не заменяет журнал.

Строчные комментарии `//` ставятся только там, где причина неочевидна из кода: ограничение внешней системы (SQLite требует `LIMIT` перед `OFFSET`), ловушка, которую код обходит (сравнение `= NULL` не находит строк), защита от ошибки вызывающего кода (`UPDATE` без условия изменил бы всю таблицу). Комментарий стоит над строкой, к которой относится, и объясняет причину, а не пересказывает действие: пишется «повторный захват семафора привёл бы к ожиданию самого себя», а не «проверяем, есть ли транзакция».

Комментарий меняется вместе с кодом: устаревший комментарий вреднее отсутствующего. В коде не оставляют закомментированный код, историю изменений («раньше здесь было…») и пометки без действия вроде «TODO: подумать». Незавершённая часть описывается как заготовка с указанием задачи, которая её доделает: «Заготовка: выполнение реализует диспетчер (#6)». Когда задача выполнена, такую пометку убирают.

Примеры стиля — `src/server/database/sql.builder.ts` и `src/server/database/database.effect.ts`.

## Effect

- Используется Effect 4 (пакет `effect`, версия 4.x).
- Используются только core-возможности Effect: модули из корня пакета — `import { Effect, Layer, Schema, Semaphore } from "effect"` или `effect/Effect`, `effect/Schema` и т. п.
- Подпакеты-каталоги (`effect/ai`, `effect/cli`, `effect/cluster`, `effect/encoding`, `effect/http`, `effect/http-api`, `effect/persistence`, `effect/rpc`, `effect/schema`, `effect/sql`, `effect/workflow` и другие) не используются. В Effect 4 они поставляются внутри пакета `effect`, но проекту не нужны. Исключение возможно только по явному решению пользователя.
- Дополнительные пакеты экосистемы (`@effect/*`) не устанавливаются. Исключение — `@effect/tsgo` для проверки кода.

## Проверка после изменений

В проекте не пишутся автотесты и не подключаются тестовые фреймворки. Агент проверяет результат сам: запускает приложение, отправляет запросы к API, проверяет работу в интерфейсе. В комментарии к issue он перечисляет, что и как проверил.

После каждого изменения кода запусти:

```bash
npm run typecheck
```

Команда `tsc` в проекте заменена на `effect-tsgo` (TypeScript 7 с Effect Language Service), поэтому она проверяет и типы, и правила Effect. Ошибки и предупреждения Effect нужно исправлять, а не подавлять.

Для ручной проверки запускай приложение на пустой базе в памяти:

```bash
npm run start:check -- --test-pin=482915 --port=3101
```

Команда собирает сервер и клиент и запускает их без файла настроек. Каждый запуск начинается с пустой базы, в которой есть только тестовый пользователь с указанным PIN; после остановки данные исчезают. Поэтому создавать отдельные файлы базы, менять локальный файл настроек и что-либо очищать после проверки не нужно. Тестовый пользователь получает все роли конфигурации. Чтобы проверить ограниченные права, добавь второго пользователя с нужной ролью: `--test-pin=111111:reader`. Порт выбирай отличным от 3000 и 5173, чтобы не мешать режиму разработки пользователя.

Команды сборки и запуска описаны в разделе [«Сборка и запуск»](docs/build-and-launch.md) архитектуры. Сервер и режим разработки запускай в фоне. На Windows после остановки фоновой задачи дочерние процессы `node`, `vite` и `tsc` могут остаться жить и занимать порты 3000, 5173 и порт проверки, поэтому после проверки завершай их и убеждайся, что порты свободны.

Подробный отчёт диагностик Effect:

```bash
npm run diagnostics
```

## Исходники внешних библиотек

Исходники внешних библиотек подключены в каталог @repos/ через `git subtree`.

- Используй их как справочник только для чтения, когда работаешь с соответствующими библиотеками.
- Опирайся на примеры и приёмы из этих исходников, а не на догадки или результаты веб-поиска.
- Не редактируй файлы в @repos/ без явной просьбы.
- Не импортируй код из @repos/: код приложения импортирует библиотеки из установленных пакетов.

В `repos/effect` лежат исходники Effect 4. Перед использованием API Effect сверяйся с `repos/effect/packages/effect/src`, `repos/effect/LLMS.md` и `repos/effect/ai-docs`.
