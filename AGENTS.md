# Инструкция для агентов

Проект документируется на русском языке. Если для изменяемой части проекта есть документация, её нужно обновить вместе с кодом.

Архитектура описана в [ARCHITECTURE.md](ARCHITECTURE.md), назначение и возможности — в [PRODUCT.md](PRODUCT.md).

## Язык и стиль текстов

Все тексты проекта пишутся на русском языке по правилу [russian-style-v2](.claude/skills/russian-style-v2/SKILL.md): документация, issues и комментарии в них, описания коммитов и pull request, комментарии в коде, сообщения об ошибках для пользователя. Прочитай правило до начала работы. Копия лежит также в `.agents/skills/russian-style-v2/SKILL.md` для агентов, которые ищут навыки там; при изменении правила обнови обе копии.

Идентификаторы в коде, имена веток и метки типа коммита (`feat`, `fix` и т. п.) пишутся латиницей.

## Ветки и worktree

- Вся работа ведётся в отдельных локальных ветках. Прямые коммиты в `main` запрещены.
- Имя ветки: `<тип>/<область>/<тема>` латиницей в kebab-case, например `feat/database/transactions`, `fix/authentication/refresh-rotation`, `docs/agents/workflow`.
  - `feat` — новая возможность;
  - `fix` — исправление ошибки;
  - `chore` — сборка, зависимости, инструменты;
  - `docs` — только документация;
  - `refactor` — изменение структуры кода без изменения поведения.
- Если параллельно работают несколько агентов, каждый работает в своём worktree рядом с основным каталогом:

  ```bash
  git worktree add ../collection-zarplata-<тема> -b <ветка> main
  ```

  После вливания ветки worktree удаляется: `git worktree remove ../collection-zarplata-<тема>`.
- Ветку можно переиспользовать, если она уже полностью влита в `main` (`git branch --merged main` её показывает). Перед новой работой переведи её на текущий `main`: `git switch <ветка> && git reset --hard main`.
- Сообщения коммитов: `<тип>(<область>): описание на русском`, например `feat(database): очередь транзакций на Semaphore`. Описание на русском обязательно.

## Вливание в main

- Вливание в `main` проходит через ручной контроль пользователя. Агент сам ветку в `main` не вливает.
- Когда работа готова, агент проверяет её (`npm run typecheck`, сборка, запуск и ручная проверка, если затронуты сервер или клиент), отправляет ветку в `origin` и, если может, открывает pull request в `main`. Описание pull request пишется на русском и содержит строку `Closes #<номер issue>`, чтобы issue закрылся при слиянии.
- Если вливание выполняется без pull request, агент, который по просьбе пользователя вливает ветку, сам закрывает issue с комментарием о результате.

## Задачи (issues)

- Задачи ведутся в GitHub Issues репозитория `EGSP/collection-zarplata`.
- В каждом issue указано имя ветки. Работа ведётся в ветке с этим именем.
- В разделе «Нужно до начала работ» перечислены issues, которые должны быть влиты раньше. Если они ещё открыты, работу не начинай.
- Если есть возможность, агент комментирует issue:
  - при начале работы — ветка и краткий план;
  - при завершении — что сделано, как проверено, что осталось или изменилось по сравнению с описанием.
- Новые issues создаются по шаблону `.github/ISSUE_TEMPLATE/task.md`.
- На issue ставится одна-две метки, не больше.

### Метки

| Метка | Смысл |
|---|---|
| `бэкенд` | Затрагивает сервер |
| `фронтенд` | Затрагивает клиент |
| `инструменты` | Сборка, окружение, зависимости, служебные скрипты |
| `документация` | Только документация |

## Правила кода

- В идентификаторах, действиях, маршрутах и полях используются полные слова без сокращений: `parameters`, а не `params`; `configuration`, а не `config`. Допустимы только общепринятые аббревиатуры: `guid`, `API`, `UI`, `SQL`, `JSON`.
- Effect используется только в бизнес-логике. Роутинг, контроллеры и DI остаются на NestJS.

## Effect

- Используется Effect 4 (пакет `effect`, версия 4.x).
- Используются только core-возможности Effect: модули из корня пакета — `import { Effect, Layer, Schema, Semaphore } from "effect"` или `effect/Effect`, `effect/Schema` и т. п.
- Подпакеты-каталоги (`effect/ai`, `effect/cli`, `effect/cluster`, `effect/encoding`, `effect/http`, `effect/http-api`, `effect/persistence`, `effect/rpc`, `effect/schema`, `effect/sql`, `effect/workflow` и другие) не используются. В Effect 4 они поставляются внутри пакета `effect`, но проекту не нужны. Исключение возможно только по явному решению пользователя.
- Дополнительные пакеты экосистемы (`@effect/*`) не устанавливаются. Исключение — `@effect/tsgo` для проверки кода.

## Проверка после изменений

В проекте не пишутся автотесты и не подключаются тестовые фреймворки. Агент проверяет результат сам: запускает приложение, отправляет запросы к API, проверяет работу в интерфейсе. В комментарии к issue и в описании pull request он перечисляет, что и как проверил.

После каждого изменения кода запусти:

```bash
npm run typecheck
```

Команда `tsc` в проекте заменена на `effect-tsgo` (TypeScript 7 с Effect Language Service), поэтому она проверяет и типы, и правила Effect. Ошибки и предупреждения Effect нужно исправлять, а не подавлять.

Команды сборки и запуска описаны в разделе «Сборка и запуск» [ARCHITECTURE.md](ARCHITECTURE.md). Сервер и режим разработки запускай в фоне. На Windows после остановки фоновой задачи дочерние процессы `node`, `vite` и `tsc` могут остаться жить и занимать порты 3000 и 5173, поэтому после проверки завершай их и убеждайся, что порты свободны.

Подробный отчёт диагностик Effect:

```bash
npm run diagnostics
```

## Исходники внешних библиотек

Исходники внешних библиотек подключены в каталог @repos/ через `git subtree`.

- Используй их как справочник только для чтения, когда работаешь с соответствующими библиотеками.
- Опирайся на примеры и приёмы из этих исходников, а не на догадки или результаты веб-поиска.
- Не редактируй файлы в @repos/ без явной просьбы.
- Не импортируй код из @repos/: код приложения импортирует библиотеки из установленных пакетов.

В `repos/effect` лежат исходники Effect 4. Перед использованием API Effect сверяйся с `repos/effect/packages/effect/src`, `repos/effect/LLMS.md` и `repos/effect/ai-docs`.
